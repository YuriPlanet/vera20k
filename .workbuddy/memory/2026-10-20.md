## 00:39 handler 语义深挖 → toggle 对确认 + 阶梯簇定性，报告提交 `e20b6aa`

### op 0x01 / 0x02 确证是 toggle 对（开/关配对）

- op 0x01 → `0x452260`，op 0x02 → `0x452360`，两 handler 检查条件**相反**、操作**同一组标志**、
  方向**相反** → 典型 enable/disable toggle pair（推断为某功能开关，如自动巡逻/自动开火一类，
  ⚠️ 具体是哪个 VERA `Command` 变体仍待反编译确认）。
- 方法论：**toggle 对判定 = 三反判据**（条件反 / 同一目标 / 方向反）。单看一个 handler 看不出语义，
  成对看才能定性。以后遇到相邻两个 opcode 结构镜像，先按此判据验。

### 阶梯簇 0x0e / 0x0f / 0x10 确为三个不同语义

- handler `0x4fa350` / `0x4fa910` / `0x4faa10` 调用的虚表槽位不同（0x4f/0x50/0x51 段各不同），
  非 alias；payload 偏移约定一致（`[esi+2]` house/flags、`[esi+7]` 目标句柄、`[esi+0xb]/[esi+0xd]` 坐标对）。

### 静态取证边界（写进报告 §2e）

- 虚表调用目标（`call [eax+0x94]` 这类）静态不可解析 → 每个未接 opcode 的 handler 最终语义
  **必须 Ghidra 反编译 + dynamic trace** 才能坐实。
- 已确立的红线：形态学证据（镜像结构 / 同一全局 / 相同 guard）可以**定性**（是 toggle 对、是改速），
  但不能单独**命名**（对应哪个 `Command` 变体）——命名需要反编译级证据。
