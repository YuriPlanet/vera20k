**草案阶段。** 接受 RFC 后才合入引擎代码；用于回答[待定问题](#待定问题)的实验放在引擎源码树外。

## 概要

mod 和地图可携带模拟模块 `rules.wasm` 和界面模块 `ui.wasm`。引擎在沙箱中加载编译好的模块。模拟模块通过属性、变量、事件和动作修改玩法，客户端模块通过节点构建界面。官方 SDK 为 TypeScript 和 Rust，其他语言按[模块 ABI](#5a-语言与-sdk)接入。函数签名、固定布局和编号见 [API 附录](0001-wasm-extension-modules-api.zh-CN.md)。

## 目标

1. modder 不改引擎也能修改玩法和界面。
2. 所有玩家运行相同的模拟模块并得到相同结果：在任何受支持的平台上（包括浏览器版）都不会不同步。
3. 开局前报告模块错误并拒绝开局；对局中模块出错时停用该模块，提示原因，对局继续。
4. 模块不得访问文件或网络。模拟模块不得读取时钟；客户端渲染计时仅用于显示。按运算量计费。客户端只读本机可见状态和获准读取的变量；模拟模块自行决定通知内容。
5. 没有模块、地图和 mod 也未使用扩展键时，沿用原版玩法。
6. 只有少数对象或类型使用的模块不会拖慢 2 万单位规模的战斗。
7. 红警 2 modder 从模板开始，几分钟内就能在游戏里看到改动效果。

## 非目标

- 原生插件（`.dll`、`.so`），或在沙箱外加载任何东西。
- 引擎里出现源代码。引擎从不解析、编译或解释任何源语言，也不内置任何语言运行时。
- 暴露引擎内部：内存布局、原生地址、内部对象下标或存储槽位（句柄是对象的创建序号，第 5 节）、渲染器的图形 API。
- 对局中新增对象类型。
- 取代原版触发器系统。模块是在它的基础上扩展。
- 修改地图地形：模块不能放置或移除覆盖物（墙、桥等），不能改地块。原版的矿石增减动作照常可用。

## 术语

| 术语 | 含义 |
| --- | --- |
| 引用 / 句柄 | 引用表示对象、类型、格子、路径点或全局状态。模拟对象句柄为永不复用的创建序号，客户端节点使用本机序号；0 为空。 |
| 触发器 / 标签 | 触发器包含事件、筛选和动作。原版地图通过标签将触发器挂到对象或格子；模块也可直接绑定。 |
| 模块触发器 | 由模块创建、通过 `Wasm.Tags` 或 `trigger_bind` 绑定，或带模块动作或决定处理函数的触发器。 |
| 安全点 | 一次计算之前、完成后或整批结果提交后，允许执行触发器立即动作的位置（第 5 节）。 |
| 帧 / 渲染帧 | 游戏时长按模拟逻辑帧计；渲染帧为本机显示周期。地图距离以 lepton 计，1 格 = 256 lepton。 |

## modder 看到的样子

### 文件

```
Mods/MyMod/
  mod.ini        ; Needs= 和其他 mod.ini 键；不含模块键
  rulesmd.ini    ; [VeraWasm]：API 版本、额度、地图政策；把标签绑定到类型
  rules.wasm     ; 模拟模块
  ui.wasm        ; 界面模块
```

地图在 `[VeraWasm]` 声明 API 和模块大小，在 `[VeraWasmRulesPack]`、`[VeraWasmUIPack]` 中嵌入压缩后按编号分行的 base64 数据。`asset` 负责嵌入、提取和加载校验。键、默认值与编码见[附录 INI 键](0001-wasm-extension-modules-api.zh-CN.md#ini-键)。

### 把触发器绑定到类型

```ini
; mod 里的 rulesmd.ini
[E1]
Wasm.Tags=GIPanicTag     ; 每个 E1 都接收这个标签的触发器

[GIPanicTag]
Trigger=GIPanic

[GIPanic]
Event=TakeDamage
Where1=Subject.HealthPercent<30      ; 筛选子句，全部成立才触发（第 6a 节）
Where2=Var(Subject,Panicked)=0
Action1=SetVar(Subject,Panicked,1)   ; 原子动作，触发时立即执行：同一帧里这个 E1 后面的伤害不再通过 Where2
Action2=Wasm:giPanic     ; 运行 mod 的 rules.wasm 中的模块动作 giPanic（第 2 节）
Repeat=Repeating         ; TagRepeat 的取值
```

每个 E1 都以自己的实例运行 `GIPanic`（第 7 节）。只有生命低于 30% 且变量 `Panicked` 为 0 的 E1 才会把记录投递给模块，其他 E1 的伤害在引擎内就被筛掉；原子动作 `SetVar` 在触发时立即写变量，所以每个 E1 只投递一条记录。键名和具体的节格式尚未确定（待定问题 4）。在 FinalAlert2 里编辑的地图触发器，也可以通过新动作调用模块函数。

### 模块代码

引擎只看到编译好的模块，源码和编译器都在作者自己的工具里。下面分别用两套官方 SDK 表达同一行为。类型绑定在 INI 和代码中任选一处；若用上一节的 INI，只注册具名回调，省略代码中的触发器创建。

```ts
// TypeScript（兼容 AssemblyScript）
import { Trigger, Event, Prop, Op, Techno, Mission, Var, VarTarget, ActionDef, Target, Rules,
         TakeDamageEvent, namedAction, onScenarioStart, onFrame, Every } from "@vera20k/sdk";

import { Panicked } from "./generated/vars";

function giPanic(e: TakeDamageEvent): void {
  Techno.setMission(e.victim, Mission.Hunt);   // 一次宿主调用：set(subject, Mission, Hunt)
}
namedAction("giPanic", giPanic);       // 名字必须是字符串字面量：SDK 构建时静态提取，写入 vera.actions，INI 才能引用这个名字

onScenarioStart((): void => {
  Trigger.on(Event.TakeDamage)
    .bind(Rules.technoType("E1"))                  // 每个 E1 运行自己的实例（第 7 节）
    .where(Prop.HealthPercent, Op.Lt, 30)
    .whereVar(VarTarget.Subject, Panicked, Op.Eq, 0)
    .immediate(ActionDef.setVar(Target.Subject, Panicked, 1))   // 原子动作，在触发器触发时执行
    .enqueue(giPanic).done();                              // 调用 trigger_create 和 trigger_bind
});

onFrame(new Every(15), (): void => {
  if (Var.local(3).get() != 0) {    // 红警 2 局部变量 3
    // ...
  }
});
```

```rust
// Rust SDK 写法
use vera20k_sdk::prelude::*;
use vera20k_sdk as vera;

use generated::vars::PANICKED;

fn gi_panic(e: &TakeDamageEvent) {
    e.victim().set_mission(Mission::Hunt);
}

#[vera::on_scenario_start]
fn start() {
    let panic_action = named_action!("giPanic", gi_panic);
    Trigger::on(Event::TakeDamage)
        .bind(rules::techno_type("E1"))
        .where_prop(Prop::HealthPercent, Op::Lt, 30)    // where 是 Rust 关键字
        .where_var(VarTarget::Subject, PANICKED, Op::Eq, 0)
        .immediate(ActionDef::set_var(Target::Subject, PANICKED, 1))
        .enqueue(panic_action).done();
}

#[vera::on_frame(every = 15)]
fn check_waves() {
    if Var::local(3).get() != 0 {
        // ...
    }
}
```

每套 SDK 都用一条命令构建出 `rules.wasm` 或 `ui.wasm`。SDK 的函数（`Techno.setMission`、`Trigger.on`）都由附录的表生成，每个包装函数只发起[附录第 3 节](0001-wasm-extension-modules-api.zh-CN.md#3-sdk-对应)列出的宿主调用，大多数恰好一次（第 5a 节）。包名只是占位。

### 示例：第一个单位开火时扔核弹

把一个 `Fire` 触发器绑定到全场第一个单位（按创建序号），它开火时，在模块动作中向它的目标格子扔一颗核弹：

```ts
// TypeScript（兼容 AssemblyScript）
import { Trigger, Event, Find, Prop, Op, Category, Action, FireEvent,
         NO_HANDLE, onScenarioStart } from "@vera20k/sdk";

function nukeAtTarget(e: FireEvent): void {
  Action.nukeStrike(e.targetCell, e.house);   // 事件记录保存的开火目标格；一次 action 调用
}

onScenarioStart((): void => {
  const first = Find.objects()
    .where(Prop.Category, Op.Ne, Category.Building)
    .where(Prop.Category, Op.Ne, Category.Projectile)
    .first();                                    // 一次 find：创建序号最小的单位；没有时为 NO_HANDLE
  if (first != NO_HANDLE) {
    Trigger.on(Event.Fire).bind(first).once().enqueue(nukeAtTarget).done();
  }
});
```

- 只有这个单位开火时才投递记录：其他单位开火时，事件触发点只检查一次自己的标志位就返回（第 15 节）。
- `.once()` 让触发器不重复，只触发一次；去掉它就每次开火都扔。
- 对象绑定随对象一起消失：单位死后不再触发。触发器本身仍留在触发器运行时中，不再需要时用 `Trigger.remove` 删除（第 7 节）。
- INI 无法选出某一个具体的对象：`Wasm.Tags` 只能绑定类型。这种逐对象的选择只能写在代码里。

## 设计

### 1. 两个世界

| | 模拟（`rules.wasm`） | 客户端（`ui.wasm`） |
| --- | --- | --- |
| 接口 | `vera:sim@1` | `vera:client@1`，每个函数都以 `client_` 开头 |
| 运行在 | 每台机器上，锁步执行 | 仅本机 |
| 确定性 | 是 | 否 |
| 可以改变 | 游戏状态，通过引擎的 owner | 界面节点、镜头、光标、本地设置、声音 |
| 影响游戏的方式 | 动作、属性写入、变量，以及给电脑所属方的指令 | 通过命令流发出标准玩家指令和消息 |
| 引擎侧 | `sim/` | `ui/`、`render/`、`audio/` |

这个划分遵循现有规则：`sim/` 从不依赖 `render/`、`ui/`、`audio/` 或 `net/`。加载器拒绝导入 `client_*` 函数的模拟模块，也拒绝导入模拟函数的客户端模块。

- 从模拟到客户端，不经过网络：客户端读取它能看到的状态和可见度允许的变量；模拟模块用 `send_notify` 向目标所属方的机器发出通知。
- 从客户端到模拟：只有命令流。标准玩家指令像任何玩家输入一样被校验；消息像玩家指令一样进入命令流（第 10 节）。回放和联机都能看到两者。

### 2. 来源：mod 和地图

mod 和地图使用同一套 API 和同一套 SDK，区别在于引擎授予它们的权限。

| | mod | 地图 |
| --- | --- | --- |
| 顺序 | 先 | 在 mod 之后，和 INI 层叠一致 |
| `on_rules` | 在 `RULESMD.INI`、`LANGRULE.INI` 和模式层之后 | 在地图层之后；能看到 mod 的结果 |
| 运算额度 | 在 mod 的 `[VeraWasm]` 中声明，引擎设上限 | 默认更小；mod 的 `[VeraWasm]` 可以调高 |
| 体积 | 受文件大小约束 | 有嵌入上限 |
| 界面 | 可以替换或重排对局界面 | 只能加覆盖层，除非 mod 允许更多 |

mod 在它的 `rulesmd.ini` 的 `[VeraWasm]` 节中控制地图模块能做什么：

```ini
; mod 里的 rulesmd.ini
[VeraWasm]
Api=1.0              ; mod 的模块需要的 API 主版本.次版本
Budget=200000        ; mod 模块每帧的额度，引擎设上限
MapBudget=50000      ; 这个 mod 下地图模块每帧的额度
MapWasm=yes          ; no：带模块的地图在这个 mod 下不能开局
MapUI=overlay        ; overlay、full 或 no
```

- 这些键放在 `rulesmd.ini` 里，因为 mod 摘要包含这个文件而不包含 `mod.ini`，所以房间里的每个玩家都会比对它们（第 11 节）。
- 每个 `[VeraWasm]` 节都从各自的文件读取，从不层叠：mod 的在任何其他层之前从 mod 的 `rulesmd.ini` 读取，地图的从地图读取。地图无法改变 mod 的键。地图自己的 `[VeraWasm]` 只放它的嵌入键、它的 `Api=` 和它的 `StorageId=`。
- 没有选择 mod 时，允许地图模块，地图界面只能是覆盖层，地图模块使用引擎的默认额度。
- 键名和取值只是占位（待定问题 4 和 7），全部键见附录的 [INI 键](0001-wasm-extension-modules-api.zh-CN.md#ini-键)。

**规则层**按以下顺序运行：`RULESMD.INI`、`LANGRULE.INI`、模式层、mod 模块的 `on_rules`、地图层、地图模块的 `on_rules`。每个 `on_rules` 读到的是它之前各层处理后的规则，引擎在它写入之后再处理一次规则，和处理 INI 文本一样。类型 ID 一经分配就不再改变：后面的层可以新增类型并得到新的 ID，但从不让已有的 ID 失效。在 mod 的 `on_rules` 中解析得到的 ID 在整个场景中都有效，存档和读档之后也一样。

**冲突规则：**

- **类型上的标签绑定**在 INI 中（`Wasm.Tags`）只从 mod 的 `rulesmd.ini` 读取。地图中的 `Wasm.Tags` 键被忽略，并在大厅中给出警告。地图在代码里绑定（`trigger_bind`，第 7 节），所以地图无法抹掉 mod 的绑定。
- **名字。** mod 的 INI 或触发器中的模块名（`Action=Wasm:name`，以及可决定事件的处理函数名）解析到 mod 的模块；地图中的模块名解析到地图的模块。在 INI 和地图触发器中，前缀 `Wasm:mod.name` 和 `Wasm:map.name` 可以指向另一方；代码创建的触发器和直接执行的 `Module` 动作只能使用本模块的分派键（`lookup(ModuleAction, ...)` 不接受前缀）。变量名（`vera.vars`）也一样：模块按名字找到的是自己来源的变量，加前缀才能找到另一方的。
- **消息和通知。** 客户端模块发出的消息（`client_send_message`）到达同一来源的模拟模块的 `on_message`：mod 的界面发给 mod 的模拟，地图的发给地图的。通知（`send_notify`）作为 `Notify` 客户端事件到达目标机器上的每个客户端模块，事件记录带着发送它的模块的来源（mod 或地图）。
- **触发器**：两边的都会触发，mod 的模块先运行。
- **可决定事件**按链式处理：mod 的模块先给出结果，地图的模块拿到这个结果后可以再改，引擎使用最终值。链上的每一环都拿到原生值和上一环的结果（第一环拿到的上一环结果也是原生值）。后一环可以推翻前一环的否决。决定记录带一个明确的“已处理”标志，而不是用特殊值表示；不处理这次请求的一环把上一环的结果原样传下去（第 6f 节）。
- **动作、属性写入和修饰器**按执行顺序走同一个 owner。修饰器的互斥组按来源分开，地图的修饰器不会顶掉 mod 的（第 6c 节）。
- **对等调用**（后续阶段）：mod 可以公开一些函数供地图调用，以后作为新的次版本增加。

### 3. 加载与校验

加载时，引擎依次：

1. 解码嵌入的模块，校验声明的大小；
2. 解析模块，只接受来自 `vera:*` 接口的导入，且本版本支持其主版本并达到模块需要的次版本（第 12 节）；模拟模块只能导入 `vera:sim` 的函数，客户端模块只能导入以 `client_` 开头的 `vera:client` 函数，跨世界的导入一律拒绝；检查这些导入与模块所在 `[VeraWasm]` 节的 `Api=` 一致（大厅已经读过它；导入的模块名带版本，见[附录第 1 节](0001-wasm-extension-modules-api.zh-CN.md#1-模拟-abi)）；拒绝超出加载时形状上限（函数数量、单个函数体大小、局部变量、导入）的模块，这样地图无法在编译时拖住大厅；检查每个 `vera.*` 自定义段符合[附录中的布局](0001-wasm-extension-modules-api.zh-CN.md#自定义段)：以格式版本开头，名字是 ASCII，没有截断或多余的字节；
3. 只接受白名单中的 Wasm 特性：MVP 核心，加上可变全局变量、符号扩展、不 trap 的浮点转整数、批量内存操作和多返回值。其他一切（SIMD、引用类型、垃圾回收、多内存、线程、64 位内存、异常、尾调用）都被拒绝，所以模块的全部状态就是内存、全局变量和一张函数表。带 `start` 段的模块被拒绝，所以实例化时不运行任何模块代码。浮点运算产生的 NaN 通过改写字节码（而不是引擎开关）规范化，这样每个引擎（包括浏览器的）得到相同的 NaN；
4. 在同一次插桩中加入运算计量和调用深度计数。深度上限远低于每个受支持引擎的真实栈上限，所以深度递归在每台机器上都停在同一次调用。模块从不被重入（第 5 节），所以模块调用之间的引擎栈帧保持有界。同一次改写把模块未导出的可变全局变量（如编译器生成的栈指针）也导出，引擎据此读写它们以存档、读档和计算哈希（第 4 节）。引擎在实例化模块时分配它的内存上限，所以上限以内的 `memory.grow` 从不失败；无法分配它的宿主在加载时让对局失败（对局错误，见下文）；
5. 检查生命周期需要的导出函数存在且签名正确，并检查 INI 中提到的每个模块动作和处理函数名（`Action=Wasm:name`）都在它所解析到的模块的 `vera.actions` 表中；
6. 检查 `vera.vars` 中的变量声明：名字在模块内唯一，作用域和可见度是表中的值，“视野内可见”只用于单个对象作用域。引擎按加载顺序（先 mod 的，再地图的）给每个变量分配 ID，再解析 INI 触发器的事件、筛选子句和原子动作。无法解析的名字在大厅中报告；
7. 把本局的模拟模块（mod 的和地图的合在一起）在各自 `vera.notify` 自定义段中声明的通知名放在一起检查哈希冲突（第 10 节）。同一模块内的冲突拒绝该模块；mod 的名字与地图的名字之间的冲突拒绝地图的模块。提示中给出两个名字。哈希为 −1（`0xFFFFFFFF`）的名字拒绝声明它的模块。mod 和地图声明同一个名字不算冲突：两者得到同一个 ID，由 `Notify` 客户端事件的来源区分。

**初始化。** 首次回调前执行一次 SDK 生成的初始化函数；读档时跳过。初始化只能解析截至当前规则层的名字、探测表项或写日志。其余调用返回 `Unsupported`。初始化、`on_rules`、`on_scenario_start` 各有高于单帧额度的一次性额度。

**失败。**

| 时机 | 结果 |
| --- | --- |
| 开局前 | 在大厅显示原因；带这个模块无法开局 |
| 在 `on_rules` 中 | 不能开局，并提示是哪个模块：它正在写的规则不完整 |
| 对局中，包括 `on_scenario_start`（trap、超出额度或调用深度、参数非法、在 `on_decide` 中调用写入函数） | 在所有机器的同一帧停用该模块；游戏告诉玩家是哪个模块停止了、原因是什么 |
| 宿主失败（分配内存上限时内存不足、Wasm 引擎的内部错误） | 对局错误，不算模块失败，因为无法证明它在每台机器的同一帧发生：对局停止并给出提示，和不同步时一样 |
| 在客户端模块中（超出每个渲染帧的额度、trap） | 该调用被停止，该模块只在这台机器上被停用，并提示该玩家 |

客户端额度用同一套计量按运算单位计算，而不是按时钟计算，所以在浏览器的主线程上也能执行。

**被停用的模拟模块。** 对局继续。

- 它创建的触发器被停用。在其他触发器中（地图触发器，或通过 `Wasm.Tags` 绑定的触发器），只跳过它的模块动作。它排队中的模块动作和指令（第 6g 节）被丢弃。
- 它在可决定事件链上的一环被跳过：上一环的结果传给下一环；首环取原生值。出错的那次调用也按此处理。
- 它的模块弹道上的抛射体改为朝目标直线飞行。
- 它做过的事保留下来：它创建的修饰器（照常到期）、它写入的变量和属性、它写入的规则和对局中的 `rules_set` 覆盖层、它写入的 AI 定义、它创建的触发器（处于停用状态），以及出错的那次调用已经做完的事。
- 它的内存保留在快照和状态哈希中，停在它停止时的样子，所以存档和重连能重现它。

**错误模型。** 属于正常游戏过程的错误只返回状态，模块继续运行：

| 状态 | 原因 |
| --- | --- |
| `Gone` | 引用为 0，或其对象已不存在 |
| `NotFound` | 名字或 ID 没有匹配任何东西，包括地图中没有的路径点 |
| `Refused` | 动作或写入被引擎规则拒绝（比如该格不能建造、该属性此时不可写），或原子动作的目标在其触发器执行时不适用（第 6b 节） |
| `Unsupported` | 本局关闭的功能（例如没有 Ares 时的 Ares 动作），本引擎不认识的表项，或在不可用的地方发起的宿主调用 |

- 调用当场返回结果。写操作返回状态；可失败的取值操作在同一次调用中返回状态，并把值经指针写入模块内存，例如读取金钱得到 (0, Ok) 表示余额为零，(0, Refused) 表示无权读取。对已消失对象的读取返回空值和 Gone，模块继续运行。批量读仍在一次调用内完成，具体签名见附录。
- 由触发器执行的原子动作没有模块代码来接收它的状态：它的错误状态（`Refused`、`Gone` 或 `NotFound`）写入游戏内日志，该动作被跳过。除此之外什么也不发生。
- 表明模块本身有问题的错误会停用模块：参数非法（包括 `trigger_create` 发现的动作非法参数和非法筛选子句，第 6b 节）、在 `on_decide` 中调用写入函数（第 6f 节）、trap、超出运算额度或调用深度。

### 4. 确定性

所有机器运行同一份模块字节，所以结果只取决于引擎如何执行它们。

- 只用白名单中的 Wasm 特性，NaN 规范化（通过改写字节码），并由插桩计数调用深度上限（第 3 节）。
- 不提供时钟、宿主随机源和 WASI。`random(lo, hi)` 从模块自己专用的随机流取数，这条流由场景种子和模块的槽位（mod 或地图）派生，所以模块不会错开原生随机流：不取随机数的模块，原生结果完全不变。会执行原生代码的动作，按那段代码原本的方式从原生随机流取数。每个表项都写明它是否从原生随机流取数（`native`），取几次由那段原生代码决定。
- `on_decide` 中也可以调用 `random`，但它不从模块的主随机流取数，而是从一条按（帧、主体的创建序号、事件种类）派生的子流取数；同一帧中主体和事件种类都相同的后续请求接着这条子流取数，没有主体时序号取 0。所以引擎发出多少次决定调用，都不改变模块主随机流的位置。
- 名字（类型 ID、节名、变量名）比较时不区分大小写，只按 ASCII 规则（`A` 到 `Z`），和 gamemd 读取 INI 的方式一致。字符串以 UTF-8 跨越边界。
- 运算额度由加载时插入的计量代码计算，不用引擎自带的 fuel，所以无论原生还是浏览器的引擎，都会数出相同的运算量，并在同一点停下。宿主调用按它们所做的工作计入同一份额度（按读取的每个属性、扫描或返回的每个对象、检查的每个格子），每个函数的费用写在接口定义中。
- 计量单位、每个宿主函数的费用、默认额度和各项上限按 API 主版本固定，所以在这些限制内运行过的模块在之后的每个版本中都能继续运行。
- 位置、速度等游戏数值以整数（lepton、定点数原始值）跨越边界，全部装在 `i64` 里。小数和倍率使用模拟的定点格式，即 `I16F16` 原始值（`SimFixed`）。模块内部可以使用浮点。
- 模块内存、可变全局变量、模块的表（按其中保存的函数下标存档）、插桩的计数器（已用运算量、调用深度）以及模块的随机流都属于模拟状态：存进快照，计入状态哈希（第 15 节）。变量、修饰器和绑定由引擎持有，同样存档和计入哈希。存档只在两次模块调用之间进行。
- 对模拟模块的调用从不来自并行代码或推测性的计算。投递的记录跨对象按创建序号排列，不取决于引擎的循环顺序；决定请求只在引擎提交结果的那一点发出，按引擎确定的顺序（第 5 节）。

### 5. 执行模型

模拟模块按需导出[生命周期函数](0001-wasm-extension-modules-api.zh-CN.md#12-导出)。SDK 用记录的分派键调用模块动作，周期回调在 `frame % N == 0` 时按注册顺序执行。

模拟模块只在模拟阶段运行。界面、渲染和音频读取已提交的结果。

**模块阶段。** 模拟帧里一个固定的阶段（待定问题 8），按模块加载顺序逐个模块执行（先 mod 的，再地图的）。先触发被推迟的连锁触发器（见下文）；然后每个模块依次收到它的 `on_message` 调用、它的 `on_events` 批次和 `on_frame`。

**投递。** 普通事件（不是可决定事件）只有一种到达模块的途径：触发器触发时，它的每个模块动作向所属模块的队列写入一条固定大小的记录，带着触发该触发器的那个事件的载荷。筛选子句在写入之前检查，不成立就不写入。队列只在模块阶段到达模块，按顺序分一次或几次 `on_events` 调用。没有单独的事件订阅。

- 如果游戏已经结束，或者触发器在模块阶段之前已被禁用或删除，排队中的模块动作会被丢弃。
- 投递前已经死亡的对象，其句柄读出来是“不存在”，绝不会指向另一个对象。主体可能在投递前消失的事件（死亡、致命伤害、受伤、碾压、引爆）在记录中带上事件发生的位置，需要的信息不必再从已消失的对象读取。
- 绑定的触发器的主体在事件引发时已经不存在时（例如绑定到武器的 `Detonated`，开火者已经死亡），记录保留主体的句柄，读出来是“不存在”。触发器的所属方是主体最后的所属方（对抛射体事件，是发射它的所属方），实例是那个已不存在的主体的实例。

**顺序。** 跨对象时，一批中的记录和一次批量提交之后触发的触发器都按主体的创建序号排列，从不按引擎的循环顺序，所以调整引擎循环的顺序或改成并行不会改变它。决定请求是同步的：它们按引擎提交结果的确定顺序到达，这个顺序在每台机器上相同，但在不同引擎版本之间可能改变（第 6f 节）。在同一个对象内，调用按引擎引发它们的顺序进行，这个顺序在不同引擎版本之间也可能改变。主体为 0 的记录（所属方和逻辑触发器，以及事件没有主体的格子触发器）排在最前，按触发器运行时触发它们的顺序排列。

**提交点、批量段和并行段。** 对模块的调用从不在并行代码或推测性的计算中发出。引擎的并行段和预计算（并行的索敌预答、寻路批次、追猎评分）只产生候选结果，要到对象自己的回合才被采用或丢弃；它们不引发事件，也不发出决定请求。

- 事件在结果提交的地方引发，从不在推测性的计算中引发。伤害、开火和抛射体推进在对象各自的回合里逐个提交，事件就在每次提交之后引发。
- 引擎在一点提交一批结果时（例如每帧对所有所属方的生产许可），这一步算作一次计算：其中引发的 VERA 事件的触发器在这批结果提交后立即触发，仍在同一帧、在下一个阶段之前；其中的可决定事件在提交之前对每个模块作为一批决定（第 6f 节）。
- 修饰器到期按到期帧处理，是串行的，不属于并行段（第 15 节）。

**不重入。** 某个模块的调用还在栈上时，引擎从不再次调用这个模块：从这次调用到达的计算中，它在可决定事件链上的一环被跳过（使用上一环的值或原生值）。它发出的动作所引发的事件照常触发其触发器，其中的模块动作照常排队。可以调用其他模块：mod 模块直接执行的动作可以到达地图模块的可决定事件。

**动作时机。**

- 原版动作和原子动作（第 6b 节）在触发器触发时执行，与原版中的原版动作一样，含有模块动作的触发器也是如此。只有模块动作排队：动作为 [原版 A、模块 B、原子 C] 的触发器，先执行 A 和 C，B 在同一帧稍后执行。需要严格顺序的作者，把触发器的全部动作都写成模块代码，再用 `action` 执行原版动作。
- 模块代码用 `action` 直接执行的动作立即执行，属性写入、`modify` 和 `var_set` 也一样。
- `order` 只排队，指令在下一帧执行玩家命令的那一步执行（第 6g 节）。
- 在模块阶段中触发的触发器，其原版动作和原子动作立即执行；其模块动作排到下一帧的模块阶段，因此模块代码不会在一帧之内循环。

**安全点。** VERA 新增的每个投递型事件都在安全点引发：一次计算完成之后（`TakeDamage` 在伤害已经提交之后），一次计算开始之前（`HouseTransfer` 在转移之前），或一次批量提交刚结束时。触发器的原版动作和原子动作从这一点起立即执行。在计算之前引发的事件之后，引擎重新检查这次计算：

- `HouseTransfer` 之后，如果某个动作已经移除了对象或改变了它的所属方，转移就不发生，也不引发 `HouseTransferred`；
- `FatalDamage` 在致命伤害提交之后、死亡流程之前引发；只有对象仍然存在且伤害仍然致命时（某个动作可能治疗了它，或给它加了 `Unkillable` 修饰器），才执行死亡流程。

投递型事件报告的是已经发生的事：模块动作无法取消原生结果（比如死亡）。要做到这一点，需要用可决定事件（第 6f 节）、修饰器（`Unkillable`），或在计算之前引发的事件（`FatalDamage`、`HouseTransfer`）上的原版动作或原子动作。

**连锁。** 立即执行的动作可以在一帧之内连锁：伤害引发 `TakeDamage`，它的触发器用原子动作造成伤害，又引发 `TakeDamage`。

- 连锁中含有模块触发器、VERA 新增的事件或原子动作时，引擎限制它每帧的深度，并且限制每帧这类连锁触发的总次数（否则一个触发另外两个的触发器会触发 2^depth 次）。具体上限是待定问题 17。
- 会超过任一上限的触发器被推迟：它在下一帧模块阶段开始时、排队的动作之前触发，带着它原有的载荷。它的原版动作和原子动作在那时执行，它的模块动作加入那一帧的批次。如果它在此期间被禁用或删除，就被丢弃；它的筛选子句重新检查，它的所属方是主体在那一刻的所属方，作用于已不存在的主体的动作得到 `Gone`。等待中的推迟触发器存档并计入哈希。
- 只由原版事件和原版动作组成的连锁从不推迟，与原版中完全一样地运行（目标 5）。

**高频事件只对绑定的对象引发。** 伤害、开火、命中、抛射体引爆、碾压和执行指令这类事件，以及绑定范围为对象或类型的可决定事件，只对相应绑定引发（第 6a 节）；没有“订阅所有对象”的用法。这是引擎对模块的硬上限之一（第 15 节）。

**存档。** 读档后，模块内存随快照恢复。初始化函数和 `on_scenario_start` 都不会再次运行，也没有 `on_load`。模块内存里的引用仍指向同样的对象，因为句柄是创建序号，不是存储位置。

**额度。** 每个模块每帧有一份运算额度，它是一个与本帧记录数无关的上限，按最慢的受支持平台确定（第 15 节）。战斗变大、记录变多时，模块得到的额度不变，多出的工作推迟到后面的帧。

- 宿主调用按它们所做的工作扣除（第 4 节）。`on_decide` 调用和筛选子句中派生属性的求值从同一份额度中扣除。
- 模块阶段中，引擎按顺序分次调用 `on_events`，每次至多投递固定条数的记录（不超过投递区容量）。本帧用量达到额度后，引擎不再开始新的一次：剩下的记录留在队列中，按下面的积压规则在下一帧最先投递。`on_message` 和 `on_frame` 照常调用。
- 本帧用量达到额度后，该模块在可决定事件链上的一环在本帧余下的时间里被跳过。
- 一次调用不会被中途推迟：单次调用用完一整帧的额度时被停止，模块被停用（第 3 节）。
- 每个模块每帧最多投递固定数量的记录。超出上限或因额度而没有投递的记录按顺序保留，存档并计入哈希，在下一帧最先投递，所以短时间的爆发只会让模块变慢，而不会让它被停用。积压超过固定帧数的记录量的模块会被停用并给出提示：它跟不上。
- 每帧额度、队列上限、每次调用的记录条数和积压上限是待定问题 7。
- 没有 `on_frame`、待投递记录、消息或决定请求时，该帧不调用模块的对局回调。

### 5a. 语言与 SDK

引擎和模块之间的约定只有 Wasm 接口：附录列出的函数，加上附录的表。任何语言，只要它的编译器产出的模块能通过加载检查，就能使用，引擎对所有模块一视同仁。

- **官方 SDK：TypeScript 和 Rust。** 两者都由同一份接口定义和同一组机器可读的表（第 12 节）生成，提供相同的功能（名称按各自语言的命名习惯），并随 API 一起发布版本。每套都附带模板、构建命令、监视模式和示例。
- SDK 按事件种类生成具名字段，原地读取投递记录。触发器用 `.immediate()` 指定立即动作、`.enqueue()` 排队、`.decideSync()` 同步决定（Rust 为 `decide_sync`）。包装函数与宿主调用逐项对应，见[附录 SDK 表](0001-wasm-extension-modules-api.zh-CN.md#3-sdk-对应)。

- **TypeScript SDK。** 预先把 TypeScript 编译成 Wasm，模块足够小，可以嵌入地图。编译器是待定问题 2。它的 API 限定在 TypeScript 与 AssemblyScript 的共同子集内：
  - 不用 `any`，除 `T | null` 外不用联合类型，回调不捕获外部变量，不用 `try`/`catch`；
  - 把多个值组合在一起的参数是用构造函数创建的类或构建器，而不是对象形状或字面量；
  - 引用是普通的 `i64` 值，没有方法，也不为每个引用创建对象：在 AssemblyScript 中，`t.health` 这样的取值器需要给每个引用分配一个对象。对引用的调用是以引用为第一个参数的命名空间函数（`Techno.health(t)`、`Techno.setMission(t, Mission.Hunt)`）；
  - 每个引用值都保持小于 2^53，所以基于 JavaScript 引擎的 SDK 可以用 number 保存它；
  - `i64`、`i32`、`f32` 和各种引用类型（`Techno`、`House`、`Node`……）是 SDK 提供的类型别名；SDK 的 `tsconfig` 不包含 `lib.dom`，所以 `Node` 不会与 DOM 的同名类型冲突；
  - 顶层代码成为初始化函数（第 3 节）。

  这样同一份源码既能用 `tsc` 做类型检查，也能用 AssemblyScript 编译，本 RFC 中的示例在两者中都有效。
- **Rust SDK。** 面向想要完全控制和更高性能的作者；引擎自己的兼容性测试用例也用它编写。引用是 newtype，可以带方法（`techno.health()`）。
- **构建产物。** 两套 SDK 的构建命令保证产出的模块能通过加载检查：TypeScript SDK 用 AssemblyScript 编译时，把顶层代码导出为初始化函数而不生成 `start` 段，也不产生默认的 `env.abort` 导入；Rust SDK 在使用标准库时，构建后用 wasm-opt 把预编译标准库带入的引用类型编码改写回白名单内的编码，`no_std` 模块不需要这一步。
- **其他模组开发语言。** C、C++、Python、.NET（如 C#）、Go、Ruby、Elixir、Perl 和 Zig 均可按同一 ABI 接入。每种工具链都需要产出符合第 3 节约束的 Wasm 核心模块，按附录签名导入和导出函数。社区可用第 12 节的表生成对应语言的包装函数。需要解释器或运行时的工具链还须把它编入模块，并满足下述导入和体积限制。
- **导入。** 模块只能导入 `vera:*` 接口。引擎不提供 WASI，项目也不发布 WASI 垫片。运行时依赖 WASI（时钟、随机数、文件）的语言，只有在它自己的工具链去掉这些导入时才能使用。
- **体积和特性。** 以 Wasm 垃圾回收或其他被拒绝的特性（第 3 节）为目标的编译器，比如某些 Kotlin、Dart 和 Java 工具链，产出的模块无法通过加载检查。会把大型运行时或垃圾回收器打包进每个模块的语言，产出的文件更大，可能超过地图嵌入上限。这是作者工具链的取舍，与引擎无关。

**宿主工具。** 独立工具可用以下绑定嵌入 Wasmtime。[Wasmtime 嵌入文档](https://docs.wasmtime.dev/lang.html)

| 宿主语言 | Wasmtime 入口 |
| --- | --- |
| Rust | `wasmtime` crate |
| C | `wasm.h`、`wasi.h`、`wasmtime.h` 头文件，可用 CMake 构建 |
| C++ | `wasmtime.hh` 头文件 |
| Python | PyPI 包 `wasmtime` |
| .NET | NuGet 包 `Wasmtime` |
| Go | `wasmtime-go` |
| Ruby | `wasmtime` gem |
| Elixir | Hex 包 `wasmex` |
| Perl | CPAN 发行包 `Wasm` 中的 `Wasm::Wasmtime` |

### 6. 五个概念

| 概念 | 函数 | 表（附录） |
| --- | --- | --- |
| 对象和属性 | `get`、`get_many`、`set`、`modify`、`unmodify`、`find`、`rules_get`、`rules_set` | [属性](0001-wasm-extension-modules-api.zh-CN.md#7-属性) |
| 变量 | `var_get`、`var_set`；声明在 `vera.vars` 中 | [自定义段](0001-wasm-extension-modules-api.zh-CN.md#自定义段) |
| 事件（含可决定事件） | `trigger_create`、`trigger_remove`、`trigger_bind`、`trigger_unbind`；导出 `on_events`、`on_decide` | [事件种类](0001-wasm-extension-modules-api.zh-CN.md#4-事件种类) |
| 动作 | `action`、`send_notify`、`order` | [动作种类](0001-wasm-extension-modules-api.zh-CN.md#5-动作种类) |
| 界面节点（客户端） | `client_node_create`、`client_node_remove`、`client_node_find`、`client_set`、`client_set_bytes` | [客户端节点](0001-wasm-extension-modules-api.zh-CN.md#710-客户端节点) |

另外几个函数是基础设施：`frame`、`random`、`log`、`has_kind`、`lookup`、`name_of`。

- 函数是冻结的界面，数量固定。事件种类、动作种类、属性、名字种类、节点种类和其他枚举都是表：新的次版本只在表的末尾追加，从不修改或删除已有的表项。`has_kind(table, id)` 告诉模块当前引擎是否提供某个表项，模块可以据此在旧引擎上降级运行。
- 每个原版动作和原子动作都调用引擎中该操作现有的实现；模块不会得到第二份实现。每个可写属性的写入同样走它现有的 owner。
- 可决定事件以游戏概念命名（`TakeDamage`、`TargetChanged`），从不以原生函数命名，这样引擎重构后它们依然成立。
- 对于非常频繁的决策，优先用数据而不是回调：目标优先级用修饰器改变 `TargetPriorityMultiplier` 属性，再配合 `TargetChanged` 事件。逐次调用的可决定事件留给不那么频繁的决策。

每个动作只调用现有 owner 完成一个游戏操作。模块通过组合动作实现复杂行为。

**位置。** 动作接受目标格、生成点和目的地。对象位置属性只读，通过传送、运动动作或移动任务改变。第 9 节第 4 层允许设置抛射体位置，由引擎钳制并照常判定碰撞。

### 6a. 触发器：事件、筛选子句和动作

触发器至少有一个事件，全部成立才触发；每个事件可带筛选子句，重复类型沿用原版。动作和决定处理函数至少要有一项。只注册决定处理函数时，动作数可为 0，且必须恰有一个可决定事件（第 6f 节）。

**订阅只通过触发器。** 模块收到事件的唯一途径是触发器，触发器有三个来源：

- 代码：`trigger_create` 用事件、筛选子句和动作创建触发器，`trigger_bind` 把它绑定到一个对象、一个类型、一个武器、弹头或抛射体类型，或一个格子；
- mod 的 INI：`Wasm.Tags` 把标签中的触发器绑定到类型（第 2 节）；
- 地图触发器：带模块动作 `Action=Wasm:name` 的触发器。

触发器随时可以创建、删除、绑定和解绑；它的 `Enabled` 属性控制启用和禁用。

**绑定。** 和对象有关的事件只对绑定的对象引发：

- 绑定了该触发器的对象（对象绑定）、类型绑定了该触发器的对象（`Wasm.Tags` 或类型绑定），以及自身标签包含该触发器的对象；
- 对于武器事件（`Fire`、`HitTarget` 和 `Detonated`），还包括使用绑定了该触发器的武器、弹头或抛射体类型的任何对象。武器绑定对使用这把武器的所有射手生效，不论射手是什么类型，射手就是主体：

  ```ini
  [RedEye2]                   ; 一把武器
  Wasm.Tags=MissileFiredTag   ; 每个使用 RedEye2 的射手开火时都引发其 Fire 触发器
  ```

- 高频事件（伤害、开火、命中、抛射体引爆、碾压、执行指令）没有“所有对象”的订阅。真的需要全部对象时，SDK 的 `bindAllTypes` 把触发器逐个绑定到每个类型上，开销因此在代码里是明的；开销叠加层对这样的绑定给出警告（第 13 节）。
- 格子绑定（代码中把触发器绑定到格子引用）只用于[附录 4.1](0001-wasm-extension-modules-api.zh-CN.md#41-原版事件-061)中注明“绑定格子”的事件；把其他事件的触发器绑定到格子是非法参数。地图的 CellTag 照原版处理。
- 和对象无关的全局事件（所属方事件、逻辑事件、`Timer`、`SuperWeaponLaunched`）不需要绑定。
- 绑定到某个类型的触发器在每个绑定对象上以各自的实例运行（第 7 节）。

**事件种类。**

- **投递型事件**发生在某个时刻（受到伤害、武器开火、被摧毁）。触发器在那一刻触发；其中的原版动作和原子动作立即执行，模块动作则带着事件的载荷排队（第 5 节）。VERA 新增的投递型事件在安全点引发（第 5 节）。
- **轮询型事件**描述一种状态（生命低于某值、金钱高于某值、变量等于某值）。引擎按触发器设定的间隔原生检查它们，这个间隔有下限（待定问题 7），事件在边沿触发：在状态变为成立的那次检查时触发，之后要等到某次检查时状态不成立，才会再次触发。对象在 `frame % interval == serial % interval` 的帧接受检查，`serial` 是它的创建序号；所属方的轮询改用所属方在所属方数组中的下标。投递型的 `Timer` 事件不错开：它从其触发器创建的那一帧算起，每个周期触发一次。
- 普通属性统一用 `PropertyPoll`：例如每 15 帧检查 `HealthPercent < 30`，SDK 写作 `Trigger.onProperty(Prop.HealthPercent, Op.Lt, 30, 15).bind(E1).enqueue(onLowHealth).done()`。引擎直接读取属性并维护条件的边沿状态。需要额外参数、组合计算或写入时重置计时器的事件见附录 4.4。
- **可决定事件**在事件表中标为“可决定”。带决定处理函数的触发器在决策点同步询问模块（第 6f 节）。
- 每个事件都标明它所附着的对象（主体），以及涉及的另一个对象（如果有的话：攻击者、目标、载具、生产者）。
- 记录的值都是整数或引用。伤害和原版一样是整数；模拟 API 中没有浮点值。

**筛选子句。** 每个事件最多带 N 条筛选子句（N 属于待定问题 7），全部成立（AND）时事件才算成立。

- 子句的形式是 `Subject|Other|House .属性 运算符 值`，或 `Var(作用域,名字) 运算符 值`。运算符为 `=`、`!=`、`<`、`<=`、`>`、`>=`，值是常量。`House` 是触发器的所属方：触发器定义的所属方不为 0 时就是它；为 0 时是主体此刻的所属方；没有主体时（全局事件）是地图的中立所属方（`Neutral`）。
- 引擎在把记录放进队列之前原生检查子句，所以不成立的事件从不投递。普通属性的子句不花模块的额度；派生属性（如 `NearbyEnemyCount`、`TargetInRange`）的求值按它的费用计入所属模块的额度（第 5 节）。
- `find` 使用同样的子句布局（第 6c 节）。
- INI 写法例如 `Where1=Subject.HealthPercent<30`、`Where2=Var(Subject,Panicked)=0`；具体格式是待定问题 4。
- 计算型的条件：常用的作为派生属性追加到属性表中（例如 `NearbyEnemyCount`、`TargetInRange`），其他的写成代码中的 `if`。条件之间的“或”、两个对象之间的比较、计数都写在代码里。
- 红警 2 的变量事件（27、28、36、37）照常可用。

触发时执行原版、原子和 AI 动作，模块动作排队投递。见[绑定示例](#把触发器绑定到类型)。事件字段、绑定范围和版本层级见[附录事件表](0001-wasm-extension-modules-api.zh-CN.md#4-事件种类)。历史值由模块保存在变量或模块内存中；INI 不提供记录器、算子或表达式。

### 6b. 动作

所有动作都在附录的[动作种类表](0001-wasm-extension-modules-api.zh-CN.md#5-动作种类)中按编号排列：原版动作 0..145（启用 Ares 时加上 146..149）、原子动作、AI 动作和模块动作。同一个种类有两种用法：

- 模块代码用 `action(kind, target, params, len)` 直接执行，目标是一个明确的引用（对象、所属方、格子或抛射体；触发器、标签和小队放在参数的 `other` 中）。创建对象的动作返回新对象的句柄，其他动作的值为 0；两者都在同一次调用中返回状态。
- 触发器的动作列表写的是同一个种类，加一个目标选择和参数（附录的[触发器定义](0001-wasm-extension-modules-api.zh-CN.md#固定布局)）。

直接设定生命值、等级或弹药只定义一次写入语义：模块代码通过 `set` 写对应属性，触发器用 `SetProperty` 编码相同的写入，两者经过同一状态所有者。SDK 可生成带属性名的写入函数。增量、伤害归属和触发时才解析的参数各有游戏语义，保留相应动作。

**原子动作**是瞬时的游戏操作，每个都有一个 owner：发射武器、发射超级武器、造成伤害、摧毁、移除、创建对象、传送、引爆弹头、写变量、修饰属性、让某个所属方结束游戏，等等（[附录 5.3](0001-wasm-extension-modules-api.zh-CN.md#53-原子动作)）。造成伤害走弹头和护甲规则，带来源，用于击杀归属和经验；直接设定生命值不计归属。传送到被占的格子时按规定的规则处理：选附近的格子，或动作失败。

在触发器中，动作的目标是一个选择（`ActionTarget`）：

- `Subject`（默认）：事件的主体；
- `Other`：事件中的另一方对象；
- `TagHolder`：标签中持有该触发器的对象，CellTag 则是那个格子；对于绑定的触发器，是引发事件的对象；
- `Projectile`：事件中的抛射体；
- `House`：参数中的所属方，它为 0 时为触发器的所属方；
- `Cell`：参数中的格子。

- 参数放在一个固定布局里：一个 ID、两个小整数、两个整数值、一个格子、一个所属方、一个引用和一段文字（附录的[动作参数](0001-wasm-extension-modules-api.zh-CN.md#固定布局)）。只在模块代码中可用的动作（例如创建抛射体）另带一段变长数据。
- 不用目标的动作（例如 `SetTechLevel` 或 `Log`）忽略目标。
- 路径点以路径点引用给出（附录的[引用](0001-wasm-extension-modules-api.zh-CN.md#引用)）。`trigger_create` 把它解析为路径点所在的格子，因为路径点不会移动。地图上没有的路径点是地图数据错误，不是模块错误：`trigger_create` 返回 `(0, NotFound)`，不创建触发器并写入日志，模块保持启用。写在 INI 中时，它在加载时于大厅中报告。

参数表达不了的部分由固定规则决定：

- 明确的所属方（`House` 目标、`SetOwner` 的新所属方、所创建对象的所属方）取参数中的所属方。它为 0 时：在触发器中使用触发器的所属方（第 6a 节）；在直接调用中是非法参数（第 3 节）。原版动作中隐含使用触发器所属方的地方（例如 `LightningStormStrike`）同样取这个所属方。
- 在触发器中，来源（伤害、击杀或引爆的来源：`Kill`、`Damage`、`DetonateWeapon`、`DetonateWarhead`）是事件中的另一方对象，并且是可选的：没有来源时，动作在没有来源的情况下执行，不计击杀归属。直接调用时，来源取参数中的引用。
- 动作施加作用的第二个对象（乘客）在触发器中是事件中的另一方对象，直接调用时是参数中的引用。没有第二个对象，或者 `FireWeapon` 没有可瞄准的格子、另一方对象或当前目标时，动作得到 `Gone` 并被跳过。
- 对象目标的格子是对象所在的格子；`Projectile` 目标的格子是抛射体下方的格子。坐标取该格子的中心；`Projectile` 目标例外，其坐标为抛射体的中心。`CreateObject` 的目标为建筑时例外：新对象从这座工厂的原生出口离开，而不是放在格子上（附录 [5.3](0001-wasm-extension-modules-api.zh-CN.md#53-原子动作)）。
- 每种动作用到的目标和字段，以及各动作自己的规则（例如 `FireWeapon` 的瞄准），见[附录 5.1](0001-wasm-extension-modules-api.zh-CN.md#51-动作的用法)。

检查：

- `trigger_create` 检查每个动作的参数。非法的参数会停用模块（第 3 节）：永远不适用于该动作的目标种类（例如 `Kill` 的目标是 `Cell`），或缺少必需的字段（`LaunchSuperWeapon` 的格子）。`action` 对直接调用做同样的检查。
- 写在 INI 中的原子动作在加载时检查，并在大厅中报告。它们的 INI 写法是待定问题 4。
- 触发器执行时才发现目标不适用（例如 `Kill` 的 `TagHolder` 是一个格子），属于数据错误：动作得到 `Refused`，状态写入日志，动作被跳过，模块保持启用。
- 原子动作立即执行，并可能引发新的事件，所以它们可以在一帧之内连锁，受第 5 节的上限约束。

### 6c. 对象、属性与修饰器

**引用。** 每个引用都是一个 `i64`：对象的句柄（单位、建筑、抛射体、所属方、小队、触发器、标签、修饰器、超级武器、客户端节点）、类型引用、格子引用、路径点引用或全局规则引用。编码由 SDK 完成，所有值都小于 2^53，0 表示“没有”（[附录：引用](0001-wasm-extension-modules-api.zh-CN.md#引用)）。

**属性。** `get(ref, prop)` 读一个属性，`get_many(refs, n, props, m, out)` 一次读 n 个引用的 m 个属性，`set(ref, prop, value)` 写一个属性。属性表按引用种类分组（对象、所属方、格子、类型和规则、全局、触发器和标签、修饰器、客户端节点），并写明每个属性：

- 值类型（整数、布尔、定点数、枚举、引用、ID 或字符串）；
- 能否写，何时能写（任何时候、只在 `on_rules`、白名单中的对局键）。写入走该属性现有的 owner：写 `Owner` 就是转移所属，写 `Mission` 就是像玩家指令一样排入一个任务；
- 客户端能否看到（第 10 节）；
- 能否被修饰。

`get` 读到的是有效值：基础值加上全部修饰器的结果。字符串属性返回一个字符串 ID，用 `name_of` 读出文字；SDK 直接返回字符串。

**派生属性和视点属性。** 有些属性是引擎算出来的：`HealthPercent`、`NearbyEnemyCount`、`TargetInRange`。还有少数属性取决于一个视点所属方（`Relation`、`Revealed`、`Buildable`、`Placeable`）：在筛选子句中，视点是触发器的所属方；在 `find` 中，视点是搜索的 `viewpoint` 字段；在客户端中，视点是本玩家。直接 `get` 它们时没有视点，返回 `Unsupported`。`Placeable` 还需要一个类型，所以只在 `find`（包括 `client_find`）中用查询的 `type` 求值，其他地方返回 `Unsupported`。

**修饰器。** `modify(ref, prop, op, value, frames, source, group)` 在一个对象或所属方的可修饰属性上加一个修饰器，返回修饰器的句柄；`unmodify(modifier)` 提前移除它。SDK 用 `Modifier.add`、`Modifier.multiply`、`Modifier.override` 分别表示加、乘和覆盖，例如 `Modifier.multiply(unit, Prop.SpeedMultiplier, fixed(0.5), 150)`。三个入口都只调用一次 `modify`；可选的来源和组直接编码为整数，省略时均为 0。

- 运算为加（`add`）、乘（`multiply`，定点数）和覆盖（`override`）。`frames` 为持续帧数，负数表示无限；`source` 是来源对象（用于击杀归属和来源规则），可为 0；`group` 是互斥组，0 表示不分组。
- 叠加、互斥组和到期都由引擎持有，存档并计入哈希。默认的合成方式：有效值 = (基础值 + 全部加值) × 全部乘数，最新的覆盖修饰器再取代这个结果。对应 Phobos 键的属性（[附录 7.2](0001-wasm-extension-modules-api.zh-CN.md#72-可修饰属性)）不用这个公式，而是用 Phobos 自己的算法（运算顺序和取整），所以修饰器和等价的 Phobos 效果得到相同的值。有效值在修饰器加入、移除或到期时重新算出并缓存，读取时不再合成（第 15 节）。同一来源模块（mod 或地图，即修饰器的 `Origin` 属性）在同一个引用上用同一个组加入新修饰器时，替换该组中已有的修饰器。叠加上限和刷新规则是待定问题 13。
- 修饰器本身也是对象，有属性（剩余帧数、目标、来源、组）；`ModifierStart`、`ModifierStacks`、`ModifierExpire` 事件报告它们；所属方上的修饰器的这些事件以全局形式引发，记录的 `house` 为该所属方（附录 [4.3](0001-wasm-extension-modules-api.zh-CN.md#43-新的投递型事件)）。
- 旧版本中的持续效果种类都变成了可修饰属性（倍率、射程、隐形、禁止开火、阻止死亡……），见[附录 7.2](0001-wasm-extension-modules-api.zh-CN.md#72-可修饰属性)。少数无法成为普通属性的变成特殊属性或动作：对攻击类型的免疫是一个位掩码属性 `ImmunityFlags`；替换武器是覆盖 `PrimaryWeapon`、`SecondaryWeapon`；激光拖尾是 `LaserTrailType`；附着动画是动作 `AttachAnim`；限时变成另一类型是带帧数的 `Convert` 动作；运动（被抛起、被推动）是以后的运动动作；传送是动作 `Teleport`。变形、超时空移动和运动互斥，由 owner 保证同一时间只有一个生效。
- 显示在对象上方的文字、数值或按钮属于客户端节点（第 10 节），不是修饰器。
- 只要模块功能开启（第 14 节），修饰器的 owner 就可用，不论 Phobos 是否开启。Phobos AttachEffect 的 INI 键（类型、武器和弹头上的 `AttachEffect.*`，以及 `[AttachEffectTypes]`）只在 Phobos 开关打开时读取，所以原版玩法保持原样；读取后，它们创建的也是同一个 owner 中的修饰器。修饰器与 Phobos 共用的代码存在于每个构建中，由运行时开关开启（Phobos 的键由 Phobos 的开关开启，模块修饰器由模块功能开启），从不放在构建 feature 后面（第 14 节）。

**搜索。** `find(query, len, out, cap)` 搜索对象、所属方、格子、类型、小队、触发器、标签、修饰器或超级武器，结果写入模块提供的缓冲区，写入数量和续页位置写入一个小的结果结构，返回状态。

- 范围：整张地图、一个格子加半径，或一个矩形；可按类型和所属方过滤；可带筛选子句，布局与触发器的相同，其中 `Subject` 是被检查的候选。
- 结果按创建序号排序，这个规则不依赖引擎如何存放对象。有四种结果保持自己的顺序：格子按格子下标，所属方按所属方数组的顺序，修饰器按加入的顺序，类型按类型 ID。
- SDK 用 `.first()` 取首项，或用 `.page(buffer, after)` 把一页写入已有缓冲区。每页一次宿主调用；下一页按前一页末尾的排序位置继续，即使该对象已删除也有效。每页读取调用时的世界状态，刚新增且排序在游标之后的匹配项可在后续页出现。
- 地图和格子的查询都是格子引用的属性：地形类型、高度、覆盖物、矿石、按移动类型是否可通行、是否已揭开、能否放置，以及 CellTag。
- 原来的探测（对象能否向它当前的目标开火、当前目标是否在主武器射程内、某类型能否放在某格）变成派生属性和视点属性：`TargetInRange`、`CanFireAtTarget`、`Placeable`。对任意武器和任意目标的探测留到以后。“最近的可放置格子”用带 `Placeable=1` 子句的 `find` 加模块代码实现。

完整的属性表见[附录第 7 节](0001-wasm-extension-modules-api.zh-CN.md#7-属性)，搜索范围见[附录 8.2](0001-wasm-extension-modules-api.zh-CN.md#82-搜索范围find)。在客户端模块中，读取只暴露本玩家自己的界面能显示的内容（第 10 节）。

### 6d. AI

电脑所属方保留它们的 AI。AI 不是一个单独的概念：

- **定义**是 INI。特遣部队、小队脚本、小队类型和 AI 触发器（`[TaskForces]`、`[ScriptTypes]`、`[TeamTypes]`、`[AITriggerTypes]`）由 `on_rules` 中的 `rules_set` 写入，和地图或 `AIMD.INI` 中的写法一样，经过同一个读取器。这四个节和它们列出的节写入 AI 文档（`AIMD.INI` 加地图，按同样的层叠），不写入规则；`rules_get` 读这些节时读合并后的 AI 文档。
- **操作**是动作种类：启动小队（原版动作 4，以及不受数量上限限制的 `CreateTeamUnlimited`）、解散小队、加入或移出成员，以及 AI 相关的原版动作（74 至 79）。
- **状态**是属性：小队的类型、脚本、脚本游标、是否成功；AI 触发器的启用状态；所属方的 AI 触发器总开关。写 `Script` 或 `Cursor` 就是修改运行中小队的脚本或跳到某一行。
- **小队脚本动作**保持为一张编号表（附录 [6.2](0001-wasm-extension-modules-api.zh-CN.md#62-小队脚本动作)），作为 `[ScriptTypes]` 中的数据使用。

AI 操作统一经过现有 AI owner。模块也可以用 `order` 像玩家一样指挥电脑所属方（第 6g 节）；指令经过命令的 owner，原生 AI 在旁照常运行。

### 6e. 变量

变量是带作用域和可见度的 `i64` 整数，取代了旧版本中的标记。

- **作用域**：全局、所属方或单个对象。`var_get(scope, var)` 和 `var_set(scope, var, value)` 的 `scope` 为 0 表示全局，否则是一个所属方或对象引用。作用域与变量的声明不符属于非法参数。
- **可见度**决定客户端能否读到它：私有（全局变量没有任何客户端能读；所属方变量只有该所属方的玩家能读；对象变量只有对象所属方的玩家能读）、盟友（再加上盟友）、视野内（单个对象作用域专用：再加上当前能看到该对象的玩家）、公开（所有人）。
- **声明。** 模块在 Wasm 自定义段 `vera.vars` 中声明它的变量：名字、作用域、可见度和默认值。SDK 构建时按项目配置中的列表写入这个段。同一份声明生成模拟读写和客户端只读访问器：全局变量写作 `Wave.get()`，所属方和对象变量须传相应引用。访问器在初始化时解析并缓存本局 ID，筛选和原子动作也接受生成的变量名；客户端读取仍按可见度检查。动态跨来源引用继续通过名字解析。`lookup` 按名字给出变量 ID；变量名写在模块字节里，所以不算秘密。
- **红警 2 的局部变量和全局变量**是固定的特例：全局作用域、私有、默认值 0，取值只有 0 和 1（写入非零值即为 1），使用固定的 ID（附录[变量 ID](0001-wasm-extension-modules-api.zh-CN.md#id)）。
- 设置变量会像地图动作那样重置等待这个变量的触发器的计时器（事件 27、28、36、37，以及 `VariablePoll`）。
- 对象作用域的变量随对象一起消失。所有变量由引擎持有，按引用索引放在旁路表中，存档并计入哈希（第 15 节）。
- 变量可以在筛选子句中判断（`Var(Subject,Panicked) = 0`），可以用原子动作 `SetVar` 在触发器中写入，也可以用 `find` 的子句搜索。

### 6f. 可决定事件

可决定事件取代了旧版本中的覆盖点。事件表有一列“可决定”，并写明结果槽的含义：例如 `TakeDamage` 的结果是最终伤害，`TargetChanged` 的结果是选中的目标，`FatalDamage` 的结果是死亡方式，`Fire` 的结果是一份射击方案。只可决定的事件（例如 `ProductionAllowed`、`CommandAllowed`）没有投递形式。

- 带决定处理函数的触发器（SDK 中的 `.decideSync(fn)`）让事件在决策点以决定请求的形式引发，而不是在安全点投递。决定请求按附录事件表的绑定范围引发，并经过筛选子句；全局事件（如 `Defeat`）无需对象绑定。
- 引擎在决策点同步调用 `on_decide(ptr, count)`。每个请求是一条固定大小的决定记录：事件记录，加上原生值、上一环的结果、结果槽和“已处理”标志（附录的[固定布局](0001-wasm-extension-modules-api.zh-CN.md#固定布局)）。需要更多空间的结果（射击方案、路径、抛射体的逐帧结果）写入请求附带的结果区。
- 决策点只在引擎提交结果的那一点：对象自己的回合里设定目标、提交一次伤害、射出一次射击的地方。调用是同步的，按引擎提交结果的确定顺序进行。引擎从不为推测性或并行的预计算（索敌预答、寻路批次、追猎评分）发出决定请求，因为这些计算的答案可能被丢弃。
- `count` 通常为 1。只有引擎本身在一点提交一批结果时（例如 `ProductionAllowed`），`count` 才可能大于 1：这批请求按主体的创建序号排列；投递区放不下全部请求和它们的结果区时，引擎按顺序分成多次调用，每次尽量填满投递区。每个请求的结果区大小按事件种类固定（待定问题 7）。
- 处理函数只可使用[导入表](0001-wasm-extension-modules-api.zh-CN.md#11-导入)标为 `decide` 的函数；调用写入函数会停用模块。
- 处理函数可以在模块内存中保存自己的状态：调用只发生在提交点，按引擎的确定顺序，所以这份状态在每台机器上相同。处理函数中的 `random` 从派生子流取数（第 4 节），决定调用的次数不改变模块主随机流。
- mod 和地图的链式规则见第 2 节，不重入和额度见第 5 节。
- 侧边栏和 AI 这类本地或频繁的读者读取缓存的结果：例如 `ProductionAllowed` 每帧对每个所属方和每个绑定类型决定一次，侧边栏显示这个结果。

版本 1 提供哪两三个可决定事件是待定问题 10。候选：`TakeDamage`（伤害）、`TargetChanged`（目标选择）、`ProductionAllowed`、`ProductionQueued`（生产入队）、`Fire`（接管一次射击，第 9 节）、`CommandAllowed`、`FatalDamage`（死亡方式）、`Defeat`（否决引擎的判负，用于自定义胜负规则）。

### 6g. 所属方指令

模拟模块用 `order(house, ptr, len)` 指挥一个电脑所属方，方式和玩家指挥自己的所属方一样。它使用客户端模块传给 `client_send_order`（第 10 节）的 `Order` 布局和[指令表](0001-wasm-extension-modules-api.zh-CN.md#83-枚举)，涵盖单位指令、生产、放置建筑、集结点、维修、出售和超级武器。

动作直接完成一项操作；指令则是让所属方去做它的玩家能做的事，花玩家要花的钱，过玩家要过的检查。`CreateObject` 直接造出一个单位，不花钱；`QueueProduction` 指令要付钱，还要等工厂造出来。

- **所属方。** `house` 必须是没有玩家控制（`IsHuman` 为 0，也不受战役玩家控制）且尚未战败的所属方，否则 `order` 返回 `Refused`。玩家的所属方只接受这名玩家的指令，包括该玩家的客户端模块；模块要移动玩家的单位，用 `SetMission`。引用为 0 或不是所属方属于非法参数（第 3 节）。
- **时机。** 引擎把指令排队。第 F 帧发出的指令在第 F + 1 帧执行，位于执行所收到玩家命令的那一步，与模块阶段在帧中的位置无关（待定问题 8）。这一步先执行该帧的玩家命令，再执行 mod 模块的指令，然后是地图模块的指令，各自按发出顺序。指令没有网络命令延迟：每台机器锁步发出同样的指令，与之并行的原生 AI 也没有延迟。
- **准入。** 原生的命令执行步骤只接受有玩家控制的所属方的命令；它也接受模块发给电脑所属方的指令。原版玩法从不为电脑所属方发命令，因此不受影响。
- **校验。** 执行时，指令按当时的状态经过与该所属方的玩家发出同一条指令时相同的检查，例如单位归属、前提条件和建筑放置。忽略玩家指令的单位（`IgnoreOrders`）同样忽略模块的指令。已消失或不再归该所属方的单位从指令中去掉。没有通过检查的指令什么也不做，和玩家一样。生产像玩家一样花钱、花建造时间。发出时，`order` 只检查所属方、指令表（`target` 和 `value` 的种类、单位列表的每一项都是对象句柄、只有表中列出单位列表的指令才带单位）和每帧上限；不符合时返回 `Refused`，不排队。未知的指令返回 `Unsupported`。
- **结果。** 执行的指令引发与同一条玩家指令相同的事件和决定，包括 `Commanded`、`CommandAllowed`、`ProductionQueued` 和 `ProductionCancelled`。`order` 在调用期间不执行任何操作，也不引发事件；模块在之后的帧中通过属性、搜索和事件看到结果。
- **开销和上限。** 每次调用按指令条数和单位项数计费。每个模块每帧的指令条数和单位项数有上限（待定问题 7）。
- **存档、回放和重连。** 指令从不进入网络命令流。等待下一帧执行的指令存档并计入哈希。回放和重连的玩家重新模拟模块，模块再次发出同样的指令，所以回放不必记录它们。
- **原生 AI。** 该所属方的原生 AI 照常运行（第 6d 节），可能改派同一批单位或排入别的生产。模块可以用现有开关收窄它（`AiTriggersActive`、`AutoBaseBuilding`、拒绝 `ProductionQueued`），但不能让它停下。把一个所属方的决策交给模块是待定问题 18。
- **被停用的模块。** 丢弃它排队中的指令（第 3 节）。

SDK 用 `Client.order` 所用的构造器组装指令（附录[第 3 节](0001-wasm-extension-modules-api.zh-CN.md#3-sdk-对应)）。

### 7. 运行时的触发器和标签

模块按地图的同一模型创建触发器：

```ts
// TypeScript（兼容 AssemblyScript），convoy 是要监视的运输车句柄：
const americans = Rules.country("Americans");
if (americans != NO_HANDLE) {
  const house = Find.houses().country(americans).first();
  if (house != NO_HANDLE) {
    const t = Trigger.on(Event.Killed).house(house).bind(convoy).enqueue(onConvoyLost).done();
    if (t != NO_HANDLE) Trigger.setEnabled(t, false);   // 暂停，写 true 恢复
  }
}

Trigger.on(Event.CrossesHorizontalLine) // 格子事件（附录 4.1 注明“绑定格子”）
  .bind(Cell.at(40, 52))                // 格子绑定
  .enqueue(onLineCrossed).done();

Trigger.on(Event.TakeDamage).bind(Rules.technoType("E1")).enqueue(giPanic).done();   // 同 Wasm.Tags=：每个 E1 运行自己的实例
```

- 新建的触发器放进现有触发器运行时的列表，和地图里的放在一起，不另存一份。它们使用确定性的编号，不会和地图里的编号冲突，并随触发器运行时一起存档和计入哈希。
- 绑定（INI 中的 `Wasm.Tags`、代码中的 `trigger_bind`）不占用对象的标签槽位，而是作为独立的订阅另外记录。所以地图上预先放置、自带标签的对象保留它的标签，同时也接收绑定的触发器。代码中的类型绑定立即作用于该类型的每个对象，mod 和地图的模块都可以使用。
- 一个对象只有一个标签，一个标签可以连接多个触发器。标签只为兼容红警 2 而保留：地图触发器通过标签挂到对象上，对象的 `Tag` 属性可以读，也可以设为另一个已有的标签（和原版一样替换原有的标签）。模块不创建标签：它用对象绑定代替。让一个对象挂多个标签属于 VERA 扩展，需要单独的 RFC。
- 被绑定的对象，以及得到一个含有模块触发器或 VERA 新增事件上的触发器的标签的对象，都会得到它自己的一个标志位，所以即使它的类型没有绑定任何东西，事件触发点也会为它引发这些事件（第 15 节）。
- 每个绑定对象以各自的实例运行绑定的触发器，重复状态按对象分开：一次性触发器对每个对象各触发一次。类型绑定只保存一份触发器定义；按对象的实例状态只在它不同于默认值时（例如一次性触发器已经触发）才创建（第 15 节）。禁用或删除触发器会作用于所有实例。触发器定义的所属方为 0 时，触发器的所属方是它触发那一刻主体的所属方；标签持有者是引发事件的对象。
- 对象绑定随对象消失，触发器本身留下，需要时用 `trigger_remove` 删除；`trigger_unbind` 提前解除绑定。删除对象、标签或触发器时，通过触发器运行时现有的清理逻辑解除关联。
- 新的事件和动作编号分配在不与 Ares、Phobos 冲突的范围内（待定问题 5）。

### 8. 修改规则

| 时机 | 能改什么 | 方式 |
| --- | --- | --- |
| `on_rules` | 任意键；新增类型；AI 定义 | `rules_set(section, key, value)`：值是 INI 文本，走原生 INI 读取器、钳制和读后处理；计入大厅哈希 |
| 对局中，按类型 | 公开白名单里的键（待定问题 11） | `rules_set("E1", "Speed", "6")`，或写类型引用上的对应属性：值像 INI 文本一样解析，从下一帧起生效，让相关缓存失效，并作为规则覆盖层存档 |
| 对局中，按对象 | 生命值、所属方、任务、等级、弹药、变量；倍率等可修饰属性 | 通过现有的单对象 owner：`set`、`modify`、动作（第 6c 节） |

- `rules_get(section, key, out, cap)` 读出原始字符串，除初始化函数外都可用。常用的键还是类型引用和全局规则引用上的带类型属性（附录 [7.7](0001-wasm-extension-modules-api.zh-CN.md#77-类型与规则)），读到的就是引擎实际使用的解析后的值；引擎从不读取的键，只能通过 `rules_get` 从合并后的文本中读出。在 `on_rules` 中，`get` 读到的是本层之前处理过的值，本次调用写入的值要等这一层处理完才读得到；对类型引用 `set` 等于用值的 INI 文本调用 `rules_set`。
- 每个白名单键都要写明修改它对地图上已有对象的影响（例如新的 `Strength` 下当前生命值如何变化）。
- 对局中不能新增类型。
- 启用 Ares 或 Phobos 时，模块能在规则中看到它们的键。白名单逐个写明这些扩展键能否在对局中修改。

### 9. 示例：抛射体弹道

四个层级都在 `rules.wasm` 中运行，因为它们决定打中什么。`ui.wasm` 可以加纯视觉效果，比如拖尾和光效。

| 层级 | 机制 | 开销 |
| --- | --- | --- |
| 1 | `on_rules` 设置现有键（`Arcing`、`ROT`、`Vertical`，启用 Phobos 时还有 Phobos 的 `Trajectory`） | 对局中无开销 |
| 2 | 武器开火、抛射体引爆的触发器：额外的抛射体、在引爆点分裂、连锁 | 每次事件，仅限绑定的类型 |
| 3 | 可决定事件 `Launch`：结果区中是一条路径（附录的 `PathSpec`：贝塞尔、抛物线、螺旋、路径点）；引擎用定点数沿路径推进抛射体 | 每个抛射体一次决定 |
| 4 | 每帧的可决定事件 `ProjectileFrame`：引擎在自己推进抛射体的过程中、按自己的顺序，在每个绑定的抛射体移动之前决定它：处理函数读速度（`VX`、`VY`、`VZ`）和位置，在结果区（附录的 `ProjectileStep`）中给出新速度、新位置、新的模块数据，或请求引爆 | 每帧每个绑定的抛射体一次调用 |

- 第 3、4 层以后再做。它们只增加事件种类，不增加新的导出。
- 引擎在原生飞行路径旁边新增一条模块路径。碰撞、引爆判定、伤害和弹头仍由引擎中各自的 owner 处理。
- 引擎会钳制模块的输出：速度和位置有上限，离开地图就引爆或删除抛射体。
- 每个抛射体有 16 字节的模块数据（`Data0` 为第 0..7 字节，`Data1` 为第 8..15 字节，各为小端序 `i64`），存档并计入哈希。决定处理函数不能调用 `set`，所以 `ProjectileFrame` 通过 `ProjectileStep` 写回模块数据，处理函数仍然只读。
- 在引爆点分裂：`Detonated` 记录带引爆点的坐标（附录 [4.3](0001-wasm-extension-modules-api.zh-CN.md#43-新的投递型事件)），模块动作用 `CreateProjectile` 以 `ProjectileSpec` 的绝对起点坐标在那里生成新的抛射体。记录中的抛射体此时已经不存在。

**齐射。** 要一次发出多枚不同弹道的抛射体，就在武器的 `Fire` 事件上挂一个模块动作，用 `CreateProjectile` 动作生成它们，每枚有自己的类型、模块数据和起点偏移。要让它们沿不同的路径飞，需要以后的 `Launch`；在此之前，它们都沿原生弹道飞向各自的目标。这个动作从它的事件记录中读出射手、目标和原生抛射体（SDK 字段 `shooter`、`target`、`projectile`）。原生抛射体在单位更新时射出，模块生成的抛射体在模块阶段射出，所以它们比原生抛射体晚至多一帧的位移，取决于模块阶段放在哪里（待定问题 8）。

**可决定的 `Fire`** 避免这段延迟。它的结果是一份射击方案：结果区中要生成的抛射体的列表，每枚带自己的类型、武器、目标、模块数据和起点偏移（附录的 `ProjectileSpec`），结果槽是条目数。

- 引擎在原生射击本应射出的那一刻立即生成它们，不生成原生抛射体。已处理的空方案什么也不发射；未处理则沿用上一环的结果，首环的输入为原生射击。
- 这次射击的其他所有原生效果照常发生：射速计时器、弹药消耗和装填、连发计数、开火音效、枪口动画、后坐，以及开火时解除隐形或暴露。
- 方案中的抛射体像原生抛射体一样引发 `ProjectileIncoming` 和目标的 `AttackedBy`。投递型的 `Fire` 事件仍然引发，其 `projectile` 为 0。
- mod 和地图的模块都决定了这次射击时，地图的一环收到 mod 的方案，可以保留、修改或替换它。

### 10. 客户端模块

引擎建立界面树并读取 INI 布局后调用客户端启动函数。每个渲染帧先投递事件，再调用渲染函数，见[客户端导出表](0001-wasm-extension-modules-api.zh-CN.md#22-导出)。

**界面树。** 引擎持有节点并负责布局与绘制。模块按部件名查找当前生效布局中的节点（节名去掉布局前缀，即 `Parts=` 中的名字），创建或删除节点、修改属性。引擎按渲染帧批量提交修改。

**节点所有权。** 每个节点记下创建它的来源：引擎和 mod 的 INI 布局、mod 的模块、地图的 INI 布局、地图的模块。

- mod 的客户端模块可以读、写和删除任何节点，所以它能替换或重排对局界面。
- `MapUI=overlay` 时，地图的客户端模块可以找到和读取任何节点，但只能写和删除地图自己的节点；对其他节点的写入和删除返回 `Refused`。它新建的顶层节点放在覆盖层，画在对局界面之上。
- `MapUI=full` 时，地图模块的权限和 mod 模块相同；`MapUI=no` 时不加载地图的 `ui.wasm`，大厅中给出提示。

作者分两部分编写界面：

- **静态布局写在 INI 里**，语法和键与 `veraui.ini` 相同（`Type`、`Hold`、`X`、`Y`、`Width`、`Height`、`Parts`、`Label`）。本 RFC 新增 `List` 部件类型，以及 `Text` 部件的 `Label` 键。引擎在对局开始时读取，不需要预编译。没有动态部分的界面不需要模块。mod 和地图把布局节放在哪里是待定问题 14。
- **动态部分写在模块代码里**：按名字找到节点后修改，或新建节点。

INI 的节点种类、布局键和可写属性见[客户端节点表](0001-wasm-extension-modules-api.zh-CN.md#710-客户端节点)。TypeScript 可在模块内部使用 React 或 JSX 风格的库。

**其他客户端功能：**

- 单个对象的显示属性用一种节点表示：`Decoration` 节点挂在一个对象上（`Anchor` 属性），带图像、调色板、着色、附加动画、可见性，以及显示在对象上方的文字、数值或按钮。它们只影响本机的画面；会影响玩法的属性（如隐形）属于模拟模块。
- 本地动作（`client_action`）：播放声音和 EVA 语音、移动镜头、本地选择、闪烁对象、显示一行消息、注册热键。镜头、光标和本地设置也是客户端拥有的引用：`Camera.cell()` 读取镜头格子；跳到格子用 `Camera.jumpTo(cell)`。精确到 lepton 的 `X`、`Y` 仍可写（均为 `v1?`），本地设置中哪些属性可写是待定问题 14。
- 点在可点击节点上的鼠标不再传给地图。点在地图上的鼠标作为 `MapClick` 客户端事件到达模块，同时照常传给游戏；模块把光标的 `CaptureMapClick` 写为 1 时，地图点击只交给模块，不传给游戏。模块热键与游戏热键冲突时，游戏热键优先。客户端可以读光标的屏幕位置和光标下的格子（附录 7.10）。
- 选中单位和点击按钮属于客户端事件。要改变游戏，模块发送一条消息，由模拟模块在 `on_message` 中处理，这样联机和回放都保持一致。
- 客户端模块可以发出标准玩家指令（移动、攻击、部署、建造……，`client_send_order`），引擎像校验任何玩家输入一样校验它们。模拟模块用同一张指令表指挥电脑所属方（第 6g 节）。消息用于自定义逻辑。
- 图像、动画和模型都按名字引用，从不按文件格式引用，所以以后新增素材格式（单独的 RFC）不需要修改 API。
- `client_log` 输出到游戏内控制台。
- 玩家自装的界面模块放到后续阶段。mod 或房间可以禁止它们。

**存储。** 每个 mod 和每张地图在玩家本机各有一个自己的小型键值存储，带容量配额，用于战役进度、成就和设置（`client_storage_read`、`client_storage_write`）。

- mod 的存储以它的 `[Mod] Name` 为键；地图的存储以它的存储 ID（`[VeraWasm] StorageId=`，默认为地图的文件名）为键，所以修改过的地图只要 ID 不变就保留它的存储。
- 地图的客户端模块使用地图的存储，在 mod 下也是如此，所以下载来的地图无法读取或修改 mod 的数据。
- 只有客户端模块能使用存储。需要影响对局的数据用消息送进模拟，因而成为命令流的一部分。
- 上限：键为 1 到 64 字节的 ASCII；单个值最多 16 KiB；每个 mod 或每张地图的存储最多 256 个键、合计 256 KiB（键和值都计入）。超出时写入返回 `Refused`，存储不变。写入长度为 0 的值即删除该键。上限按 API 主版本固定（第 12 节）。

**通知**从模拟模块发往客户端。

- 名字只解析一次，换成 ID：`lookup` 对通知名返回一个通知 ID，即名字按 ASCII 折叠为小写（只折叠 `A` 到 `Z`）后的 UTF-8 字节的 32 位 FNV-1a 哈希，在每台机器上、在两侧都相同。哈希为 −1 的名字在加载时被拒绝（第 3 节第 7 步）。
- 模拟模块要声明它发送的通知名：SDK 构建时按模块项目配置中的列表（属于 SDK 文档，不属于引擎 API），把这些名字写进 Wasm 自定义段 `vera.notify`。客户端模块不声明任何名字；已声明但没有任何客户端模块接收的名字不算错误。
- 对模拟模块没有声明的名字，以及在客户端模块中对本局没有任何模拟模块声明过的名字，`lookup` 返回 `(−1, NotFound)`：引擎保存着已声明名字的表，所以客户端从不会靠哈希匹配到未声明的名字。加载时的冲突检查（第 3 节第 7 步）保证每个已声明的名字都有 ID。
- `send_notify(to, id, ptr, len)` 发给所属方 `to` 的玩家的客户端；`to` 为 0 时发给每个观战者的客户端。那里的每个客户端模块都收到一个 `Notify` 客户端事件，带着 ID、数据和发送它的模块的来源。回放观看者收到他所观看视角的玩家的通知，或观战者的通知。单条通知的大小和每帧条数有上限（待定问题 7），超出时 `send_notify` 返回 `Refused`。
- 观战者客户端的消息会被拒绝。

**客户端读取**（`client_get`、`client_get_many`、`client_find`、`client_var_get`）只暴露本玩家自己的界面能显示的内容；其他任何东西都通过通知送达客户端。属性表的“客户端”一列逐个写明。

- 本玩家的所属方和对象（含超级武器）可读取属性表中标为 all、own、seen 的项；标为 sim 的属性及小队、修饰器对象仅供模拟使用。
- 其他所属方，包括盟友：只有公开信息（名字、国家、阵营、同盟关系、是否已战败、是否为人类玩家），没有金钱、电力、建筑、生产、科技等级、超级武器或统计数据。
- 本玩家当前能看到的其他所属方的对象：只有类型、位置、所属方和生命，以及画面上看得到的染色和激光拖尾；没有乘客、目标、任务、等级、弹药、修饰器或真实的伪装身份。伪装的敌人读出来是它伪装成的样子（类型和所属方）。
- 黑幕下的对象不出现，迷雾下本玩家当前看不到的其他所属方对象也不出现：引擎不保存“最后一次看到”的副本。隐形的敌人除非被侦测到，否则不出现。格子的地形类型和高度对客户端全部公开，因为地图文件本身就是公开的；路径点编号也公开；其他格子属性遵守附录 7.6 的视野、视点或仅模拟限制。
- 变量按它的可见度（第 6e 节）。触发器和标签只属于模拟。视点属性只以本玩家自己的所属方为视点。
- 观战者的模块看到观战者能看到的范围，房间允许时为整张地图。观战者没有自己的所属方，所以只有在房间向观战者显示某个所属方的信息时，针对自己所属方的读取才有回答。
- 客户端只能写客户端拥有的引用：节点、镜头、光标和本地设置。没有对模拟状态的写入，模拟也从不读取客户端的状态，客户端之间也没有直接的通道。

**通信。** 模拟到客户端不经过网络：客户端读取它能看到的状态和变量，模拟用 `send_notify` 发出通知。客户端到模拟只有命令流：

- `client_send_message(ptr, len)`：消息进入命令流，在命令延迟之后的同一帧，在每台机器上到达同一来源的模拟模块的 `on_message`。
- `client_send_order(ptr, len)`：标准玩家指令。
- 两者都不可信：模拟必须校验内容，发送者由引擎填写，模块无法伪造。大小和频率有上限（待定问题 7），回放记录它们。

一个完整的来回：玩家点击按钮，界面发出消息，模拟校验后写入一个所属方变量，界面读这个变量来更新按钮：

```ts
// ui.wasm — TypeScript（兼容 AssemblyScript）
import { ReinforcementsBought } from "./generated/vars";
const BUY_MESSAGE = new Uint8Array(1);           // 消息类型 1：购买
BUY_MESSAGE[0] = 1;
let buy: Node = 0;

onStart((): void => {
  buy = Ui.find("BuyReinforcements");            // veraui.ini 中的一个按钮
  Node.setClickable(buy, true);
});
onClientEvent(ClientEvent.Click, (e: ClickEvent): void => {
  if (e.node == buy) Client.sendMessage(BUY_MESSAGE);   // client_send_message
});
onRender((dt: f32, alpha: f32): void => {
  const me = Client.viewer();                                   // 观战者为 NO_HANDLE
  if (me == NO_HANDLE) { Node.setVisible(buy, false); return; } // 观战者没有所属方：以 0（全局）读所属方变量是非法参数
  Node.setVisible(buy, ReinforcementsBought.get(me) == 0);               // client_var_get：读本玩家自己所属方的私有变量是允许的
});
```

```ts
// rules.wasm — TypeScript（兼容 AssemblyScript）
import { ReinforcementsBought } from "./generated/vars";
const HTNK = Rules.technoType("HTNK");

onMessage((sender: House, data: Uint8Array): void => {
  if (data.length != 1 || data[0] != 1) return;                         // 消息不可信：全部要校验
  if (HTNK == NO_HANDLE) return;
  if (ReinforcementsBought.get(sender) != 0 || House.money(sender) < 2000) return;
  const tank = Action.createObject(Waypoint.cell(3), HTNK, sender);     // 格子被占时为 NO_HANDLE（Refused）

  Action.addMoney(sender, -2000);
  ReinforcementsBought.set(sender, 1);                                           // 客户端下一次读取时就能看到
});
```

### 11. 联机

- 嵌入的模块随地图传输。mod 的模块计入现有的 mod 文件校验。
- 大厅比对模块哈希和所需的 API 版本；它在加载模块之前读取每个 `[VeraWasm] Api=`。需要房间的游戏所没有的 API 版本的地图或 mod 无法被选择；离线时，这样的存档或回放会被拒绝。每种拒绝都给出所需的版本。
- mod 的 `[VeraWasm]` 键在它的 `rulesmd.ini` 中，mod 摘要包含这个文件，所以每个玩家都会比对它们；摘要不包括的 `mod.ini` 不放任何模块键。
- 每条消息的发送者由引擎填写，模块无法伪造；单条消息大小和每帧消息数有上限。
- 通知只送达目标玩家或观战者。通知的内容是模块自己的字节，由模块作者负责：引擎无法过滤它。
- 联机只交换指令，从不交换状态。重连的玩家从头重新模拟整局，包括模块；模块消息本身就是指令，所以不需要额外发送任何东西。因此模块每帧的开销也会拖慢追帧速度。追帧期间不投递通知，客户端模块也不运行；追帧结束后它们收到一次 `client_on_start`。
- 存档和回放记录游戏版本、模块哈希和 API 版本。模块与当前安装的 mod 或地图不一致的存档或回放会被拒绝，并提示是哪些模块；旧版本会拒绝新版本生成的存档和回放，并给出提示。
- 房间要求所有玩家运行同一版本，所以混合版本的房间不会开局。
- 离线时，支持模块之前的版本会不带模块地运行模块地图：它忽略 `[VeraWasm*]` 节，其触发器中的模块动作什么也不做。已发布的版本无法再修改，所以这是一个明确记录的遗留问题。为了涵盖之后的版本，支持模块之前的那个版本增加一个地图键 `[Basic] VeraMinVersion=`（名字未定），对需要更新版本的地图拒绝运行并给出指明版本的提示。模块地图设置这个键。
- 这项改动要更新 [Networking](../Networking.md)，说明已发布的游戏、混合版本的房间以及回退版本分别如何处理模块。

### 12. 版本与 ABI

- 一份用 WIT 语法编写的接口定义是 API 的唯一来源，附带机器可读的表（事件种类、动作种类、属性、名字种类、节点种类和其他枚举）。项目自己的生成器由它们生成 Rust 和 TypeScript SDK 的包装函数、参考文档和兼容性检查；其他语言的绑定也从同样的表生成。WIT 只是接口描述语言：模块不使用 Component Model 的 canonical ABI。
- 二进制接口是 core module ABI：core Wasm 模块的导入和导出、`i64` 引用和值、`i32` ID、字符串、字节和缓冲区用的指针加长度，以及由宿主写入模块缓冲区的批量结果。宿主导入最多返回一个值：有返回值的调用返回状态，值由宿主经输出指针写入模块内存，因为稳定版 Rust 和 AssemblyScript 都无法导入多返回值的函数；模块内部仍可使用多返回值（第 3 节）。返回值、状态和续页位置见附录签名。
- 冻结两个接口的导入和导出签名（[附录第 1 节](0001-wasm-extension-modules-api.zh-CN.md#1-模拟-abi)和[第 2 节](0001-wasm-extension-modules-api.zh-CN.md#2-客户端-abi)）。事件种类、动作种类、属性、名字种类、搜索范围、节点种类、客户端事件和动作种类，以及其他枚举，都是只追加的表，在次版本中追加；`has_kind` 让模块在不认识某个表项的旧引擎上降级运行。
- 以后的某个主版本可以在 core ABI 之上增加一个 Component Model 适配层。已有模块继续使用 core ABI，不受影响。
- 接口是带版本的包：`vera:sim@1`、`vera:client@1`。版本号是“主版本.次版本”。新的主版本不兼容，每个主版本都通过适配层永久保留；新的次版本只做增加。模块通过它的导入说明需要的主版本和最低次版本（导入的模块名为 `vera:sim@<主>.<次>` 或 `vera:client@<主>.<次>`），地图或 mod 在 `[VeraWasm] Api=` 中写明同样的版本。`vera:sim` 和 `vera:client` 共用一个版本号，总是一起发布，所以一个 `Api=` 同时说明两者。大厅用每个玩家的游戏检查 `Api=`；加载时检查模块的导入与 `Api=` 一致（第 3 节）。
- 不稳定的接口放在 `vera:unstable/*` 下，需要显式开启，可以不经通知就改变。它们和 `0.x` 预览版都不是已发布的版本：不保留适配层，使用它们的模块只能在为之构建的那个版本上运行。
- 每个已发布的版本都一直可用。旧版本是现行实现之上的薄适配层，从不是第二份实现。适配层从不把旧版本没有定义的值交给旧模块：该版本的表中没有的事件种类的记录不投递给它，该版本没有的属性对它不存在，更新的状态值或枚举值以该版本定义过的值交给它，具体对应关系按表写在接口定义中。
- CI 从仓库内的 Rust SDK 源码构建并运行各已发布版本的兼容性用例；不提交 Wasm 二进制。每次发布追加用例。
- 计量单位、每个宿主函数的费用、默认额度和各项上限属于主版本的一部分，随主版本固定（第 4 节）。
- 函数和表项可以弃用并向模块作者发出警告，但已发布的版本永不删除。
- 已发布的函数、属性和表项永不改变单位或含义。要改变，就追加新的表项或发布新版本。
- 自定义段 `vera.actions`、`vera.notify`、`vera.vars` 和 `vera.delivery`（投递区声明）各有[附录中的固定布局](0001-wasm-extension-modules-api.zh-CN.md#自定义段)，以一个格式版本开头。其中的名字是 UTF-8，必须是 ASCII，并且只按 ASCII 规则统一大小写。
- 模块动作和决定处理函数用模块自选的 32 位分派键标识，写在触发器定义中；事件记录携带这个键，SDK 生成的 `on_events` 和 `on_decide` 据此分派，因此处理函数不必是 Wasm 导出函数。`vera.actions` 把名字对应到分派键，只有被 INI 或地图引用的处理函数才需要名字。分派键只在本模块内有意义，跨来源的名字只在 INI 中解析（第 2 节）。

### 14. 项目契约

- 扩展模块功能（不要与浏览器版的 `wasm`、`wasm-net` 和 `wasm-threads` 构建 feature 混淆）存在于每个构建中，当 mod 或地图提供模块，或使用它的任何键（`Wasm.Tags`、筛选子句、INI 原子动作、`[VeraWasm]`）时，在运行时开启。从不放在构建 feature 后面。只要它开启，修饰器的 owner 就可用（第 6c 节）。
- Wasm 运行时按平台选择，放在平台构建 feature 后面，项目契约允许平台 feature 这样做：桌面上用原生引擎，浏览器版用浏览器自带的 WebAssembly 或另一个引擎（待定问题 1）。模拟通过同一个接口访问运行时，所以 `vera20k-core` 和 `sim/` 仍能为浏览器编译。
- 每次模块调用都通过状态现有的 owner 访问状态。属性写入、修饰器和变量都只有一个 owner；API 不引入竞争状态。
- 功能在 `docs/` 下为 modder 编写文档。`docs/modding.md` 目前写着 mod 只是数据、VERA20k 不会运行 mod 里的程序；这段要改成：模块只在沙箱中运行，无法访问文件和网络，模拟模块也无法访问时钟。Mods 菜单和地图列表要标出带模块的 mod 和地图。
- 模块出错在游戏中报告，从不只写进日志。

### 15. 性能

以 2 万单位、30 个所属方为性能基线（[模拟线程预算](../sim-thread.md)）。热路径用初始化时缓存的 ID 或引用；名字只用于初始化及低频规则修改。批量读取、分页和事件投递使用模块的缓冲区。搜索不分配内存，排序成本随结果数增长；抛射体逐帧数据直接写入模块结果区。SDK 原地读取事件，逐对象和逐事件均不分配包装对象。

#### 15.1 实现要求

以下各条都是必须的：它们是实现的验收标准，逐条审查。

1. **没有模块就没有开销。** 每个事件触发点和决策点先检查标志位；标志位不成立时不构造任何载荷，其余代码都不运行。每个被绑定的对象，以及得到带模块触发器的标签的对象，设置自己的一个标志位（第 7 节）；这些按对象的标志位放在实体存储的侧列中，检查时不加载对象本身。类型、武器、弹头和抛射体类型的绑定标志位放在模拟持有的可变表中：对局中规则数据是只读的，而模块可以在对局中绑定类型。
2. **有效值在变化时算出并缓存。** 修饰器加入、移除或到期时，引擎重新算出受影响属性的有效值，缓存在实体上；热循环（移动、开火判定、索敌评分）只读这个缓存，从不在读取时查旁路表或合成修饰器。没有修饰器的属性读到的就是基础值。修饰器保存绝对到期帧，按到期帧分桶处理，每帧的开销只随本帧到期的修饰器数增长；`Remaining` 由到期帧算出。这与引擎现有的各个倍率层的做法相同。
3. **对应 Phobos 键的修饰器沿用 Phobos 的算法**（第 6c 节），所以值与 Phobos 一致。它们与 Phobos 共用的代码存在于每个构建中，由运行时开关开启（Phobos 的键由 Phobos 的开关开启，模块修饰器由模块功能开启），从不放在构建 feature 后面（项目契约，第 14 节）。
4. **决定只在提交点。** 可决定事件只在引擎提交结果的那一点同步调用，按引擎的确定顺序；从不为推测性或并行的预计算（索敌预答、寻路批次、追猎评分）调用，因为这些计算的答案可能被丢弃。`count` 通常为 1（第 6f 节）。投递型事件同样在结果提交的地方引发，从不在推测性的计算中引发（第 5 节）。
5. **决定处理函数中的随机数**从按（帧、主体的创建序号、事件种类）派生的子流取数（第 4 节），所以决定调用的次数不改变模块主随机流。处理函数照常可以写自己的模块内存：调用只发生在提交点，按确定的顺序。
6. **`ProjectileFrame`**（以后的层级）在引擎自己推进抛射体的过程中、按它的顺序、在该抛射体移动之前调用（第 9 节），不在推进之前另设一个阶段。
7. **模块内存的哈希。** 只哈希实际增长到的内存（`memory.size`），不按内存上限。页按轮转哈希：每帧哈希 1/15 的页，再与其余页缓存的摘要合成模块的摘要，所以每页每 15 帧检查一次，没有尖峰。联机的多人同步校验、回放日志的诊断哈希和完整状态哈希共用这个结果，所以模块内存中的分歧在联机时 15 帧之内被检测到。存档只保存已用的非零页，并压缩。
8. **展示快照不含模块。** 每帧为绘制复制的展示快照不包含模块的运行时状态（实例、线性内存、全局变量和表）。
9. **稀疏的实例和旁路表。** 变量、修饰器、绑定和每个抛射体的模块数据放在按引用索引的旁路表里，类型绑定放在按类型索引的表里，只有用到它们的对象和类型才占空间；按对象的触发器实例状态只在它不同于默认值时才创建（第 7 节）。它们存档并计入哈希；它们对每帧同步校验的贡献在写入时增量维护，不在每帧遍历全部条目。

#### 15.2 引擎对模块的硬上限

下面是提议的默认值，最终值是待定问题 7，按 API 主版本固定（第 12 节）。

- **每帧运算额度。** 每个模块每帧一份，与记录数无关。锁步联机中最慢的机器决定整体速度，计量会让模块代码变慢，浏览器版还可能用解释器运行模块，所以额度按最慢的受支持平台确定：提议为该平台上约 2 ms 的运算量。超出额度的工作推迟到下一帧，记录留在队列中（第 5 节）；在积压上限内追不上的模块被停用并给出提示。
- **内存上限。** 地图模块 16 MiB，mod 模块 32 MiB，绝对上限 64 MiB；引擎在实例化时分配（第 3 节）。
- **按绑定范围引发。** 高频事件和绑定范围为对象或类型的可决定事件只对相应绑定引发；全局决定按事件表引发（第 5 节、第 6a 节）。`bindAllTypes` 在开销叠加层中给出警告（第 13 节）。
- **派生属性计费。** 筛选子句中求值的派生属性（如 `NearbyEnemyCount`、`TargetInRange`）按费用计入所属模块的额度（第 6a 节）；附录的属性表标出费用高的派生属性。

结果：写得不好的模块只会让它自己变慢，或者被停用；它无法拖住对局，也无法造成不同步。

#### 15.3 SDK 默认做法

SDK 与模板按对象或所属方错开周期任务。读多个对象或属性用一次 `get_many`；可在入队前判断的条件使用筛选子句。范围效果使用长时修饰器，仅在进入和离开范围时添加或移除。

## 流程

1. **草案。** 本文档公开讨论。每次修改都提升 RFC 版本号，并记入[修订记录](#修订记录)。
2. **回答待定问题。** 用一次性实验回答下面的待定问题，结论汇总到本文。
3. **接受。** 维护者把某个版本标为已接受，此后才开始开发。
4. **预览。** API 以 `0.x` 发布，允许破坏性变更并记入变更日志；预览版不是已发布的版本（第 12 节）。至少用它重做一个真实任务或模式，并请外部 modder 试用。
5. **稳定。** 冻结 `vera:sim@1` 和 `vera:client@1` 的函数，表的范围仅限预览期实际用到的部分，包括待定问题 10 中首批的两三个可决定事件。兼容性测试用例加入 CI。
6. **增长。** 每批新的表项（事件种类、动作种类、属性）或新函数是一个小的后续 RFC 和一个新的次版本。

接受之后的计划顺序：

| 阶段 | 内容 |
| --- | --- |
| 1 | `rules.wasm`：原版和新的事件与动作；筛选子句；属性和修饰器；变量；搜索；AI 动作和属性；类型标签绑定、对象绑定和触发器动作；首批两三个可决定事件（待定问题 10）；地图嵌入、`asset` 命令；TypeScript 和 Rust SDK 及模板 |
| 2 | `ui.wasm`：带 INI 布局的界面树、节点种类和属性、客户端事件、视野过滤、消息和通知 |
| 3 | 用模块重做一个真实任务，外部 modder 试用，冻结版本 1 |
| 以后 | 逐个增加更多可决定事件、模块弹道（`Launch`、`ProjectileFrame`）、对等调用、玩家界面模块 |

## 设计范围

使用 core Wasm 模块和版本化函数表。模拟可读完整状态，客户端按本机视野读取；跨客户端通信经过模拟。普通事件批量投递，同步决定可写模块内存并使用决定子随机流。沿用数据驱动的触发器、Phobos 弹道与 AttachEffect。

## 待定问题

1. **浏览器版。** 浏览器版能否以和原生版完全一致的结果运行模块？用哪个引擎？wasmtime 可能无法在浏览器中运行。两个候选，都要实测，触发器型和计算型模块各测一次：
   - 浏览器自带的引擎运行模块，模块实例的导入直接链接到引擎实例的导出，中间没有 JavaScript，也就没有 `i64` 与 BigInt 之间的转换；
   - 引擎内嵌一个解释器运行模块：模块代码估计慢 6 到 20 倍，但宿主调用不经过 JavaScript，模块内存就在引擎内存中。
2. **TypeScript 编译器。** TypeScript SDK 用哪种编译器：把 TypeScript 子集编译成 Wasm 的编译器（如 AssemblyScript），还是把 JavaScript 引擎编译进每个模块？引擎对两者没有区别；这个选择决定模块体积、速度，以及普通 TypeScript 代码能用多少。
3. **计量。** 运算计数和调用深度用哪种插桩？估计插桩让模块代码慢 10% 到 40%，分支密集的紧循环可达 2 倍，要在原生引擎和浏览器引擎上都实测。NaN 规范化只放在可被观察的出口（内存写入、`reinterpret`、宿主调用的参数和返回值），不在每次浮点运算之后。还要实测状态哈希在 wasm32 上的吞吐，以及按页轮转（第 15 节）时每帧的模块内存哈希开销。
4. **INI 格式。** 用文中所示的具名节，还是用原版逗号分隔的触发器编码以便 FinalAlert2 编辑绑定，还是两者都要？筛选子句（`Where1=`）、决定处理函数名和原子动作怎么写？考虑到绑定、筛选子句和原子动作在没有模块时也能用，键用什么前缀？
5. **事件和动作编号。** 新的事件种类和动作种类用哪个范围才不与 Ares、Phobos 冲突？
6. **FinalAlert2。** 保存地图时会不会保留 `[VeraWasmRulesPack]` 这类它不认识的节？
7. **上限。** mod 和地图的嵌入体积、内存、加载时形状上限、每帧运算额度、每个宿主函数的费用、初始化函数、`on_rules` 和 `on_scenario_start` 的一次性额度、每帧队列上限、每次 `on_events` 调用的记录条数、积压上限、每个事件的筛选子句条数 N、客户端模块每个渲染帧的运算额度、最小轮询间隔、消息大小和频率、通知大小和每帧条数、每个模块每帧的指令条数和单位项数、每个可决定事件的结果区大小。存储上限已在第 10 节给出。提议的默认值：每帧运算额度为最慢的受支持平台上约 2 ms 的运算量；内存上限地图模块 16 MiB、mod 模块 32 MiB、绝对上限 64 MiB（第 15 节）。它们按 API 主版本固定（第 12 节）。
8. **帧阶段。** 模块阶段放在模拟帧的哪个位置；模块弹道分支相对碰撞和引爆判定的位置。`ProjectileFrame` 定在引擎推进每个抛射体时、该抛射体移动之前运行，它与碰撞和引爆判定的相对顺序待定。
9. **存档体积。** 快照中的模块内存：压缩方式。只保存已用的非零页并压缩时，估计典型模块的存档增量小于 1 MiB，要实测。
10. **首批可决定事件。** 版本 1 提供哪两三个可决定事件（第 6f 节的候选）。
11. **白名单。** 版本 1 中哪些键可以在对局中按类型修改（`rules_set` 和类型引用上的可写属性）。
12. **版本 1 清单。** 附录中哪些事件种类、动作种类、属性、可修饰属性和搜索范围，以及其他哪些 `v1?` 条目，进入版本 1。
13. **修饰器叠加。** 加、乘、覆盖修饰器的默认合成方式（第 6c 节）是否够用；每个可修饰属性的叠加上限、刷新规则、互斥组，以及 Phobos AttachEffect 叠加键（`Cumulative`、`Cumulative.MaxCount`……）如何对应。
14. **界面布局和节点种类。** mod 和地图把布局节放在哪里；版本 1 的节点种类和节点属性，以及本地设置引用上有哪些属性。
15. **地图文字。** 地图无法携带字符串表，地图模块的文字如何翻译。
16. **战役。** 每一关的模块是重新开始，还是延续上一关的状态（包括变量）。
17. **连锁上限。** 含有模块触发器、VERA 新增的事件或原子动作的连锁，每帧的深度上限，以及每帧这类连锁触发总次数的上限（第 5 节）。
18. **所属方接管。** 是否允许模块从原生 AI 手中接过一个电脑所属方的决策（建造基地、生产、组建小队、部署基地车），而该所属方仍算电脑所属方？大厅是否按座位选择这样的模块？在此之前，`order` 与原生 AI 共用这个所属方（第 6g 节）。
