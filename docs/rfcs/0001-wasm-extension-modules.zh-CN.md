## 概要

让 mod 和地图携带编译好的 WebAssembly 模块（`rules.wasm`、`ui.wasm`），由 VERA20k 在沙箱中运行。模块可以在规则读完后修改规则、响应触发器、执行动作和下达任务、覆盖指定的游戏决策，并构建自己的界面。作者可以用任何能编译到 WebAssembly 的语言、用自己的工具编写模块，引擎只运行编译好的 `.wasm`。官方提供 TypeScript 和 Rust 两套 SDK。API 使用红警 2 modder 已经熟悉的术语：触发器、事件、动作、标签、任务、局部和全局变量、帧，并新增约束条件、持续效果和标记。

所有函数、事件、约束条件、持续效果和覆盖点，以及它们在引擎中的 owner 和出处，列在 [API 清单附录](0001-wasm-extension-modules-api.zh-CN.md)中。

API 从第一次发布起就带版本。已发布的 API 版本在之后所有 VERA20k 版本中都能继续使用。

## 动机

INI 文件和地图触发器表达不了 modder 想要的很多东西：自定义弹道、波次逻辑、新的超级武器行为、任务目标面板。Ares 和 Phobos 为此加了很多键，但每个新想法仍然需要改引擎。脚本层让 modder 自己实现这些，同时引擎仍然是游戏状态唯一的 owner。

API 一旦被 mod 依赖就无法收回，所以它必须公开设计、以带版本的小步增长，并用测试保证每个已发布版本一直能运行。

## 目标

1. modder 不改引擎也能修改玩法和界面。
2. 所有玩家运行相同的模块并得到相同结果：在任何受支持的平台上（包括浏览器版）都不会不同步。
3. 外部模块永远不会让游戏停下。出错的模块被停用，并告诉玩家原因。
4. 模块不能读文件、不能联网、不能读时钟，也看不到玩家无权看到的东西。
5. 没有模块时，游戏和现在完全一样。
6. 只有少数类型使用的模块不会拖慢 2 万单位规模的战斗。
7. 红警 2 modder 从模板开始，几分钟内就能在游戏里看到改动效果。

## 非目标

- 原生插件（`.dll`、`.so`），或在沙箱外加载任何东西。
- 引擎里出现源代码。引擎从不解析、编译或解释任何源语言，也不内置任何语言运行时（见[备选方案](#备选方案)）。
- 暴露引擎内部：内存布局、原生地址、内部对象下标、渲染器的图形 API。
- 对局中新增对象类型。
- 取代原版触发器系统。模块是在它的基础上扩展。

## 术语

凡是红警 2 已有的术语，API 都沿用。代码和 INI 中的名字以本表为准。

| 术语 | 含义 |
| --- | --- |
| **扩展模块**（Extension module） | 一个编译好的 `.wasm` 文件。不叫“脚本”：红警 2 里的脚本指 AI 小队脚本（`[ScriptTypes]`）。 |
| **触发器**（Trigger） | 和地图里一样：一个事件加一个或多个动作，属于某个所属方，带难度标志。VERA 增加可选的约束条件。 |
| **事件**（Event） | 触发器的条件。原版事件编号含义不变。 |
| **动作**（Action） | 触发器执行的内容。原版动作编号不变。新增一个动作：执行模块函数。 |
| **约束条件**（Condition） | 触发器执行动作之前，由引擎原生检查的过滤条件。 |
| **标签**（Tag） | 把触发器挂到对象或格子（CellTag）上的东西。一个对象只有一个标签。 |
| **标记**（Mark） | 对象或所属方携带的文字记号，供约束条件判断，可以带一个整数值和可见度等级。不是标签：一个对象可以有任意多个标记。 |
| **持续效果**（Attached effect） | 对象身上带持续时间的状态，例如倍率或免疫（沿用 Phobos AttachEffect 的叫法）。 |
| **任务**（Mission） | 对象的命令：Move、Attack、Guard、Area Guard、Hunt、Sleep 等。 |
| **局部/全局变量**（Local / Global） | 和地图里一样的局部变量和全局变量。 |
| **帧**（Frame） | 模拟的一个逻辑帧，也是 `ROF`、`Rate` 和计时器的单位。 |
| **渲染帧**（Render frame） | 某台机器上画出的一帧。不同步。 |
| **覆盖**（Override） | 一个具名的决策点，模块可以在这里改变引擎的结果。 |
| **House、Techno、Building、Vehicle、Infantry、Aircraft、Projectile、Weapon、Warhead** | 与 INI 文件中的含义相同。 |
| **格子、lepton**（Cell、lepton） | 地图坐标。1 格等于 256 lepton。 |
| **运算额度**（Operation budget） | 模块每次调用可以做的工作量，以确定性的运算单位计量。 |

## modder 看到的样子

### 文件

```
Mods/MyMod/
  mod.ini        ; Needs=、WasmApi=1、政策键
  rulesmd.ini    ; 把标签绑定到类型
  rules.wasm     ; 模拟模块
  ui.wasm        ; 界面模块
```

地图以文本形式携带模块，方式和现在携带 `IsoMapPack5` 一样：压缩、base64 编码、按编号分行。

```ini
[VeraWasm]
Api=1
RulesSize=48213          ; 解码后的字节数，加载时校验
UISize=9120

[VeraWasmRulesPack]
1=eJzt3XlcVOX+B...
2=...

[VeraWasmUIPack]
1=...
```

`asset` 工具增加命令：把模块嵌入地图、从地图中取出模块，以及运行和游戏相同的加载检查。

### 把触发器绑定到类型

```ini
; mod 里的 rulesmd.ini
[E1]
Wasm.Tags=GIPanicTag     ; 每个 E1 都接收这个标签的触发器

[GIPanicTag]
Trigger=GIPanic

[GIPanic]
Event=TakeDamage
Action=Wasm:giPanic      ; 调用 rules.wasm 导出的 giPanic 函数
Repeat=yes
```

键名和具体的节格式尚未确定（见[待定问题](#待定问题)）。在 FinalAlert2 里编辑的地图触发器，也可以通过新动作调用模块函数。

### 模块代码

引擎只看到编译好的模块，源码和编译器都在作者自己的工具里。同一个模块分别用两套官方 SDK 写：

```ts
// TypeScript（AssemblyScript 兼容）
import { action, onFrame, Mission, EventRecord, Ctx } from "@vera20k/sdk";

export const giPanic = action((ctx: Ctx, e: EventRecord) => {
  const techno = e.subject;
  if (techno.healthPercent < 30) {
    techno.setMission(Mission.Hunt);
  }
});

export const checkWaves = onFrame({ every: 15 }, (ctx: Ctx) => {
  if (ctx.local(3).get()) {
    // ...
  }
});
```

```rust
// Rust SDK
use vera20k_sdk::prelude::*;

#[vera::action(export = "giPanic")]
fn gi_panic(ctx: &mut Ctx, e: EventRecord) {
    let techno = e.subject();
    if techno.health_percent() < 30 {
        techno.set_mission(Mission::Hunt);
    }
}

#[vera::on_frame(every = 15)]
fn check_waves(ctx: &mut Ctx) {
    if ctx.local(3).get() {
        // ...
    }
}
```

每套 SDK 都用一条命令构建出 `rules.wasm` 或 `ui.wasm`。包名只是占位。语言和 SDK 见第 5a 节。

## 设计

### 1. 两个世界

| | 模拟（`rules.wasm`） | 客户端（`ui.wasm`） |
| --- | --- | --- |
| 运行在 | 每台机器上，锁步执行 | 仅本机 |
| 确定性 | 是 | 否 |
| 可以改变 | 游戏状态，通过引擎的 owner | 界面、显示、声音 |
| 影响游戏的方式 | 动作和任务 | 向命令流发送消息 |
| 引擎侧 | `sim/` | `ui/`、`render/`、`audio/` |

这个划分遵循现有规则：`sim/` 从不依赖 `render/`、`ui/`、`audio/` 或 `net/`。数据从模拟流向客户端，靠经过视野过滤的查询和本地通知；从客户端流向模拟，只能通过 `sendMessage`。消息像玩家指令一样进入命令流，所以回放和联机都能看到它。

### 2. 来源：mod 和地图

mod 和地图使用同一套 API 和同一套 SDK，区别在于引擎授予它们的权限。

| | mod | 地图 |
| --- | --- | --- |
| 顺序 | 先 | 在 mod 之后，和 INI 层叠一致 |
| `onRules` | 在 mod 的 INI 层之后 | 在地图的 INI 层之后，能看到 mod 的结果 |
| 运算额度 | 由 mod 声明，引擎设上限 | 默认更小，mod 可以调高 |
| 体积 | 受文件大小约束 | 有嵌入上限 |
| 界面 | 可以替换或重排对局界面 | 只能加覆盖层，除非 mod 允许更多 |

mod 控制地图模块能做什么：

```ini
[Mod]
WasmApi=1
MapWasm=yes          ; no：带模块的地图在这个 mod 下不能开局
MapUI=overlay        ; overlay、full 或 no
```

没有选择 mod 时，允许地图模块，地图界面只能是覆盖层。

冲突规则：

- **类型上的标签绑定**只从 mod 的规则层读取。地图模块在代码里创建触发器和标签（第 7 节），所以地图的 INI 不会因为层叠覆盖而抹掉 mod 的绑定。
- **触发器**：两边的都会触发，mod 的模块先运行。
- **覆盖**按链式处理：mod 的模块先算出结果，地图的模块拿到这个结果后可以再改，引擎使用最终值。链上的每一环都同时拿到原生值和上一环的结果。后一环可以推翻前一环的否决。数值类覆盖点返回一个明确的“已处理”标志，而不是用特殊值表示。
- **动作和任务**按执行顺序走同一个 owner。
- **对等调用**（后续阶段）：mod 可以公开一些函数，地图用 `callPeer("mod", name, bytes)` 调用。只有 mod 为此导出的函数才能被调用。

### 3. 加载与校验

加载时，引擎依次：

1. 解码嵌入的模块，校验声明的大小；
2. 解析模块，只接受来自本版本支持的 `vera:*` 接口版本的导入；
3. 拒绝线程、relaxed SIMD 和 64 位内存，并把浮点运算产生的 NaN 规范化；
4. 加入运算计量，设置内存上限；
5. 检查 INI 和生命周期需要的导出函数存在且签名正确；
6. 把本局加载的所有模块（mod 的和地图的合在一起）的通知名放在一起检查哈希冲突（第 10 节）。

开局前失败：在大厅显示原因，带这个模块无法开局。对局中失败（trap、超出额度、参数非法）：在所有机器的同一帧停用该模块，游戏告诉玩家是哪个模块停止了、原因是什么，对局继续。模块留下的东西按以下方式处理：

- 它的触发器被停用；
- 它的覆盖点被跳过：由链中的下一个模块或原生结果生效；
- 它的模块弹道上的抛射体改为朝目标直线飞行；
- 它添加的持续效果和标记保留，因为它们属于引擎状态。

属于正常游戏过程的错误只返回状态，模块继续运行：句柄对应的对象已不存在、名字不存在、动作被引擎规则拒绝（比如该格不能建造）、触发器中原子动作的目标种类不适用于该动作（第 6b 节）。表明模块本身有问题的错误会停用模块：参数非法、trap、超出运算额度。

`docs/modding.md` 目前写着“mod 只是数据，VERA20k 不会运行 mod 里的程序”。这段要改成：模块只在沙箱中运行，无法访问文件、网络和时钟。Mods 菜单和地图列表要标出带模块的 mod 和地图。

### 4. 确定性

所有机器运行同一份模块字节，所以结果只取决于引擎如何执行它们。

- 不用线程，不用 relaxed SIMD，NaN 规范化。
- 不提供时钟、宿主随机源和 WASI。模块从自己专用的随机流取数，这条流由场景种子派生，所以模块不会错开原生随机流：不取随机数的模块，原生结果完全不变。会执行原生代码的动作，按那段代码原本的方式从原生随机流取数。每个 API 都写明自己取几次随机数。
- 名字（类型 ID、节名）比较时不区分大小写，和 gamemd 读取 INI 的方式一致。
- 运算额度由加载时插入的计量代码计算，不用引擎自带的 fuel。这样无论原生还是浏览器的引擎，都会数出相同的运算量，并在同一点停下。
- 位置、速度等游戏数值以整数（lepton、定点数原始值）跨越边界。小数和倍率使用模拟的定点格式，即 `I16F16` 原始值（`SimFixed`）。模块内部可以使用浮点。
- 模块内存、可变全局变量和表都属于模拟状态：存进快照，计入定期的状态哈希（第 15 节）。

### 5. 执行模型

模拟模块的导出：

| 导出 | 时机 |
| --- | --- |
| `onRules` | INI 层读完后运行一次；可以修改和新增类型 |
| `onScenarioStart` | 场景开始时运行一次 |
| `onFrame` | 每个订阅的模块每帧一次，或每 N 帧一次 |
| 动作 | 在模块阶段，其触发器触发时排队 |
| 覆盖 | 引擎走到该决策时同步调用 |
| `onMessage(player, bytes)` | 客户端消息到达模拟时 |

客户端模块的导出：`onStart`；`onRender(dt, alpha)`，每个渲染帧一次；以及点击、热键等界面回调。

模块调用在模拟帧里一个固定的阶段运行，按模块加载顺序执行。本帧内触发的触发器中的模块动作会排队，每个都带着触发其触发器的那个事件的载荷，在这个阶段、`onFrame` 之前统一投递，每个模块一批（第 15 节）。模块只能通过这种方式收到事件：没有单独的事件记录。覆盖是例外：引擎需要答案时当场调用。对象引用是带代数的句柄，所以投递前已经死亡的对象读出来是“不存在”，绝不会读到被复用的槽位。

顺序规则：

- 原版动作和第 6b 节的原子动作在触发器触发时立即执行，与原版中的原版动作完全一致，含有模块动作的触发器也是如此。只有模块动作（模块函数）排队，在模块阶段按触发顺序、每个模块一批执行。动作为 [原版 A、模块 B、原子 C] 的触发器，先执行 A 和 C，B 在同一帧稍后执行。需要严格顺序的作者，把触发器的全部动作都写成模块代码，再通过 API（L1）调用原版动作。
- VERA 新增的每个事件都在安全点引发：安全点是不处在任何计算之中的时刻。一次计算完成之后是安全点（例如 `TakeDamage` 在伤害已经提交之后），一次计算开始之前也是（例如 `HouseTransfer` 在转移开始之前）。触发器的原版动作和原子动作从这一点起立即执行。
- 立即执行的动作可以在一帧之内连锁：伤害引发 `TakeDamage`，它的触发器用原子动作造成伤害，又引发 `TakeDamage`，依此类推。连锁中含有由模块创建或绑定的触发器、VERA 新增的事件或原子动作时，引擎限制它每帧的深度；会超过上限的触发器改到下一帧触发，所以这样的连锁不会无限循环。具体上限是待定问题 18。只由原版事件和原版动作组成的连锁，与原版中完全一样地运行（目标 5）。
- 如果游戏已经结束，或者触发器在模块阶段之前已被禁用或删除，排队中的模块动作会被丢弃。已不存在的对象，其句柄读出来是“不存在”。
- 在模块阶段运行期间触发的触发器（例如因为某个模块动作造成了伤害），其原版动作和原子动作立即执行；其模块动作排到下一帧的模块阶段，因此模块代码不会在一帧之内循环。
- 覆盖点只能读状态、返回结果，不能执行动作，因为引擎调用它时正处在一次计算的中途。
- 投递型事件报告的是已经发生的事，无法取消原生结果（比如死亡）。要改变这类结果，需要用覆盖点或持续效果（比如阻止死亡）。
- 高频事件（伤害、开火、抛射体引爆、碾压、移动失败）和所有覆盖点只对绑定的类型触发（对象、武器、弹头或抛射体类型；第 6a 节），没有“订阅所有对象”的用法。
- 读档后，模块内存随快照恢复。`onScenarioStart` 不会再次运行，也没有单独的读档回调。模块内存里保存的句柄，读档后仍指向同样的对象。

每个模块每帧有运算额度。订阅都需要显式开启：一个模块既不导出 `onFrame`，也不绑定触发器，那它每帧的开销为零。

### 5a. 语言与 SDK

引擎和模块之间的约定只有 Wasm 接口。任何语言，只要它的编译器产出的模块能通过加载检查，就能使用，引擎对所有模块一视同仁。

- **官方 SDK：TypeScript 和 Rust。** 两者都由同一份接口定义（第 12 节）生成，提供相同的函数（名称按各自语言的命名习惯），并随 API 一起发布版本。每套都附带模板、构建命令、监视模式和示例。
- **TypeScript SDK。** 预先把 TypeScript 编译成 Wasm，模块足够小，可以嵌入地图。具体用哪个编译器是待定问题。它的 API 限定在 TypeScript 与 AssemblyScript 的共同子集内：不用 `any`，除 `T | null` 外不用联合类型，回调不捕获外部变量，不用 `try`/`catch`，参数用类而不是任意对象形状。这样同一份源码既能用 `tsc` 做类型检查，也能用 AssemblyScript 编译，本 RFC 中的示例在两者中都有效。
- **Rust SDK。** 面向想要完全控制和更高性能的作者；引擎自己的兼容性测试用例也用它编写。
- **其他语言**（C、C++、Zig、Go……）使用公开的接口定义，绑定由社区维护。
- **导入。** 模块只能导入 `vera:*` 接口。引擎不提供 WASI，项目也不发布 WASI 垫片。运行时依赖 WASI（时钟、随机数、文件）的语言，只有在它自己的工具链去掉这些导入时才能使用。
- **体积。** 会把大型运行时或垃圾回收器打包进每个模块的语言，产出的文件更大，可能超过地图嵌入上限。这是作者工具链的取舍，与引擎无关。

### 6. API 分层

| 层 | 内容 | 首个 API 版本 |
| --- | --- | --- |
| L1 动作和任务 | 所有原版触发器动作、任务、生产、所属方和对象命令 | 包含 |
| L2 触发器 | 原版事件加新事件（武器开火、抛射体引爆……），投递给动作 | 包含 |
| L3 覆盖 | 具名决策：选择目标、伤害、是否允许生产、接管武器的一次射击…… | 从 modder 需求中选两三个 |
| L4 逐帧行为 | 对绑定类型的对象进行批量逐帧控制 | 不包含，以后再做 |

查询是只读的，遍历顺序确定。每个 L1 动作调用该动作现有的 Rust 移植（例如 `sim/trigger_runtime` 里的）；模块不会得到第二份实现。

覆盖以游戏概念命名，例如 `Override.Damage`、`Override.TargetChoice`，从不以原生函数命名，这样引擎重构后它们依然成立。`Override.Fire` 让模块接管武器的一次射击，原生抛射体就不再生成（第 9 节）。

对于非常频繁的决策，优先用数据而不是回调：目标优先级用持续效果携带的倍率表示，再配合 `TargetChanged` 事件；逐次调用的覆盖点只留给不那么频繁的决策。`Override.CommandAllowed` 和 `Override.Death` 是另外两个候选。由模块定义并执行的自定义任务留给后续 RFC。

L4 每帧对每种行为类型调用一次模块，把该类型的全部对象一起交给它，从不按单个对象调用。

**粒度。** 一个 API 函数对应一个游戏操作，这个操作在引擎里有且只有一个 owner：发射武器、添加持续效果、设置任务、修改生命、创建对象。更大的行为（比如一次空袭、一条心灵控制链）由作者用这些函数组合。

坐标可以作为任何操作的参数：目标、生成点、传送目的地。例如模块可以往任意格子扔核弹。不开放的是绕过 owner 的步骤，比如直接写已有对象的位置字段或内部字段。对象的位置关联着格子占用、碰撞、视野、所在地图层以及乘客关系，只有引擎自己的流程能保持它们一致，所以对象只能通过传送、运动效果或移动任务改变位置。抛射体是第 9 节第 4 层的例外：它们不占格子，引擎会钳制其位置，碰撞判定照常进行。

### 6a. 触发器：事件、约束条件和动作

一个触发器有一个事件、任意个约束条件，以及一个或多个动作。

- **事件**分两类。*投递型事件*发生在某个时刻（受到伤害、武器开火、被摧毁）：触发器在那一刻触发，其中的原版动作和原子动作立即执行，模块动作则带着事件的载荷排队到模块阶段执行（第 5 节）。VERA 新增的投递型事件在安全点引发，即不处在任何计算之中的时刻：在产生它的那次计算完成之后，或在一次计算开始之前，例如 `HouseTransfer` 在转移开始之前引发（第 5 节）。*轮询型事件*描述一种状态（生命低于某值、金钱高于某值），由引擎按触发器设定的间隔原生检查，状态成立时触发。
- **约束条件**在任何模块代码运行之前过滤触发器。引擎原生检查，全部满足时才调用模块。条件可以取反。更复杂的逻辑（条件之间的“或”、两个对象之间的比较、计数）写在模块代码里。
- **动作**可以是原版触发器动作、第 6b 节的原子动作，或模块函数。原版动作和原子动作在触发器触发时执行；模块函数排队到模块阶段（第 5 节）。模块函数也是模块收到事件的唯一途径。
- 每个事件都标明它所附着的对象，以及涉及的另一个对象（如果有的话：攻击者、目标、载具、生产者）。约束条件可以判断其中任意一个。
- 事件只对绑定的对象触发：类型绑定了该触发器的对象（`Wasm.Tags`）、自身标签包含该触发器的对象；对于武器事件（携带抛射体句柄的 Fire、HitTarget 和抛射体 Detonated），还包括使用绑定了该触发器的武器、弹头或抛射体类型的任何对象。武器绑定对使用这把武器的所有射手生效，不论射手是什么类型：

  ```ini
  [RedEye2]                   ; 一把武器
  Wasm.Tags=MissileFiredTag   ; 所有使用 RedEye2 的射手开火时都会触发其 Fire 触发器
  ```

```ts
const PANICKED = Mark.id("Panicked");   // 只解析一次，之后的调用都传 ID

Trigger.create({
  event: Event.TakeDamage,
  conditions: [Cond.healthBelowPercent(30), Cond.not(Cond.hasMark(PANICKED))],
  actions: [Action.wasm("giPanic")],
  difficulty: Difficulty.All,
});
```

版本 1 的投递型事件候选：

轮询型事件候选：生命、弹药、乘客数、运载空间、载矿量、当前任务、移动或停止、地形类型、所属方金钱、所属方电力、效果层数、与另一对象的距离。

来自调研的其他候选事件：Built、Idle、MoveFailed、Arrived、Promoted、Cloaked、Spotted、Lost、AmmoChanged、MissionChanged、HouseDefeated、PlayerLeft、StorageFull、MotionEnded。

约束条件候选：敌我关系（自己、盟友、敌人、中立）、类别（步兵、车辆、建筑、飞行器、抛射体）、所在层（空中、地面、水面）、类型 ID、护甲、是否平民阵营、生命值或百分比、地形类型、所属方电力状态、所属方金钱、拥有某效果（及其层数）、拥有某标记、效果来源、距离在某武器射程内。

参数值都是整数或句柄；伤害和原版一样是整数，模拟 API 中没有浮点值。历史数据（比如某个攻击者累计造成的伤害）由模块在自己的内存里记录。

**不进入引擎的：** INI 里的记录器、算子和表达式键。这类状态由模块保存在自己的内存里，几行代码就能算出来，并随模块一起存档和计入哈希。INI 保持为数据，不变成一门编程语言。

### 6b. 原子动作与持续效果

版本 1 的瞬时动作候选：发射武器（按索引或名称，目标可以是格子、对象或当前目标）、发射超级武器、生成动画、移除、摧毁、通过弹头和护甲规则造成伤害（带来源，用于击杀归属和经验）、直接设定生命值（无归属）、创建对象、设置任务、传送到某格（与超时空传送相同；目标格被占时，按规定的规则选附近的格子或动作失败）、清除目标、清除伪装、区域搜索（返回对象列表的查询）、播放声音、增加经验、增减金钱、修改科技树、转移所属、清除心灵控制、修改弹药、增删乘客、添加或移除持续效果、添加或移除标记、生成抛射体（类型、起点、目标对象或坐标、用于击杀和经验归属的来源、初始模块数据）、在某个坐标以指定伤害和来源引爆弹头、立即引爆抛射体、移除抛射体而不引爆、让某个所属方结束游戏（胜利或失败）并设置分数、向游戏内日志写一行。

在触发器中，每个原子动作都带一个明确的目标参数：主体（默认）、事件中的另一方对象、标签持有者（标签中持有该触发器的对象；CellTag 的标签持有者是那个格子）、某个所属方（未指定时为触发器的所属方），或一个格子或路径点。目标种类不适用于该动作属于数据错误，不表明模块有问题：动作返回错误状态，模块保持启用（第 3 节）。原子动作立即执行，并可能引发新的事件，所以它们可以在一帧之内连锁，深度受第 5 节的上限约束。

持续效果是对象身上带持续时间的状态，由 `sim/attach_effect.rs` 负责（第 8 节）。候选：染色、附着动画、阻止死亡、变成另一类型、替换武器、运动（被抛起、被推动）、超时空移动、受伤倍率、火力倍率、速度倍率、射速倍率、射程、目标优先级倍率（第 6 节）、隐形、对某弹头或攻击类型免疫、禁止开火、停止索敌、伤害修正、无法被选中、无视玩家指令、不可被选为目标、所属方断电。

- 每种效果类型声明自己的叠加方式：叠加到上限、新的替换旧的，或拒绝新的。不能同时生效的效果（变形、超时空移动、运动）组成一个互斥组，由 owner 保证同一时间只有一个生效。
- 效果的属性凡是 Phobos AttachEffect 已有键的都沿用：持续时间、延迟、间隔、重新附加前的冷却、最大触发次数、来源、变形或创建时是否继承、是否无视铁幕。新增属性使用同一个读取器。
- 运动由引擎叠加到对象的移动上，从不以坐标形式写入。
- 显示在对象上方的文字、数值或按钮属于客户端显示属性（第 10 节），不是效果。

一个对象可以携带任意多个标记，所属方也可以。动作和效果负责添加和移除，约束条件负责判断。一个标记可以带一个整数值和一个可见度等级：仅本所属方、盟友、能看到该对象的玩家，或所有人。客户端查询只返回本玩家有权看到的标记。标记不能嵌套。

### 6c. 查询

查询是只读的。结果按对象创建顺序返回，这个规则不依赖引擎如何存放对象；结果写入模块提供的缓冲区（第 15 节）。在客户端模块中，查询按本地玩家的视野过滤。

- **对象：** 按格子、半径或矩形区域，按类型、所属方或类别查找；对象的类型、所属方、生命、位置、任务、目标、等级、弹药、乘客、持续效果和标记。
- **所属方：** 金钱、发电量和耗电量、拥有的建筑和已满足的前提条件、科技等级、盟友和敌人、阵营、是否已战败。
- **地图：** 尺寸；格子的地形类型、高度、覆盖物和矿石、对某种移动区域是否可通行、某个所属方能否看到；路径点和 CellTag。
- **规则：** 任意类型的任意键，以解析后的值返回。
- **场景：** 帧号、难度、游戏模式、玩家数。
- **探测：** 某武器现在能否向某目标开火、目标是否在射程内、某类型能否由某所属方建在某格，以及最近的可放置格子。它们复用引擎自己的规则。

### 6d. AI

电脑所属方保留它们的 AI。版本 1 允许模块创建特遣部队和小队类型（`[TaskForces]`、`[TeamTypes]`）、指派 AI 小队脚本（`[ScriptTypes]`）、启动和解散小队，以及启用或禁用 AI 触发器（`[AITriggerTypes]`），全部通过现有的 owner（`sim/ai_team_creation.rs`、`sim/team_script_vm.rs`）完成。让 AI 学会使用 mod 新增的机制，留给后续 RFC。

### 7. 运行时的触发器和标签

模块按地图的同一模型创建触发器和标签：

```ts
const t = Trigger.create({
  house: ctx.house("Americans"),
  event: Event.Killed,
  actions: [Action.wasm("onConvoyLost")],
  difficulty: Difficulty.All,
});
const tag = Tag.create([t], TagRepeat.Repeating);
techno.setTag(tag);     // 和原版一样，替换对象原有的标签
cell.setTag(tag);       // CellTag
t.disable();
```

- 新建的触发器和标签放进现有触发器运行时的列表，和地图里的放在一起，不另存一份。
- 它们使用确定性的编号，不会和地图里的编号冲突，并随触发器运行时一起存档和计入哈希。
- 一个对象只有一个标签（`ObjectClass` 的 `AttachedTag`，`+0x34`），一个标签可以连接多个触发器。让一个对象挂多个标签属于 VERA 扩展，需要单独的 RFC。
- 类型绑定（`Wasm.Tags`）不占用这个槽位，而是作为对象的独立订阅另外记录。所以地图上预先放置、自带标签的对象保留它的标签，同时也接收所属类型的触发器。
- 删除对象或标签时，通过触发器运行时现有的清理逻辑解除关联。

新的事件和动作编号分配在不与 Ares、Phobos 冲突的范围内。

### 8. 修改规则

| 时机 | 能改什么 | 方式 |
| --- | --- | --- |
| `onRules` | 任意键；新增类型 | 走原生 INI 读取器、钳制和读后处理；计入大厅哈希 |
| 对局中，按类型 | 公开白名单里的键 | `rules.set("E1", "Speed", "6")`：值像 INI 文本一样解析，从下一帧起生效，让相关缓存失效，并作为规则覆盖层存档 |
| 对局中，按对象 | 倍率、等级、所属方、换类型、生命值 | 通过现有的单对象 owner，包括持续效果（第 6b 节） |

- 单对象的倍率复用 `sim/attach_effect.rs` 中已有的 owner。那部分代码有一部分还在 `cfg(feature = "phobos")` 后面，按项目契约的要求，在模块能使用它之前要先迁移到运行时开关。
- 每个白名单键都要写明修改它对地图上已有对象的影响（例如新的 `Strength` 下当前生命值如何变化）。
- 对局中不能新增类型。
- 启用 Ares 或 Phobos 时，模块能在规则中看到它们的键。白名单逐个写明这些扩展键能否在对局中修改。

### 9. 示例：抛射体弹道

四个层级都在 `rules.wasm` 中运行，因为它们决定打中什么。`ui.wasm` 可以加纯视觉效果，比如拖尾和光效。

| 层级 | 机制 | 开销 |
| --- | --- | --- |
| 1 | `onRules` 设置现有键（`Arcing`、`ROT`、`Vertical`，启用 Phobos 时还有 `Trajectory`） | 对局中无开销 |
| 2 | 武器开火、抛射体引爆的触发器：额外的抛射体、分裂、连锁 | 每次事件，仅限绑定的类型 |
| 3 | `onLaunch` 返回一条路径（贝塞尔、抛物线、螺旋、路径点），引擎用定点数沿路径推进抛射体 | 每个抛射体一次调用 |
| 4 | `onTrajectoryFrame(type, bullets)` 修改速度或位置，或请求引爆，一次处理该类型的全部抛射体 | 每帧每类型一次调用 |

引擎在 `ProjectileTrajectory` 里，在三条原生飞行分支（`BulletClass::AI` `0x004666E0`）旁边新增一条模块分支。碰撞仍由 `world::projectile_collision` 处理，引爆判定仍在 `sim/projectile`，伤害和弹头仍在 `combat`。引擎会钳制模块的输出：速度和位置有上限，离开地图就引爆或删除。每个抛射体有 16 字节的模块数据，存档并计入哈希。

要一次发出多枚不同弹道的抛射体，就在武器的开火事件上挂一个动作来生成它们，每枚有自己的类型和模块数据，再由 `onLaunch` 分别给出路径。这个动作是模块函数，从它的事件记录中读出射手、目标和原生抛射体（`e.subject`、`e.other`、`e.projectile`）。使用 `Override.Fire` 时，模块接管这次射击，原生抛射体不再生成。不使用时，原生抛射体在单位更新时射出，模块生成的抛射体在同一帧的模块阶段射出，位移上落后一帧。由触发器自身的原子动作生成的抛射体在触发器触发时射出，与原生抛射体同时。

### 10. 客户端模块

**界面树。** 界面树由引擎持有，引擎负责布局和绘制。模块通过一小组操作修改它：新建和删除节点、设置属性（标签、图像、位置、可见性）、按名字查找节点，以及接收点击、悬停和热键。修改按渲染帧批量提交，不会每帧重建整棵树。不暴露图形 API。

作者分两部分编写界面：

- **静态布局写在 INI 里**，语法和键与 `veraui.ini` 相同（`Type`、`Hold`、`X`、`Y`、`Width`、`Height`、`Parts`、`Label`）。本 RFC 新增 `List` 部件类型，以及 `Text` 部件的 `Label` 键。引擎在对局开始时读取，不需要预编译。没有动态部分的界面不需要模块。
- **动态部分写在模块代码里**：按名字找到节点后修改，或新建节点。

```ini
[Mission.Field]
Parts=Messages,Timers,Banner,Powers,Clock,Objectives

[Mission.Objectives]
Type=Column
Hold=TopRight
Width=240
Parts=ObjTitle,ObjList

[Mission.ObjTitle]
Type=Text
Label=TXT_OBJECTIVES    ; Text 新增的键：字符串表中的一行，跟随游戏语言

[Mission.ObjList]
Type=List               ; 新增的部件类型
```

```ts
export const onStart = start((ui: Ui) => {
  ui.find("ObjList").setItems(["TXT_OBJ_RADAR", "TXT_OBJ_CONVOY"]);
  ui.create(Column.hold(Hold.BottomLeft).child(Text.label("TXT_WAVE")));
});
```

React 或 JSX 风格的库可以放在 SDK 里：它在模块内部计算差异，再发出同样的操作，引擎完全不知道它的存在。这类库只能用于 TypeScript（AssemblyScript 没有闭包），不属于官方 API。

**其他客户端功能：**

- 单个对象的显示属性：图像、调色板、着色、附加动画、可见性，以及显示在它上方的文字、数值或按钮。会影响玩法的属性（如隐身）属于模拟模块。
- 选中单位和点击按钮属于客户端事件。要改变游戏，模块发送一条消息（第 1 节），由模拟模块在 `onMessage` 中处理，这样联机和回放都保持一致。
- 客户端模块可以发出标准玩家指令（选择、移动、攻击、部署、建造），引擎像校验任何玩家输入一样校验它们。`sendMessage` 用于自定义逻辑。
- 每个 mod 在玩家本机有一个小型键值存储，用于战役进度、成就和设置。只有客户端模块能使用它。需要影响对局的数据通过 `sendMessage` 送进模拟，因而成为命令流的一部分。
- 图像、动画和模型都按名字引用，从不按文件格式引用，所以以后新增素材格式（单独的 RFC）不需要修改 API。
- 声音和消息；`log()` 输出到游戏内控制台。
- 通知是具名的，名字只解析一次，换成 ID：`Notify.id("WaveStarted")` 返回一个 `NotifyId`。这个 ID 是名字统一大小写（case-fold）后的稳定哈希，在每台机器上、在模拟模块和客户端模块中都按同样的方式计算。引擎在加载模块时，把本局加载的所有模块（mod 的和地图的合在一起）的通知名放在一起检查冲突，通知名发生冲突的模块会被拒绝，并提示是哪些名字（第 3 节第 6 步），所以 `Notify.id` 总能返回 ID。模拟模块用 `notify(player, id, bytes)` 向某个玩家的客户端发送通知，客户端模块在 `onNotify(id, bytes)` 中接收。
- 所有查询都按本地玩家的视野过滤。观战者的客户端模块看到观战者能看到的范围，房间允许时为整张地图。玩家当前看不到的敌方对象不出现在结果中；引擎不保存“最后一次看到”的副本。
- 玩家自装的界面模块放到后续阶段。mod 或房间可以禁止它们。

### 11. 联机

- 嵌入的模块随地图传输。mod 的模块计入现有的 mod 文件校验。
- 大厅比对模块哈希和所需的 API 版本。游戏不支持所需版本的玩家会被拒绝，并看到所需版本的提示。
- 每条消息的发送者由引擎填写，模块无法伪造；单条消息大小和每帧消息数有上限。
- 模拟模块发给客户端的通知只送达目标玩家。通知的内容是模块自己的字节，由模块负责：引擎无法过滤它。
- 联机只交换指令，从不交换状态。重连的玩家从头重新模拟整局，包括模块；模块消息本身就是指令，所以不需要额外发送任何东西。因此模块每帧的开销也会拖慢追帧速度。
- 回放记录模块哈希和 API 版本。模块不一致的回放会被拒绝并提示原因。
- 存档记录模块哈希。模块与当前安装的 mod 或地图不一致的存档会被拒绝，并提示是哪些模块。
- 实现时更新 [Networking](../Networking.md)，说明已发布的游戏、混合版本的房间以及回退版本分别如何处理模块。

### 12. 版本与 ABI

- 一份接口定义（WIT 语法）是 API、SDK 绑定、参考文档和兼容性检查的唯一来源。
- 接口是带版本的包：`vera:sim@1`、`vera:client@1`。不稳定的接口放在 `vera:unstable/*` 下，需要显式开启，可以不经通知就改变。
- 每个已发布的版本都一直可用。旧版本是现行实现之上的薄适配层，从不是第二份实现。
- 每个已发布的版本都在 CI 中运行一组已提交的 `.wasm` 测试用例。破坏其中任何一个都会让构建失败。
- 函数可以弃用并向模块作者发出警告，但已发布的版本永不删除。
- 已发布的函数永不改变单位或含义。要改变，就新增函数或发布新版本。
- 二进制接口采用 core module ABI（整数句柄、指针加长度）还是 Component Model，是待定问题。

### 14. 项目契约

- 功能存在于每个构建中，只有 mod 或地图提供模块时才开启。从不放在构建 feature 后面。
- 每次模块调用都通过状态现有的 owner 访问状态。API 不引入竞争状态。
- 功能在 `docs/` 下为 modder 编写文档。
- 模块出错在游戏中报告，从不只写进日志。

### 15. 性能

引擎只保留一份游戏状态。模块持有整数句柄和 ID，需要数据时再查询；不会把游戏世界复制进模块内存。下面这些规则让跨边界的开销保持很低，它们属于 ABI 的一部分：

- **热路径用 ID，不用名字。** 类型、所属方、武器、弹头、抛射体、标记和效果的名字，以及附录列出的其他命名种类，都只解析一次，换成整数 ID（`ctx.typeId("E1")`、`Mark.id("Panicked")`），通常在 `onRules` 或 `onScenarioStart` 中完成。其他所有调用都传 ID。接受名字的调用（查找、`rules.set`、创建触发器）只用于初始化和不频繁的修改；SDK 会缓存 ID。通知 ID 是名字统一大小写后的稳定哈希，在每台机器上、在两侧都相同（第 10 节）。
- **每个模块每帧只投递一次。** 本帧排队的模块动作按触发顺序写成固定大小的紧凑记录，一次调用交给每个模块（第 5 节）。每条记录是一个模块动作，加上触发其触发器的那个事件的载荷；没有单独的事件记录。记录的布局属于接口定义。
- **查询结果写进模块的缓冲区。** 结果直接写入模块提供的缓冲区，引擎每次查询都不分配内存。结果多时分页返回。创建顺序来自引擎维护的创建序号，结果不需要按存放位置重新排序。
- **旁路表。** 标记、类型绑定、订阅和每个抛射体的模块数据都放在按句柄索引的旁路表里，只有用到它们的对象才占空间。每个事件触发点只检查对象所属类型的一个标志位；该类型没有绑定模块时，其余代码都不运行。
- **轮询型事件**有最小间隔，引擎把不同对象的检查分散到不同的帧。
- **哈希中的模块内存。** 联机每帧的同步校验不包含模块内存。定期的完整状态哈希（目前每 15 帧一次）包含模块内存，但只哈希上次之后被写过的内存页。
- **SDK 不为每个事件分配对象。** 句柄和 ID 都是值类型：TypeScript 中是 64 位整数，Rust 中是 newtype。只有 `Trigger.create` 这类初始化调用才会创建对象。
- **逐帧批量数据**（L4 行为、模块弹道）直接写入模块内存，再从中读回，每个对象几十字节。
- **按最慢的平台定额度。** 计量会让模块代码变慢，浏览器版还可能用解释器运行模块。锁步联机中最慢的机器决定整体速度，所以默认运算额度按最慢的受支持平台确定，并在 RFC 接受之前实测（待定问题 1 和 4）。
- **没有模块就没有开销。** 没有模块时，每个事件触发点只多一次标志位检查，其余代码都不运行。

## 流程

1. **草案。** 本文档公开讨论。每次修改都提升 RFC 版本号，并记入[修订记录](#修订记录)。
2. **回答待定问题。** 在 `src/` 之外做实验，回答下面的待定问题，结论汇总到本文。
3. **接受。** 维护者把某个版本标为已接受，此后才开始开发。
4. **预览。** API 以 `0.x` 发布，允许破坏性变更并记入变更日志。至少用它重做一个真实任务或模式，并请外部 modder 试用。
5. **稳定。** 冻结 `vera:sim@1` 和 `vera:client@1`，范围仅限预览期实际用到的部分。兼容性测试用例加入 CI。
6. **增长。** 每个新接口或覆盖点是一个小的后续 RFC 和一个新的次版本。

接受之后的计划顺序：

| 阶段 | 内容 |
| --- | --- |
| P1 | `rules.wasm`：`onRules`、`onScenarioStart`、`onFrame`、L1、带约束条件的 L2、持续效果、标记、查询、AI 小队、类型标签绑定、触发器动作、地图嵌入、`asset` 命令、TypeScript 和 Rust SDK 及模板 |
| P2 | `ui.wasm`：带 INI 布局的界面树、显示属性、视野过滤、消息 |

| 以后 | 逐个增加覆盖点、L4 行为、对等调用、玩家界面模块 |

## 备选方案

- **由引擎运行 Lua**（Recoil 的做法）。对 modder 友好，但浮点和表遍历顺序的确定性要靠修改解释器保证，API 也会长成一个没有版本的全局命名空间。
- **在引擎里内置语言运行时**（随 VERA20k 发布 Lua 或 JavaScript 运行时，供模块导入）。模块会更小，但引擎要永远维护一个语言运行时，并且每个 API 版本都要固定一个构建。未采用：语言留在作者的工具里。
- **原生插件。** 无法移植到浏览器版，也没有沙箱。
- **以某个所属方的视角做模拟查询。** 暂不采用。模拟查询能看到全部，客户端查询按视野过滤。
- **客户端模块之间直接发消息。** 不采用。玩家之间的所有通信都经过模拟，联机只保留一条通道。
- **只增加 INI 键。** 简单需求仍然适用，够用时依然是首选，但表达不了通用逻辑。

## 参考先例

- **Recoil（Spring）。** 同步与非同步代码分离；非同步代码只能通过网络消息影响模拟；单对象的数值带可见度等级；代价高的回调只对脚本关注的对象触发。借鉴的教训：不暴露底层图形 API；用带版本的包取代单一全局命名空间；回调需显式订阅。
- **红警 3（SAGE）。** 在数据文件里把对象事件绑定到脚本函数，可以继承，处理函数收到对象本身。借鉴：在数据里绑定，而不是在代码里。
- **Phobos。** 抛射体的 `Trajectory=` 类型；用于单对象修正的 AttachEffect。
- **社区的“触发-效果-约束条件”设计**（本 RFC 讨论期间分享的一份表格）。借鉴：触发器由事件、约束条件和动作组成；投递型与轮询型事件；带类型参数的事件清单；瞬时动作、持续效果和约束条件清单。未采用：INI 里的记录器和算子，改由模块代码实现。

## 待定问题

1. **浏览器版。** 浏览器版能否以和原生版完全一致的结果运行模块？用哪个引擎？wasmtime 可能无法在浏览器中运行。
2. **ABI。** 用 core module ABI 还是 Component Model？
3. **TypeScript 编译器。** TypeScript SDK 用哪种编译器：把 TypeScript 子集编译成 Wasm 的编译器（如 AssemblyScript），还是把 JavaScript 引擎编译进每个模块？引擎对两者没有区别；这个选择决定模块体积、速度，以及普通 TypeScript 代码能用多少。
4. **计量。** 用哪种计量插桩？在 2 万单位下开销多大？
5. **INI 格式。** 用文中所示的具名节，还是用原版逗号分隔的触发器编码以便 FinalAlert2 编辑绑定，还是两者都要？键用什么前缀？
6. **事件和动作编号。** 哪个范围不与 Ares、Phobos 冲突？
7. **FinalAlert2。** 保存地图时会不会保留 `[VeraWasmRulesPack]` 这类它不认识的节？
8. **上限。** mod 和地图的嵌入体积、内存和默认运算额度。
9. **帧阶段。** 模块阶段放在模拟帧的哪个位置；模块弹道分支相对碰撞和引爆判定的位置。
10. **存档体积。** 快照中的模块内存：压缩方式和内存上限。
11. **首批覆盖点。** 版本 1 提供哪两三个覆盖点。
12. **白名单。** 版本 1 中哪些键可以在对局中按类型修改。
13. **版本 1 清单。** 第 6a、6b 节中哪些事件、约束条件、动作和持续效果进入版本 1。
14. **效果叠加。** 每种持续效果的叠加方式和所属互斥组。
15. **界面布局。** mod 和地图把布局节放在哪里，以及版本 1 的控件集合。
16. **地图文字。** 地图无法携带字符串表，地图模块的文字如何翻译。
17. **战役。** 每一关的模块是重新开始，还是延续上一关的状态。
18. **连锁深度。** 含有由模块创建或绑定的触发器、VERA 新增的事件或原子动作的连锁，每帧的深度上限（第 5 节）。
