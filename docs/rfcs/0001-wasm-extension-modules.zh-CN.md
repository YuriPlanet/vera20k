**开发门槛。** 本 RFC 的某个版本被接受之前，这个功能的引擎代码一律不合入。在此之前，工作只限于讨论和修订本文档，以及为回答[待定问题](#待定问题)而做的一次性实验。这些实验放在引擎源码树之外，不合并。

## 概要

让 mod 和地图携带编译好的 WebAssembly 模块（`rules.wasm`、`ui.wasm`），由 VERA20k 在沙箱中运行。模块可以在规则读完后修改规则、响应触发器、执行动作和下达任务、覆盖指定的游戏决策，并构建自己的界面。作者可以用任何能编译到 WebAssembly 的语言、用自己的工具编写模块，引擎只运行编译好的 `.wasm`。官方提供 TypeScript 和 Rust 两套 SDK。API 使用红警 2 modder 已经熟悉的术语：触发器、事件、动作、标签、任务、局部和全局变量、帧，并新增约束条件、持续效果和标记。

[API 清单附录](0001-wasm-extension-modules-api.zh-CN.md)列出所有函数、类型、事件、约束条件、持续效果和覆盖点。它只是参考：规则在本文中陈述。

API 从第一次发布起就带版本。已发布的 API 版本在之后所有 VERA20k 版本中都能继续使用。

## 动机

INI 文件和地图触发器表达不了 modder 想要的很多东西：自定义弹道、波次逻辑、新的超级武器行为、任务目标面板。Ares 和 Phobos 为此加了很多键，但每个新想法仍然需要改引擎。脚本层让 modder 自己实现这些，同时引擎仍然是游戏状态唯一的 owner。

API 一旦被 mod 依赖就无法收回，所以它必须公开设计、以带版本的小步增长，并用测试保证每个已发布版本一直能运行。

## 目标

1. modder 不改引擎也能修改玩法和界面。
2. 所有玩家运行相同的模拟模块并得到相同结果：在任何受支持的平台上（包括浏览器版）都不会不同步。
3. 外部模块永远不会让游戏停下。出错的模块被停用，并告诉玩家原因。
4. 任何模块都不能读文件、不能联网，任何模拟模块都不能读时钟；客户端模块得到的渲染计时只用于显示，并且按运算量而不是时间计量（第 3 节）。引擎的查询从不泄露隐藏信息：客户端模块的查询只暴露本玩家自己的界面能显示的内容（第 10 节），其他任何东西只能通过通知到达客户端。模拟模块选择把什么通知给玩家，由模块作者负责（第 11 节）。
5. 没有模块时，游戏和现在完全一样。
6. 只有少数类型使用的模块不会拖慢 2 万单位规模的战斗。
7. 红警 2 modder 从模板开始，几分钟内就能在游戏里看到改动效果。

## 非目标

- 原生插件（`.dll`、`.so`），或在沙箱外加载任何东西。
- 引擎里出现源代码。引擎从不解析、编译或解释任何源语言，也不内置任何语言运行时（见[备选方案](#备选方案)）。
- 暴露引擎内部：内存布局、原生地址、内部对象下标或存储槽位（句柄是对象的创建序号，第 5 节）、渲染器的图形 API。
- 对局中新增对象类型。
- 取代原版触发器系统。模块是在它的基础上扩展。

## 术语

凡是红警 2 已有的术语，API 都沿用。代码和 INI 中的名字以本表为准。

| 术语 | 含义 |
| --- | --- |
| **扩展模块**（Extension module） | 一个编译好的 `.wasm` 文件。不叫“脚本”：红警 2 里的脚本指 AI 小队脚本（`[ScriptTypes]`）。 |
| **触发器**（Trigger） | 和地图里一样：一个或多个事件（必须全部成立）加一个或多个动作，属于某个所属方，带难度标志和原版的重复类型。VERA 增加可选的约束条件。 |
| **事件**（Event） | 让触发器触发的东西。原版事件编号含义不变。 |
| **动作**（Action） | 触发器执行的内容。原版动作编号不变。新增一个动作：执行模块函数。 |
| **模块触发器**（Module trigger） | 至少带一个模块动作（`Action.wasm`）、由模块创建，或通过 `Wasm.Tags` 或 `Trigger.bindType` 绑定的触发器。带模块动作的地图触发器也算。 |
| **约束条件**（Condition） | 触发器执行动作之前，由引擎原生检查的过滤条件。 |
| **标签**（Tag） | 把触发器挂到对象或格子（CellTag）上的东西。一个对象只有一个标签。 |
| **标记**（Mark） | 对象或所属方携带的文字记号，供约束条件判断，带一个整数值和一个可见度等级。不是标签：一个对象可以有任意多个标记。 |
| **持续效果**（Attached effect） | 对象身上带持续时间的状态，例如倍率或免疫（沿用 Phobos AttachEffect 的叫法）。 |
| **任务**（Mission） | 对象的命令：Move、Attack、Guard、Area Guard、Hunt、Sleep 等。 |
| **局部/全局变量**（Local / Global） | 和地图里一样的局部变量和全局变量。 |
| **帧**（Frame） | 模拟的一个逻辑帧，也是 `ROF`、`Rate` 和计时器的单位。 |
| **渲染帧**（Render frame） | 某台机器上画出的一帧。不同步。 |
| **覆盖点**（Override） | 一个具名的决策点，模块可以在这里改变引擎的结果。 |
| **House、Techno、Building、Vehicle、Infantry、Aircraft、Projectile、Weapon、Warhead** | 与 INI 文件中的含义相同。 |
| **格子、lepton**（Cell、lepton） | 地图坐标。1 格等于 256 lepton。 |
| **运算额度**（Operation budget） | 模块每帧可以做的工作量，以确定性的运算单位计量：一个基础额度，加上本帧投递的每条记录各一份额度（第 5 节）。模块代码和它发起的宿主调用都计入。 |
| **创建序号**（Creation serial） | 引擎在每个对象和抛射体创建时给它的一个 64 位编号，从不复用。它就是对象的句柄；跨对象时，查询结果、覆盖调用和投递的记录都按它排序，与引擎如何存放对象、循环按什么顺序无关。 |
| **安全点**（Safe point） | 不处在任何计算之中的时刻，VERA 新增的事件在这里引发，其触发器的原版动作和原子动作在这里执行。批量或并行的引擎段算作一次计算（第 5 节）。 |

## modder 看到的样子


### 文件

```
Mods/MyMod/
  mod.ini        ; Needs= and the other mod.ini keys; no module keys
  rulesmd.ini    ; [VeraWasm] API version, budgets, map policy; binds tags to types
  rules.wasm     ; simulation module
  ui.wasm        ; interface module
```

代码注释说明：`mod.ini` 放 `Needs=` 和其他 mod.ini 键，不含模块键；`rulesmd.ini` 的 `[VeraWasm]` 放 API 版本、额度和地图政策，并把标签绑定到类型；`rules.wasm` 是模拟模块，`ui.wasm` 是界面模块。

地图以文本形式携带模块，方式和现在携带 `IsoMapPack5` 一样：压缩、base64 编码、按编号分行。

```ini
[Basic]
VeraMinVersion=0.9.0     ; example; older releases refuse the map with a message (section 11)

[VeraWasm]
Api=1.0                  ; major.minor of the API the modules need (section 12)
RulesSize=48213          ; decoded size, checked on load
UISize=9120
StorageId=MyCampaign     ; the client store (section 10); default: the map's file name

[VeraWasmRulesPack]
1=eJzt3XlcVOX+B...
2=...

[VeraWasmUIPack]
1=...
```

代码注释说明：`VeraMinVersion` 是示例，更旧的版本会拒绝这张地图并给出提示（第 11 节）；`Api` 是模块需要的 API 主版本.次版本（第 12 节）；`RulesSize` 是解码后的字节数，加载时校验；`StorageId` 是客户端存储（第 10 节），默认为地图的文件名。

`asset` 工具增加命令：把模块嵌入地图、从地图中取出模块，以及运行和游戏相同的加载检查。

### 把触发器绑定到类型

```ini
; rulesmd.ini in the mod
[E1]
Wasm.Tags=GIPanicTag     ; every E1 receives this tag's triggers

[GIPanicTag]
Trigger=GIPanic

[GIPanic]
Event=TakeDamage
Action=Wasm:giPanic      ; runs the module action giPanic of the mod's rules.wasm (section 2)
Repeat=yes
```

代码注释说明：这是 mod 里的 rulesmd.ini；每个 E1 都接收这个标签的触发器；`Action=Wasm:giPanic` 运行 mod 的 rules.wasm 的模块动作 giPanic（第 2 节）。

每个 E1 都以自己的实例运行 `GIPanic`（第 7 节）。键名和具体的节格式尚未确定（待定问题 4）。在 FinalAlert2 里编辑的地图触发器，也可以通过新动作调用模块函数。

### 模块代码

引擎只看到编译好的模块，源码和编译器都在作者自己的工具里。同一个模块分别用两套官方 SDK 写：

```ts
// TypeScript (AssemblyScript-compatible)
import { action, onFrame, Every, Techno, Mission, EventRecord, Ctx } from "@vera20k/sdk";

action("giPanic", (ctx: Ctx, e: EventRecord): void => {
  const techno = e.subject;
  if (Techno.healthPercent(techno) < 30) {
    Techno.setMission(techno, Mission.Hunt);
  }
});

onFrame(new Every(15), (ctx: Ctx): void => {
  if (ctx.local(3).get()) {
    // ...
  }
});
```

```rust
// Rust SDK
use vera20k_sdk::prelude::*;

#[vera::action(name = "giPanic")]
fn gi_panic(ctx: &mut Ctx, e: EventRecord) {
    let techno = e.subject();
    if techno.health_percent() < 30 {
        techno.set_mission(Mission::Hunt);
    }
}

#[vera::on_frame(every = 15)]
fn check_waves(ctx: &mut Ctx) {
    if ctx.local(3).get() {
        // ...
    }
}
```

每套 SDK 都用一条命令构建出 `rules.wasm` 或 `ui.wasm`。构建时把模块的动作名列在 Wasm 自定义段 `vera.actions` 中，并给每个名字一个下标（第 12 节）。包名只是占位。

## 设计

### 1. 两个世界

| | 模拟（`rules.wasm`） | 客户端（`ui.wasm`） |
| --- | --- | --- |
| 运行在 | 每台机器上，锁步执行 | 仅本机 |
| 确定性 | 是 | 否 |
| 可以改变 | 游戏状态，通过引擎的 owner | 界面、显示、声音 |
| 影响游戏的方式 | 动作和任务 | 通过命令流发出标准玩家指令和消息 |
| 引擎侧 | `sim/` | `ui/`、`render/`、`audio/` |

这个划分遵循现有规则：`sim/` 从不依赖 `render/`、`ui/`、`audio/` 或 `net/`。

- 从模拟到客户端：经过视野过滤的查询和本地通知。
- 从客户端到模拟：只有命令流。标准玩家指令像任何玩家输入一样被校验；`sendMessage` 像玩家指令一样进入命令流（第 10 节）。回放和联机都能看到两者。

### 2. 来源：mod 和地图

mod 和地图使用同一套 API 和同一套 SDK，区别在于引擎授予它们的权限。

| | mod | 地图 |
| --- | --- | --- |
| 顺序 | 先 | 在 mod 之后，和 INI 层叠一致 |
| `onRules` | 在 `RULESMD.INI`、`LANGRULE.INI` 和模式层之后 | 在地图层之后；能看到 mod 的结果 |
| 运算额度 | 在 mod 的 `[VeraWasm]` 中声明，引擎设上限 | 默认更小；mod 的 `[VeraWasm]` 可以调高 |
| 体积 | 受文件大小约束 | 有嵌入上限 |
| 界面 | 可以替换或重排对局界面 | 只能加覆盖层，除非 mod 允许更多 |

mod 在它的 `rulesmd.ini` 的 `[VeraWasm]` 节中控制地图模块能做什么：

```ini
; rulesmd.ini in the mod
[VeraWasm]
Api=1.0              ; major.minor of the API the mod's modules need
Budget=200000        ; the mod module's base budget per frame, capped by the engine
MapBudget=50000      ; the base budget a map's module may use under this mod
MapWasm=yes          ; no: a map with modules cannot start under this mod
MapUI=overlay        ; overlay, full or no
```

代码注释说明：`Api` 是 mod 的模块需要的 API 主版本.次版本；`Budget` 是 mod 模块每帧的基础额度，引擎设上限；`MapBudget` 是在这个 mod 下地图模块可用的基础额度；`MapWasm=no` 时，带模块的地图在这个 mod 下不能开局；`MapUI` 取 overlay、full 或 no。

- 这些键放在 `rulesmd.ini` 里，因为 mod 摘要包含这个文件而不包含 `mod.ini`，所以房间里的每个玩家都会比对它们（第 11 节）。
- 每个 `[VeraWasm]` 节都从各自的文件读取，从不层叠：mod 的在任何其他层之前从 mod 的 `rulesmd.ini` 读取，地图的从地图读取。地图无法改变 mod 的键。地图自己的 `[VeraWasm]` 只放它的嵌入键、它的 `Api=` 和它的 `StorageId=`。
- 没有选择 mod 时，允许地图模块，地图界面只能是覆盖层，地图模块使用引擎的默认额度。
- 键名和取值只是占位（待定问题 4 和 7）。

**规则层**按以下顺序运行：`RULESMD.INI`、`LANGRULE.INI`、模式层、mod 模块的 `onRules`、地图层、地图模块的 `onRules`。每个 `onRules` 读到的是它之前各层处理后的规则，引擎在它写入之后再处理一次规则，和处理 INI 文本一样。类型 ID 一经分配就不再改变：后面的层可以新增类型并得到新的 ID，但从不让已有的 ID 失效。在 mod 的 `onRules` 中解析得到的 ID 在整个场景中都有效，存档和读档之后也一样。

**冲突规则：**

- **类型上的标签绑定**在 INI 中（`Wasm.Tags`）只从 mod 的 `rulesmd.ini` 读取。地图中的 `Wasm.Tags` 键被忽略，并在大厅中给出警告。地图在代码里绑定类型（`Trigger.bindType` 及其武器、弹头和抛射体形式，第 7 节），所以地图无法抹掉 mod 的绑定。
- **名字。** mod 的 INI 或触发器中的模块名（`Action=Wasm:name`、覆盖点绑定）解析到 mod 的模块；地图中的模块名解析到地图的模块。前缀 `Wasm:mod.name` 和 `Wasm:map.name` 可以指向另一方。模块代码中的 `Action.wasm` 按创建它的模块的来源以同样方式解析。INI 中的覆盖点绑定按来源分别读取，所以地图的绑定是在链上加入地图的一环，从不取代 mod 的。
- **消息。** 客户端消息（`sendMessage`）到达每个模拟模块的 `onMessage`，通知（`notify`）到达每个客户端模块的 `onNotify`。两者都携带发送它的模块的来源（mod 或地图）。
- **触发器**：两边的都会触发，mod 的模块先运行。
- **覆盖点**按链式处理：mod 的模块先算出结果，地图的模块拿到这个结果后可以再改，引擎使用最终值。链上的每一环都拿到原生值和上一环的结果（第一环拿到的上一环结果也是原生值）。后一环可以推翻前一环的否决。数值类覆盖点返回一个明确的“已处理”标志，而不是用特殊值表示；不处理这次查询的一环把上一环的结果原样传下去。
- **动作和任务**按执行顺序走同一个 owner。
- **对等调用**（后续阶段）：mod 可以公开一些函数，地图用 `callPeer("mod", name, bytes)` 调用。只有 mod 为此导出的函数才能被调用。

### 3. 加载与校验

加载时，引擎依次：

1. 解码嵌入的模块，校验声明的大小；
2. 解析模块，只接受来自 `vera:*` 接口的导入，且本版本支持其主版本并达到模块需要的次版本（第 12 节）；检查这些导入与模块所在 `[VeraWasm]` 节的 `Api=` 一致（大厅已经读过它）；拒绝超出加载时形状上限（函数数量、单个函数体大小、局部变量、导入）的模块，这样地图无法在编译时拖住大厅；检查每个 `vera.*` 自定义段以格式版本开头，且其中的名字是 ASCII；
3. 只接受白名单中的 Wasm 特性：MVP 核心，加上可变全局变量、符号扩展、不 trap 的浮点转整数、批量内存操作和多返回值。其他一切（SIMD、引用类型、垃圾回收、多内存、线程、64 位内存、异常、尾调用）都被拒绝，所以模块的全部状态就是内存、全局变量和一张函数表。带 `start` 段的模块被拒绝，所以实例化时不运行任何模块代码。浮点运算产生的 NaN 通过改写字节码（而不是引擎开关）规范化，这样每个引擎（包括浏览器的）得到相同的 NaN；
4. 在同一次插桩中加入运算计量和调用深度计数。深度上限远低于每个受支持引擎的真实栈上限，所以深度递归在每台机器上都停在同一次调用。模块从不被重入（第 5 节），所以模块调用之间的引擎栈帧保持有界。引擎在实例化模块时分配它的内存上限，所以上限以内的 `memory.grow` 从不失败；无法分配它的宿主在加载时让对局失败（对局错误，见下文）；
5. 检查生命周期需要的导出函数存在且签名正确，并检查 INI 中提到的每个模块动作（`Action=Wasm:name`）都在它所解析到的模块的 `vera.actions` 表中；
6. 把本局的模拟模块（mod 的和地图的合在一起）在各自 `vera.notify` 自定义段中声明的通知名放在一起检查哈希冲突（第 10 节）。同一模块内的冲突拒绝该模块；mod 的名字与地图的名字之间的冲突拒绝地图的模块。提示中给出两个名字。

**初始化函数。** SDK 把模块的顶层代码变成一个导出的初始化函数。引擎在模块的第一次其他调用之前调用它一次（导出了 `onRules` 时在 `onRules` 之前，否则在 `onScenarioStart` 之前；在客户端模块中，在 `onStart` 之前），读档后不再调用，因为模块内存已经恢复。在初始化函数中只有名字查找可用，包括 `Mark.id`，它们看到的是到此为止处理过的规则；其他宿主调用返回 `Unsupported`。初始化函数、`onRules` 和 `onScenarioStart` 各有自己的一次性额度，比一帧的额度大（待定问题 7）。

**失败。**

| 时机 | 结果 |
| --- | --- |
| 开局前 | 在大厅显示原因；带这个模块无法开局 |
| 在 `onRules` 中 | 不能开局，并提示是哪个模块：它正在写的规则不完整 |
| 对局中，包括 `onScenarioStart`（trap、超出额度或调用深度、参数非法） | 在所有机器的同一帧停用该模块；游戏告诉玩家是哪个模块停止了、原因是什么 |
| 宿主失败（分配内存上限时内存不足、Wasm 引擎的内部错误） | 对局错误，不算模块失败，因为无法证明它在每台机器的同一帧发生：对局停止并给出提示，和不同步时一样 |
| 在客户端模块中（超出每个渲染帧的额度、trap） | 该调用被停止，该模块只在这台机器上被停用，并提示该玩家 |

客户端额度用同一套计量按运算单位计算，而不是按时钟计算，所以在浏览器的主线程上也能执行。

**被停用的模拟模块。** 对局继续。

- 它创建的触发器被停用。在其他触发器中（地图触发器，或通过 `Wasm.Tags` 绑定的触发器），只跳过它的模块动作。它排队中的模块动作被丢弃。
- 它的覆盖点被跳过：由链中的下一环或原生结果生效，出错的那次调用也是如此。
- 它的模块弹道上的抛射体改为朝目标直线飞行。
- 它做过的事保留下来：它添加的持续效果和标记、它写入的规则和 `rules.set` 覆盖层、它创建的 AI 定义、标签和触发器（触发器处于停用状态），以及出错的那次调用已经做完的事。
- 它的内存保留在快照和状态哈希中，停在它停止时的样子，所以存档和重连能重现它。

**错误模型。** 属于正常游戏过程的错误只返回状态，模块继续运行：

| 状态 | 原因 |
| --- | --- |
| `Gone` | 句柄为 `NO_HANDLE` 或其对象已不存在 |
| `NotFound` | 名字或 ID 没有匹配任何东西，包括地图中没有的路径点 |
| `Refused` | 动作被引擎规则拒绝（比如该格不能建造），或原子动作的目标在其触发器执行时不适用（第 6b 节） |
| `Unsupported` | 本局关闭的功能（例如没有 Ares 时的 Ares 动作），或在不可用的地方发起的宿主调用 |

- 对 `NO_HANDLE` 或对象已不存在的句柄发起的调用什么也不做，包括不返回任何值的方法（例如界面节点的方法）。返回状态的调用返回 `Gone`，并把上一次调用的状态（`ctx.lastStatus()`，客户端模块中为 `ui.lastStatus()`）设为 `Gone`。它从不停用模块。
- 对返回句柄、ID 或数值的函数，`ctx.lastStatus()` 也给出上一次调用的状态。
- 由触发器执行的原子动作没有模块代码来接收它的状态：它的错误状态（`Refused`、`Gone` 或 `NotFound`）写入游戏内日志，该动作被跳过。除此之外什么也不发生。
- 表明模块本身有问题的错误会停用模块：参数非法（包括 `Trigger.create` 运行时发现的原子动作非法参数，第 6b 节）、trap、超出运算额度或调用深度。

### 4. 确定性

所有机器运行同一份模块字节，所以结果只取决于引擎如何执行它们。

- 只用白名单中的 Wasm 特性，NaN 规范化（通过改写字节码），并由插桩计数调用深度上限（第 3 节）。
- 不提供时钟、宿主随机源和 WASI。每个模块从自己专用的随机流取数，这条流由场景种子和模块的槽位（mod 或地图）派生，所以模块不会错开原生随机流：不取随机数的模块，原生结果完全不变。会执行原生代码的动作，按那段代码原本的方式从原生随机流取数。每个 API 都写明自己取几次随机数。
- 名字（类型 ID、节名）比较时不区分大小写，只按 ASCII 规则（`A` 到 `Z`），和 gamemd 读取 INI 的方式一致。字符串以 UTF-8 跨越边界。
- 运算额度由加载时插入的计量代码计算，不用引擎自带的 fuel，所以无论原生还是浏览器的引擎，都会数出相同的运算量，并在同一点停下。宿主调用按它们所做的工作计入同一份额度（按扫描或返回的每个对象、检查的每个格子），每类调用的费用写在接口定义中。
- 计量单位、每类宿主调用的费用、默认额度和各项上限按 API 主版本固定，所以在这些限制内运行过的模块在之后的每个版本中都能继续运行。
- 位置、速度等游戏数值以整数（lepton、定点数原始值）跨越边界。小数和倍率使用模拟的定点格式，即 `I16F16` 原始值（`SimFixed`）。模块内部可以使用浮点。
- 模块内存、可变全局变量、模块的表（按其中保存的函数下标存档）、插桩的计数器（已用运算量、调用深度）以及模块的随机流都属于模拟状态：存进快照，计入状态哈希（第 15 节）。存档只在两次模块调用之间进行。
- 对模拟模块的调用从不来自并行或批量代码，跨对象的调用顺序也不取决于引擎的循环顺序（第 5 节）。

### 5. 执行模型

**模拟模块的导出。** 每次模拟调用还会收到 `ctx`，每次客户端调用还会收到 `ui`（签名见附录第 1 节）。

| 导出 | 时机 |
| --- | --- |
| 初始化函数 | 由 SDK 从顶层代码生成；在模块的第一次其他调用之前运行一次，读档后不再运行（第 3 节） |
| `onRules(rules)` | 在模块所处的规则层位置运行一次（第 2 节）；可以修改和新增类型 |
| `onScenarioStart(ctx)` | 场景开始时运行一次 |
| `onFrame(ctx)` | 导出时每帧一次；SDK 在 `frame % N == 0` 的帧按注册顺序运行每个注册的函数 |
| 模块动作 | 通过 SDK 注册，不是 Wasm 导出函数（第 12 节）；其触发器触发时排队，在模块阶段由 `onEvents` 运行 |
| `onEvents(ctx, batch)` | 由 SDK 生成；在模块阶段，每个有排队模块动作的模块调用一次，在 `onMessage` 之后、`onFrame` 之前 |
| 覆盖点 | 引擎走到该决策时，在帧内固定的步骤调用，顺序见下文 |
| `onMessage(ctx, sender, source, data)` | 在模块阶段，客户端消息已到达模拟时；`source` 是发送它的客户端模块的来源（第 2 节） |

客户端模块的导出：`onStart(ui)`；`onRender(ui, dt, alpha)`，每个渲染帧一次；`onNotify(ui, source, id, data)`；以及点击、热键等界面回调。

**模块代码在哪里运行。** 只在模拟的阶段内运行。本地代码（侧边栏、光标、界面、渲染、客户端查询）从不调用模拟模块；它们读取模拟最近一次算出的结果，就像侧边栏显示缓存的 `Override.ProductionAllowed` 那样。

**模块阶段。** 模拟帧里一个固定的阶段（待定问题 8），按模块加载顺序逐个模块执行（先 mod 的，再地图的）。先触发被推迟的连锁触发器（见下文）；然后每个模块依次收到它的 `onMessage` 调用、它的 `onEvents` 批次和 `onFrame`。

**投递。** 触发器触发时，它的每个模块动作向所属模块的队列写入一条固定大小的记录，带着触发该触发器的那个事件的载荷。队列在模块阶段作为一批到达模块。模块只能通过这种方式收到事件：没有单独的事件记录。

- 如果游戏已经结束，或者触发器在模块阶段之前已被禁用或删除，排队中的模块动作会被丢弃。
- 投递前已经死亡的对象，其句柄读出来是“不存在”，绝不会指向另一个对象。
- 绑定的触发器的主体在事件引发时已经不存在时（例如绑定到武器的 `Detonated`，开火者已经死亡），记录保留主体的句柄，读出来是“不存在”。触发器的所属方是主体最后的所属方（对抛射体事件，是发射它的所属方），实例是那个已不存在的主体的实例。

**顺序。** 跨对象时，覆盖调用、批量段结束后触发的触发器以及一批中的记录都按主体的创建序号排列，从不按引擎的循环顺序，所以调整引擎循环的顺序或改成并行不会改变它。在同一个对象内，调用按引擎引发它们的顺序进行，这个顺序在不同引擎版本之间可能改变。主体为 `NO_HANDLE` 的记录（所属方和逻辑触发器，以及事件没有主体的格子触发器）排在最前，按触发器运行时触发它们的顺序排列。

**批量段和并行段。** 对模块的调用从不在并行或批量代码中发出。批量或并行的引擎段（例如伤害提交或并行的索敌扫描）算作一次计算。在其中引发的 VERA 事件被收集起来，它们的触发器在该段结束后立即触发，仍在同一帧、在下一个阶段之前。在其中走到的覆盖点按批处理：引擎收集该段的所有查询，对每个模块用全部查询调用一次，再应用结果。

**不重入。** 某个模块的调用还在栈上时，引擎从不再次调用这个模块：从这次调用到达的计算中，它的覆盖点被跳过（使用上一环的值或原生值）。它发出的动作所引发的事件照常触发其触发器，其中的模块动作照常排队。可以调用其他模块：mod 模块的直接动作可以到达地图模块的覆盖点。

**动作时机。**

- 原版动作和原子动作（第 6b 节）在触发器触发时执行，与原版中的原版动作一样，含有模块动作的触发器也是如此。只有模块动作排队：动作为 [原版 A、模块 B、原子 C] 的触发器，先执行 A 和 C，B 在同一帧稍后执行。需要严格顺序的作者，把触发器的全部动作都写成模块代码，再通过 API（L1）调用原版动作。
- 从模块代码中直接调用的动作立即执行。
- 在模块阶段中触发的触发器，其原版动作和原子动作立即执行；其模块动作排到下一帧的模块阶段，因此模块代码不会在一帧之内循环。

**安全点。** VERA 新增的每个事件都在安全点引发：一次计算完成之后（`TakeDamage` 在伤害已经提交之后），一次计算开始之前（`HouseTransfer` 在转移之前），或批量段、并行段刚结束时。触发器的原版动作和原子动作从这一点起立即执行。在计算之前引发的事件之后，引擎重新检查这次计算：

- `HouseTransfer` 之后，如果某个动作已经移除了对象或改变了它的所属方，转移就不发生，也不引发 `HouseTransferred`；
- `FatalDamage` 在致命伤害提交之后、死亡流程之前引发；只有对象仍然存在且伤害仍然致命时（某个动作可能治疗了它，或添加了阻止死亡的效果），才执行死亡流程。

投递型事件报告的是已经发生的事：模块动作无法取消原生结果（比如死亡）。要做到这一点，需要用覆盖点、持续效果（阻止死亡），或在计算之前引发的事件（`FatalDamage`、`HouseTransfer`）上的原版动作或原子动作。

**连锁。** 立即执行的动作可以在一帧之内连锁：伤害引发 `TakeDamage`，它的触发器用原子动作造成伤害，又引发 `TakeDamage`。

- 连锁中含有模块触发器、VERA 新增的事件或原子动作时，引擎限制它每帧的深度，并且限制每帧这类连锁触发的总次数（否则一个触发另外两个的触发器会触发 2^depth 次）。具体上限是待定问题 17。
- 会超过任一上限的触发器被推迟：它在下一帧模块阶段开始时、排队的动作之前触发，带着它原有的载荷。它的原版动作和原子动作在那时执行，它的模块动作加入那一帧的批次。如果它在此期间被禁用或删除，就被丢弃；它的约束条件重新检查，它的所属方是主体在那一刻的所属方，作用于已不存在的主体的动作得到 `Gone`。等待中的推迟触发器存档并计入哈希。
- 只由原版事件和原版动作组成的连锁从不推迟，与原版中完全一样地运行（目标 5）。

**覆盖点**返回结果，不能执行动作：引擎正处在一次计算的中途。它们可以读状态，在模块内存中保存自己的状态，从模块的随机流取数；上述调用顺序让这一切是确定的。高频事件（伤害、开火、抛射体引爆、碾压、移动失败）和所有覆盖点只对绑定的类型触发（第 6a 节）；没有“订阅所有对象”的用法。

**存档。** 读档后，模块内存随快照恢复。初始化函数和 `onScenarioStart` 都不会再次运行，也没有 `onLoad`。模块内存里的句柄仍指向同样的对象，因为句柄是创建序号，不是存储位置。

**额度。** 每个模块每帧有运算额度：一个基础额度，加上本帧投递给它的每条记录各一份额度，所以一个绑定在更大的战斗中产生更多记录时，也得到更多额度。

- 宿主调用按它们所做的工作扣除（第 4 节）。覆盖调用从同一份额度中扣除，每次调用增加一条记录的额度。额度用完后，该模块的覆盖点在本帧余下的时间里被跳过，模块在本帧结束时被停用。
- 每个模块的队列每帧最多容纳固定数量的记录。超出上限的记录按顺序保留，存档并计入哈希，在下一帧最先投递，所以短时间的爆发只会让模块变慢，而不会让它被停用。积压超过固定帧数的记录量的模块会被停用并给出提示：它跟不上。
- 基础额度、每条记录的额度、队列上限和积压上限是待定问题 7。
- 一个模块既不导出 `onFrame`，也不绑定触发器，那它每帧的开销为零。

### 5a. 语言与 SDK

引擎和模块之间的约定只有 Wasm 接口。任何语言，只要它的编译器产出的模块能通过加载检查，就能使用，引擎对所有模块一视同仁。

- **官方 SDK：TypeScript 和 Rust。** 两者都由同一份接口定义（第 12 节）生成，提供相同的函数（名称按各自语言的命名习惯），并随 API 一起发布版本。每套都附带模板、构建命令、监视模式和示例。
- **TypeScript SDK。** 预先把 TypeScript 编译成 Wasm，模块足够小，可以嵌入地图。编译器是待定问题 2。它的 API 限定在 TypeScript 与 AssemblyScript 的共同子集内：
  - 不用 `any`，除 `T | null` 外不用联合类型，回调不捕获外部变量，不用 `try`/`catch`；
  - 把多个值组合在一起的参数是用构造函数创建的类（`new TriggerDef(...)`），而不是对象形状或字面量；
  - 句柄是普通整数，没有方法：对句柄的调用是以句柄为第一个参数的命名空间函数（`Techno.healthPercent(t)`、`Techno.setMission(t, Mission.Hunt)`）；
  - 每个句柄值（一个创建序号）都保持小于 2^53，所以基于 JavaScript 引擎的 SDK 可以用 number 保存它；
  - 顶层代码成为初始化函数（第 3 节）。

  这样同一份源码既能用 `tsc` 做类型检查，也能用 AssemblyScript 编译，本 RFC 中的示例在两者中都有效。
- **Rust SDK。** 面向想要完全控制和更高性能的作者；引擎自己的兼容性测试用例也用它编写。它可以在句柄的 newtype 上保留方法（`techno.health_percent()`）。
- **其他语言**（C、C++、Zig、Go……）使用公开的接口定义及其到 core module ABI 的映射（第 12 节），绑定由社区维护。
- **导入。** 模块只能导入 `vera:*` 接口。引擎不提供 WASI，项目也不发布 WASI 垫片。运行时依赖 WASI（时钟、随机数、文件）的语言，只有在它自己的工具链去掉这些导入时才能使用。
- **体积和特性。** 以 Wasm 垃圾回收或其他被拒绝的特性（第 3 节）为目标的编译器，比如某些 Kotlin、Dart 和 Java 工具链，产出的模块无法通过加载检查。会把大型运行时或垃圾回收器打包进每个模块的语言，产出的文件更大，可能超过地图嵌入上限。这是作者工具链的取舍，与引擎无关。

### 6. API 分层

| 层 | 内容 | 首个 API 版本 |
| --- | --- | --- |
| L1 动作和任务 | 所有原版触发器动作、任务、生产、所属方和对象命令 | 包含 |
| L2 触发器 | 原版事件加新事件（武器开火、抛射体引爆……），投递给动作 | 包含 |
| L3 覆盖点 | 具名决策：选择目标、伤害、是否允许生产、接管武器的一次射击…… | 从 modder 需求中选两三个（待定问题 10） |
| L4 逐帧行为 | 对绑定类型的对象进行批量逐帧控制 | 不包含，以后再做 |

- 查询是只读的，遍历顺序确定（第 6c 节）。
- 每个 L1 动作调用引擎中该动作现有的实现；模块不会得到第二份实现。
- 覆盖点以游戏概念命名（`Override.Damage`、`Override.TargetChoice`），从不以原生函数命名，这样引擎重构后它们依然成立。`Override.Fire` 让模块接管武器的一次射击（第 9 节）。`Override.CommandAllowed` 和 `Override.Death` 是另外两个候选。
- 对于非常频繁的决策，优先用数据而不是回调：目标优先级用持续效果携带的倍率表示，再配合 `TargetChanged` 事件。逐次调用的覆盖点留给不那么频繁的决策。
- L4 每帧对每种行为类型调用一次模块，把该类型的全部对象一起交给它，从不按单个对象调用。

**粒度。** 一个 API 函数对应一个游戏操作，这个操作在引擎里有且只有一个 owner：发射武器、添加持续效果、设置任务、修改生命、创建对象。更大的行为（比如一次空袭、一条心灵控制链）由作者用这些函数组合。

**坐标**可以作为任何操作的参数：目标、生成点、传送目的地。例如模块可以往任意格子扔核弹。不开放的是绕过 owner 的步骤，比如直接写已有对象的位置字段或内部字段。对象的位置关联着格子占用、碰撞、视野、所在地图层以及乘客关系，只有引擎自己的流程能保持它们一致，所以对象只能通过传送、运动效果或移动任务改变位置。抛射体是第 9 节第 4 层的例外：它们不占格子，引擎会钳制其位置，碰撞判定照常进行。

### 6a. 触发器：事件、约束条件和动作

一个触发器有一个或多个事件（必须全部成立）、任意个约束条件、一个或多个动作，以及原版的一种重复类型。

- **投递型事件**发生在某个时刻（受到伤害、武器开火、被摧毁）。触发器在那一刻触发；其中的原版动作和原子动作立即执行，模块动作则带着事件的载荷排队（第 5 节）。VERA 新增的投递型事件在安全点引发（第 5 节）。
- **轮询型事件**描述一种状态（生命低于某值、金钱高于某值）。引擎按触发器设定的间隔原生检查它们，这个间隔有下限（待定问题 7），事件在边沿触发：在状态变为成立的那次检查时触发，之后要等到某次检查时状态不成立，才会再次触发。对象在 `frame % interval == serial % interval` 的帧接受检查，`serial` 是它的创建序号；所属方的轮询改用所属方在所属方数组中的下标。投递型的 `Timer` 事件不错开：它从其触发器创建的那一帧算起，每个周期触发一次。
- **约束条件**在任何模块代码运行之前过滤触发器。引擎原生检查，全部满足时才调用模块。条件可以取反。更复杂的逻辑（条件之间的“或”、两个对象之间的比较、计数）写在模块代码里。
- **动作**可以是原版触发器动作、原子动作（第 6b 节）或模块函数。模块函数是模块收到事件的唯一途径。
- 每个事件都标明它所附着的对象（主体），以及涉及的另一个对象（如果有的话：攻击者、目标、载具、生产者）。约束条件可以判断其中任意一个。
- 载荷的值都是整数或句柄。伤害和原版一样是整数；模拟 API 中没有浮点值。
- 事件只对绑定的对象触发：类型绑定了该触发器的对象（`Wasm.Tags`）、自身标签包含该触发器的对象；对于武器事件（携带抛射体句柄的 `Fire`、`HitTarget` 和 `Detonated`），还包括使用绑定了该触发器的武器、弹头或抛射体类型的任何对象。武器绑定对使用这把武器的所有射手生效，不论射手是什么类型，射手就是主体：

  ```ini
  [RedEye2]                   ; a weapon
  Wasm.Tags=MissileFiredTag   ; every shooter of RedEye2 raises its Fire triggers
  ```

  代码注释说明：`[RedEye2]` 是一把武器；所有使用 RedEye2 的射手开火时都会触发其 Fire 触发器。

- 绑定到某个类型的触发器在每个绑定对象上以各自的实例运行（第 7 节）。

```ts
// TypeScript (AssemblyScript-compatible)
const PANICKED = Mark.id("Panicked");   // top level: runs once, in the SDK's init function (section 3); calls take the ID

onScenarioStart((ctx: Ctx): void => {
  const def = new TriggerDef([new EventDef(Event.TakeDamage)], [Action.wasm("giPanic")]);
  def.conditions = [Cond.healthBelowPercent(30), Cond.not(Cond.hasMark(PANICKED))];
  Trigger.bindType(Trigger.create(def), ctx.typeId("E1"));   // every E1 runs its own instance (section 7)
});
```

代码注释说明：顶层代码在 SDK 的初始化函数中只运行一次（第 3 节），之后的调用都传 ID；`Trigger.bindType` 让每个 E1 运行自己的实例（第 7 节）。

版本 1 的候选连同各自的载荷列在附录中：投递型事件见 [2.3](0001-wasm-extension-modules-api.zh-CN.md#23-新的投递型事件)（`TakeDamage`、`HitByWarhead`、`AttackedBy`、`FatalDamage`、`Killed`、`Fire`、`SpawnFire`、`HitTarget`、`Detonated`、`TargetChanged`、`ProjectileIncoming`、`Birth`、`TransportEntered`、`TransportExited`、`PassengerAdded`、`PassengerRemoved`、`Crushed`、`HouseTransfer`、`HouseTransferred`、`EffectStart`、`EffectStacks`、`EffectExpire`、`Timer`、`SuperWeaponLaunched`），轮询型事件见 [2.4](0001-wasm-extension-modules-api.zh-CN.md#24-新的轮询型事件)（生命、弹药、乘客数、运载空间、载矿量、任务、是否移动、地形类型、所属方金钱、所属方电力、效果层数、距离），约束条件见 [3](0001-wasm-extension-modules-api.zh-CN.md#3-约束条件)。哪些进入版本 1 是待定问题 12。

**不进入引擎的：** INI 里的记录器、算子和表达式键。历史数据（比如某个攻击者累计造成的伤害）由模块在自己的内存里记录，并随模块一起存档和计入哈希。INI 保持为数据，不变成一门编程语言。

### 6b. 原子动作与持续效果

**原子动作**是瞬时的游戏操作，每个都有一个 owner：发射武器、发射超级武器、造成伤害、摧毁、移除、创建对象、传送、引爆弹头、让某个所属方结束游戏，等等（[附录 4.3](0001-wasm-extension-modules-api.zh-CN.md#43-原子动作)）。造成伤害走弹头和护甲规则，带来源，用于击杀归属和经验；直接设定生命值不计归属。传送到被占的格子时按规定的规则处理：选附近的格子，或动作失败。

在触发器中，原子动作写作 `Action.atomic(kind, target, params)`，与 `Action.original` 和 `Action.wasm` 并列。

- 它只用于参数放得下的动作：一个目标、一个 ID、至多两个整数、一个格子和一个所属方（`AtomicParams`）。`Log` 是唯一的例外：它另外带它要写的那行文字。需要更多参数的动作（例如生成抛射体）写成模块动作。
- 目标是一个明确的参数（`ActionTarget`）：
  - `Subject`（默认）：事件的主体；
  - `Other`：事件中的另一方对象；
  - `TagHolder`：标签中持有该触发器的对象，CellTag 则是那个格子；对于绑定到类型或武器、弹头、抛射体类型的触发器，是引发事件的对象；
  - `Projectile`：事件中的抛射体；
  - `House`：`params.house` 中的所属方，它为 `NO_HANDLE` 时为触发器的所属方；
  - `Cell`：`params.cell` 中的格子。
- 不用目标的动作（例如 `SetTechLevel` 或 `Log`）忽略目标。
- 路径点以带有其编号的格子给出：`Cell.waypoint(n)`。`Trigger.create` 把它解析为路径点所在的格子，因为路径点不会移动。地图上没有的路径点是地图数据错误，不是模块错误：`Trigger.create` 返回 `NO_HANDLE` 并设置 `NotFound`，不创建触发器并写入日志，模块保持启用。写在 INI 中时，它在加载时于大厅中报告。

参数表达不了的部分由固定规则决定：

- 明确的所属方（`House` 目标、`SetOwner` 的新所属方、所创建对象的所属方）取 `params.house`；它为 `NO_HANDLE` 时，使用触发器的所属方，对于绑定的触发器，它是主体在那一刻的所属方。
- 来源（伤害、击杀或引爆的来源：`Kill`、`Damage`、`DetonateWeapon`、`DetonateWarhead`）是事件中的另一方对象，并且是可选的：没有来源时，动作在没有来源的情况下执行，不计击杀归属。
- 动作施加作用的第二个对象（乘客）是事件中的另一方对象。事件没有另一方对象，或者 `FireWeapon` 没有可瞄准的格子、另一方对象或当前目标时，动作得到 `Gone` 并被跳过。
- 对象目标的格子是对象所在的格子；`Projectile` 目标的格子是抛射体下方的格子。坐标取该格子的中心；`Projectile` 目标例外，其坐标为抛射体的中心。
- 每种动作用到的目标和字段，以及各动作自己的规则（例如 `FireWeapon` 的瞄准），见[附录 4.1](0001-wasm-extension-modules-api.zh-CN.md#41-动作的用法)。到每个函数参数的对应关系属于接口定义（第 12 节）。

检查：

- `Trigger.create` 检查每个 `Action.atomic` 的参数。非法的参数会停用模块（第 3 节）：永远不适用于该动作的目标种类（例如 `Kill` 的目标是 `Cell`），或缺少必需的字段（`LaunchSuperWeapon` 的格子）。
- 写在 INI 中的原子动作在加载时检查，并在大厅中报告。它们的 INI 写法是待定问题 4。
- 触发器执行时才发现目标不适用（例如 `Kill` 的 `TagHolder` 是一个格子），属于数据错误：动作得到 `Refused`，状态写入日志，动作被跳过，模块保持启用。
- 原子动作立即执行，并可能引发新的事件，所以它们可以在一帧之内连锁，受第 5 节的上限约束。

**持续效果**是对象身上带持续时间的状态（候选见[附录 5.4](0001-wasm-extension-modules-api.zh-CN.md#54-效果种类)）。

- 每种效果类型声明自己的叠加方式：叠加到上限、新的替换旧的，或拒绝新的（待定问题 13）。
- 不能同时生效的效果（变形、超时空移动、运动）组成一个互斥组，由 owner 保证同一时间只有一个生效。
- 效果的属性凡是 Phobos AttachEffect 已有键的都沿用：持续时间、延迟、间隔、重新附加前的冷却、最大触发次数、来源、变形或创建时是否继承、是否无视铁幕。新增属性使用同一个读取器。
- 运动由引擎叠加到对象的移动上，从不以坐标形式写入。
- 显示在对象上方的文字、数值或按钮属于客户端显示属性（第 10 节），不是效果。

**标记。** 一个对象可以携带任意多个标记，所属方也可以。

- 动作和效果负责添加和移除，约束条件负责判断。标记不能嵌套。
- 一个标记带一个整数值和一个可见度等级：仅本所属方、盟友、能看到该对象的玩家，或所有人。两者都在添加标记时给出（`addMark(t, mark, value, visibility)`）；再次添加时仍只有一个标记，两者都被重新设置。`markValue` 读取值，`setMarkValue` 修改值。
- 客户端查询只返回本玩家有权看到的标记。
- 标记名只由模拟代码注册（`Mark.id`）。注册表属于模拟状态，存档并计入哈希；客户端模块只能查找名字。标记名不算隐藏信息：客户端可以知道某个名字已被注册，但永远不会知道哪些对象或所属方携带它无权看到的标记，所以作者不应把秘密放在标记名里。

### 6c. 查询

- 查询是只读的。
- 结果按创建序号排序，这个规则不依赖引擎如何存放对象；结果写入模块提供的缓冲区（第 15 节）。有三个列表保持自己的顺序：对象的持续效果按添加顺序，它的标记按加上的顺序，所属方按所属方数组的顺序。
- 在客户端模块中，查询只暴露本玩家自己的界面能显示的内容（第 10 节）。

可以查询的内容（完整列表见[附录第 7 节](0001-wasm-extension-modules-api.zh-CN.md#7-查询)）：

- **对象：** 按格子、半径或矩形区域，按类型、所属方或类别查找；对象的类型、所属方、生命、位置、任务、目标、等级、弹药、乘客、持续效果和标记。
- **所属方：** 金钱、发电量和耗电量、拥有的建筑和已满足的前提条件、科技等级、盟友和敌人、阵营、是否已战败。
- **地图：** 尺寸；格子的地形类型、高度、覆盖物和矿石、对某种移动区域是否可通行、某个所属方能否看到；路径点和 CellTag。
- **规则：** 任意类型的任意键，以解析后的值返回。
- **场景：** 帧号、难度、游戏模式、玩家数。
- **探测**（版本 1 候选，待定问题 12）：某武器现在能否向某目标开火、目标是否在射程内、某类型能否由某所属方建在某格，以及最近的可放置格子。它们复用引擎自己的规则。

### 6d. AI

电脑所属方保留它们的 AI。版本 1 允许模块创建特遣部队和小队类型（`[TaskForces]`、`[TeamTypes]`）、指派 AI 小队脚本（`[ScriptTypes]`）、启动和解散小队，以及启用或禁用 AI 触发器（`[AITriggerTypes]`），全部通过引擎现有的 AI owner 完成。让 AI 学会使用 mod 新增的机制，留给后续 RFC。

### 7. 运行时的触发器和标签

模块按地图的同一模型创建触发器和标签：

```ts
// TypeScript (AssemblyScript-compatible), inside an action (ctx, e):
const def = new TriggerDef([new EventDef(Event.Killed)], [Action.wasm("onConvoyLost")]);
def.house = ctx.house("Americans");
const t = Trigger.create(def);
const tag = Tag.create([t], TagRepeat.Repeating);
Techno.setTag(e.subject, tag);   // replaces the object's tag, as in the original
const cell = new Cell(40, 52);
cell.setTag(tag);                // CellTag; Cell is a class, not a handle
Trigger.disable(t);

const panic = Trigger.create(new TriggerDef([new EventDef(Event.TakeDamage)], [Action.wasm("giPanic")]));
Trigger.bindType(panic, ctx.typeId("E1"));   // as Wasm.Tags=: every E1 runs its own instance
```

代码注释说明：这段代码写在一个动作 `(ctx, e)` 内部；`Techno.setTag` 和原版一样替换对象原有的标签；`cell.setTag` 设置 CellTag，`Cell` 是类，不是句柄；`Trigger.bindType` 和 `Wasm.Tags=` 一样，让每个 E1 运行自己的实例。

- 新建的触发器和标签放进现有触发器运行时的列表，和地图里的放在一起，不另存一份。
- 它们使用确定性的编号，不会和地图里的编号冲突，并随触发器运行时一起存档和计入哈希。
- 一个对象只有一个标签，一个标签可以连接多个触发器。让一个对象挂多个标签属于 VERA 扩展，需要单独的 RFC。
- 类型绑定（INI 中的 `Wasm.Tags`、代码中的 `Trigger.bindType`，以及用于武器事件的 `Trigger.bindWeaponType`、`bindWarheadType` 和 `bindProjectileType`）不占用这个槽位，而是作为独立的订阅另外记录。所以地图上预先放置、自带标签的对象保留它的标签，同时也接收所属类型的触发器。代码中的绑定立即作用于该类型的每个对象，mod 和地图的模块都可以使用。
- 得到一个标签（`Techno.setTag`）、而该标签含有模块触发器或 VERA 新增事件上的触发器的对象，会得到它自己的一个标志位，所以即使它的类型没有绑定任何东西，事件触发点也会为它引发这些事件（第 15 节）。
- 每个绑定对象以各自的实例运行绑定的触发器，重复状态按对象分开：一次性触发器对每个对象各触发一次。禁用或删除触发器会作用于所有实例。触发器的所属方是它触发那一刻主体的所属方，标签持有者是引发事件的对象。
- 删除对象或标签时，通过触发器运行时现有的清理逻辑解除关联。
- 新的事件和动作编号分配在不与 Ares、Phobos 冲突的范围内（待定问题 5）。

### 8. 修改规则

| 时机 | 能改什么 | 方式 |
| --- | --- | --- |
| `onRules` | 任意键；新增类型 | 走原生 INI 读取器、钳制和读后处理；计入大厅哈希 |
| 对局中，按类型 | 公开白名单里的键（待定问题 11） | `rules.set("E1", "Speed", "6")`：值像 INI 文本一样解析，从下一帧起生效，让相关缓存失效，并作为规则覆盖层存档 |
| 对局中，按对象 | 倍率、等级、所属方、换类型、生命值 | 通过现有的单对象 owner，包括持续效果（第 6b 节） |

- 每个白名单键都要写明修改它对地图上已有对象的影响（例如新的 `Strength` 下当前生命值如何变化）。
- 对局中不能新增类型。
- 启用 Ares 或 Phobos 时，模块能在规则中看到它们的键。白名单逐个写明这些扩展键能否在对局中修改。
- 只要模块功能开启（第 14 节），持续效果的 owner 就可用，不论 Phobos 是否开启。Phobos AttachEffect 的 INI 键（类型、武器和弹头上的 `AttachEffect.*`，以及 `[AttachEffectTypes]`）只在 Phobos 开关打开时读取，所以原版玩法保持原样。模块定义的效果类型在 `onRules` 中创建（`rules.defineEffectType`），使用同一个读取器，不需要这些键。只有 VERA 才有的效果种类也以同样方式开启。

### 9. 示例：抛射体弹道

四个层级都在 `rules.wasm` 中运行，因为它们决定打中什么。`ui.wasm` 可以加纯视觉效果，比如拖尾和光效。

| 层级 | 机制 | 开销 |
| --- | --- | --- |
| 1 | `onRules` 设置现有键（`Arcing`、`ROT`、`Vertical`，启用 Phobos 时还有 Phobos 的 `Trajectory`） | 对局中无开销 |
| 2 | 武器开火、抛射体引爆的触发器：额外的抛射体、分裂、连锁 | 每次事件，仅限绑定的类型 |
| 3 | `onLaunch` 返回一条路径（贝塞尔、抛物线、螺旋、路径点）；引擎用定点数沿路径推进抛射体 | 每个抛射体一次调用 |
| 4 | `onTrajectoryFrame(type, bullets)` 修改速度或位置，或请求引爆，一次处理该类型的全部抛射体 | 每帧每类型一次调用 |

- 引擎在原生飞行路径旁边新增一条模块路径。碰撞、引爆判定、伤害和弹头仍由引擎中各自的 owner 处理。
- 引擎会钳制模块的输出：速度和位置有上限，离开地图就引爆或删除抛射体。
- 每个抛射体有 16 字节的模块数据，存档并计入哈希。

**齐射。** 要一次发出多枚不同弹道的抛射体，就在武器的 `Fire` 事件上挂一个模块动作来生成它们，每枚有自己的类型和模块数据，再由 `onLaunch` 分别给出路径。这个动作从它的事件记录中读出射手、目标和原生抛射体（`e.subject`、`e.other`、`e.projectile`）。原生抛射体在单位更新时射出，模块生成的抛射体在模块阶段射出，所以它们比原生抛射体晚至多一帧的位移，取决于模块阶段放在哪里（待定问题 8）。

**`Override.Fire`** 避免这段延迟。它返回一份射击方案：要生成的抛射体的列表，每枚带自己的类型、模块数据和参数。

- 引擎在原生射击本应射出的那一刻立即生成它们，不生成原生抛射体。空方案什么也不发射；“未处理”则保留原生射击。
- 这次射击的其他所有原生效果照常发生：射速计时器、弹药消耗和装填、连发计数、开火音效、枪口动画、后坐，以及开火时解除隐形或暴露。
- 方案中的抛射体像原生抛射体一样引发 `ProjectileIncoming` 和目标的 `AttackedBy`。`Fire` 事件仍然引发，其 `projectile` 为 `NO_HANDLE`。
- mod 和地图的模块都绑定了这次射击时，地图的一环收到 mod 的方案，可以保留、修改或替换它。
- 开火步骤是批量段时，抛射体在该段结束时生成（第 5 节）。

### 10. 客户端模块

**界面树。** 界面树由引擎持有，引擎负责布局和绘制。模块通过一小组操作修改它：新建和删除节点、设置属性（显示文字、图像、位置、可见性）、按名字查找节点，以及接收点击、悬停和热键。修改按渲染帧批量提交，不会每帧重建整棵树。不暴露图形 API。

作者分两部分编写界面：

- **静态布局写在 INI 里**，语法和键与 `veraui.ini` 相同（`Type`、`Hold`、`X`、`Y`、`Width`、`Height`、`Parts`、`Label`）。本 RFC 新增 `List` 部件类型，以及 `Text` 部件的 `Label` 键。引擎在对局开始时读取，不需要预编译。没有动态部分的界面不需要模块。mod 和地图把布局节放在哪里是待定问题 14。
- **动态部分写在模块代码里**：按名字找到节点后修改，或新建节点。

```ini
[Mission.Field]
Parts=Messages,Timers,Banner,Powers,Clock,Objectives

[Mission.Objectives]
Type=Column
Hold=TopRight
Width=240
Parts=ObjTitle,ObjList

[Mission.ObjTitle]
Type=Text
Label=TXT_OBJECTIVES    ; new for Text: a string-table line, follows the game language

[Mission.ObjList]
Type=List               ; new part type
```

代码注释说明：`Label=TXT_OBJECTIVES` 是 `Text` 新增的键，取字符串表中的一行，跟随游戏语言；`Type=List` 是新增的部件类型。

```ts
// TypeScript (AssemblyScript-compatible)
onStart((ui: Ui): void => {
  Node.setItems(ui.find("ObjList"), ["TXT_OBJ_RADAR", "TXT_OBJ_CONVOY"]);
  ui.create(new Column(Hold.BottomLeft, [new Text("TXT_WAVE")]));
});
```

React 或 JSX 风格的库可以放在 SDK 里：它在模块内部计算差异，再发出同样的操作，引擎完全不知道它的存在。这类库只能用于 TypeScript（AssemblyScript 没有闭包），不属于官方 API。

**其他客户端功能：**

- 单个对象的显示属性：图像、调色板、着色、附加动画、可见性，以及显示在它上方的文字、数值或按钮。它们只影响本机的画面；会影响玩法的属性（如隐身）属于模拟模块。
- 选中单位和点击按钮属于客户端事件。要改变游戏，模块发送一条消息（`sendMessage`），由模拟模块在 `onMessage` 中处理，这样联机和回放都保持一致。
- 客户端模块可以发出标准玩家指令（选择、移动、攻击、部署、建造），引擎像校验任何玩家输入一样校验它们。`sendMessage` 用于自定义逻辑。
- 图像、动画和模型都按名字引用，从不按文件格式引用，所以以后新增素材格式（单独的 RFC）不需要修改 API。
- 声音和消息；`log()` 输出到游戏内控制台。
- 玩家自装的界面模块放到后续阶段。mod 或房间可以禁止它们。

**存储。** 每个 mod 和每张地图在玩家本机各有一个自己的小型键值存储，带容量配额，用于战役进度、成就和设置。

- mod 的存储以它的 `[Mod] Name` 为键；地图的存储以它的存储 ID（`[VeraWasm] StorageId=`，默认为地图的文件名）为键，所以修改过的地图只要 ID 不变就保留它的存储。
- 地图的客户端模块使用地图的存储，在 mod 下也是如此，所以下载来的地图无法读取或修改 mod 的数据。
- 只有客户端模块能使用存储。需要影响对局的数据通过 `sendMessage` 送进模拟，因而成为命令流的一部分。

**通知**从模拟模块发往客户端。

- 名字只解析一次，换成 ID：`Notify.id("WaveStarted")` 返回一个 `NotifyId`，即名字按 ASCII 统一大小写（只折叠 `A` 到 `Z`）后的 UTF-8 字节的 32 位 FNV-1a 哈希，在每台机器上、在两侧都相同。
- 模拟模块要声明它发送的通知名：SDK 构建时按模块项目配置中的列表（属于 SDK 文档，不属于引擎 API），把这些名字写进 Wasm 自定义段 `vera.notify`。客户端模块不声明任何名字；已声明但没有任何客户端模块接收的名字不算错误。
- 对模拟模块没有声明的名字，以及在客户端模块中对本局没有任何模拟模块声明过的名字，`Notify.id` 返回 `NO_ID` 并设置 `NotFound`：引擎保存着已声明名字的表，所以客户端从不会靠哈希匹配到未声明的名字。加载时的冲突检查（第 3 节第 6 步）保证每个已声明的名字都有 ID。
- `ctx.notify(house, id, data)` 发给某个玩家的客户端，`ctx.notifySpectators(id, data)` 发给每个观战者的客户端。那里的每个客户端模块都在 `onNotify(ui, source, id, data)` 中接收，并得到发送它的模块的来源。回放观看者收到他所观看视角的玩家的通知，或观战者的通知。
- 观战者客户端的 `sendMessage` 会被拒绝。

**客户端查询**只暴露本玩家自己的界面能显示的内容；其他任何东西都通过通知送达客户端。

- 本玩家自己的所属方和对象：一切。
- 其他所属方，包括盟友：只有公开信息（名字、国家、阵营、同盟关系、是否已战败、是否为人类玩家），没有金钱、电力、建筑、生产、科技等级、超级武器或统计数据。
- 本玩家当前能看到的其他所属方的对象：只有类型、位置、所属方、生命，以及可见度允许本玩家看到的标记；没有乘客、目标、任务、等级、弹药、效果或真实的伪装身份。伪装的敌人读出来是它伪装成的样子（类型和所属方）。
- 黑幕下的对象不出现，迷雾下本玩家当前看不到的其他所属方对象也不出现：引擎不保存“最后一次看到”的副本。隐形的敌人除非被侦测到，否则不出现。
- 变量、触发器和标签只属于模拟。视野查询和探测只回答本玩家自己所属方的情况。
- 观战者的模块看到观战者能看到的范围，房间允许时为整张地图。观战者没有自己的所属方，所以只有在房间向观战者显示某个所属方的信息时，针对自己所属方的查询才有回答。

### 11. 联机

- 嵌入的模块随地图传输。mod 的模块计入现有的 mod 文件校验。
- 大厅比对模块哈希和所需的 API 版本；它在加载模块之前读取每个 `[VeraWasm] Api=`。需要房间的游戏所没有的 API 版本的地图或 mod 无法被选择；离线时，这样的存档或回放会被拒绝。每种拒绝都给出所需的版本。
- mod 的 `[VeraWasm]` 键在它的 `rulesmd.ini` 中，mod 摘要包含这个文件，所以每个玩家都会比对它们；摘要不包括的 `mod.ini` 不放任何模块键。
- 每条消息的发送者由引擎填写，模块无法伪造；单条消息大小和每帧消息数有上限。
- 通知只送达目标玩家或观战者。通知的内容是模块自己的字节，由模块作者负责：引擎无法过滤它。
- 联机只交换指令，从不交换状态。重连的玩家从头重新模拟整局，包括模块；模块消息本身就是指令，所以不需要额外发送任何东西。因此模块每帧的开销也会拖慢追帧速度。追帧期间不投递通知，客户端模块也不运行；追帧结束后它们收到一次 `onStart`。
- 存档和回放记录游戏版本、模块哈希和 API 版本。模块与当前安装的 mod 或地图不一致的存档或回放会被拒绝，并提示是哪些模块；旧版本会拒绝新版本生成的存档和回放，并给出提示。
- 房间要求所有玩家运行同一版本，所以混合版本的房间不会开局。
- 离线时，支持模块之前的版本会不带模块地运行模块地图：它忽略 `[VeraWasm*]` 节，其触发器中的模块动作什么也不做。已发布的版本无法再修改，所以这是一个明确记录的遗留问题。为了涵盖之后的版本，支持模块之前的那个版本增加一个地图键 `[Basic] VeraMinVersion=`（名字未定），对需要更新版本的地图拒绝运行并给出指明版本的提示。模块地图设置这个键。
- 这项改动要更新 [Networking](../Networking.md)，说明已发布的游戏、混合版本的房间以及回退版本分别如何处理模块。

### 12. 版本与 ABI

- 一份用 WIT 语法编写的接口定义是 API 的唯一来源。项目自己的生成器由它生成 Rust 和 TypeScript SDK 的绑定、参考文档和兼容性检查。WIT 只是接口描述语言：模块不使用 Component Model 的 canonical ABI。
- 二进制接口是 core module ABI：core Wasm 模块的导入和导出、整数句柄和 ID、字符串、字节和缓冲区用的指针加长度，以及由宿主写入模块所提供缓冲区的结果。接口定义写明它的每种类型如何映射到这个 ABI。原因：浏览器版可能使用的每个引擎，包括浏览器自带的引擎和解释器，都能运行 core 模块（待定问题 1）；宿主把查询结果、记录和批量数据直接写进模块内存（第 15 节）；模块的全部状态都在线性内存、全局变量和表中，所以存档、状态哈希和重连都能完整捕获它（第 4 节）；AssemblyScript 能产出可以嵌入地图的小模块，它构建的是 core 模块（待定问题 2）；core 规范已经冻结。
- 以后的某个主版本可以在 core ABI 之上增加一个 Component Model 适配层。已有模块继续使用 core ABI，不受影响。
- 接口是带版本的包：`vera:sim@1`、`vera:client@1`。版本号是“主版本.次版本”。新的主版本不兼容，每个主版本都通过适配层永久保留；新的次版本只做增加。模块通过它的导入说明需要的主版本和最低次版本，地图或 mod 在 `[VeraWasm] Api=` 中写明同样的版本。大厅用每个玩家的游戏检查 `Api=`；加载时检查模块的导入与 `Api=` 一致（第 3 节）。
- 不稳定的接口放在 `vera:unstable/*` 下，需要显式开启，可以不经通知就改变。它们和 `0.x` 预览版都不是已发布的版本：不保留适配层，使用它们的模块只能在为之构建的那个版本上运行。
- 每个已发布的版本都一直可用。旧版本是现行实现之上的薄适配层，从不是第二份实现。适配层从不把旧版本没有定义的值交给旧模块：该版本不认识的事件的记录不投递给它，更新的状态值或枚举值以该版本定义过的值交给它，具体对应关系按枚举写在接口定义中。
- 对每个已发布的版本，CI 用仓库中提交的 Rust SDK 源码构建一组兼容性测试用例并运行它们；不提交 `.wasm` 二进制文件。破坏其中任何一个都会让构建失败。这组用例随每个版本增长，是对项目“每个修复一到三个回归测试”规则的有意例外。
- 计量单位、每类宿主调用的费用、默认额度和各项上限属于主版本的一部分，随主版本固定（第 4 节）。
- 函数可以弃用并向模块作者发出警告，但已发布的版本永不删除。
- 已发布的函数永不改变单位或含义。要改变，就新增函数或发布新版本。
- 自定义段 `vera.actions`、`vera.notify` 和投递区声明各以一个格式版本开头。其中的名字是 UTF-8，必须是 ASCII，并且只按 ASCII 规则统一大小写。
- `Trigger.create` 和 INI 通过模块的 `vera.actions` 表把 `Action.wasm` 的名字解析为一个下标。`EventRecord.action` 携带这个下标，SDK 生成的 `onEvents` 据此分派，因此动作函数不必是 Wasm 导出函数。

### 14. 项目契约

- 扩展模块功能（不要与浏览器版的 `wasm`、`wasm-net` 和 `wasm-threads` 构建 feature 混淆）存在于每个构建中，当 mod 或地图提供模块，或使用它的任何键（`Wasm.Tags`、INI 原子动作、`[VeraWasm]`）时，在运行时开启。从不放在构建 feature 后面。只要它开启，持续效果的 owner 就可用（第 8 节）。
- Wasm 运行时按平台选择，放在平台构建 feature 后面，项目契约允许平台 feature 这样做：桌面上用原生引擎，浏览器版用浏览器自带的 WebAssembly 或另一个引擎（待定问题 1）。模拟通过同一个接口访问运行时，所以 `vera20k-core` 和 `sim/` 仍能为浏览器编译。
- 每次模块调用都通过状态现有的 owner 访问状态。API 不引入竞争状态。
- 功能在 `docs/` 下为 modder 编写文档。`docs/modding.md` 目前写着 mod 只是数据、VERA20k 不会运行 mod 里的程序；这段要改成：模块只在沙箱中运行，无法访问文件和网络，模拟模块也无法访问时钟。Mods 菜单和地图列表要标出带模块的 mod 和地图。
- 模块出错在游戏中报告，从不只写进日志。

### 15. 性能

引擎只保留一份游戏状态。模块持有整数句柄和 ID，需要数据时再查询；不会把游戏世界复制进模块内存。下面这些规则让跨边界的开销保持很低，它们属于接口定义的一部分，并依赖 core module ABI（第 12 节）：

- **热路径用 ID，不用名字。** 类型、所属方、武器、弹头、抛射体、标记和效果的名字，以及附录列出的其他命名种类，都只解析一次，换成整数 ID（`ctx.typeId("E1")`、`Mark.id("Panicked")`），通常在 `onRules` 或 `onScenarioStart` 中完成；ID 一经分配就不再改变（第 2 节）。其他所有调用都传 ID。接受名字的调用（查找、`rules.set`、创建触发器）只用于初始化和不频繁的修改；SDK 会缓存 ID。
- **每个模块每帧只投递一次**（第 5 节），以固定大小的记录投递，记录的布局属于接口定义。SDK 在模块内存中预留投递区，并在加载时说明它的大小；每帧的队列上限限制一次调用投递的数量。
- **查询结果写进模块的缓冲区。** 引擎每次查询都不分配内存。按创建序号排序的开销随结果的大小增长，而不是随整个世界的大小增长。分页查询的结果集在一次模块调用中读取第一页时确定，保存在每个模块一个可复用的暂存缓冲区中，同一次调用中后面的页延续这个结果集，即使世界在两页之间发生了变化。
- **宿主调用按实际工作计费**（第 4 节），所以模块无法用看似廉价的调用拖住每台机器；轮询型事件有最小间隔，并且错开检查（第 6a 节）。
- **旁路表。** 标记、订阅和每个抛射体的模块数据放在按句柄索引的旁路表里，类型绑定放在按类型索引的表里，只有用到它们的对象和类型才占空间。旁路表存档并计入哈希。每个对象、武器、弹头和抛射体类型带一个标志位，表示是否有模块绑定它；每个对象在得到带模块触发器的标签时设置自己的一个标志位（第 7 节）。每个事件触发点先检查这些标志位。
- **哈希中的模块内存。** 联机的不同步检测使用每帧的多人同步校验。它每 15 帧包含一次每个模块内存的哈希，模块内存的大小受内存上限约束，所以模块内存中的分歧在联机时能被检测到。回放日志的诊断哈希（每 15 帧一次）和完整状态哈希也包含模块内存。它们的开销属于待定问题 3。
- **SDK 不为每个事件分配对象。** 句柄和 ID 都是值类型：在 TypeScript 中，句柄是小于 2^53 的 64 位整数，ID 是 32 位整数；在 Rust 中，两者都是 newtype。SDK 原地读取记录。只有 `Trigger.create` 这类初始化调用才会创建对象。
- **逐帧批量数据**（L4 行为、模块弹道）直接写入模块内存，再从中读回，每个对象几十字节。
- **按最慢的平台定额度。** 计量会让模块代码变慢，浏览器版还可能用解释器运行模块。锁步联机中最慢的机器决定整体速度，所以默认运算额度按最慢的受支持平台确定，并在 RFC 接受之前实测（待定问题 1 和 3）。
- **没有模块就没有开销。** 没有模块时，每个事件触发点只多一次标志位检查，其余代码都不运行。

## 流程

1. **草案。** 本文档公开讨论。每次修改都提升 RFC 版本号，并记入[修订记录](#修订记录)。
2. **回答待定问题。** 用一次性实验回答下面的待定问题，结论汇总到本文。
3. **接受。** 维护者把某个版本标为已接受，此后才开始开发。
4. **预览。** API 以 `0.x` 发布，允许破坏性变更并记入变更日志；预览版不是已发布的版本（第 12 节）。至少用它重做一个真实任务或模式，并请外部 modder 试用。
5. **稳定。** 冻结 `vera:sim@1` 和 `vera:client@1`，范围仅限预览期实际用到的部分，包括待定问题 10 中首批的两三个覆盖点。兼容性测试用例加入 CI。
6. **增长。** 每个新接口或覆盖点是一个小的后续 RFC 和一个新的次版本。

接受之后的计划顺序：

## 备选方案

- **由引擎运行 Lua**（Recoil 的做法）。对 modder 友好，但浮点和表遍历顺序的确定性要靠修改解释器保证，API 也会长成一个没有版本的全局命名空间。
- **在引擎里内置语言运行时**（随 VERA20k 发布 Lua 或 JavaScript 运行时，供模块导入）。模块会更小，但引擎要永远维护一个语言运行时，并且每个 API 版本都要固定一个构建。不采用：语言留在作者的工具里。
- **原生插件。** 无法移植到浏览器版，也没有沙箱。
- **以 Component Model 及其 canonical ABI 作为二进制接口。** 出于第 12 节的原因不采用：浏览器不能原生运行组件；canonical ABI 通过模块内的分配传回结果；它的资源句柄放在模块内存之外、每个实例一张的表中；AssemblyScript 不产出组件；组件规范仍在变化。WIT 仍作为接口描述语言。
- **以某个所属方的视角做模拟查询**（`ctx.asHouse(h)`，查询结果按所属方 `h` 能看到的范围过滤）。暂不采用：模拟查询能看到全部，客户端查询按视野过滤。
- **由宿主保证覆盖点是纯函数**（丢弃覆盖点调用期间写入的状态，禁止取随机数）。不采用：固定的调用顺序（第 5 节）以更低的代价让覆盖点的状态保持确定。
- **客户端模块之间直接发消息**（`client.broadcast` 发给盟友或观战者，在 `onPeerMessage` 中接收）。不采用：玩家之间的所有通信都经过模拟，联机只保留一条通道。
- **只增加 INI 键。** 简单需求仍然适用，够用时依然是首选，但表达不了通用逻辑。

## 参考先例

- **Recoil（Spring）。** 同步与非同步代码分离；非同步代码只能通过网络消息影响模拟；单对象的数值带可见度等级；代价高的回调只对脚本关注的对象触发。借鉴：不暴露底层图形 API；用带版本的包取代单一全局命名空间；回调需显式订阅。
- **红警 3（SAGE）。** 在数据文件里把对象事件绑定到脚本函数，可以继承，处理函数收到对象本身。借鉴：在数据里绑定，而不是在代码里。
- **Phobos。** 抛射体的 `Trajectory=` 类型；用于单对象修正的 AttachEffect。
- **社区的触发器、效果和约束条件设计**，在本 RFC 讨论期间分享。借鉴：触发器由事件、约束条件和动作组成；投递型与轮询型事件；带类型参数的事件清单；瞬时动作、持续效果和约束条件清单。不借鉴：INI 里的记录器和算子，改由模块代码实现。

## 未来可能的方向

不在版本 1 中。每一项都会是一个后续 RFC 或一个新的次版本。

- 更多投递型事件，也是待定问题 12 下的候选：`Built`（`other` 为建造者）、`Idle`（任务结束且没有排队的任务）、`MoveFailed` 和 `Arrived`（`cell` 为目的地）、`Stunned` 和 `Unstunned`（`other` 为来源）、`Promoted`（`value` 为新等级）、`Cloaked` 和 `Decloaked`、`Spotted` 和 `Lost`（`house` 为现在看到或失去该对象的所属方）、`AmmoChanged`（`value` 为旧值，`value2` 为新值）、`MissionChanged`（`value` 为任务）、`HouseDefeated`、`PlayerLeft` 和 `StorageFull`（`house`）、`MotionEnded`（`value` 为原因）。
- 由模块定义并每帧执行的自定义任务。
- 让 AI 学会使用 mod 新增的机制。
- 一个对象挂多个标签。
- 在盟友中搜索目标的持续效果。
- 界面树中的数据绑定（属性绑定到一个公开的值），以及供客户端模块改写指令的钩子。
- L4 逐帧行为、模块弹道、对等调用和玩家自装的界面模块（见上文的计划）。

## 待定问题

1. **浏览器版。** 浏览器版能否以和原生版完全一致的结果运行模块？用哪个引擎？wasmtime 可能无法在浏览器中运行。
2. **TypeScript 编译器。** TypeScript SDK 用哪种编译器：把 TypeScript 子集编译成 Wasm 的编译器（如 AssemblyScript），还是把 JavaScript 引擎编译进每个模块？引擎对两者没有区别；这个选择决定模块体积、速度，以及普通 TypeScript 代码能用多少。
3. **计量。** 运算计数和调用深度用哪种插桩？在 2 万单位下开销多大？在多人同步校验中每 15 帧哈希一次全部模块内存的开销多大？回放时，其他包含模块内存的状态哈希开销多大？
4. **INI 格式。** 用文中所示的具名节，还是用原版逗号分隔的触发器编码以便 FinalAlert2 编辑绑定，还是两者都要？考虑到绑定、约束条件和原子动作在没有模块时也能用，键用什么前缀？
5. **事件和动作编号。** 哪个范围不与 Ares、Phobos 冲突？
6. **FinalAlert2。** 保存地图时会不会保留 `[VeraWasmRulesPack]` 这类它不认识的节？
7. **上限。** mod 和地图的嵌入体积、内存、加载时形状上限、基础运算额度和每条记录的额度、每类宿主调用的费用、初始化函数、`onRules` 和 `onScenarioStart` 的一次性额度、每帧队列上限、积压上限、客户端模块每个渲染帧的运算额度、最小轮询间隔、消息大小和频率，以及存储配额。它们按 API 主版本固定（第 12 节）。
8. **帧阶段。** 模块阶段放在模拟帧的哪个位置；模块弹道分支相对碰撞和引爆判定的位置。
9. **存档体积。** 快照中的模块内存：压缩方式和内存上限。
10. **首批覆盖点。** 版本 1 提供哪两三个覆盖点。
11. **白名单。** 版本 1 中哪些键可以在对局中按类型修改。
12. **版本 1 清单。** 第 6a 到 6c 节中哪些事件、约束条件、动作、持续效果、查询和探测，以及附录中其他哪些 `v1?` 条目，进入版本 1。
13. **效果叠加。** 每种持续效果的叠加方式和所属互斥组。
14. **界面布局。** mod 和地图把布局节放在哪里，以及版本 1 的控件集合。
15. **地图文字。** 地图无法携带字符串表，地图模块的文字如何翻译。
16. **战役。** 每一关的模块是重新开始，还是延续上一关的状态。
17. **连锁上限。** 含有模块触发器、VERA 新增的事件或原子动作的连锁，每帧的深度上限，以及每帧这类连锁触发总次数的上限（第 5 节）。
