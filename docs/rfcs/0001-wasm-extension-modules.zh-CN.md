## 概要

让 mod 和地图携带编译好的 WebAssembly 模块（`rules.wasm`、`ui.wasm`），由 VERA20k 在沙箱中运行。模块可以在规则读完后修改规则、响应触发器、执行动作和下达任务、覆盖指定的游戏决策，并构建自己的界面。作者可以用任何能编译到 WebAssembly 的语言、用自己的工具编写模块，引擎只运行编译好的 `.wasm`。官方提供 TypeScript 和 Rust 两套 SDK。API 使用红警 2 modder 已经熟悉的术语：触发器、事件、动作、标签、任务、局部和全局变量、帧，并新增约束条件、持续效果和标记。

所有函数、事件、约束条件、持续效果和覆盖点，以及它们在引擎中的 owner 和出处，列在 [API 清单附录](0001-wasm-extension-modules-api.zh-CN.md)中。

API 从第一次发布起就带版本。已发布的 API 版本在之后所有 VERA20k 版本中都能继续使用。

## 动机

INI 文件和地图触发器表达不了 modder 想要的很多东西：自定义弹道、波次逻辑、新的超级武器行为、任务目标面板。Ares 和 Phobos 为此加了很多键，但每个新想法仍然需要改引擎。脚本层让 modder 自己实现这些，同时引擎仍然是游戏状态唯一的 owner。

API 一旦被 mod 依赖就无法收回，所以它必须公开设计、以带版本的小步增长，并用测试保证每个已发布版本一直能运行。

## 目标

1. modder 不改引擎也能修改玩法和界面。
2. 所有玩家运行相同的模拟模块并得到相同结果：在任何受支持的平台上（包括浏览器版）都不会不同步。
3. 外部模块永远不会让游戏停下。出错的模块被停用，并告诉玩家原因。
4. 任何模块都不能读文件、不能联网，任何模拟模块都不能读时钟；客户端模块得到的渲染计时只用于显示，并且按运算量而不是时间计量（第 3 节）。引擎的查询从不泄露隐藏信息：客户端模块的查询只暴露本玩家自己的界面能显示的内容（附录 7.7），其他任何东西只能通过通知到达客户端。模拟模块选择把什么通知给玩家，由模块作者负责（第 11 节）。
5. 没有模块时，游戏和现在完全一样。
6. 只有少数类型使用的模块不会拖慢 2 万单位规模的战斗。
7. 红警 2 modder 从模板开始，几分钟内就能在游戏里看到改动效果。

## 非目标

- 原生插件（`.dll`、`.so`），或在沙箱外加载任何东西。
- 引擎里出现源代码。引擎从不解析、编译或解释任何源语言，也不内置任何语言运行时（见[备选方案](#备选方案)）。
- 暴露引擎内部：内存布局、原生地址、内部对象下标或存储槽位（句柄是对象的创建序号，第 5 节）、渲染器的图形 API。
- 对局中新增对象类型。
- 取代原版触发器系统。模块是在它的基础上扩展。

## 术语

凡是红警 2 已有的术语，API 都沿用。代码和 INI 中的名字以本表为准。

| 术语 | 含义 |
| --- | --- |
| **扩展模块**（Extension module） | 一个编译好的 `.wasm` 文件。不叫“脚本”：红警 2 里的脚本指 AI 小队脚本（`[ScriptTypes]`）。 |
| **触发器**（Trigger） | 和地图里一样：一个或多个事件（必须全部成立）加一个或多个动作，属于某个所属方，带难度标志和原版的重复类型。VERA 增加可选的约束条件。 |
| **事件**（Event） | 让触发器触发的东西。原版事件编号含义不变。 |
| **动作**（Action） | 触发器执行的内容。原版动作编号不变。新增一个动作：执行模块函数。 |
| **模块触发器**（Module trigger） | 至少带一个模块动作（`Action.wasm`）、由模块创建，或通过 `Wasm.Tags` 或 `Trigger.bindType` 绑定的触发器。带模块动作的地图触发器也算。 |
| **约束条件**（Condition） | 触发器执行动作之前，由引擎原生检查的过滤条件。 |
| **标签**（Tag） | 把触发器挂到对象或格子（CellTag）上的东西。一个对象只有一个标签。 |
| **标记**（Mark） | 对象或所属方携带的文字记号，供约束条件判断，带一个整数值和一个可见度等级。不是标签：一个对象可以有任意多个标记。 |
| **持续效果**（Attached effect） | 对象身上带持续时间的状态，例如倍率或免疫（沿用 Phobos AttachEffect 的叫法）。 |
| **任务**（Mission） | 对象的命令：Move、Attack、Guard、Area Guard、Hunt、Sleep 等。 |
| **局部/全局变量**（Local / Global） | 和地图里一样的局部变量和全局变量。 |
| **帧**（Frame） | 模拟的一个逻辑帧，也是 `ROF`、`Rate` 和计时器的单位。 |
| **渲染帧**（Render frame） | 某台机器上画出的一帧。不同步。 |
| **覆盖点**（Override） | 一个具名的决策点，模块可以在这里改变引擎的结果。 |
| **House、Techno、Building、Vehicle、Infantry、Aircraft、Projectile、Weapon、Warhead** | 与 INI 文件中的含义相同。 |
| **格子、lepton**（Cell、lepton） | 地图坐标。1 格等于 256 lepton。 |
| **运算额度**（Operation budget） | 模块每帧可以做的工作量，以确定性的运算单位计量：一个基础额度，加上本帧投递的每条记录各一份额度（第 5 节）。模块代码和它发起的宿主调用都计入。 |
| **创建序号**（Creation serial） | 引擎在每个对象和抛射体创建时给它的一个 64 位编号，从不复用。它就是对象的句柄；跨对象时，查询结果、覆盖调用和投递的记录都按它排序，与引擎如何存放对象、循环按什么顺序无关。 |
| **安全点**（Safe point） | 不处在任何计算之中的时刻，VERA 新增的事件在这里引发，其触发器的原版动作和原子动作在这里执行。批量或并行的引擎段算作一次计算（第 5 节）。 |

## modder 看到的样子

### 文件

```
Mods/MyMod/
  mod.ini        ; Needs= 和其他 mod.ini 键；不含模块键
  rulesmd.ini    ; [VeraWasm] API 版本、额度、地图政策；把标签绑定到类型
  rules.wasm     ; 模拟模块
  ui.wasm        ; 界面模块
```

地图以文本形式携带模块，方式和现在携带 `IsoMapPack5` 一样：压缩、base64 编码、按编号分行。

```ini
[Basic]
VeraMinVersion=0.9.0     ; 示例；更旧的版本会拒绝这张地图并给出提示（第 11 节）

[VeraWasm]
Api=1.0                  ; 模块需要的 API 主版本.次版本（第 12 节）
RulesSize=48213          ; 解码后的字节数，加载时校验
UISize=9120
StorageId=MyCampaign     ; 客户端存储（第 10 节）；默认为地图的文件名

[VeraWasmRulesPack]
1=eJzt3XlcVOX+B...
2=...

[VeraWasmUIPack]
1=...
```

`asset` 工具增加命令：把模块嵌入地图、从地图中取出模块，以及运行和游戏相同的加载检查。

### 把触发器绑定到类型

```ini
; mod 里的 rulesmd.ini
[E1]
Wasm.Tags=GIPanicTag     ; 每个 E1 都接收这个标签的触发器

[GIPanicTag]
Trigger=GIPanic

[GIPanic]
Event=TakeDamage
Action=Wasm:giPanic      ; 运行 mod 的 rules.wasm 的模块动作 giPanic（第 2 节）
Repeat=yes
```

每个 E1 都以自己的实例运行 `GIPanic`（第 7 节）。键名和具体的节格式尚未确定（见[待定问题](#待定问题)）。在 FinalAlert2 里编辑的地图触发器，也可以通过新动作调用模块函数。

### 模块代码

引擎只看到编译好的模块，源码和编译器都在作者自己的工具里。同一个模块分别用两套官方 SDK 写：

```ts
// TypeScript（AssemblyScript 兼容）
import { action, onFrame, Every, Techno, Mission, EventRecord, Ctx } from "@vera20k/sdk";

action("giPanic", (ctx: Ctx, e: EventRecord): void => {
  const techno = e.subject;
  if (Techno.healthPercent(techno) < 30) {
    Techno.setMission(techno, Mission.Hunt);
  }
});

onFrame(new Every(15), (ctx: Ctx): void => {
  if (ctx.local(3).get()) {
    // ...
  }
});
```

```rust
// Rust SDK
use vera20k_sdk::prelude::*;

#[vera::action(name = "giPanic")]
fn gi_panic(ctx: &mut Ctx, e: EventRecord) {
    let techno = e.subject();
    if techno.health_percent() < 30 {
        techno.set_mission(Mission::Hunt);
    }
}

#[vera::on_frame(every = 15)]
fn check_waves(ctx: &mut Ctx) {
    if ctx.local(3).get() {
        // ...
    }
}
```

每套 SDK 都用一条命令构建出 `rules.wasm` 或 `ui.wasm`。构建时把模块的动作名列在 Wasm 自定义段 `vera.actions` 中，并给每个名字一个下标（第 12 节）。包名只是占位。语言和 SDK 见第 5a 节。

## 设计

### 1. 两个世界

| | 模拟（`rules.wasm`） | 客户端（`ui.wasm`） |
| --- | --- | --- |
| 运行在 | 每台机器上，锁步执行 | 仅本机 |
| 确定性 | 是 | 否 |
| 可以改变 | 游戏状态，通过引擎的 owner | 界面、显示、声音 |
| 影响游戏的方式 | 动作和任务 | 通过命令流发出标准玩家指令和消息 |
| 引擎侧 | `sim/` | `ui/`、`render/`、`audio/` |

这个划分遵循现有规则：`sim/` 从不依赖 `render/`、`ui/`、`audio/` 或 `net/`。数据从模拟流向客户端，靠经过视野过滤的查询和本地通知；从客户端流向模拟，只能通过命令流：标准玩家指令（引擎像校验任何玩家输入一样校验它们），以及 `sendMessage`，它像玩家指令一样进入命令流（第 10 节），所以回放和联机都能看到两者。

### 2. 来源：mod 和地图

mod 和地图使用同一套 API 和同一套 SDK，区别在于引擎授予它们的权限。

| | mod | 地图 |
| --- | --- | --- |
| 顺序 | 先 | 在 mod 之后，和 INI 层叠一致 |
| `onRules` | 在 `RULESMD.INI`、`LANGRULE.INI` 和模式层之后 | 在地图层之后，能看到 mod 的结果 |
| 运算额度 | 在 mod 的 `[VeraWasm]` 中声明，引擎设上限 | 默认更小，mod 的 `[VeraWasm]` 可以调高 |
| 体积 | 受文件大小约束 | 有嵌入上限 |
| 界面 | 可以替换或重排对局界面 | 只能加覆盖层，除非 mod 允许更多 |

mod 在它的 `rulesmd.ini` 的 `[VeraWasm]` 节中控制地图模块能做什么：

```ini
; mod 里的 rulesmd.ini
[VeraWasm]
Api=1.0              ; mod 的模块需要的 API 主版本.次版本
Budget=200000        ; mod 模块每帧的基础额度，引擎设上限
MapBudget=50000      ; 在这个 mod 下地图模块可用的基础额度
MapWasm=yes          ; no：带模块的地图在这个 mod 下不能开局
MapUI=overlay        ; overlay、full 或 no
```

这些键放在 `rulesmd.ini` 里，因为 mod 摘要包含这个文件而不包含 `mod.ini`，所以房间里的每个玩家都会比对它们（第 11 节）。引擎从各自的文件读取每个 `[VeraWasm]` 节：mod 的在任何其他层之前从 mod 的 `rulesmd.ini` 读取，地图的从地图读取，两者从不层叠，所以地图无法改变 mod 的键；地图自己的 `[VeraWasm]` 节只放它的嵌入键、它的 `Api=` 和它的 `StorageId=`。键名和取值只是占位（待定问题 4 和 7）。

没有选择 mod 时，允许地图模块，地图界面只能是覆盖层，地图模块使用引擎的默认额度。

规则层按以下顺序运行：`RULESMD.INI`、`LANGRULE.INI`、模式层、mod 模块的 `onRules`、地图层、地图模块的 `onRules`。每个 `onRules` 读到的是它之前各层处理后的规则，引擎在它写入之后再处理一次规则，和处理 INI 文本一样。类型 ID 一经分配就不再改变：后面的层可以新增类型并得到新的 ID，但从不让已有的 ID 失效，所以在 mod 的 `onRules` 中解析得到的 ID 在整个场景中都有效。

冲突规则：

- **类型上的标签绑定**在 INI 中（`Wasm.Tags`）只从 mod 的 `rulesmd.ini` 读取；地图中的 `Wasm.Tags` 键被忽略，并在大厅中给出警告。地图在代码里用 `Trigger.bindType` 及其武器、弹头和抛射体形式绑定类型（第 7 节），所以地图无法通过层叠抹掉 mod 的绑定。
- **名字和消息。** mod 的 INI 或触发器中的模块名（`Action=Wasm:name`、覆盖点绑定）解析到 mod 的模块；地图的 INI 或触发器中的模块名解析到地图的模块；显式前缀（`Wasm:mod.name`、`Wasm:map.name`）可以指向另一方。模块代码中的 `Action.wasm` 按创建它的模块的来源以同样方式解析。INI 中的覆盖点绑定按来源分别读取，所以地图的绑定是在链上加入地图的一环，从不取代 mod 的。客户端消息（`sendMessage`）到达每个模拟模块的 `onMessage`，通知（`notify`）到达每个客户端模块的 `onNotify`；两者都携带发送它的模块的来源（mod 或地图），由接收方读取。
- **触发器**：两边的都会触发，mod 的模块先运行。
- **覆盖点**按链式处理：mod 的模块先算出结果，地图的模块拿到这个结果后可以再改，引擎使用最终值。链上的每一环都同时拿到原生值和上一环的结果，如附录（第 8 节）中的签名所示。后一环可以推翻前一环的否决。数值类覆盖点返回一个明确的“已处理”标志，而不是用特殊值表示。
- **动作和任务**按执行顺序走同一个 owner。
- **对等调用**（后续阶段）：mod 可以公开一些函数，地图用 `callPeer("mod", name, bytes)` 调用。只有 mod 为此导出的函数才能被调用。

### 3. 加载与校验

加载时，引擎依次：

1. 解码嵌入的模块，校验声明的大小；
2. 解析模块，只接受来自 `vera:*` 接口的导入，且本版本支持其主版本并达到模块需要的次版本（第 12 节），检查这些导入与模块所在 `[VeraWasm]` 节的 `Api=` 一致（大厅已经读过它）；超出加载时形状上限（函数数量、单个函数体大小、局部变量、导入）的模块被拒绝，这样地图无法在编译时拖住大厅；每个 `vera.*` 自定义段以格式版本开头，其中的名字是 UTF-8，且必须是 ASCII；
3. 只接受白名单中的 Wasm 特性：MVP 核心，加上可变全局变量、符号扩展、不 trap 的浮点转整数、批量内存操作和多返回值。其他一切，包括 SIMD、引用类型、垃圾回收、多内存、线程、64 位内存、异常和尾调用，都被拒绝，所以模块的全部状态就是内存、全局变量和一张函数表（第 4 节）。带 `start` 段的模块被拒绝，所以实例化时不运行任何模块代码。引擎还通过改写字节码（而不是引擎开关）把浮点运算产生的 NaN 规范化，这样每个引擎（包括浏览器的）得到相同的 NaN；
4. 在同一次插桩中向字节码加入运算计量和调用深度计数：深度上限设得远低于每个受支持引擎的真实栈上限，所以深度递归在每台机器上都停在同一次调用。模块从不被重入（第 5 节），所以每个模块在栈上至多有一个调用，模块调用之间的引擎栈帧也保持有界。引擎在实例化模块时分配它的内存上限，所以上限以内的 `memory.grow` 从不失败；无法分配它的宿主在加载时让对局失败，这是对局错误（见下文）；
5. 检查生命周期需要的导出函数存在且签名正确，并检查 INI 中提到的每个模块动作（`Action=Wasm:name`，第 2 节）都在它所解析到的模块的 `vera.actions` 表中；
6. 把本局加载的所有模拟模块（mod 的和地图的合在一起）在各自 `vera.notify` 自定义段中声明的通知名放在一起检查哈希冲突（第 10 节）：同一模块内的冲突拒绝该模块，mod 的名字与地图的名字之间的冲突拒绝地图的模块；提示中给出两个名字。

SDK 把模块的顶层初始化代码变成一个导出的初始化函数。引擎在模块的第一次其他调用之前调用它一次（模块导出 `onRules` 时在 `onRules` 之前，否则在 `onScenarioStart` 之前；在客户端模块中，在 `onStart` 之前），读档后不再调用，因为模块内存已经恢复。在初始化函数中只有名字查找（第 15 节）可用，包括 `Mark.id`，它们看到的是到此为止处理过的规则；其他宿主调用返回 `Unsupported`。

初始化函数、`onRules` 和 `onScenarioStart` 各有自己的一次性额度，比一帧的额度大（待定问题 7）。

开局前失败：在大厅显示原因，带这个模块无法开局。`onRules` 中失败也会阻止开局，并提示是哪个模块，因为它正在写的规则不完整。对局中失败，包括 `onScenarioStart` 中的失败（trap、超出额度、超出调用深度、参数非法）：在所有机器的同一帧停用该模块，游戏告诉玩家是哪个模块停止了、原因是什么。宿主本身的失败，例如分配内存上限时内存不足或 Wasm 引擎的内部错误，不算模块失败，因为无法证明它在每台机器的同一帧发生：它是对局错误，游戏停止对局并给出提示，和不同步时一样。

模块被停用后对局继续，它留下的东西按以下方式处理：

- 它创建的触发器被停用。在其他触发器中（地图触发器，或通过 `Wasm.Tags` 绑定的触发器），只跳过它的模块动作，触发器的原版动作和原子动作照常执行；它排队中的模块动作被丢弃；
- 它的覆盖点被跳过：由链中的下一个模块或原生结果生效。对于出错的那次覆盖调用，引擎使用上一环的值或原生值；
- 它的模块弹道上的抛射体改为朝目标直线飞行；
- 保留的东西：它添加的持续效果和标记，因为它们属于引擎状态；它在 `onRules` 中写入的规则和 `rules.set` 覆盖层；它创建的 AI 定义、标签和触发器（触发器处于停用状态）；以及出错的那次调用已经做完的事，因为立即执行的动作不会撤销；
- 它的内存保留在快照和状态哈希中，停在它停止时的样子，所以存档和重连能重现它。

客户端模块只在一台机器上运行，所以它们的失败是本地的。每个客户端模块在每个渲染帧有一份额度，用同一套计量按运算单位计算，而不是按时钟计算，所以在浏览器的主线程上也能执行：超出额度或 trap 的调用被停止，该模块只在这台机器上被停用，并提示该玩家。它影响不到对局。

属于正常游戏过程的错误只返回状态，模块继续运行：句柄为 `NO_HANDLE` 或其对象已不存在时为 `Gone`，名字没有匹配时为 `NotFound`，动作被引擎规则拒绝（比如该格不能建造）或触发器中原子动作的目标在触发器执行时才发现不适用于该动作（第 6b 节）时为 `Refused`，本局关闭的功能（例如没有 Ares 时的 Ares 动作）或在不可用的地方发起的宿主调用为 `Unsupported`。对 `NO_HANDLE` 或对象已不存在的句柄发起的调用，包括不返回任何值的方法（例如界面节点的方法），什么也不做，并把上一次调用的状态（`ctx.lastStatus()`，或客户端中对应的函数）设为 `Gone`；它从不停用模块。由触发器执行的原子动作没有模块代码来接收它的状态：它的错误状态（`Refused`、`Gone` 或 `NotFound`）写入游戏内日志，该动作被跳过，除此之外什么也不发生。表明模块本身有问题的错误会停用模块：参数非法（包括 `Trigger.create` 运行时发现的原子动作非法参数，例如永远不适用于该动作的目标种类，第 6b 节）、trap、超出运算额度或调用深度。

`docs/modding.md` 目前写着“mod 只是数据，VERA20k 不会运行 mod 里的程序”。这段要改成：模块只在沙箱中运行，无法访问文件和网络，模拟模块也无法访问时钟。Mods 菜单和地图列表要标出带模块的 mod 和地图。

### 4. 确定性

所有机器运行同一份模块字节，所以结果只取决于引擎如何执行它们。

- 只用白名单中的 Wasm 特性（第 3 节），NaN 规范化（通过改写字节码），并由插桩计数调用深度上限。
- 不提供时钟、宿主随机源和 WASI。每个模块从自己专用的随机流取数，这条流由场景种子和模块的槽位（mod 或地图）派生，所以模块不会错开原生随机流：不取随机数的模块，原生结果完全不变。会执行原生代码的动作，按那段代码原本的方式从原生随机流取数。每个 API 都写明自己取几次随机数。
- 名字（类型 ID、节名）比较时不区分大小写，只按 ASCII 规则（`A` 到 `Z`），和 gamemd 读取 INI 的方式一致。字符串以 UTF-8 跨越边界。
- 运算额度由加载时插入的计量代码计算，不用引擎自带的 fuel。这样无论原生还是浏览器的引擎，都会数出相同的运算量，并在同一点停下。宿主调用按它们所做的工作计入同一份额度（例如按扫描或返回的每个对象、检查的每个格子），每类调用的费用写在接口定义中（第 12 节）。
- 计量单位、每类宿主调用的费用、默认额度和各项上限按 API 主版本固定，所以在这些限制内运行过的模块在之后的每个版本中都能继续运行。
- 位置、速度等游戏数值以整数（lepton、定点数原始值）跨越边界。小数和倍率使用模拟的定点格式，即 `I16F16` 原始值（`SimFixed`）。模块内部可以使用浮点。
- 模块内存、可变全局变量、模块的表（按其中保存的函数下标存档）、插桩的计数器（已用运算量、调用深度）以及模块的随机流都属于模拟状态：存进快照，计入状态哈希（第 15 节）。存档只在两次模块调用之间进行。
- 对模拟模块的调用从不来自并行或批量代码，跨对象的调用顺序也不取决于引擎的循环顺序（第 5 节）。

### 5. 执行模型

模拟模块的导出（每次模拟调用还会收到 `ctx`，每次客户端调用还会收到 `ui`，见附录）：

| 导出 | 时机 |
| --- | --- |
| 初始化函数 | 由 SDK 从顶层代码生成；在模块的第一次其他调用之前运行一次，读档后不再运行（第 3 节） |
| `onRules(rules)` | 在模块所处的规则层位置运行一次（第 2 节）；可以修改和新增类型 |
| `onScenarioStart(ctx)` | 场景开始时运行一次 |
| `onFrame(ctx)` | 导出时每帧一次；SDK 在 `frame % N == 0` 的帧运行每个注册的函数 |
| 模块动作 | 通过 SDK 注册，不是 Wasm 导出函数（第 12 节）；其触发器触发时排队，在模块阶段由 `onEvents` 运行 |
| `onEvents(ctx, batch)` | 由 SDK 生成；在模块阶段，每个有排队模块动作的模块调用一次，在 `onMessage` 之后、`onFrame` 之前 |
| 覆盖点 | 引擎走到该决策时，在帧内固定的步骤调用，顺序见下文 |
| `onMessage(ctx, sender, source, data)` | 在模块阶段，客户端消息已到达模拟时；`source` 是发送它的客户端模块的来源（第 2 节） |

客户端模块的导出：`onStart(ui)`；`onRender(ui, dt, alpha)`，每个渲染帧一次；`onNotify(ui, source, id, data)`；以及点击、热键等界面回调。

模拟模块的代码只在模拟的阶段内运行。本地代码，例如侧边栏、光标、界面、渲染和客户端查询，从不调用模拟模块；它们读取模拟最近一次算出的结果。例如 `Override.ProductionAllowed` 在模拟中求值，侧边栏显示缓存的结果（附录第 8 节）。

模块调用在模拟帧里一个固定的阶段运行，按模块加载顺序逐个模块执行（先 mod 的，再地图的）。每个模块先收到它的 `onMessage` 调用，然后是它的 `onEvents` 批次，最后是 `onFrame`。本帧内触发的触发器中的模块动作会排队，每个都带着触发其触发器的那个事件的载荷，在这个阶段统一投递，每个模块一批（第 15 节）。模块只能通过这种方式收到事件：没有单独的事件记录。覆盖点是例外：引擎需要答案时当场调用。句柄是对象的创建序号，一个从不复用的 64 位编号，由引擎把序号映射到对象，所以投递前已经死亡的对象读出来是“不存在”，绝不会指向另一个对象。

对模块的调用从不在并行或批量代码中发出。批量或并行的引擎段（例如伤害提交或并行的索敌扫描；附录列出每个引发点）算作一次计算。在其中引发的 VERA 事件被收集起来，它们的触发器在该段结束后立即触发，仍在同一帧、在下一个阶段之前：那就是它们的安全点，它们的原版动作和原子动作从那里“立即”执行。在这样的段中走到的覆盖点按批处理：引擎收集该段的所有查询，对每个模块用全部查询调用一次，再应用结果。跨对象时，覆盖调用、段结束后触发的触发器以及一批中的记录都按主体的创建序号排列，从不按引擎的循环顺序，所以引擎为了速度而调整循环顺序或改成并行，不会改变这个顺序。在同一个对象内，调用按引擎引发它们的顺序进行，这个顺序在不同引擎版本之间可能改变。主体为 `NO_HANDLE` 的记录（所属方和逻辑触发器，以及事件没有主体的格子触发器）排在最前，按触发器运行时触发它们的顺序排列。

**不重入。** 某个模块的调用还在栈上时，引擎从不再次调用这个模块。从这次调用到达的计算中，它的覆盖点被跳过（使用上一环的值或原生值）；它发出的动作所引发的事件照常触发其触发器，其中的模块动作照常排队。可以调用其他模块：mod 模块的直接动作可以到达地图模块的覆盖点。

顺序规则：

- 原版动作和第 6b 节的原子动作在触发器触发时立即执行，与原版中的原版动作完全一致，含有模块动作的触发器也是如此。只有模块动作（模块函数）排队，在模块阶段按上述顺序、每个模块一批执行。动作为 [原版 A、模块 B、原子 C] 的触发器，先执行 A 和 C，B 在同一帧稍后执行。需要严格顺序的作者，把触发器的全部动作都写成模块代码，再通过 API（L1）调用原版动作。
- VERA 新增的每个事件都在安全点引发：安全点是不处在任何计算之中的时刻。一次计算完成之后是安全点（例如 `TakeDamage` 在伤害已经提交之后），一次计算开始之前也是（例如 `HouseTransfer` 在转移开始之前）。在批量或并行段之内，安全点是该段结束后的那一刻（见上文）。触发器的原版动作和原子动作从这一点起立即执行。在计算之前引发的事件之后，引擎在执行这次计算前重新检查它是否仍然有效：如果某个动作已经移除了对象或改变了它的所属方，转移就不发生，也不引发 `HouseTransferred`；`FatalDamage` 在死亡流程之前引发，在它的动作执行之后，引擎重新检查伤害是否仍然致命（例如某个动作治疗了对象，或添加了阻止死亡的效果），只有仍然致命时才执行死亡流程。
- 立即执行的动作可以在一帧之内连锁：伤害引发 `TakeDamage`，它的触发器用原子动作造成伤害，又引发 `TakeDamage`，依此类推。连锁中含有模块触发器（见[术语](#术语)）、VERA 新增的事件或原子动作时，引擎限制它每帧的深度，并且限制每帧这类连锁触发的总次数，因为一个每层都触发另外两个的触发器，否则会触发 2^depth 次；会超过任一上限的触发器改到下一帧触发，所以这样的连锁不会无限循环。这样推迟的触发器在下一帧模块阶段开始时、该阶段排队的动作之前触发，带着它原有的载荷：它的原版动作和原子动作在那时执行，因此比没有上限时晚一帧，它的模块动作加入那一帧的批次。如果它在此期间被禁用或删除，就被丢弃；它触发时重新检查约束条件，它的所属方是主体在那一刻的所属方，作用于已不存在的主体的动作得到 `Gone`。等待中的推迟触发器存档并计入哈希。具体上限是待定问题 17。只由原版事件和原版动作组成的连锁从不推迟，与原版中完全一样地运行（目标 5）。
- 如果游戏已经结束，或者触发器在模块阶段之前已被禁用或删除，排队中的模块动作会被丢弃。已不存在的对象，其句柄读出来是“不存在”。
- 在模块阶段运行期间触发的触发器（例如因为某个模块动作造成了伤害），其原版动作和原子动作立即执行；其模块动作排到下一帧的模块阶段，因此模块代码不会在一帧之内循环。
- 覆盖点返回结果，不能执行动作，因为引擎调用它时正处在一次计算的中途。它们可以读状态，可以在模块内存中保存自己的状态，也可以从模块的随机流取数：上述调用顺序让这一切是确定的。跨对象的顺序在不同引擎版本之间保持不变；同一对象内的顺序可能在版本之间改变（见上文）。`Override.Fire` 返回一份射击方案，由引擎自己执行（第 9 节）。
- 投递型事件报告的是已经发生的事，而模块动作在模块阶段中稍后才执行，无法取消原生结果（比如死亡）。要改变这类结果，需要用覆盖点、持续效果（比如阻止死亡），或在计算之前引发的事件（`FatalDamage`、`HouseTransfer`）上的原版动作或原子动作，引擎会重新检查（见上文）。
- 高频事件（伤害、开火、抛射体引爆、碾压、移动失败）和所有覆盖点只对绑定的类型触发（对象、武器、弹头或抛射体类型；第 6a 节），没有“订阅所有对象”的用法。
- 读档后，模块内存随快照恢复。初始化函数和 `onScenarioStart` 都不会再次运行，也没有单独的读档回调。模块内存里保存的句柄，读档后仍指向同样的对象，因为句柄是创建序号，不是存储位置。

每个模块每帧有运算额度：一个基础额度，加上本帧投递给它的每条记录各一份额度，所以一个绑定在更大的战斗中产生更多记录时，也得到更多额度。宿主调用按它们所做的工作从中扣除（第 4 节）。覆盖调用从同一份每帧额度中扣除，每次调用和一条记录一样增加一份额度；额度用完后，该模块的覆盖点在本帧余下的时间里被跳过（使用上一环的值或原生值），模块在本帧结束时被停用。每个模块的队列每帧最多容纳固定数量的记录；超出上限的记录按顺序保留，在下一帧最先投递，所以短时间的爆发只会让模块的反应变慢，而不会让它被停用。被推迟的记录存档并计入哈希。如果一个模块积压的推迟记录超过固定帧数的量，说明它跟不上，模块会被停用并给出提示。基础额度、每条记录的额度、队列上限和积压上限是待定问题 7。订阅都需要显式开启：一个模块既不导出 `onFrame`，也不绑定触发器，那它每帧的开销为零。

### 5a. 语言与 SDK

引擎和模块之间的约定只有 Wasm 接口。任何语言，只要它的编译器产出的模块能通过加载检查，就能使用，引擎对所有模块一视同仁。

- **官方 SDK：TypeScript 和 Rust。** 两者都由同一份接口定义（第 12 节）生成，提供相同的函数（名称按各自语言的命名习惯），并随 API 一起发布版本。每套都附带模板、构建命令、监视模式和示例。
- **TypeScript SDK。** 预先把 TypeScript 编译成 Wasm，模块足够小，可以嵌入地图。具体用哪个编译器是待定问题 2。它的 API 限定在 TypeScript 与 AssemblyScript 的共同子集内：不用 `any`，除 `T | null` 外不用联合类型，回调不捕获外部变量，不用 `try`/`catch`，参数用类而不是任意对象形状。句柄是普通整数，所以没有方法：TypeScript SDK 使用以句柄为第一个参数的命名空间函数（`Techno.healthPercent(t)`、`Techno.setMission(t, Mission.Hunt)`），初始化参数是用构造函数创建的类（`new TriggerDef(...)`），而不是对象字面量。每个句柄值（一个创建序号）都保持小于 2^53，所以基于 JavaScript 引擎的 SDK 可以用 number 保存它。顶层代码成为初始化函数（第 3 节）。这样同一份源码既能用 `tsc` 做类型检查，也能用 AssemblyScript 编译，本 RFC 中的示例在两者中都有效。
- **Rust SDK。** 面向想要完全控制和更高性能的作者；引擎自己的兼容性测试用例也用它编写。它可以在句柄的 newtype 上保留方法（`techno.health_percent()`）。
- **其他语言**（C、C++、Zig、Go……）使用公开的接口定义及其到 core module ABI 的映射（第 12 节），绑定由社区维护。
- **导入。** 模块只能导入 `vera:*` 接口。引擎不提供 WASI，项目也不发布 WASI 垫片。运行时依赖 WASI（时钟、随机数、文件）的语言，只有在它自己的工具链去掉这些导入时才能使用。
- **体积和特性。** 以 Wasm 垃圾回收或其他被拒绝的特性（第 3 节）为目标的编译器，比如某些 Kotlin、Dart 和 Java 工具链，产出的模块无法通过加载检查。会把大型运行时或线性内存中的垃圾回收器打包进每个模块的语言，产出的文件更大，可能超过地图嵌入上限。这是作者工具链的取舍，与引擎无关。

### 6. API 分层

| 层 | 内容 | 首个 API 版本 |
| --- | --- | --- |
| L1 动作和任务 | 所有原版触发器动作、任务、生产、所属方和对象命令 | 包含 |
| L2 触发器 | 原版事件加新事件（武器开火、抛射体引爆……），投递给动作 | 包含 |
| L3 覆盖点 | 具名决策：选择目标、伤害、是否允许生产、接管武器的一次射击…… | 从 modder 需求中选两三个（待定问题 10） |
| L4 逐帧行为 | 对绑定类型的对象进行批量逐帧控制 | 不包含，以后再做 |

查询是只读的，遍历顺序确定。每个 L1 动作调用该动作现有的 Rust 移植（例如 `sim/trigger_runtime` 里的）；模块不会得到第二份实现。

覆盖点以游戏概念命名，例如 `Override.Damage`、`Override.TargetChoice`，从不以原生函数命名，这样引擎重构后它们依然成立。`Override.Fire` 让模块接管武器的一次射击：它返回一份射击方案，即要生成的抛射体及其参数的列表，由引擎立即生成，取代原生抛射体（第 9 节）。

对于非常频繁的决策，优先用数据而不是回调：目标优先级用持续效果携带的倍率表示，再配合 `TargetChanged` 事件；逐次调用的覆盖点只留给不那么频繁的决策。`Override.CommandAllowed` 和 `Override.Death` 是另外两个候选。由模块定义并执行的自定义任务留给后续 RFC。

L4 每帧对每种行为类型调用一次模块，把该类型的全部对象一起交给它，从不按单个对象调用。

**粒度。** 一个 API 函数对应一个游戏操作，这个操作在引擎里有且只有一个 owner：发射武器、添加持续效果、设置任务、修改生命、创建对象。更大的行为（比如一次空袭、一条心灵控制链）由作者用这些函数组合。

坐标可以作为任何操作的参数：目标、生成点、传送目的地。例如模块可以往任意格子扔核弹。不开放的是绕过 owner 的步骤，比如直接写已有对象的位置字段或内部字段。对象的位置关联着格子占用、碰撞、视野、所在地图层以及乘客关系，只有引擎自己的流程能保持它们一致，所以对象只能通过传送、运动效果或移动任务改变位置。抛射体是第 9 节第 4 层的例外：它们不占格子，引擎会钳制其位置，碰撞判定照常进行。

### 6a. 触发器：事件、约束条件和动作

和原版一样，一个触发器有一个或多个事件（必须全部成立）、任意个约束条件、一个或多个动作，以及原版的一种重复类型。

- **事件**分两类。*投递型事件*发生在某个时刻（受到伤害、武器开火、被摧毁）：触发器在那一刻触发，其中的原版动作和原子动作立即执行，模块动作则带着事件的载荷排队到模块阶段执行（第 5 节）。VERA 新增的投递型事件在安全点引发，即不处在任何计算之中的时刻：在产生它的那次计算完成之后，或在一次计算开始之前，例如 `HouseTransfer` 在转移开始之前引发（第 5 节）。*轮询型事件*描述一种状态（生命低于某值、金钱高于某值），由引擎按触发器设定的间隔原生检查，事件在边沿触发：在状态变为成立的那次检查时触发，之后要等到某次检查时状态不成立，才会再次触发。不同对象的检查是错开的：对象在 `frame % interval == serial % interval` 的帧接受检查，`serial` 是它的创建序号；所属方的轮询改用所属方在所属方数组中的下标。
- **约束条件**在任何模块代码运行之前过滤触发器。引擎原生检查，全部满足时才调用模块。条件可以取反。更复杂的逻辑（条件之间的“或”、两个对象之间的比较、计数）写在模块代码里。
- **动作**可以是原版触发器动作、第 6b 节的原子动作，或模块函数。原版动作和原子动作在触发器触发时执行；模块函数排队到模块阶段（第 5 节）。模块函数也是模块收到事件的唯一途径。
- 每个事件都标明它所附着的对象，以及涉及的另一个对象（如果有的话：攻击者、目标、载具、生产者）。约束条件可以判断其中任意一个。
- 事件只对绑定的对象触发：类型绑定了该触发器的对象（`Wasm.Tags`）、自身标签包含该触发器的对象；对于武器事件（携带抛射体句柄的 Fire、HitTarget 和抛射体 Detonated），还包括使用绑定了该触发器的武器、弹头或抛射体类型的任何对象。武器绑定对使用这把武器的所有射手生效，不论射手是什么类型：

  ```ini
  [RedEye2]                   ; 一把武器
  Wasm.Tags=MissileFiredTag   ; 所有使用 RedEye2 的射手开火时都会触发其 Fire 触发器
  ```

- 绑定到某个类型，或绑定到某个武器、弹头或抛射体类型的触发器，在每个绑定对象上以各自的实例运行，有各自的重复状态：一次性触发器对每个对象各触发一次。触发器的所属方是主体在那一刻的所属方，标签持有者是引发事件的对象（第 7 节）。

```ts
const PANICKED = Mark.id("Panicked");   // 顶层代码：在 SDK 的初始化函数中只运行一次（第 3 节）；之后的调用都传 ID

onScenarioStart((ctx: Ctx): void => {
  const def = new TriggerDef([new EventDef(Event.TakeDamage)], [Action.wasm("giPanic")]);
  def.conditions = [Cond.healthBelowPercent(30), Cond.not(Cond.hasMark(PANICKED))];
  Trigger.bindType(Trigger.create(def), ctx.typeId("E1"));   // 每个 E1 运行自己的实例（第 7 节）
});
```

### 6b. 原子动作与持续效果

版本 1 的瞬时动作候选：发射武器（按索引或名称，目标可以是格子、对象或当前目标）、发射超级武器、生成动画、移除、摧毁、通过弹头和护甲规则造成伤害（带来源，用于击杀归属和经验）、直接设定生命值（无归属）、创建对象、设置任务、传送到某格（与超时空传送相同；目标格被占时，按规定的规则选附近的格子或动作失败）、清除目标、清除伪装、区域搜索（返回对象列表的查询）、播放声音、增加经验、增减金钱、修改科技树、转移所属、清除心灵控制、修改弹药、增删乘客、添加或移除持续效果、添加或移除标记、生成抛射体（类型、起点、目标对象或坐标、用于击杀和经验归属的来源、初始模块数据）、在某个坐标以指定伤害和来源引爆弹头、立即引爆抛射体、移除抛射体而不引爆、让某个所属方结束游戏（胜利或失败）并设置分数、向游戏内日志写一行。

在触发器中，原子动作写作 `Action.atomic(kind, target, params)`，与 `Action.original` 和 `Action.wasm` 并列。它只用于参数放得下的动作：一个目标、一个 ID、至多两个整数、一个格子和一个所属方。`Log` 是唯一被接受的例外：它另外带它要写的那行文字。需要更多参数的动作（例如生成抛射体）写成模块动作。目标是一个明确的参数：主体（默认）、事件中的另一方对象、标签持有者（标签中持有该触发器的对象；CellTag 的标签持有者是那个格子）、事件中的抛射体、某个所属方，或一个格子。路径点以带有其编号的格子给出：`Cell.waypoint(n)` 返回这样的格子，`Trigger.create` 把它解析为路径点所在的格子，因为路径点不会移动。地图上没有的路径点是地图数据错误，不是模块错误：`Trigger.create` 返回 `NO_HANDLE` 并设置 `NotFound`，不创建触发器并写入日志，模块保持启用；写在 INI 中时，它在加载时于大厅中报告。不用目标的动作（例如设定科技等级，或 `Log`）忽略目标。对于绑定到类型或武器、弹头、抛射体类型的触发器，标签持有者是引发事件的对象。其余由固定规则决定：

- 明确的所属方（所属方目标、转移所属时的新所属方、所创建对象的所属方）取参数中给出的所属方；没有给出时，使用触发器的所属方，对于绑定的触发器，它是主体在那一刻的所属方。
- 来源（伤害、击杀或引爆的来源）是事件中的另一方对象，并且是可选的：事件没有另一方对象时，动作在没有来源的情况下执行，不计击杀归属。需要对第二个对象施加作用的动作（乘客）使用事件中的另一方对象；事件没有另一方对象时，动作得到 `Gone` 并被跳过，状态写入日志。
- `FireWeapon` 发射参数中给出的武器类型；没有给出时，发射参数所给槽位中的武器（默认 0，即主武器）。它的瞄准对象按优先顺序为：参数中给出的格子；没有时为事件中的另一方对象；再没有时为射手当前的目标；三者都没有时，动作得到 `Gone` 并被跳过。
- 需要格子的原子动作（例如 `LaunchSuperWeapon`）没有得到格子时，属于非法参数。
- 对象目标的格子是对象所在的格子；`Projectile` 目标也算对象目标，它的格子是抛射体下方的格子。坐标取给定格子的中心，或目标所在格子的中心；抛射体目标例外，其坐标为抛射体的中心。
- 每种动作接受哪些目标种类、用到哪些字段由附录列出；每种动作到其参数的确切对应关系属于接口定义（第 12 节）。

`Trigger.create` 检查每个原子动作的参数：非法的参数，包括永远不适用于该动作的目标种类（例如击杀动作的目标是格子），属于模块代码给出的非法参数，会停用模块（第 3 节）。写在 INI 中的原子动作在加载时检查，并在大厅中报告；它们的 INI 写法是待定问题 4。触发器执行时才发现目标不适用于该动作（例如击杀动作的标签持有者是一个格子），属于数据错误，不表明模块有问题：动作得到 `Refused`，其状态写入游戏内日志，动作被跳过，模块保持启用（第 3 节）。原子动作立即执行，并可能引发新的事件，所以它们可以在一帧之内连锁，深度受第 5 节的上限约束。

持续效果是对象身上带持续时间的状态，由 `sim/attach_effect.rs` 负责（第 8 节）。候选：染色、附着动画、阻止死亡、变成另一类型、替换武器、运动（被抛起、被推动）、超时空移动、受伤倍率、火力倍率、速度倍率、射速倍率、射程、目标优先级倍率（第 6 节）、隐形、对某弹头或攻击类型免疫、禁止开火、停止索敌、伤害修正、无法被选中、无视玩家指令、不可被选为目标、所属方断电。

- 每种效果类型声明自己的叠加方式：叠加到上限、新的替换旧的，或拒绝新的。不能同时生效的效果（变形、超时空移动、运动）组成一个互斥组，由 owner 保证同一时间只有一个生效。
- 效果的属性凡是 Phobos AttachEffect 已有键的都沿用：持续时间、延迟、间隔、重新附加前的冷却、最大触发次数、来源、变形或创建时是否继承、是否无视铁幕。新增属性使用同一个读取器。
- 运动由引擎叠加到对象的移动上，从不以坐标形式写入。
- 显示在对象上方的文字、数值或按钮属于客户端显示属性（第 10 节），不是效果。

一个对象可以携带任意多个标记，所属方也可以。动作和效果负责添加和移除，约束条件负责判断。一个标记带一个整数值和一个可见度等级：仅本所属方、盟友、能看到该对象的玩家，或所有人。两者都在添加标记时给出（`addMark(t, mark, value, visibility)`）；`markValue` 读取值，`setMarkValue` 修改值。客户端查询只返回本玩家有权看到的标记。标记不能嵌套。标记名只由模拟代码注册；注册表属于模拟状态，存档并计入哈希，客户端模块只能查找名字（附录“ID”一节）。

### 6c. 查询

查询是只读的。结果按创建序号排序，这个规则不依赖引擎如何存放对象；结果写入模块提供的缓冲区（第 15 节）。有三个列表保持自己的顺序：对象的持续效果按添加顺序，它的标记按加上的顺序，所属方按所属方数组的顺序。在客户端模块中，查询只暴露本玩家自己的界面能显示的内容（附录 7.7）：本玩家自己的所属方和对象的全部信息，其他所属方的公开信息，以及本玩家能看到的其他所属方对象的类型、位置、所属方和生命。

- **对象：** 按格子、半径或矩形区域，按类型、所属方或类别查找；对象的类型、所属方、生命、位置、任务、目标、等级、弹药、乘客、持续效果和标记。
- **所属方：** 金钱、发电量和耗电量、拥有的建筑和已满足的前提条件、科技等级、盟友和敌人、阵营、是否已战败。
- **地图：** 尺寸；格子的地形类型、高度、覆盖物和矿石、对某种移动区域是否可通行、某个所属方能否看到；路径点和 CellTag。
- **规则：** 任意类型的任意键，以解析后的值返回。
- **场景：** 帧号、难度、游戏模式、玩家数。
- **探测**（版本 1 候选，待定问题 12）：某武器现在能否向某目标开火、目标是否在射程内、某类型能否由某所属方建在某格，以及最近的可放置格子。它们复用引擎自己的规则。

### 6d. AI

电脑所属方保留它们的 AI。版本 1 允许模块创建特遣部队和小队类型（`[TaskForces]`、`[TeamTypes]`）、指派 AI 小队脚本（`[ScriptTypes]`）、启动和解散小队，以及启用或禁用 AI 触发器（`[AITriggerTypes]`），全部通过现有的 owner（`sim/ai_team_creation.rs`、`sim/team_script_vm.rs`）完成。让 AI 学会使用 mod 新增的机制，留给后续 RFC。

### 7. 运行时的触发器和标签

模块按地图的同一模型创建触发器和标签：

```ts
// 在一个动作 (ctx, e) 内部：
const def = new TriggerDef([new EventDef(Event.Killed)], [Action.wasm("onConvoyLost")]);
def.house = ctx.house("Americans");
const t = Trigger.create(def);
const tag = Tag.create([t], TagRepeat.Repeating);
Techno.setTag(e.subject, tag);   // 和原版一样，替换对象原有的标签
const cell = new Cell(40, 52);
cell.setTag(tag);                // CellTag；Cell 是类，不是句柄
Trigger.disable(t);

const panic = Trigger.create(new TriggerDef([new EventDef(Event.TakeDamage)], [Action.wasm("giPanic")]));
Trigger.bindType(panic, ctx.typeId("E1"));   // 和 Wasm.Tags= 一样：每个 E1 运行自己的实例
```

- 新建的触发器和标签放进现有触发器运行时的列表，和地图里的放在一起，不另存一份。
- 它们使用确定性的编号，不会和地图里的编号冲突，并随触发器运行时一起存档和计入哈希。
- 一个对象只有一个标签（`ObjectClass` 的 `AttachedTag`，`+0x34`），一个标签可以连接多个触发器。让一个对象挂多个标签属于 VERA 扩展，需要单独的 RFC。
- 类型绑定（INI 中的 `Wasm.Tags`、代码中的 `Trigger.bindType`，以及用于武器事件的 `Trigger.bindWeaponType`、`bindWarheadType` 和 `bindProjectileType`）不占用这个槽位，而是作为独立的订阅另外记录。所以地图上预先放置、自带标签的对象保留它的标签，同时也接收所属类型的触发器。代码中的绑定立即作用于该类型的每个对象，mod 和地图的模块都可以使用。
- 得到一个标签（`Techno.setTag`）、而该标签含有模块触发器或 VERA 新增事件上的触发器的对象，会得到它自己的一个标志位，所以即使它的类型没有绑定任何东西，事件触发点也会为它引发这些事件（第 15 节）。
- 每个绑定对象以各自的实例运行绑定的触发器：重复状态按对象分开，所以一次性触发器对每个对象各触发一次。禁用或删除触发器会作用于所有实例。触发器的所属方是它触发那一刻主体的所属方，标签持有者是引发事件的对象。
- 删除对象或标签时，通过触发器运行时现有的清理逻辑解除关联。

新的事件和动作编号分配在不与 Ares、Phobos 冲突的范围内。

### 8. 修改规则

| 时机 | 能改什么 | 方式 |
| --- | --- | --- |
| `onRules` | 任意键；新增类型 | 走原生 INI 读取器、钳制和读后处理；计入大厅哈希 |
| 对局中，按类型 | 公开白名单里的键 | `rules.set("E1", "Speed", "6")`：值像 INI 文本一样解析，从下一帧起生效，让相关缓存失效，并作为规则覆盖层存档 |
| 对局中，按对象 | 倍率、等级、所属方、换类型、生命值 | 通过现有的单对象 owner，包括持续效果（第 6b 节） |

- 单对象的倍率复用 `sim/attach_effect.rs` 中已有的 owner。那部分代码有一部分还在 `cfg(feature = "phobos")` 后面，按项目契约的要求，在模块能使用它之前要先迁移到运行时开关。只要模块功能开启（第 14 节），这个 owner 就可用。Phobos AttachEffect 的 INI 键（类型、武器和弹头上的 `AttachEffect.*`，以及 `[AttachEffectTypes]`）只在 Phobos 开关打开时读取，所以原版玩法保持原样；模块定义的效果类型通过模块 API（`onRules`）创建，不需要这些键。只有 VERA 才有的效果种类也以同样方式开启。
- 每个白名单键都要写明修改它对地图上已有对象的影响（例如新的 `Strength` 下当前生命值如何变化）。
- 对局中不能新增类型。
- 启用 Ares 或 Phobos 时，模块能在规则中看到它们的键。白名单逐个写明这些扩展键能否在对局中修改。

### 9. 示例：抛射体弹道

四个层级都在 `rules.wasm` 中运行，因为它们决定打中什么。`ui.wasm` 可以加纯视觉效果，比如拖尾和光效。

| 层级 | 机制 | 开销 |
| --- | --- | --- |
| 1 | `onRules` 设置现有键（`Arcing`、`ROT`、`Vertical`，启用 Phobos 时还有 `Trajectory`） | 对局中无开销 |
| 2 | 武器开火、抛射体引爆的触发器：额外的抛射体、分裂、连锁 | 每次事件，仅限绑定的类型 |
| 3 | `onLaunch` 返回一条路径（贝塞尔、抛物线、螺旋、路径点），引擎用定点数沿路径推进抛射体 | 每个抛射体一次调用 |
| 4 | `onTrajectoryFrame(type, bullets)` 修改速度或位置，或请求引爆，一次处理该类型的全部抛射体 | 每帧每类型一次调用 |

引擎在 `ProjectileTrajectory` 里，在三条原生飞行分支（`BulletClass::AI` `0x004666E0`）旁边新增一条模块分支。碰撞仍由 `world::projectile_collision` 处理，引爆判定仍在 `sim/projectile`，伤害和弹头仍在 `combat`。引擎会钳制模块的输出：速度和位置有上限，离开地图就引爆或删除。每个抛射体有 16 字节的模块数据，存档并计入哈希。

要一次发出多枚不同弹道的抛射体，就在武器的开火事件上挂一个动作来生成它们，每枚有自己的类型和模块数据，再由 `onLaunch` 分别给出路径。这个动作是模块函数，从它的事件记录中读出射手、目标和原生抛射体（`e.subject`、`e.other`、`e.projectile`）。原生抛射体在单位更新时射出，模块生成的抛射体在模块阶段射出，所以它们比原生抛射体晚两者之间的那段时间：至多一帧的位移，取决于模块阶段放在哪里（待定问题 8）。生成抛射体需要的参数比原子动作能带的多（第 6b 节），所以触发器只能通过模块动作生成抛射体。

`Override.Fire` 避免这段延迟。它返回一份射击方案：要生成的抛射体的列表，每枚带自己的类型、模块数据和参数。引擎在原生射击本应射出的那一刻立即生成它们，不生成原生抛射体；空方案什么也不发射，“未处理”则保留原生射击。这次射击的其他所有原生效果照常发生：射速计时器、弹药消耗和装填、连发计数、开火音效、枪口动画、后坐，以及开火时解除隐形或暴露。方案中的抛射体像原生抛射体一样引发 `ProjectileIncoming` 和目标的 `AttackedBy`。`Fire` 事件仍然引发，其 `projectile` 为 `NO_HANDLE`。mod 和地图的模块都绑定了这次射击时，地图的一环收到 mod 的方案，可以保留、修改或替换它。开火步骤是批量段时，抛射体在该段结束时生成（第 5 节）。

### 10. 客户端模块

**界面树。** 界面树由引擎持有，引擎负责布局和绘制。模块通过一小组操作修改它：新建和删除节点、设置属性（显示文字、图像、位置、可见性）、按名字查找节点，以及接收点击、悬停和热键。修改按渲染帧批量提交，不会每帧重建整棵树。不暴露图形 API。

作者分两部分编写界面：

- **静态布局写在 INI 里**，语法和键与 `veraui.ini` 相同（`Type`、`Hold`、`X`、`Y`、`Width`、`Height`、`Parts`、`Label`）。本 RFC 新增 `List` 部件类型，以及 `Text` 部件的 `Label` 键。引擎在对局开始时读取，不需要预编译。没有动态部分的界面不需要模块。
- **动态部分写在模块代码里**：按名字找到节点后修改，或新建节点。

```ini
[Mission.Field]
Parts=Messages,Timers,Banner,Powers,Clock,Objectives

[Mission.Objectives]
Type=Column
Hold=TopRight
Width=240
Parts=ObjTitle,ObjList

[Mission.ObjTitle]
Type=Text
Label=TXT_OBJECTIVES    ; Text 新增的键：字符串表中的一行，跟随游戏语言

[Mission.ObjList]
Type=List               ; 新增的部件类型
```

```ts
onStart((ui: Ui): void => {
  Node.setItems(ui.find("ObjList"), ["TXT_OBJ_RADAR", "TXT_OBJ_CONVOY"]);
  ui.create(new Column(Hold.BottomLeft, [new Text("TXT_WAVE")]));
});
```

React 或 JSX 风格的库可以放在 SDK 里：它在模块内部计算差异，再发出同样的操作，引擎完全不知道它的存在。这类库只能用于 TypeScript（AssemblyScript 没有闭包），不属于官方 API。

**其他客户端功能：**

- 单个对象的显示属性：图像、调色板、着色、附加动画、可见性，以及显示在它上方的文字、数值或按钮。会影响玩法的属性（如隐身）属于模拟模块。
- 选中单位和点击按钮属于客户端事件。要改变游戏，模块发送一条消息（第 1 节），由模拟模块在 `onMessage` 中处理，这样联机和回放都保持一致。
- 客户端模块可以发出标准玩家指令（选择、移动、攻击、部署、建造），引擎像校验任何玩家输入一样校验它们。`sendMessage` 用于自定义逻辑。
- 每个 mod 和每张地图在玩家本机各有一个自己的小型键值存储，带容量配额，用于战役进度、成就和设置。mod 的存储以它的 `[Mod] Name` 为键；地图的存储以它的存储 ID（`[VeraWasm] StorageId=`，默认为地图的文件名）为键，所以修改过的地图只要 ID 不变就保留它的存储。地图的客户端模块使用地图的存储，在 mod 下也是如此，所以下载来的地图无法读取或修改 mod 的数据。只有客户端模块能使用存储。需要影响对局的数据通过 `sendMessage` 送进模拟，因而成为命令流的一部分。
- 图像、动画和模型都按名字引用，从不按文件格式引用，所以以后新增素材格式（单独的 RFC）不需要修改 API。
- 声音和消息；`log()` 输出到游戏内控制台。
- 通知是具名的，名字只解析一次，换成 ID：`Notify.id("WaveStarted")` 返回一个 `NotifyId`。这个 ID 是名字按 ASCII 统一大小写（只折叠 `A` 到 `Z`）后的 UTF-8 字节的 32 位 FNV-1a 哈希，在每台机器上、在模拟模块和客户端模块中都按同样的方式计算。模拟模块要预先声明它发送的通知名：SDK 构建时按模块项目配置中的列表，把这些名字写进 Wasm 自定义段 `vera.notify`。这个列表的格式属于 SDK 文档，不属于引擎 API。客户端模块不声明任何名字；已声明但没有任何客户端模块接收的名字不算错误。在模拟模块中，对模块没有声明的名字，`Notify.id` 返回 `NO_ID` 并设置 `NotFound`。在客户端模块中，只有本局某个模拟模块声明过的名字才返回 ID，因为引擎保存着已声明名字的表；其他名字返回 `NO_ID` 并设置 `NotFound`，所以客户端从不会靠哈希匹配到未声明的名字。引擎在加载模块时，把本局加载的所有模拟模块（mod 的和地图的合在一起）声明的通知名放在一起检查冲突，通知名发生冲突的模块会被拒绝，并提示是哪些名字（第 3 节第 6 步），所以对每个已声明的名字，`Notify.id` 都能返回 ID。模拟模块用 `ctx.notify(house, id, data)` 向某个玩家的客户端发送通知，或用 `ctx.notifySpectators(id, data)` 发给每个观战者的客户端；每个客户端模块都在 `onNotify(ui, source, id, data)` 中接收，并得到发送它的模块的来源（第 2 节）。回放观看者收到他所观看视角的玩家的通知，或观战者的通知。观战者不能向模拟发送消息：观战者客户端的 `sendMessage` 会被拒绝。
- 客户端查询只暴露本玩家自己的界面能显示的内容（附录 7.7）：本玩家自己的所属方和对象的一切；其他所属方只有公开信息（名字、阵营、同盟关系、是否已战败）；本玩家当前能看到的其他所属方的对象，只有类型（对伪装的敌人是伪装成的类型）、位置、所属方和生命。乘客、目标、任务、超级武器充能、其他所属方的金钱和电力、全局和局部变量、触发器和标签永远不可见，视野查询只回答本玩家自己所属方的情况。客户端需要的其他任何东西都通过通知送达。观战者的客户端模块看到观战者能看到的范围，房间允许时为整张地图。玩家当前看不到的其他所属方的对象不出现在结果中；引擎不保存“最后一次看到”的副本。
- 玩家自装的界面模块放到后续阶段。mod 或房间可以禁止它们。

### 11. 联机

- 嵌入的模块随地图传输。mod 的模块计入现有的 mod 文件校验。
- 大厅比对模块哈希和所需的 API 版本；它在加载模块之前读取每个 `[VeraWasm] Api=`。由于房间要求同一游戏版本（见下文），版本检查只在版本可能不同的地方起作用：需要房间的游戏所没有的 API 版本的地图或 mod 无法被选择；离线时，存档或回放会被拒绝；每种情况都给出指明所需版本的提示。mod 的 `[VeraWasm]` 键（额度、地图政策、API 版本）在它的 `rulesmd.ini` 中，mod 摘要包含这个文件，所以每个玩家都会比对它们；摘要不包括的 `mod.ini` 不放任何模块键。
- 每条消息的发送者由引擎填写，模块无法伪造；单条消息大小和每帧消息数有上限。
- 模拟模块发给客户端的通知只送达目标玩家或观战者。通知的内容是模块自己的字节，由模块作者负责：引擎无法过滤它。
- 联机只交换指令，从不交换状态。重连的玩家从头重新模拟整局，包括模块；模块消息本身就是指令，所以不需要额外发送任何东西。因此模块每帧的开销也会拖慢追帧速度。追帧期间不投递通知，客户端模块也不运行；追帧结束后它们收到一次 `onStart`。
- 回放记录模块哈希和 API 版本。模块不一致的回放会被拒绝并提示原因。
- 存档记录模块哈希。模块与当前安装的 mod 或地图不一致的存档会被拒绝，并提示是哪些模块。
- 房间要求所有玩家运行同一版本，所以混合版本的房间不会开局，联机是安全的。
- 离线时，支持模块之前的版本会不带模块地运行模块地图：它忽略 `[VeraWasm*]` 节，地图触发器中的模块动作什么也不做。已发布的版本无法再修改，所以这是一个明确记录的遗留问题。为了涵盖之后的版本，支持模块之前的那个版本增加一个地图键 `[Basic] VeraMinVersion=`（名字未定），对需要更新版本的地图拒绝运行并给出指明版本的提示；模块地图设置这个键，所以从那以后的每个版本都会拒绝它们，而不是错误地运行。
- 存档和回放记录游戏版本和模块哈希；旧版本会拒绝新版本生成的存档和回放，并给出提示。
- 实现时更新 [Networking](../Networking.md)，说明已发布的游戏、混合版本的房间以及回退版本分别如何处理模块。

### 12. 版本与 ABI

- 一份用 WIT 语法编写的接口定义是 API 的唯一来源。项目自己的生成器由它生成 Rust 和 TypeScript SDK 的绑定、参考文档和兼容性检查。WIT 只是接口描述语言：模块不使用 Component Model 的 canonical ABI。
- 二进制接口是 core module ABI：core Wasm 模块的导入和导出、整数句柄和 ID、字符串、字节和缓冲区用的指针加长度，以及由宿主写入模块所提供缓冲区的结果。接口定义写明它的每种类型如何映射到这个 ABI。原因如下：
  - 浏览器版可能使用的每个引擎，包括浏览器自带的引擎和解释器，都能运行 core 模块（第 14 节，待定问题 1）；
  - 第 15 节需要零拷贝缓冲区：宿主把查询结果、事件记录和批量数据直接写进模块内存；
  - 模块的全部状态都在线性内存、全局变量和表中，所以存档、状态哈希和重连都能完整捕获它（第 4 节）；
  - AssemblyScript 能产出可以嵌入地图的小模块，它构建的是 core 模块（第 5a 节，待定问题 2）；
  - core 规范已经冻结。
- 以后的某个主版本可以在 core ABI 之上增加一个 Component Model 适配层。已有模块继续使用 core ABI，不受影响。
- 接口是带版本的包：`vera:sim@1`、`vera:client@1`。版本号是“主版本.次版本”。新的主版本不兼容，每个主版本都通过适配层永久保留；新的次版本只做增加。模块通过它的导入说明需要的主版本和最低次版本，地图或 mod 在 `[VeraWasm] Api=` 中写明同样的版本。大厅在加载之前读取 `Api=`，检查每个玩家的游戏都支持这个主版本，且次版本不低于它；加载时检查模块的导入与它一致（第 3 节）。
- 不稳定的接口放在 `vera:unstable/*` 下，需要显式开启，可以不经通知就改变。它们和 `0.x` 预览版都不是已发布的版本：不保留适配层，使用它们的模块只能在为之构建的那个版本上运行。
- 每个已发布的版本都一直可用。旧版本是现行实现之上的薄适配层，从不是第二份实现。适配层从不把旧版本没有定义的值交给旧模块：该版本不认识的事件的记录不投递给它，更新的状态值或枚举值以该版本定义过的值交给它，具体对应关系按枚举写在接口定义中。
- 对每个已发布的版本，CI 用仓库中提交的 Rust SDK 源码构建一组兼容性测试用例并运行它们；不提交 `.wasm` 二进制文件。破坏其中任何一个都会让构建失败。这组用例随每个版本增长，是对项目“每个修复一到三个回归测试”规则的有意例外。
- 计量单位、每类宿主调用的费用、默认额度和各项上限属于主版本的一部分，随主版本固定（第 4 节）。
- 函数可以弃用并向模块作者发出警告，但已发布的版本永不删除。
- 已发布的函数永不改变单位或含义。要改变，就新增函数或发布新版本。
- 自定义段 `vera.actions`、`vera.notify` 和投递区声明各以一个格式版本开头。其中的名字是 UTF-8，必须是 ASCII，并且只按 ASCII 规则统一大小写。
- `Trigger.create` 和 INI 通过模块的 `vera.actions` 表把 `Action.wasm` 的名字解析为一个下标；`EventRecord.action` 携带这个下标，SDK 生成的 `onEvents` 据此分派。因此动作函数不必是 Wasm 导出函数。

### 14. 项目契约

- 扩展模块功能（不要与浏览器版的 `wasm`、`wasm-net` 和 `wasm-threads` 构建 feature 混淆）存在于每个构建中，当 mod 或地图提供模块，或使用它的任何键（`Wasm.Tags`、INI 原子动作、`[VeraWasm]`）时，在运行时开启。从不放在构建 feature 后面。只要它开启，持续效果的 owner 就可用；Phobos AttachEffect 的 INI 键仍然只在 Phobos 开关打开时读取（第 8 节）。
- Wasm 运行时按平台选择，放在平台构建 feature 后面，项目契约允许平台 feature 这样做：桌面上用原生引擎，浏览器版用浏览器自带的 WebAssembly 或另一个引擎（待定问题 1）。模拟通过同一个接口访问运行时，所以 `vera20k-core` 和 `sim/` 仍能为浏览器编译。
- 每次模块调用都通过状态现有的 owner 访问状态。API 不引入竞争状态。
- 功能在 `docs/` 下为 modder 编写文档。
- 模块出错在游戏中报告，从不只写进日志。

### 15. 性能

引擎只保留一份游戏状态。模块持有整数句柄和 ID，需要数据时再查询；不会把游戏世界复制进模块内存。下面这些规则让跨边界的开销保持很低，它们属于接口定义的一部分，并依赖 core module ABI（第 12 节）：

- **热路径用 ID，不用名字。** 类型、所属方、武器、弹头、抛射体、标记和效果的名字，以及附录列出的其他命名种类，都只解析一次，换成整数 ID（`ctx.typeId("E1")`、`Mark.id("Panicked")`），通常在 `onRules` 或 `onScenarioStart` 中完成；ID 一经分配就不再改变（第 2 节）。其他所有调用都传 ID。接受名字的调用（查找、`rules.set`、创建触发器）只用于初始化和不频繁的修改；SDK 会缓存 ID。通知 ID 是名字统一大小写后的稳定哈希，在每台机器上、在两侧都相同（第 10 节）。
- **每个模块每帧只投递一次。** 本帧排队的模块动作按第 5 节的顺序（主体的创建序号，再按同一对象内的引发顺序）写成固定大小的记录，一次调用交给每个模块。每条记录是一个模块动作，加上触发其触发器的那个事件的载荷；没有单独的事件记录。记录的布局属于接口定义。SDK 在模块内存中预留投递区，并在加载时说明它的大小；每帧的队列上限（第 5 节）限制一次调用投递的数量。
- **查询结果写进模块的缓冲区。** 结果直接写入模块提供的缓冲区，引擎每次查询都不分配内存。结果按创建序号排序（第 6c 节的三个例外除外），开销随结果的大小增长，而不是随整个世界的大小增长。结果多时分页返回：分页查询的结果集在一次模块调用中读取第一页时确定，保存在每个模块一个可复用的暂存缓冲区中，同一次调用中后面的页延续这个结果集，即使世界在两页之间发生了变化。
- **宿主调用按实际工作计费。** 每次宿主调用按它所做的工作从运算额度中扣除，按扫描或返回的每个对象或检查的每个格子计算，所以模块无法用看似廉价的调用拖住每台机器（第 4 节）。
- **旁路表。** 标记、订阅和每个抛射体的模块数据放在按句柄索引的旁路表里，类型绑定放在按类型索引的表里，只有用到它们的对象和类型才占空间。每个事件触发点只检查对象所属类型的一个标志位，或者在对象得到带模块触发器的标签时检查对象自身的标志位（第 7 节）；两者都没有设置时，其余代码都不运行。
- **轮询型事件**有最小间隔，引擎按创建序号对间隔取模，把不同对象的检查分散到不同的帧（第 6a 节）。
- **哈希中的模块内存。** 联机的不同步检测使用每帧的多人同步校验。它每 15 帧包含一次每个模块内存的哈希，模块内存的大小受内存上限约束，所以模块内存中的分歧在联机时能被检测到。回放日志的诊断哈希（每 15 帧一次）和完整状态哈希也包含模块内存。它们的开销属于待定问题 3。
- **SDK 不为每个事件分配对象。** 句柄和 ID 都是值类型：在 TypeScript 中，句柄是小于 2^53 的 64 位整数，ID 是 32 位整数；在 Rust 中，两者都是 newtype。只有 `Trigger.create` 这类初始化调用才会创建对象。
- **逐帧批量数据**（L4 行为、模块弹道）直接写入模块内存，再从中读回，每个对象几十字节。
- **按最慢的平台定额度。** 计量会让模块代码变慢，浏览器版还可能用解释器运行模块。锁步联机中最慢的机器决定整体速度，所以默认运算额度按最慢的受支持平台确定，并在 RFC 接受之前实测（待定问题 1 和 3）。
- **没有模块就没有开销。** 没有模块时，每个事件触发点只多一次标志位检查，其余代码都不运行。

## 备选方案

- **由引擎运行 Lua**（Recoil 的做法）。对 modder 友好，但浮点和表遍历顺序的确定性要靠修改解释器保证，API 也会长成一个没有版本的全局命名空间。
- **在引擎里内置语言运行时**（随 VERA20k 发布 Lua 或 JavaScript 运行时，供模块导入）。模块会更小，但引擎要永远维护一个语言运行时，并且每个 API 版本都要固定一个构建。未采用：语言留在作者的工具里。
- **原生插件。** 无法移植到浏览器版，也没有沙箱。
- **以 Component Model 及其 canonical ABI 作为二进制接口。** 不采用（第 12 节）：浏览器不能原生运行组件，浏览器版中的解释器也还需要一个组件运行时；canonical ABI 通过模块内的分配传回结果，而第 15 节需要宿主写入模块自己的缓冲区；资源句柄放在模块内存之外、每个实例一张的表中，存档、状态哈希和重连都得另外捕获它；AssemblyScript 不产出组件；组件规范仍在变化，而 core 规范已经冻结。WIT 仍作为接口描述语言。以后的某个主版本可以在 core ABI 之上增加 Component Model 适配层，不影响已有模块。
- **以某个所属方的视角做模拟查询。** 暂不采用。模拟查询能看到全部，客户端查询按视野过滤。
- **由宿主保证覆盖点是纯函数**（丢弃覆盖点调用期间写入的状态，禁止取随机数）。不采用：固定的调用顺序（第 5 节）以更低的代价让覆盖点的状态保持确定。
- **客户端模块之间直接发消息。** 不采用。玩家之间的所有通信都经过模拟，联机只保留一条通道。
- **只增加 INI 键。** 简单需求仍然适用，够用时依然是首选，但表达不了通用逻辑。

## 参考先例

- **Recoil（Spring）。** 同步与非同步代码分离；非同步代码只能通过网络消息影响模拟；单对象的数值带可见度等级；代价高的回调只对脚本关注的对象触发。借鉴的教训：不暴露底层图形 API；用带版本的包取代单一全局命名空间；回调需显式订阅。
- **红警 3（SAGE）。** 在数据文件里把对象事件绑定到脚本函数，可以继承，处理函数收到对象本身。借鉴：在数据里绑定，而不是在代码里。
- **Phobos。** 抛射体的 `Trajectory=` 类型；用于单对象修正的 AttachEffect。
- **社区的“触发-效果-约束条件”设计**（本 RFC 讨论期间分享的一份表格）。借鉴：触发器由事件、约束条件和动作组成；投递型与轮询型事件；带类型参数的事件清单；瞬时动作、持续效果和约束条件清单。未采用：INI 里的记录器和算子，改由模块代码实现。

## 待定问题

1. **浏览器版。** 浏览器版能否以和原生版完全一致的结果运行模块？用哪个引擎？wasmtime 可能无法在浏览器中运行。
2. **TypeScript 编译器。** TypeScript SDK 用哪种编译器：把 TypeScript 子集编译成 Wasm 的编译器（如 AssemblyScript），还是把 JavaScript 引擎编译进每个模块？引擎对两者没有区别；这个选择决定模块体积、速度，以及普通 TypeScript 代码能用多少。
3. **计量。** 运算计数和调用深度用哪种插桩？在 2 万单位下开销多大？在多人同步校验中每 15 帧哈希一次全部模块内存的开销多大？回放时，其他包含模块内存的状态哈希开销多大？
4. **INI 格式。** 用文中所示的具名节，还是用原版逗号分隔的触发器编码以便 FinalAlert2 编辑绑定，还是两者都要？考虑到绑定、约束条件和原子动作在没有模块时也能用，键用什么前缀？
5. **事件和动作编号。** 哪个范围不与 Ares、Phobos 冲突？
6. **FinalAlert2。** 保存地图时会不会保留 `[VeraWasmRulesPack]` 这类它不认识的节？
7. **上限。** mod 和地图的嵌入体积、内存、加载时形状上限、基础运算额度和每条记录的额度、每类宿主调用的费用、初始化函数、`onRules` 和 `onScenarioStart` 的一次性额度、每帧队列上限、积压上限、客户端模块每个渲染帧的运算额度、最小轮询间隔、消息大小和频率，以及存储配额。它们按 API 主版本固定（第 12 节）。
8. **帧阶段。** 模块阶段放在模拟帧的哪个位置；模块弹道分支相对碰撞和引爆判定的位置。
9. **存档体积。** 快照中的模块内存：压缩方式和内存上限。
10. **首批覆盖点。** 版本 1 提供哪两三个覆盖点。
11. **白名单。** 版本 1 中哪些键可以在对局中按类型修改。
12. **版本 1 清单。** 第 6a 到 6c 节中哪些事件、约束条件、动作、持续效果、查询和探测，以及附录中其他哪些 `v1?` 条目，进入版本 1。
13. **效果叠加。** 每种持续效果的叠加方式和所属互斥组。
14. **界面布局。** mod 和地图把布局节放在哪里，以及版本 1 的控件集合。
15. **地图文字。** 地图无法携带字符串表，地图模块的文字如何翻译。
16. **战役。** 每一关的模块是重新开始，还是延续上一关的状态。
17. **连锁上限。** 含有模块触发器、VERA 新增的事件或原子动作的连锁，每帧的深度上限，以及每帧这类连锁触发总次数的上限（第 5 节）。
