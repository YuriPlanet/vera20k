**实现状态。** 0.1.0 版描述引擎已实现的样子：第 1 阶段（`rules.wasm`，含控制点）和第 2 阶段（`ui.wasm` 客户端模块）都已进入引擎，随附 Rust SDK 和 [TypeScript SDK](../wasm-modules/ts-sdk.zh-CN.md)。引擎与早先草案不一致之处，本文以引擎为准。尚未实现的设计保留在文中，标为“0.1.0 未实现”，或在附录中标为 `later`。API 处于 `0.x` 预览期（流程第 4 步）：版本 1 冻结之前，编号、上限和布局仍可能变化。

## 概要

mod 和地图可携带模拟模块 `rules.wasm` 和界面模块 `ui.wasm`。引擎在沙箱中加载编译好的模块。模拟模块通过属性、变量、事件和动作修改玩法，客户端模块通过节点构建界面。官方 SDK 为 TypeScript 和 Rust：Rust SDK 随 0.1.0 提供，TypeScript SDK 正在实现中。其他语言按[模块 ABI](#5a-语言与-sdk)接入。函数签名、固定布局和编号见 [API 附录](0001-wasm-extension-modules-api.zh-CN.md)。模块可以把自己的机制注册为 INI 名字，供不写代码的 modder 使用（第 6h 节），也可以替电脑所属方或本玩家操作（第 6i 节）。

## 目标

1. modder 不改引擎也能修改玩法和界面。
2. 所有玩家运行相同的模拟模块并得到相同结果：在任何受支持的平台上（包括浏览器版）都不会不同步。
3. 开局前报告模块错误并拒绝开局；对局中模块出错时停用该模块，提示原因，对局继续。
4. 模块不得访问文件或网络。模拟模块不得读取时钟；客户端渲染计时仅用于显示。按运算量计费。客户端只读本机可见状态和获准读取的变量；模拟模块自行决定通知内容。
5. 没有模块、地图和 mod 也未使用扩展键时，沿用原版玩法。
6. 只有少数对象或类型使用的模块不会拖慢 2 万单位规模的战斗。
7. 红警 2 modder 从模板开始，几分钟内就能在游戏里看到改动效果。

## 非目标

- 原生插件（`.dll`、`.so`），或在沙箱外加载任何东西。
- 引擎里出现源代码。引擎从不解析、编译或解释任何源语言，也不内置任何语言运行时。
- 暴露引擎内部：内存布局、原生地址、内部对象下标或存储槽位（句柄是对象的创建序号，第 5 节）、渲染器的图形 API。
- 对局中新增对象类型。
- 取代原版触发器系统。模块是在它的基础上扩展。
- 修改地图地形：模块不能放置或移除覆盖物（墙、桥等），不能改地块。原版的矿石增减动作照常可用。

## 术语

| 术语 | 含义 |
| --- | --- |
| 引用 / 句柄 | 引用表示对象、类型、格子、路径点或全局状态。模拟对象句柄为永不复用的创建序号，客户端节点使用本机序号；0 为空。 |
| 触发器 / 标签 | 触发器包含事件、筛选和动作。原版地图通过标签将触发器挂到对象或格子；模块也可直接绑定。 |
| 模块触发器 | 由模块创建、通过 `Wasm.Tags` 或 `trigger_bind` 绑定，或带模块动作或决定处理函数的触发器。 |
| 安全点 | 一次计算之前、完成后或整批结果提交后，允许执行触发器立即动作的位置（第 5 节）。 |
| 帧 / 渲染帧 | 游戏时长按模拟逻辑帧计；渲染帧为本机显示周期。地图距离以 lepton 计，1 格 = 256 lepton。 |

## modder 看到的样子

### 文件

```
Mods/MyMod/
  mod.ini        ; Needs= 和其他 mod.ini 键；不含模块键
  rulesmd.ini    ; [VeraWasm]：API 版本、额度、地图政策；把标签绑定到类型
  rules.wasm     ; 模拟模块
  ui.wasm        ; 界面模块
```

地图在 `[VeraWasm]` 声明 API 和模块大小，在 `[VeraWasmRulesPack]`、`[VeraWasmUIPack]` 中嵌入压缩后按编号分行的 base64 数据。`asset` 负责嵌入、提取和加载校验。键、默认值与编码见[附录 INI 键](0001-wasm-extension-modules-api.zh-CN.md#ini-键)。

嵌入节不依赖注释、空节、节顺序或键顺序：地图编辑器保存时会丢掉或重排它们。`asset` 可以对编辑器保存过的地图重新嵌入和校验。

### 把触发器绑定到类型

```ini
; mod 里的 rulesmd.ini
[E1]
Wasm.Tags=GIPanicTag     ; 每个 E1 都接收这个标签的触发器

[GIPanicTag]
Trigger=GIPanic

[GIPanic]
Event=TakeDamage
Where1=Subject.HealthPercent<30      ; 筛选子句，全部成立才触发（第 6a 节）
Where2=Var(Subject,Panicked)=0
Action1=SetVar(Subject,Panicked,1)   ; 原子动作，触发时立即执行：同一帧里这个 E1 后面的伤害不再通过 Where2
Action2=Wasm:giPanic     ; 运行 mod 的 rules.wasm 中的模块动作 giPanic（第 2 节）
Repeat=Repeating         ; TagRepeat 的取值
```

每个 E1 都以自己的实例运行 `GIPanic`（第 7 节）。只有生命低于 30% 且变量 `Panicked` 为 0 的 E1 才会把记录投递给模块，其他 E1 的伤害在引擎内就被筛掉；原子动作 `SetVar` 在触发时立即写变量，所以每个 E1 只投递一条记录。节格式见第 6a 节。不装模块时，变量可在 `[VeraVars]` 中声明（0.1.0 未实现：变量由模块的 `vera.vars` 声明）。在 FinalAlert2 里编辑的地图触发器通过动作 1036 调用模块函数（0.1.0 未实现）。

### 模块代码

引擎只看到编译好的模块，源码和编译器都在作者自己的工具里。下面分别用两套官方 SDK 表达同一行为：Rust 示例用的是 0.1.0 的 SDK，TypeScript 示例用于说明设计。可构建的例子见 [TypeScript 模拟模块教程](../wasm-modules/ts-tutorial.zh-CN.md)和[客户端模块教程](../wasm-modules/ts-ui-tutorial.zh-CN.md)。类型绑定在 INI 和代码中任选一处；若用上一节的 INI，只注册具名回调，省略代码中的触发器创建。

```ts
// TypeScript 设计示例
import { Trigger, Event, Prop, Op, Techno, Mission, Var, VarTarget, ActionDef, Target, Rules,
         TakeDamageEvent, namedAction, onScenarioStart, onFrame, Every } from "@vera20k/sdk";

import { Panicked } from "./generated/vars";

function giPanic(e: TakeDamageEvent): void {
  Techno.setMission(e.victim, Mission.Hunt);   // 一次宿主调用：set(subject, Mission, Hunt)
}
namedAction("giPanic", giPanic);       // 名字必须是字符串字面量：SDK 构建时静态提取，写入 vera.actions，INI 才能引用这个名字

onScenarioStart((): void => {
  Trigger.on(Event.TakeDamage)
    .bind(Rules.technoType("E1"))                  // 每个 E1 运行自己的实例（第 7 节）
    .where(Prop.HealthPercent, Op.Lt, 30)
    .whereVar(VarTarget.Subject, Panicked, Op.Eq, 0)
    .immediate(ActionDef.setVar(Target.Subject, Panicked, 1))   // 原子动作，在触发器触发时执行
    .enqueue(giPanic).done();                              // 调用 trigger_create 和 trigger_bind
});

onFrame(new Every(15), (): void => {
  if (Var.local(3).get() != 0) {    // 红警 2 局部变量 3
    // ...
  }
});
```

```rust
// Rust SDK 写法（vera20k-sdk，no_std）
#![no_std]
use vera20k_sdk::prelude::*;

vera20k_sdk::vars! {
    static PANICKED: ObjectVar = ("Panicked", Private, 0);   // vera.vars
}
vera20k_sdk::named_actions! { GI_PANIC = "giPanic" => 1 }    // vera.actions：INI 可用 Wasm:giPanic 调用

fn gi_panic(e: TakeDamageEvent) {
    let victim = e.victim();
    if PANICKED.get(victim) == Ok(0) {         // SDK 的 where_var 只能测全局变量
        let _ = PANICKED.set(victim, 1);
        let _ = victim.set_mission(Mission::Hunt);
    }
}

fn start() {
    let Ok(e1) = TypeRef::techno_type("E1") else { return };
    let _ = Trigger::on(Event::TAKE_DAMAGE)
        .bind(e1)                                       // 每个 E1 一个实例（第 7 节）
        .where_prop(Prop::HealthPercent, Op::Lt, 30)    // where 是 Rust 关键字
        .enqueue(GI_PANIC)
        .done();                                        // 调用 trigger_create 和 trigger_bind
}

fn check_waves() {
    if Var::local(3).get() != 0 {    // 红警2 局部变量 3
        // ...
    }
}

vera20k_sdk::on_scenario_start!(start);
vera20k_sdk::on_frame!(every = 15, check_waves);   // 每个模块只有一个 on_frame!
vera20k_sdk::on_events!(GI_PANIC => gi_panic);     // 按分派键分发 on_events 的记录
```

每套 SDK 都用一条命令构建出 `rules.wasm` 或 `ui.wasm`（Rust SDK：以白名单特性为 wasm32 目标执行 `cargo build --release`）。SDK 的函数（`Techno.setMission`、`Trigger.on`）设计上由附录的表生成；0.1.0 的 Rust SDK 是手写的，由引擎测试把它的属性常量与引擎的属性表核对（第 12 节）。每个包装函数只发起[附录第 3 节](0001-wasm-extension-modules-api.zh-CN.md#3-sdk-对应)列出的宿主调用，大多数恰好一次（第 5a 节）。Rust SDK 的 crate 名为 `vera20k-sdk`；TypeScript 包名为 `@vera20k/sdk`，位于源码树的 `sdk/typescript`。

### 示例：第一个单位开火时扔核弹

把一个 `Fire` 触发器绑定到全场第一个单位（按创建序号），它开火时，在模块动作中向它的目标格子扔一颗核弹：

```ts
// TypeScript 设计示例
import { Trigger, Event, Find, Prop, Op, Category, Action, FireEvent,
         NO_HANDLE, onScenarioStart } from "@vera20k/sdk";

function nukeAtTarget(e: FireEvent): void {
  Action.nukeStrike(e.targetCell, e.house);   // 事件记录保存的开火目标格；一次 action 调用
}

onScenarioStart((): void => {
  const first = Find.objects()
    .where(Prop.Category, Op.Ne, Category.Building)
    .where(Prop.Category, Op.Ne, Category.Projectile)
    .first();                                    // 一次 find：创建序号最小的单位；没有时为 NO_HANDLE
  if (first != NO_HANDLE) {
    Trigger.on(Event.Fire).bind(first).once().enqueue(nukeAtTarget).done();
  }
});
```

- 只有这个单位开火时才投递记录：其他单位开火时，事件触发点只检查一次自己的标志位就返回（第 15 节）。
- `.once()` 让触发器不重复，只触发一次；去掉它就每次开火都扔。
- 对象绑定随对象一起消失：单位死后不再触发。触发器本身仍留在触发器运行时中，不再需要时用 `Trigger.remove` 删除（第 7 节）。
- INI 无法选出某一个具体的对象：`Wasm.Tags` 只能绑定类型。这种逐对象的选择只能写在代码里。

## 设计

### 1. 两个世界

| | 模拟（`rules.wasm`） | 客户端（`ui.wasm`） |
| --- | --- | --- |
| 接口 | `vera:sim@1` | `vera:client@1`，每个函数都以 `client_` 开头 |
| 运行在 | 每台机器上，锁步执行 | 仅本机 |
| 确定性 | 是 | 否 |
| 可以改变 | 游戏状态，通过引擎的 owner | 界面节点、镜头、光标、本地设置、声音 |
| 影响游戏的方式 | 动作、属性写入、变量、给任何所属方的单位下任务，给电脑所属方的指令，以及认领电脑所属方的领域（第 6i 节） | 通过命令流发出标准玩家指令和消息，包括替本玩家操作（第 6i 节） |
| 引擎侧 | `sim/` | `ui/`、`render/`、`audio/` |

这个划分遵循现有规则：`sim/` 从不依赖 `render/`、`ui/`、`audio/` 或 `net/`。加载器拒绝导入 `client_*` 函数的模拟模块，也拒绝导入模拟函数的客户端模块。

- 从模拟到客户端，不经过网络：客户端读取它能看到的状态和可见度允许的变量；模拟模块用 `send_notify` 向目标所属方的机器发出通知。
- 从客户端到模拟：只有命令流。标准玩家指令像任何玩家输入一样被校验；消息像玩家指令一样进入命令流（第 10 节）。回放和联机都能看到两者。

### 2. 来源：mod 和地图

mod 和地图使用同一套 API 和同一套 SDK，区别在于引擎授予它们的权限。

| | mod | 地图 |
| --- | --- | --- |
| 顺序 | 先 | 在 mod 之后，和 INI 层叠一致 |
| `on_rules` | 在 `RULESMD.INI`、`LANGRULE.INI` 和模式层之后 | 在地图层之后；能看到 mod 的结果 |
| 运算额度 | 在 mod 的 `[VeraWasm]` 中声明，引擎设上限 | 默认更小；mod 的 `[VeraWasm]` 可以调高 |
| 体积 | 受文件大小约束 | 有嵌入上限 |
| 界面 | 可以替换或重排对局界面 | 只能加覆盖层，除非 mod 允许更多 |

mod 在它的 `rulesmd.ini` 的 `[VeraWasm]` 节中控制地图模块能做什么：

```ini
; mod 里的 rulesmd.ini
[VeraWasm]
Api=1.0              ; mod 的模块需要的 API 主版本.次版本
Budget=200000        ; mod 模块每帧的额度，引擎设上限
MapBudget=100000     ; 这个 mod 下地图模块每帧的额度
MapWasm=yes          ; no：带模块的地图在这个 mod 下不能开局
MapUI=overlay        ; overlay、full 或 no
```

- 这些键放在 `rulesmd.ini` 里，因为 mod 摘要包含这个文件而不包含 `mod.ini`，所以房间里的每个玩家都会比对它们（第 11 节）。
- 每个 `[VeraWasm]` 节都从各自的文件读取，从不层叠：mod 的在任何其他层之前从 mod 的 `rulesmd.ini` 读取，地图的从地图读取。地图无法改变 mod 的键。地图自己的 `[VeraWasm]` 只放它的嵌入键、它的 `Api=` 和它的 `StorageId=`。
- 没有选择 mod 时，允许地图模块，地图界面只能是覆盖层，地图模块使用引擎的默认额度。
- 取值是预览期默认值（第 15.4 节），全部键见附录的 [INI 键](0001-wasm-extension-modules-api.zh-CN.md#ini-键)。
- **随地图分发的文件只有地图的权限。** 平台与地图一起分发的文件（例如作为隐藏 mod 安装的地图附带文件）属于地图来源：其中的 `rules.wasm`、`ui.wasm`、`[VeraWasm]` 和类型绑定不能取得 mod 的额度、权限或顺序。分发方须把这个来源告诉引擎；做不到时，分发方拒绝带有模块的附带文件。地图模块只通过嵌入节分发。

**规则层**按以下顺序运行：`RULESMD.INI`、`LANGRULE.INI`、模式层、mod 模块的 `on_rules`、地图层、地图模块的 `on_rules`。每个 `on_rules` 读到的是它之前各层处理后的规则，引擎在它写入之后再处理一次规则，和处理 INI 文本一样。类型 ID 一经分配就不再改变：后面的层可以新增类型并得到新的 ID，但从不让已有的 ID 失效。在 mod 的 `on_rules` 中解析得到的 ID 在整个场景中都有效，存档和读档之后也一样。

**冲突规则：**

- **类型上的标签绑定**在 INI 中（`Wasm.Tags`）只从 mod 的 `rulesmd.ini` 读取。地图中的 `Wasm.Tags` 键被忽略，并告知玩家（0.1.0 在开局时提示，因为大厅不读地图规则）。地图在代码里绑定（`trigger_bind`，第 7 节），所以地图无法抹掉 mod 的绑定。
- **名字。** mod 的 INI 或触发器中的模块名（`Action=Wasm:name`，以及可决定事件的处理函数名）解析到 mod 的模块；地图中的模块名解析到地图的模块。在 INI 中，前缀 `Wasm:mod.name` 和 `Wasm:map.name` 可以指向另一方；地图触发器的动作 1036 中写作 `mod.name`、`map.name`（第 6a 节；0.1.0 未实现）；0.1.0 中同一个 INI 触发器的所有 `Wasm:` 动作必须指向同一个模块；代码创建的触发器和直接执行的 `Module` 动作只能使用本模块的分派键（`lookup(ModuleAction, ...)` 不接受前缀）。变量名（`vera.vars`）也一样：模块按名字找到的是自己来源的变量，加前缀才能找到另一方的。用 `ini_register` 注册的键、注册表和模块事件名不同：同一种类中在本局唯一，mod 和地图共用一个名字空间，不使用前缀（第 6h 节）。
- **消息和通知。** 客户端模块发出的消息（`client_send_message`）到达同一来源的模拟模块的 `on_message`：mod 的界面发给 mod 的模拟，地图的发给地图的。通知（`send_notify`）作为 `Notify` 客户端事件到达目标机器上的每个客户端模块，事件记录带着发送它的模块的来源（mod 或地图）。
- **触发器**：两边的都会触发，mod 的模块先运行。
- **可决定事件**按链式处理：mod 的模块先给出结果，地图的模块拿到这个结果后可以再改，引擎使用最终值。链上的每一环都拿到原生值和上一环的结果（第一环拿到的上一环结果也是原生值）。后一环可以推翻前一环的否决。决定记录带一个明确的“已处理”标志，而不是用特殊值表示；不处理这次请求的一环把上一环的结果原样传下去（第 6f 节）。
- **动作、属性写入和修饰器**按执行顺序走同一个 owner。修饰器的互斥组按来源分开，地图的修饰器不会顶掉 mod 的（第 6c 节）。
- **对等调用**（后续阶段）：mod 可以公开一些函数供地图调用，以后作为新的次版本增加。

### 3. 加载与校验

加载时，引擎依次：

1. 解码嵌入的模块，校验声明的大小；
2. 解析模块，只接受来自 `vera:*` 接口的导入，且本版本支持其主版本并达到模块需要的次版本（第 12 节）；模拟模块只能导入 `vera:sim` 的函数，客户端模块只能导入以 `client_` 开头的 `vera:client` 函数，跨世界的导入一律拒绝；检查这些导入与模块所在 `[VeraWasm]` 节的 `Api=` 一致（大厅已经读过它；导入的模块名带版本，见[附录第 1 节](0001-wasm-extension-modules-api.zh-CN.md#1-模拟-abi)）；在编译之前拒绝超出加载时形状上限（模块大小、函数数量、单个函数体大小、局部变量、导入、导出、类型、全局变量、表项、段和自定义段的项数，第 15.4 节）的模块，这样地图无法在编译时拖住大厅；检查每个 `vera.*` 自定义段符合[附录中的布局](0001-wasm-extension-modules-api.zh-CN.md#自定义段)：以格式版本开头，名字是 ASCII，没有截断或多余的字节。0.1.0 中导入模块只有 `vera:sim@1.0` 和 `vera:client@1.0`，按原样精确匹配，每个导入都必须是该接口的函数；地图的 `Api=` 必须是主版本 1、次版本不高于 0；mod 的 `Api=` 会读取，但尚未与其模块的导入核对。形状上限中，0.1.0 检查模块大小、函数数量、函数体大小，以及 `vera.vars` 和 `vera.notify` 的项数，其余 0.1.0 未实现；
3. 只接受白名单中的 Wasm 特性：MVP 核心，加上可变全局变量、符号扩展、不 trap 的浮点转整数、多返回值，以及批量内存操作中的 `memory.copy` 和 `memory.fill`。其他一切都被拒绝，包括 SIMD、引用类型、垃圾回收、多内存、线程、64 位内存、异常、尾调用，以及被动段和声明段、`memory.init`、`data.drop`、`table.init`、`table.copy`、`elem.drop`。这样段没有运行时状态，函数表在实例化之后不可变，实例中会变化的状态只有内存（含大小）和可变全局变量。定义内存的模块必须把它导出为 `memory`。以后放宽这个子集时，须先规定新增状态如何存档和计入哈希。批量内存的限制 0.1.0 未实现：校验器接受整个批量内存提案（被动段、`memory.init`、`data.drop`、`table.init`、`table.copy`、`elem.drop`），和 `memory.copy` 一样按长度计费，但段和表的状态既不存档也不计入哈希。在检查收紧之前，模块应只用 `memory.copy` 和 `memory.fill`。带 `start` 段的模块被拒绝，所以实例化时不运行任何模块代码。每个可能产生 NaN 的浮点算术和精度转换之后，通过改写字节码（而不是引擎开关）把 NaN 换成正的规范 NaN；`neg`、`abs`、`copysign`、读写和 `reinterpret` 按位进行。只在出口规范化是不够的：`copysign(1, NaN)` 会把 NaN 不确定的符号变成普通数值；
4. 在同一次插桩中加入运算计量和调用栈计量。改写是所有平台共用的纯函数。每个基本块在执行前预扣整块费用（每条原始指令一次运算），批量内存操作按长度追加费用（每 8 字节一次运算）。调用栈限制加权栈槽，远低于每个受支持引擎的真实栈上限，所以深度递归在每台机器上都停在同一次调用；0.1.0 中每次调用计 4 个槽加上它的参数和声明的局部变量（不计操作数栈），一个调用栈最多 8,192 个槽，这也限定了深度（最多 2,048 次调用）；先触发引擎栈上限属于对局错误。模块从不被重入（第 5 节），所以模块调用之间的引擎栈帧保持有界。同一次改写把模块未导出的可变全局变量（如编译器生成的栈指针）也导出，引擎据此读写它们以存档、读档和计算哈希（第 4 节）。改写把内存声明的最大值降到模块的内存上限（第 15.2 节），所以超出上限的 `memory.grow` 在每个引擎上都在同一大小失败；初始大小超出上限的内存被拒绝。在实例化时分配最大内存、让无法提供的宿主在加载时让对局失败，0.1.0 未实现；
5. 检查生命周期需要的导出函数存在且签名正确，并检查 INI 中提到的每个模块动作和处理函数名（`Action=Wasm:name`）都在它所解析到的模块的 `vera.actions` 表中；
6. 检查 `vera.vars` 中的变量声明：名字在模块内唯一，作用域和可见度是表中的值，“视野内可见”只用于单个对象作用域。引擎按加载顺序（先 mod 的，再地图的）给每个变量分配 ID，再解析 INI 触发器的事件、筛选子句和原子动作。无法解析的名字在大厅中报告；
7. 把本局的模拟模块（mod 的和地图的合在一起）在各自 `vera.notify` 自定义段中声明的通知名放在一起检查哈希冲突（第 10 节）。同一模块内的冲突拒绝该模块；mod 的名字与地图的名字之间的冲突拒绝地图的模块。提示中给出两个名字。哈希为 −1（`0xFFFFFFFF`）的名字拒绝声明它的模块。mod 和地图声明同一个名字不算冲突：两者得到同一个 ID，由 `Notify` 客户端事件的来源区分。

**初始化。** 首次回调前执行一次 SDK 生成的初始化函数；读档时跳过。初始化只能解析截至当前规则层的名字、探测表项、写日志，以及用 `ini_register` 注册 INI 名字（第 6h 节）。其余调用返回 `Unsupported`（0.1.0 中 `random` 在这里写入 0 并返回 `Ok`）。初始化、`on_rules`、`on_scenario_start` 各有高于单帧额度的一次性额度。导出了 `on_rules` 的模块在自己的规则层运行初始化；没有 `on_rules` 的模块在本局模块安装时运行，此时所有模块的变量都已声明。

**失败。**

| 时机 | 结果 |
| --- | --- |
| 开局前 | 在大厅显示原因；带这个模块无法开局 |
| 在 `on_rules` 中 | 不能开局，并提示是哪个模块：它正在写的规则不完整 |
| 对局中，包括 `on_scenario_start`（trap、超出额度或调用深度、参数非法、在 `on_decide` 中调用写入函数） | 在所有机器的同一帧停用该模块；游戏告诉玩家是哪个模块停止了、原因是什么 |
| 宿主失败（分配内存上限时内存不足、Wasm 引擎的内部错误） | 对局错误，不算模块失败，因为无法证明它在每台机器的同一帧发生：对局停止并给出提示，和不同步时一样 |
| 在客户端模块中（超出每个渲染帧的额度、trap） | 该调用被停止，该模块只在这台机器上被停用，并提示该玩家 |

客户端额度用同一套计量按运算单位计算，而不是按时钟计算，所以在浏览器的主线程上也能执行。

**被停用的模拟模块。** 对局继续。

- 它创建的触发器被停用。在其他触发器中（地图触发器，或通过 `Wasm.Tags` 绑定的触发器），只跳过它的模块动作。它排队中的模块动作和指令（第 6g 节）被丢弃。
- 它在可决定事件链上的一环被跳过：上一环的结果传给下一环；首环取原生值。出错的那次调用也按此处理。
- 它的模块弹道上的抛射体改为朝目标直线飞行。
- 它做过的事保留下来：它创建的修饰器（照常到期）、它写入的变量和属性、它写入的规则、它创建的触发器（处于停用状态），以及出错的那次调用已经做完的事。
- 它注册的 INI 名字保留，INI 中对它们的引用不会变成错误；没有模块再引发它的模块事件，其他来源仍可引发（第 6h 节）。
- 它认领的所属方领域全部释放，原生 AI 从下一帧起恢复（第 6i 节）。
- 它的内存保留在快照和状态哈希中，停在它停止时的样子，所以存档和重连能重现它。

**错误模型。** 属于正常游戏过程的错误只返回状态，模块继续运行：

| 状态 | 原因 |
| --- | --- |
| `Gone` | 引用为 0，或其对象已不存在 |
| `NotFound` | 名字或 ID 没有匹配任何东西，包括地图中没有的路径点 |
| `Refused` | 动作或写入被引擎规则拒绝（比如该格不能建造、该属性此时不可写），或原子动作的目标在其触发器执行时不适用（第 6b 节） |
| `Unsupported` | 本局关闭的功能（例如没有 Ares 时的 Ares 动作），本引擎不认识的表项，或在不可用的地方发起的宿主调用 |

- 调用当场返回结果。写操作返回状态；可失败的取值操作在同一次调用中返回状态，并把值经指针写入模块内存，例如读取金钱得到 (0, Ok) 表示余额为零，(0, Refused) 表示无权读取。对已消失对象的读取返回空值和 Gone，模块继续运行。批量读仍在一次调用内完成，具体签名见附录。
- 由触发器执行的原子动作没有模块代码来接收它的状态：它的错误状态（`Refused`、`Gone` 或 `NotFound`）写入游戏内日志，该动作被跳过。除此之外什么也不发生。
- 表明模块本身有问题的错误会停用模块：参数非法（包括 `trigger_create` 发现的动作非法参数和非法筛选子句，第 6b 节）、在 `on_decide` 中调用写入函数（第 6f 节）、trap、超出运算额度或调用深度。

### 4. 确定性

所有机器运行同一份模块字节，所以结果只取决于引擎如何执行它们。

- 只用白名单中的 Wasm 特性；NaN、运算量和调用栈都由同一次字节码改写确定（第 3 节），不取决于引擎的 fuel、NaN 开关或栈大小。
- 运行后端和运行线程不属于模拟语义：同一模块、状态和输入，在原生引擎、浏览器版、主线程和模拟 Worker 上得到相同的内存、全局变量、运算量、停止点和宿主调用序列。
- 不提供时钟、宿主随机源和 WASI。`random(lo, hi)` 从模块自己专用的随机流取数，这条流由场景种子和模块的槽位（mod 或地图）派生，所以模块不会错开原生随机流：不取随机数的模块，原生结果完全不变。会执行原生代码的动作，按那段代码原本的方式从原生随机流取数。每个表项都写明它是否从原生随机流取数（`native`），取几次由那段原生代码决定。
- `on_decide` 中也可以调用 `random`，但它不从模块的主随机流取数，而是从一条按（场景种子、模块槽位、帧、事件种类、主体的创建序号）派生的子流取数。没有主体时序号取 0。没有主体时把事件的所属方和 `id` 也计入键、让不同所属方和类型的生产许可各有子流，0.1.0 未实现：同一帧同一种类的这类请求共用一条子流。同一帧中键相同的后续请求接着这条子流取数。每次 `on_decide` 只有一条记录（第 6f 节），所以宿主总知道一次 `random` 属于哪个请求。引擎发出多少次决定调用，都不改变模块主随机流的位置。
- **种子派生。** 模块主随机流、决定子流和原生随机流各带不同的域标记。标记和各组成部分须先分别完整混入，再截短到随机流的种子宽度：域标记不能在截短时丢失，不同的流也不能因组成部分的异或而重合。
- 名字（类型 ID、节名、变量名）比较时不区分大小写，只按 ASCII 规则（`A` 到 `Z`），和 gamemd 读取 INI 的方式一致。字符串以 UTF-8 跨越边界。
- 运算额度由加载时插入的计量代码计算，不用引擎自带的 fuel，所以无论原生还是浏览器的引擎，都会数出相同的运算量，并在同一点停下。宿主调用按它们所做的工作计入同一份额度（按读取的每个属性、扫描或返回的每个对象、检查的每个格子），每个函数的费用写在接口定义中。有数据量的调用在工作之前分段扣费，不在工作完成之后补扣；费用与引擎实际做的工作成比例，包括筛选子句的求值和分页时跳过的项。搜索检查的项数不超过调用方剩余额度付得起的数量；如果扫描因此在单次上限（第 15.4 节）之前中止，这次调用按超出额度处理。
- 计量单位、每个宿主函数的费用、默认额度和各项上限按 API 主版本固定，所以在这些限制内运行过的模块在之后的每个版本中都能继续运行。
- 位置、速度等游戏数值以整数（lepton、定点数原始值）跨越边界，全部装在 `i64` 里。小数和倍率使用模拟的定点格式，即 `I16F16` 原始值（`SimFixed`）。模块内部可以使用浮点。
- 模块内存及其大小、可变全局变量、模块的随机流、是否已执行 `on_scenario_start` 和是否被停用都属于模拟状态：存进快照，计入状态哈希（第 15 节）。随机流、停用状态和排队记录的全部载荷也计入联机同步校验。函数表和各段不可变（第 3 节），由模块字节重建，不另存。读档时先实例化，再用快照覆盖内存和全局变量。变量、修饰器和绑定由引擎持有，同样存档和计入哈希。存档只在帧边界、本帧还没有任何模块调用和决定时进行：此时插桩计数器、本帧用量、决定子流和连锁计数都是初值，所以不存。以后若在帧中途存档，这些也必须存档并计入哈希。
- 对模拟模块的调用从不来自并行代码或推测性的计算。投递的记录跨对象按创建序号排列，不取决于引擎的循环顺序；决定请求只在引擎提交结果的那一点发出，按引擎确定的顺序（第 5 节）。

### 5. 执行模型

模拟模块按需导出[生命周期函数](0001-wasm-extension-modules-api.zh-CN.md#12-导出)。SDK 用记录的分派键调用模块动作，周期回调在 `frame % N == 0` 时按注册顺序执行。

模拟模块只在模拟阶段运行。界面、渲染和音频读取已提交的结果。

**模块阶段。** 每个模拟帧一次，位于 Triggers 步的末尾：在地图触发器轮询之后，在黑幕、小队、对象回合、工厂和所属方更新之前。它读到上一帧已完成的全部结果和本帧地图触发器的结果；它的写入在同一帧对后续各步和联机校验可见。阶段内依次为：修饰器到期，按帧批量的决定，限时状态恢复，被推迟的连锁触发器（见下文），轮询，计时器；然后按加载顺序逐个模块执行 `on_message`、`on_events` 批次和 `on_frame`（先 mod 的，再地图的）。`on_scenario_start` 在第一次模块阶段运行，所以看不到那一帧地图触发器轮询引发的事件。

本帧第一个模块运行之前排队的记录在本帧投递，包括本阶段前面各步引发的记录。任何模块运行期间引发的记录，不论属于哪个模块，都在下一帧投递。对象回合、工厂和所属方更新中引发的事件也在下一帧投递。

**投递。** 普通事件（不是可决定事件）只有一种到达模块的途径：触发器触发时，它的每个模块动作向所属模块的队列写入一条固定大小的记录，带着触发该触发器的那个事件的载荷。筛选子句在写入之前检查，不成立就不写入。队列只在模块阶段到达模块，按顺序分一次或几次 `on_events` 调用。没有单独的事件订阅。

- 如果游戏已经结束，或者触发器在该模块本帧开始投递之前已被禁用或删除，排队中的模块动作会被丢弃。本帧要投递的记录在这一刻确定：投递期间禁用或删除触发器只影响留到以后各帧的记录，所以结果不取决于一批里有几条。
- 投递前已经死亡的对象，其句柄读出来是“不存在”，绝不会指向另一个对象。主体可能在投递前消失的事件（死亡、致命伤害、受伤、碾压、引爆）在记录中带上事件发生的位置，需要的信息不必再从已消失的对象读取。
- 绑定的触发器的主体在事件引发时已经不存在时（例如绑定到武器的 `Detonated`，开火者已经死亡），记录保留主体的句柄，读出来是“不存在”。触发器的所属方是主体最后的所属方（对抛射体事件，是发射它的所属方），实例是那个已不存在的主体的实例。

**顺序。** 跨对象时，一批中的记录和一次批量提交之后触发的触发器都按主体的创建序号排列，从不按引擎的循环顺序，所以调整引擎循环的顺序或改成并行不会改变它。决定请求是同步的：它们按引擎提交结果的确定顺序到达，这个顺序在每台机器上相同，但在不同引擎版本之间可能改变（第 6f 节）。在同一个对象内，调用按引擎引发它们的顺序进行，这个顺序在不同引擎版本之间也可能改变。主体为 0 的记录（所属方和逻辑触发器，以及事件没有主体的格子触发器）排在最前，按触发器运行时触发它们的顺序排列。

**提交点、批量段和并行段。** 对模块的调用从不在并行代码或推测性的计算中发出。引擎的并行段和预计算（并行的索敌预答、寻路批次、追猎评分）只产生候选结果，要到对象自己的回合才被采用或丢弃；它们不引发事件，也不发出决定请求。

- 事件在结果提交的地方引发，从不在推测性的计算中引发。伤害、开火和抛射体推进在对象各自的回合里逐个提交，事件就在每次提交之后引发。
- 引擎在一点提交一批结果时（例如每帧对所有所属方的生产许可），这一步算作一次计算：其中引发的 VERA 事件的触发器在这批结果提交后立即触发，仍在同一帧、在下一个阶段之前；其中的可决定事件在提交之前按确定的顺序逐个请求、逐环决定（第 6f 节）。
- 修饰器到期按到期帧处理，是串行的，不属于并行段（第 15 节）。

**不重入。** 某个模块的调用还在栈上时，引擎从不再次调用这个模块：从这次调用到达的计算中，它在可决定事件链上的一环被跳过（使用上一环的值或原生值）。因此模块自己的动作造成的伤害不经过它自己的 `TakeDamage`、`DamageIncoming` 处理函数（它的护盾不吸收它自己造成的伤害）。它发出的动作所引发的事件照常触发其触发器，其中的模块动作照常排队。可以调用其他模块：mod 模块直接执行的动作可以到达地图模块的可决定事件。

**动作时机。**

- 原版动作和原子动作（第 6b 节）在触发器触发时执行，与原版中的原版动作一样，含有模块动作的触发器也是如此。只有模块动作排队：动作为 [原版 A、模块 B、原子 C] 的触发器，先执行 A 和 C，B 在同一帧稍后执行。需要严格顺序的作者，把触发器的全部动作都写成模块代码，再用 `action` 执行原版动作。
- 模块代码用 `action` 直接执行的动作立即执行，属性写入、`modify` 和 `var_set` 也一样。
- `order` 只排队，指令在下一帧执行玩家命令的那一步执行（第 6g 节）。
- 在模块代码运行期间触发的触发器，其原版动作和原子动作立即执行；其模块动作（包括另一个模块的）排到下一帧的模块阶段，因此模块代码不会在一帧之内循环。

**安全点。** VERA 新增的每个投递型事件都在安全点引发：一次计算完成之后（`TakeDamage` 在伤害已经提交之后），一次计算开始之前（`HouseTransfer` 在转移之前），或一次批量提交刚结束时。触发器的原版动作和原子动作从这一点起立即执行。在计算之前引发的事件之后，引擎重新检查这次计算：

- `HouseTransfer` 之后，如果某个动作已经移除了对象或改变了它的所属方，转移就不发生，也不引发 `HouseTransferred`；
- `FatalDamage` 在致命伤害提交之后、死亡流程之前引发；只有对象仍然存在且伤害仍然致命时（某个动作可能治疗了它，或给它加了 `Unkillable` 修饰器），才执行死亡流程。

投递型事件报告的是已经发生的事：模块动作无法取消原生结果（比如死亡）。要做到这一点，需要用可决定事件（第 6f 节）、修饰器（`Unkillable`），或在计算之前引发的事件（`FatalDamage`、`HouseTransfer`）上的原版动作或原子动作。

**连锁。** 立即执行的动作可以在一帧之内连锁：伤害引发 `TakeDamage`，它的触发器用原子动作造成伤害，又引发 `TakeDamage`。

- 连锁中含有模块触发器、VERA 新增的事件或原子动作时，引擎限制它的深度（按整个调用栈计，跨模块累加），并且按来源（mod、地图）分别限制每帧这类连锁触发的次数（否则一个触发另外两个的触发器会触发 2^depth 次）。引擎事件、模块代码直接执行的动作引发的第一次触发，以及上一帧推迟而来的触发是连锁的起点，不占次数。预览期上限见第 15.4 节。一个来源用完次数不影响另一个来源。0.1.0 未实现：两个来源共用一个每帧次数（待处理的推迟触发上限按来源分开）。
- 会超过任一上限的触发器被推迟：它在下一帧模块阶段开始时、排队的动作之前触发，带着它原有的全部载荷（含事件自带的所属方）。每个来源等待中的推迟触发有上限：超过时停用该模块并提示；该来源没有运行中的模块时丢弃超出的触发并提示一次。它的原版动作和原子动作在那时执行，它的模块动作加入那一帧的批次。如果它在此期间被禁用或删除，就被丢弃；它的筛选子句重新检查，它的所属方是主体在那一刻的所属方，作用于已不存在的主体的动作得到 `Gone`。等待中的推迟触发器存档并计入哈希。
- 只由原版事件和原版动作组成的连锁从不推迟，与原版中完全一样地运行（目标 5）。

**高频事件只对绑定的对象引发。** 伤害、开火、命中、抛射体引爆、碾压和执行指令这类事件，以及绑定范围为对象或类型的可决定事件，只对相应绑定引发（第 6a 节）；没有“订阅所有对象”的用法。这是引擎对模块的硬上限之一（第 15 节）。

**存档。** 读档后，模块内存随快照恢复。初始化函数和 `on_scenario_start` 都不会再次运行，也没有 `on_load`。模块内存里的引用仍指向同样的对象，因为句柄是创建序号，不是存储位置。

**额度。** 每个模块每帧有一份运算额度 B，它与本帧记录数无关，按最慢的受支持平台确定（第 15 节）。战斗变大、记录变多时，模块得到的额度不变，多出的工作推迟到后面的帧。B 是开始新调用的门槛，也是单次调用的上限。

- 宿主调用按它们所做的工作扣除（第 4 节）。筛选子句中派生属性的求值和按帧批量的 `ProductionAllowed` 也从 B 中扣除；其他决定用自己的额度（见下文）。
- 模块阶段中，每帧第一次 `on_message` 或 `on_events`（每次至多固定条数，不超过投递区容量）总会开始，所以 `ProductionAllowed` 用完 B 也挡不住投递；之后只有本帧已用量低于 B 时，引擎才开始新的一次；否则它们留在队列中，按下面的积压规则在下一帧最先投递。`on_frame` 每帧照常调用，即使 B 已经用完。每次调用各自至多使用 B，**不因本帧已用量而缩小**，所以一帧的最坏用量不到 3B，另加一次决定调用的上限和决定额度。
- 决定调用另有一份每帧额度，模块阶段的工作不占用它，否则一有积压，整帧战斗中的否决（如护盾）都会失效。已用量低于它时才调用，每次有固定的单次上限。用完后该模块在可决定事件链上的一环在本帧余下的时间里被跳过、沿用上一环的值，开销叠加层报告跳过的次数。两个例外：`ProductionAllowed` 中因额度没有被询问的请求沿用上次缓存的结果，所以否决不会因额度而失效；`Defeat` 有单独的一份额度，用完时本帧不判负，下一帧再问。
- 一次调用不会被中途推迟。只有单次调用自己用完一整份 B（决定为单次上限）时才被停止、模块被停用（第 3 节）；本帧之前的用量从不使一次正常的调用变成故障。
- 每个模块每帧最多投递固定数量的记录。超出上限或因额度而没有投递的记录按顺序保留，存档并计入哈希，在下一帧最先投递，所以短时间的爆发只会让模块变慢，而不会让它被停用。积压超过固定帧数的记录量的模块会被停用并给出提示：它跟不上。
- 各项取值见第 15.4 节。
- 没有 `on_frame`、待投递记录、消息或决定请求时，该帧不调用模块的对局回调。

### 5a. 语言与 SDK

引擎和模块之间的约定只有 Wasm 接口：附录列出的函数，加上附录的表。任何语言，只要它的编译器产出的模块能通过加载检查，就能使用，引擎对所有模块一视同仁。

- **官方 SDK：TypeScript 和 Rust。** 两者都由同一份接口定义和同一组机器可读的表（第 12 节）生成，提供相同的功能（名称按各自语言的命名习惯），并随 API 一起发布版本。每套都附带模板、构建命令、监视模式和示例。0.1.0 的 Rust SDK 是手写的（由测试与引擎的表核对），附带示例模块和 mod；Rust 的模板和监视模式尚未实现。TypeScript SDK 从 Rust SDK 生成编号表与事件视图，其 `vera20k` 命令提供 `init`、`build`、`watch` 和 `generate`。
- SDK 按事件种类生成具名字段，原地读取投递记录。触发器用 `.immediate()` 指定立即动作、`.enqueue()` 排队、`.decideSync()` 同步决定（Rust 为 `decide_sync`）。包装函数与宿主调用逐项对应，见[附录 SDK 表](0001-wasm-extension-modules-api.zh-CN.md#3-sdk-对应)。

- **TypeScript SDK。** 预先把 TypeScript 编译成 Wasm，模块足够小，可以嵌入地图。当前 SDK 使用 AssemblyScript 0.28.20；版本 1 的编译器选择仍须满足待定问题 2 的验收条件。它不是完整的 TypeScript：`tsc` 只用于编辑器和类型检查，数值语义以 AssemblyScript 为准；同步决定处理函数不得分配内存。它的 API 限定在 TypeScript 与 AssemblyScript 的共同子集内：
  - 不用 `any`，除 `T | null` 外不用联合类型，回调不捕获外部变量，不用 `try`/`catch`；
  - 把多个值组合在一起的参数是用构造函数创建的类或构建器，而不是对象形状或字面量；
  - 引用是普通的 `i64` 值，没有方法，也不为每个引用创建对象：在 AssemblyScript 中，`t.health` 这样的取值器需要给每个引用分配一个对象。对引用的调用是以引用为第一个参数的命名空间函数（`Techno.health(t)`、`Techno.setMission(t, Mission.Hunt)`）；
  - 每个引用值都保持小于 2^53，所以基于 JavaScript 引擎的 SDK 可以用 number 保存它；
  - `i64`、`i32`、`f32` 和各种引用类型（`Techno`、`House`、`Node`……）是 SDK 提供的类型别名；SDK 的 `tsconfig` 不包含 `lib.dom`，所以 `Node` 不会与 DOM 的同名类型冲突；
  - 顶层代码成为初始化函数（第 3 节）。

  这样同一份源码既能用 `tsc` 做类型检查，也能用 AssemblyScript 编译。可直接编译的示例在 `sdk/typescript/examples`。
- **Rust SDK。** 面向想要完全控制和更高性能的作者；引擎自己的兼容性测试用例也用它编写。引用是 newtype，可以带方法（`techno.health()`）。
- **构建产物。** 两套 SDK 的构建命令保证产出的模块能通过加载检查：TypeScript SDK 用 AssemblyScript 编译时，把顶层代码导出为初始化函数而不生成 `start` 段，也不产生默认的 `env.abort`、`env.trace`、`env.seed` 导入，并在编译后写入 `vera.*` 自定义段；Rust SDK 在使用标准库时，构建后用 wasm-opt 把预编译标准库带入的引用类型编码改写回白名单内的编码，`no_std` 模块不需要这一步。0.1.0 的 Rust SDK 及其示例都是 `no_std`，wasm-opt 这一步未实现。即使在 `no_std` 模块里，`core::fmt` 也会带入加载检查拒绝的编码。
- **其他模组开发语言。** C、C++、Python、.NET（如 C#）、Go、Ruby、Elixir、Perl 和 Zig 均可按同一 ABI 接入。每种工具链都需要产出符合第 3 节约束的 Wasm 核心模块，按附录签名导入和导出函数。社区可用第 12 节的表生成对应语言的包装函数。需要解释器或运行时的工具链还须把它编入模块，并满足下述导入和体积限制。
- **导入。** 模块只能导入 `vera:*` 接口。引擎不提供 WASI，项目也不发布 WASI 垫片。运行时依赖 WASI（时钟、随机数、文件）的语言，只有在它自己的工具链去掉这些导入时才能使用。
- **体积和特性。** 以 Wasm 垃圾回收或其他被拒绝的特性（第 3 节）为目标的编译器，比如某些 Kotlin、Dart 和 Java 工具链，产出的模块无法通过加载检查。会把大型运行时或垃圾回收器打包进每个模块的语言，产出的文件更大，可能超过地图嵌入上限。这是作者工具链的取舍，与引擎无关。

**宿主工具。** 独立工具可用以下绑定嵌入 Wasmtime。[Wasmtime 嵌入文档](https://docs.wasmtime.dev/lang.html)

| 宿主语言 | Wasmtime 入口 |
| --- | --- |
| Rust | `wasmtime` crate |
| C | `wasm.h`、`wasi.h`、`wasmtime.h` 头文件，可用 CMake 构建 |
| C++ | `wasmtime.hh` 头文件 |
| Python | PyPI 包 `wasmtime` |
| .NET | NuGet 包 `Wasmtime` |
| Go | `wasmtime-go` |
| Ruby | `wasmtime` gem |
| Elixir | Hex 包 `wasmex` |
| Perl | CPAN 发行包 `Wasm` 中的 `Wasm::Wasmtime` |

### 6. 五个概念

| 概念 | 函数 | 表（附录） |
| --- | --- | --- |
| 对象和属性 | `get`、`get_many`、`set`、`modify`、`unmodify`、`find`、`rules_get`、`rules_set` | [属性](0001-wasm-extension-modules-api.zh-CN.md#7-属性) |
| 变量 | `var_get`、`var_set`；声明在 `vera.vars` 中 | [自定义段](0001-wasm-extension-modules-api.zh-CN.md#自定义段) |
| 事件（含可决定事件） | `trigger_create`、`trigger_remove`、`trigger_bind`、`trigger_unbind`；导出 `on_events`、`on_decide` | [事件种类](0001-wasm-extension-modules-api.zh-CN.md#4-事件种类) |
| 动作 | `action`、`send_notify`、`order` | [动作种类](0001-wasm-extension-modules-api.zh-CN.md#5-动作种类) |
| 界面节点（客户端） | `client_node_create`、`client_node_remove`、`client_node_find`、`client_set`、`client_set_bytes` | [客户端节点](0001-wasm-extension-modules-api.zh-CN.md#710-客户端节点) |

另外几个函数是基础设施：`frame`、`random`、`log`、`has_kind`、`lookup`、`name_of`、`ini_register`（第 6h 节）。

- 函数是冻结的界面，数量固定。事件种类、动作种类、属性、名字种类、节点种类和其他枚举都是表：新的次版本只在表的末尾追加，从不修改或删除已有的表项。`has_kind(table, id)` 告诉模块当前引擎是否提供某个表项，模块可以据此在旧引擎上降级运行。
- 每个原版动作和原子动作都调用引擎中该操作现有的实现；模块不会得到第二份实现。每个可写属性的写入同样走它现有的 owner。
- 可决定事件以游戏概念命名（`TakeDamage`、`TargetChanged`），从不以原生函数命名，这样引擎重构后它们依然成立。
- 对于非常频繁的决策，优先用数据而不是回调：目标优先级用修饰器改变 `TargetPriorityMultiplier` 属性，再配合 `TargetChanged` 事件。逐次调用的可决定事件留给不那么频繁的决策。

每个动作只调用现有 owner 完成一个游戏操作。模块通过组合动作实现复杂行为。

**位置。** 动作接受目标格、生成点和目的地。对象位置属性只读，通过传送、运动动作或移动任务改变。第 9 节第 4 层允许设置抛射体位置，由引擎钳制并照常判定碰撞。

### 6a. 触发器：事件、筛选子句和动作

触发器至少有一个事件，全部成立才触发；每个事件可带筛选子句，重复类型沿用原版。动作和决定处理函数至少要有一项。只注册决定处理函数时，动作数可为 0，且必须恰有一个可决定事件（第 6f 节）。0.1.0 中带决定处理函数的触发器不能再带即时动作：`trigger_create` 返回 `Unsupported`（第 6f 节）。

**订阅只通过触发器。** 模块收到事件的唯一途径是触发器，触发器有三个来源：

- 代码：`trigger_create` 用事件、筛选子句和动作创建触发器，`trigger_bind` 把它绑定到一个对象、一个类型、一个武器、弹头或抛射体类型，或一个格子；
- mod 的 INI：`Wasm.Tags` 把标签中的触发器绑定到类型（第 2 节）；
- 地图触发器：`[Actions]` 中种类为 1036（`Module`）的动作，参数类型为 4，参数 2 是模块动作名，例如 `1036,4,giPanic,0,0,0,0,A`。名字默认解析到地图的模块，`mod.name`、`map.name` 明确指定来源；连同前缀最多 31 字节 ASCII，不含逗号、分号和空白。`Wasm:name` 只用于具名节：`[Actions]` 的种类字段只能是数字。0.1.0 未实现：地图触发器还不能调用模块动作。

触发器随时可以创建、删除、绑定和解绑；它的 `Enabled` 属性控制启用和禁用。

**绑定。** 和对象有关的事件只对绑定的对象引发：

- 绑定了该触发器的对象（对象绑定）、类型绑定了该触发器的对象（`Wasm.Tags` 或类型绑定），以及自身标签包含该触发器的对象；
- 对于武器事件（`Fire`、`HitTarget` 和 `Detonated`），还包括使用绑定了该触发器的武器、弹头或抛射体类型的任何对象。武器绑定对使用这把武器的所有射手生效，不论射手是什么类型，射手就是主体：

  ```ini
  [RedEye2]                   ; 一把武器
  Wasm.Tags=MissileFiredTag   ; 每个使用 RedEye2 的射手开火时都引发其 Fire 触发器
  ```

- 高频事件（伤害、开火、命中、抛射体引爆、碾压、执行指令）没有“所有对象”的订阅。真的需要全部对象时，SDK 的 `bindAllTypes` 把触发器逐个绑定到每个类型上，开销因此在代码里是明的；开销叠加层对这样的绑定给出警告（第 13 节）。
- 格子绑定（代码中把触发器绑定到格子引用）只用于[附录 4.1](0001-wasm-extension-modules-api.zh-CN.md#41-原版事件-061)中注明“绑定格子”的事件；把其他事件的触发器绑定到格子是非法参数。地图的 CellTag 照原版处理。
- 和对象无关的全局事件（所属方事件、逻辑事件、`Timer`、`SuperWeaponLaunched`）不需要绑定。
- 绑定到某个类型的触发器在每个绑定对象上以各自的实例运行（第 7 节）。

**事件种类。**

- **投递型事件**发生在某个时刻（受到伤害、武器开火、被摧毁）。触发器在那一刻触发；其中的原版动作和原子动作立即执行，模块动作则带着事件的载荷排队（第 5 节）。VERA 新增的投递型事件在安全点引发（第 5 节）。
- **轮询型事件**描述一种状态（生命低于某值、金钱高于某值、变量等于某值）。引擎按触发器设定的间隔原生检查它们，对象范围的间隔有下限（第 15.4 节），事件在边沿触发：在状态变为成立的那次检查时触发，之后要等到某次检查时状态不成立，才会再次触发。对象在 `frame % interval == serial % interval` 的帧接受检查，`serial` 是它的创建序号；所属方的轮询改用所属方在所属方数组中的下标。投递型的 `Timer` 事件不错开：它从其触发器创建的那一帧算起，每个周期触发一次。
- 普通属性统一用 `PropertyPoll`：例如每 15 帧检查 `HealthPercent < 30`，SDK 写作 `Trigger.onProperty(Prop.HealthPercent, Op.Lt, 30, 15).bind(E1).enqueue(onLowHealth).done()`。引擎直接读取属性并维护条件的边沿状态。需要额外参数、组合计算或写入时重置计时器的事件见附录 4.4。
- **可决定事件**在事件表中标为“可决定”。带决定处理函数的触发器在决策点同步询问模块（第 6f 节）。
- 每个事件都标明它所附着的对象（主体），以及涉及的另一个对象（如果有的话：攻击者、目标、载具、生产者）。
- 记录的值都是整数或引用。伤害和原版一样是整数；模拟 API 中没有浮点值。

**筛选子句。** 每个事件最多带 N 条筛选子句（N 见第 15.4 节），全部成立（AND）时事件才算成立。

- 子句的形式是 `Subject|Other|House .属性 运算符 值`，或 `Var(作用域,名字) 运算符 值`。运算符为 `=`、`!=`、`<`、`<=`、`>`、`>=`，值是常量。`House` 是触发器的所属方：触发器定义的所属方不为 0 时就是它；为 0 时是主体此刻的所属方；没有主体时（全局事件）是地图的中立所属方（`Neutral`）。
- 引擎在把记录放进队列之前原生检查子句，所以不成立的事件从不投递。普通属性的子句不花模块的额度；派生属性（如 `NearbyEnemyCount`、`TargetInRange`）的求值按它的费用计入所属模块的额度（第 5 节）。
- `find` 使用同样的子句布局（第 6c 节）。
- INI 写法例如 `Where1=Subject.HealthPercent<30`、`Where2=Var(Subject,Panicked)=0`；格式见下文“INI 格式”。
- 计算型的条件：常用的作为派生属性追加到属性表中（例如 `NearbyEnemyCount`、`TargetInRange`），其他的写成代码中的 `if`。条件之间的“或”、两个对象之间的比较、计数都写在代码里。
- 红警 2 的变量事件（27、28、36、37）照常可用。

**INI 格式。** mod 的类型绑定用具名节，地图触发器用原版逗号编码，两者不互相替代。地图中的 `Wasm.Tags` 被忽略并给出警告，地图的 `[Events]`、`[Actions]` 不接受筛选子句。

- 节以 `Vera` 开头。模块的策略、嵌入、按名调用和类型绑定键用 `Wasm`：`[VeraWasm]`、两个 Pack 节、`Wasm:名字` 和 `Wasm.Tags`。0.0.16 到 0.0.25 的草案把绑定键叫作 `Vera.Tags`；引擎读取的是 `Wasm.Tags`。
- 触发器节只接受附录列出的键。未知键、同一节中重复的键、带编号与不带编号的同一个键、`Event<n>` 或 `Action<n>` 编号不连续、无法解析的名字都拒绝开局，并指出节和键。编号从 1 起，不带编号即 1。
- 文字参数只能是最后一个参数，它取余下的全部内容，可含逗号，不能含分号。
- 物理行连同键名最多 511 字节；VERA 的键超出时报错，不截断。
- `Event=Wasm:名字` 监听一个已注册的模块事件；`Action=Wasm:名字(目标,文本)` 是带目标和参数文本的模块动作：第一个参数是 `ActionTarget` 名（可空，默认 `Subject`），其后到最后一个右括号为止的内容原样交给模块，可含逗号（第 6h 节）。`Decide=Wasm:名字` 不带参数。
- 没有模块时，mod 可在 `rulesmd.ini` 的 `[VeraVars]` 中声明变量，例如 `Panicked=Object,Private,0`（作用域、可见度、默认值，语义同 `vera.vars`）。它们与 mod 模块声明的变量共用一张表，先 INI（按文件顺序），后模块；同名时拒绝开局。地图不能用这个节声明变量。`[VeraVars]` 0.1.0 未实现。

触发时执行原版、原子和 AI 动作，模块动作排队投递。见[绑定示例](#把触发器绑定到类型)。事件字段、绑定范围和版本层级见[附录事件表](0001-wasm-extension-modules-api.zh-CN.md#4-事件种类)。历史值由模块保存在变量或模块内存中；INI 不提供记录器、算子或表达式。

### 6b. 动作

所有动作都在附录的[动作种类表](0001-wasm-extension-modules-api.zh-CN.md#5-动作种类)中按编号排列：原版动作 0..145（启用 Ares 时加上 146..149）、原子动作、AI 动作和模块动作。同一个种类有两种用法：

- 模块代码用 `action(kind, target, params, len)` 直接执行，目标是一个明确的引用（对象、所属方、格子或抛射体；触发器、标签和小队放在参数的 `other` 中）。创建对象的动作返回新对象的句柄，其他动作的值为 0；两者都在同一次调用中返回状态。
- 触发器的动作列表写的是同一个种类，加一个目标选择和参数（附录的[触发器定义](0001-wasm-extension-modules-api.zh-CN.md#固定布局)）。

直接设定生命值、等级或弹药只定义一次写入语义：模块代码通过 `set` 写对应属性，触发器用 `SetProperty` 编码相同的写入，两者经过同一状态所有者。SDK 可生成带属性名的写入函数。增量、伤害归属和触发时才解析的参数各有游戏语义，保留相应动作。

**原子动作**是瞬时的游戏操作，每个都有一个 owner：发射武器、发射超级武器、造成伤害、摧毁、移除、创建对象、传送、引爆弹头、写变量、修饰属性、让某个所属方结束游戏，等等（[附录 5.3](0001-wasm-extension-modules-api.zh-CN.md#53-原子动作)）。造成伤害走弹头和护甲规则，带来源，用于击杀归属和经验；直接设定生命值不计归属。传送到被占的格子时按规定的规则处理：选附近的格子，或动作失败。

在触发器中，动作的目标是一个选择（`ActionTarget`）：

- `Subject`（默认）：事件的主体；
- `Other`：事件中的另一方对象；
- `TagHolder`：标签中持有该触发器的对象，CellTag 则是那个格子；对于绑定的触发器，是引发事件的对象；
- `Projectile`：事件中的抛射体；
- `House`：参数中的所属方，它为 0 时为触发器的所属方；
- `Cell`：参数中的格子。

- 参数放在一个固定布局里：一个 ID、两个小整数、两个整数值、一个格子、一个所属方、一个引用和一段文字（附录的[动作参数](0001-wasm-extension-modules-api.zh-CN.md#固定布局)）。只在模块代码中可用的动作（例如创建抛射体）另带一段变长数据。
- 不用目标的动作（例如 `SetTechLevel` 或 `Log`）忽略目标。
- 路径点以路径点引用给出（附录的[引用](0001-wasm-extension-modules-api.zh-CN.md#引用)）。`trigger_create` 把它解析为路径点所在的格子，因为路径点不会移动。地图上没有的路径点是地图数据错误，不是模块错误：`trigger_create` 返回 `(0, NotFound)`，不创建触发器并写入日志，模块保持启用。写在 INI 中时，它在加载时于大厅中报告。

参数表达不了的部分由固定规则决定：

- 明确的所属方（`House` 目标、`SetOwner` 的新所属方、所创建对象的所属方）取参数中的所属方。它为 0 时：在触发器中使用触发器的所属方（第 6a 节）；在直接调用中是非法参数（第 3 节）。原版动作中隐含使用触发器所属方的地方（例如 `LightningStormStrike`）同样取这个所属方。
- 在触发器中，来源（伤害、击杀或引爆的来源：`Kill`、`Damage`、`DetonateWeapon`、`DetonateWarhead`）是事件中的另一方对象，并且是可选的：没有来源时，动作在没有来源的情况下执行，不计击杀归属。直接调用时，来源取参数中的引用。
- 动作施加作用的第二个对象（乘客）在触发器中是事件中的另一方对象，直接调用时是参数中的引用。没有第二个对象，或者 `FireWeapon` 没有可瞄准的格子、另一方对象或当前目标时，动作得到 `Gone` 并被跳过。
- 对象目标的格子是对象所在的格子；`Projectile` 目标的格子是抛射体下方的格子。坐标取该格子的中心；`Projectile` 目标例外，其坐标为抛射体的中心。`CreateObject` 的目标为建筑时例外：新对象从这座工厂的原生出口离开，而不是放在格子上（附录 [5.3](0001-wasm-extension-modules-api.zh-CN.md#53-原子动作)）。
- 每种动作用到的目标和字段，以及各动作自己的规则（例如 `FireWeapon` 的瞄准），见[附录 5.1](0001-wasm-extension-modules-api.zh-CN.md#51-动作的用法)。

检查：

- `trigger_create` 检查每个动作的参数。非法的参数会停用模块（第 3 节）：永远不适用于该动作的目标种类（例如 `Kill` 的目标是 `Cell`），或缺少必需的字段（`LaunchSuperWeapon` 的格子）。`action` 对直接调用做同样的检查。
- 写在 INI 中的原子动作在加载时检查，并在大厅中报告。写法见第 6a 节。
- 触发器执行时才发现目标不适用（例如 `Kill` 的 `TagHolder` 是一个格子），属于数据错误：动作得到 `Refused`，状态写入日志，动作被跳过，模块保持启用。
- 原子动作立即执行，并可能引发新的事件，所以它们可以在一帧之内连锁，受第 5 节的上限约束。

### 6c. 对象、属性与修饰器

**引用。** 每个引用都是一个 `i64`：对象的句柄（单位、建筑、抛射体、所属方、小队、触发器、标签、修饰器、超级武器、客户端节点）、类型引用、格子引用、路径点引用或全局规则引用。编码由 SDK 完成，所有值都小于 2^53，0 表示“没有”（[附录：引用](0001-wasm-extension-modules-api.zh-CN.md#引用)）。

**属性。** `get(ref, prop)` 读一个属性，`get_many(refs, n, props, m, out)` 一次读 n 个引用的 m 个属性，`set(ref, prop, value)` 写一个属性。属性表按引用种类分组（对象、所属方、格子、类型和规则、全局、触发器和标签、修饰器、客户端节点），并写明每个属性：

- 值类型（整数、布尔、定点数、枚举、引用、ID 或字符串）；
- 能否写，何时能写（任何时候、只在 `on_rules`）。写入走该属性现有的 owner：写 `Owner` 就是转移所属，写 `Mission` 就是像玩家指令一样排入一个任务；
- 客户端能否看到（第 10 节）；
- 能否被修饰。

`get` 读到的是有效值：基础值加上全部修饰器的结果。字符串属性返回一个字符串 ID，用 `name_of` 读出文字；SDK 直接返回字符串。

**派生属性和视点属性。** 有些属性是引擎算出来的：`HealthPercent`、`NearbyEnemyCount`、`TargetInRange`。还有少数属性取决于一个视点所属方（`Relation`、`Revealed`、`Buildable`、`Placeable`）：在筛选子句中，视点是触发器的所属方；在 `find` 中，视点是搜索的 `viewpoint` 字段；在客户端中，视点是本玩家。直接 `get` 它们时没有视点，返回 `Unsupported`。`Placeable` 还需要一个类型，所以只在 `find`（包括 `client_find`）中用查询的 `type` 求值，其他地方返回 `Unsupported`。

**修饰器。** `modify(ref, prop, op, value, frames, source, group)` 在一个对象或所属方的可修饰属性上加一个修饰器，返回修饰器的句柄；`unmodify(modifier)` 提前移除它。SDK 用 `Modifier.add`、`Modifier.multiply`、`Modifier.override` 分别表示加、乘和覆盖，例如 `Modifier.multiply(unit, Prop.SpeedMultiplier, fixed(0.5), 150)`。三个入口都只调用一次 `modify`；可选的来源和组直接编码为整数，省略时均为 0。0.1.0 中修饰器只作用于对象：目标是所属方，或是引擎尚未接线的可修饰属性时，返回 `Unsupported`。

- 运算为加（`add`）、乘（`multiply`，定点数）和覆盖（`override`）。`frames` 为持续帧数，负数表示无限；`source` 是来源对象（用于击杀归属和来源规则），可为 0；`group` 是互斥组，0 表示不分组。
- 叠加、互斥组和到期都由引擎持有，存档并计入哈希。
- **合成。** 记 P 为原生和 Phobos 在该读取阶段的值，A 为加值之和，M 为按句柄顺序排列的乘数，O 为最新的覆盖值。倍率属性为 P × (1 + A) × 全部 M；数量属性为 (P + A) × 全部 M；有 O 时结果为 O。布尔、ID、枚举、掩码和颜色只接受覆盖；属性不接受的运算和倍率属性的负乘数返回 `Refused`。射程先按 Phobos 的顺序计算，再依次乘 (1 + A) 和各 M，每次乘法后向零截断，加值最后相加；有 O 时它取代 Phobos 和模块的这一项。受弹头筛选或有概率的 Phobos 项留在自己的阶段，不被 O 取代。只钳制模块的项，不钳制 P。除射程这类须按武器计算的属性外，结果在变化时算出并缓存（第 15 节）。
- **精度。** 修饰器的小数是 Q16.16，Phobos 效果保持自己的 double 值、不转换成修饰器。两者的阶段和运算顺序相同，但不能精确表示的小数可能让取整结果差 1。
- **叠加。** 组 0 各自叠加。非 0 的组以（来源、对象或所属方、属性、组）为键，加入时替换原有的一个。每个（来源、对象或所属方、属性）的层数有上限（第 15.4 节），替换不另占名额；超出时返回 `Refused`，不淘汰旧的。0.1.0 未实现层数上限，只实现每个来源的修饰器数量上限（第 15.4 节）。0.1.0 把合成后的乘数限制在 0..32,768（`ArmorMultiplier` 至少 2^−16），lepton 值限制在 ±2^24。
- **刷新。** `modify` 没有原地刷新：同组替换产生新句柄，值、来源和时长都取新的（即使更短），排到最后，先后引发 `ModifierExpire`、`ModifierStart`。按来源刷新、层数和冷却属于 INI 行为或 Phobos 效果，不是 `modify` 的参数。
- **时长。** 第 F 帧加入、`frames = N` 时，在第 F + N 帧模块阶段开始时到期，0 按 1 处理，负数为无限。对象离场、在载具内或被冻结时不暂停。改变所属方或原地变形时保留；对象被替换或消失时不转移。
- **来源。** 组替换和 `RemoveModifiers` 只作用于本来源；`unmodify` 按句柄精确移除，不限来源。
- 修饰器本身也是对象，有属性（剩余帧数、目标、来源、组）；`ModifierStart`、`ModifierStacks`、`ModifierExpire` 事件报告它们；所属方上的修饰器的这些事件以全局形式引发，记录的 `house` 为该所属方（附录 [4.3](0001-wasm-extension-modules-api.zh-CN.md#43-新的投递型事件)）。
- 旧版本中的持续效果种类都变成了可修饰属性（倍率、射程、隐形、禁止开火、阻止死亡……），见[附录 7.2](0001-wasm-extension-modules-api.zh-CN.md#72-可修饰属性)。少数无法成为普通属性的变成特殊属性或动作：对攻击类型的免疫是一个位掩码属性 `ImmunityFlags`；替换武器是覆盖 `PrimaryWeapon`、`SecondaryWeapon`；激光拖尾是 `LaserTrailType`；附着动画是动作 `AttachAnim`；限时变成另一类型是带帧数的 `Convert` 动作；运动（被抛起、被推动）是以后的运动动作；传送是动作 `Teleport`。变形、超时空移动和运动互斥，由 owner 保证同一时间只有一个生效。
- 显示在对象上方的文字、数值或按钮属于客户端节点，不在版本 1 中（第 10 节）。
- 只要模块功能开启（第 14 节），修饰器的 owner 就独立于 Phobos 启用。只有 Phobos 开关才启用对它的 AttachEffect INI 键的读取（类型、武器、弹头上的 `AttachEffect.*` 和 `[AttachEffectTypes]`），以保持原版行为。读取后，它们由 Phobos AttachEffect 的 owner 按效果实例持有和计时，并在同一读取阶段先于修饰器合成。它们不是修饰器：不出现在 `find(Modifiers)` 中，不引发修饰器事件。共用的代码存在于每个构建中，由运行时开关开启各自的输入（第 14 节）。

**搜索。** `find(query, len, out, cap)` 搜索对象、所属方、格子、类型、小队、触发器、标签、修饰器或超级武器，结果写入模块提供的缓冲区，写入数量和续页位置写入一个小的结果结构，返回状态。

- 范围：整张地图、一个格子加半径，或一个矩形；可按类型和所属方过滤；可带筛选子句，布局与触发器的相同，其中 `Subject` 是被检查的候选。
- 结果按创建序号排序，这个规则不依赖引擎如何存放对象。有四种结果保持自己的顺序：格子按格子下标，所属方按所属方数组的顺序，修饰器按加入的顺序，类型按类型 ID。
- SDK 用 `.first()` 取首项，或用 `.page(buffer, after)` 把一页写入已有缓冲区。每页一次宿主调用；下一页按前一页末尾的排序位置继续，即使该对象已删除也有效。每页读取调用时的世界状态，刚新增且排序在游标之后的匹配项可在后续页出现。
- 地图和格子的查询都是格子引用的属性：地形类型、高度、覆盖物、矿石、按移动类型是否可通行、是否已揭开、能否放置，以及 CellTag。
- 原来的探测（对象能否向它当前的目标开火、当前目标是否在主武器射程内、某类型能否放在某格）变成派生属性和视点属性：`TargetInRange`、`CanFireAtTarget`、`Placeable`。对任意武器和任意目标的探测留到以后。“最近的可放置格子”用带 `Placeable=1` 子句的 `find` 加模块代码实现。

完整的属性表见[附录第 7 节](0001-wasm-extension-modules-api.zh-CN.md#7-属性)，搜索范围见[附录 8.2](0001-wasm-extension-modules-api.zh-CN.md#82-搜索范围find)。在客户端模块中，读取只暴露本玩家自己的界面能显示的内容（第 10 节）。

### 6d. AI

电脑所属方保留它们的 AI。AI 不是一个单独的概念：

- **定义**是 INI：特遣部队、小队脚本、小队类型和 AI 触发器（`[TaskForces]`、`[ScriptTypes]`、`[TeamTypes]`、`[AITriggerTypes]`）及其列出的节属于 AI 文档（`AIMD.INI` 加地图，层叠规则不变）。`rules_get` 从合并后的 AI 文档读取它们。
- **操作**是动作种类：启动小队（原版动作 4，以及不受数量上限限制的 `CreateTeamUnlimited`）、解散小队、加入或移出成员，以及 AI 相关的原版动作（74 至 79）。
- **状态**是属性：小队的类型、脚本、脚本游标、是否成功；AI 触发器的启用状态；所属方的 AI 触发器总开关。写 `Script` 或 `Cursor` 就是修改运行中小队的脚本或跳到某一行。
- **小队脚本动作**保持为一张编号表（附录 [6.2](0001-wasm-extension-modules-api.zh-CN.md#62-小队脚本动作)），作为 `[ScriptTypes]` 中的数据使用。

版本 1 的 `on_rules` 不能写 AI 文档：对上述四个列表节及其列出的节调用 `rules_set` 返回 `Refused`，而不是静默无效。AI 定义用 `AIMD.INI` 或地图；模块写入留给以后的次版本。

AI 操作统一经过现有 AI owner。模块也可以用 `order` 像玩家一样指挥电脑所属方（第 6g 节）；指令经过命令的 owner。模块认领了领域的所属方，原生 AI 只在未认领的领域运行（第 6i 节）；没有认领时原生 AI 照常运行。

### 6e. 变量

变量是带作用域和可见度的 `i64` 整数，取代了旧版本中的标记。

- **作用域**：全局、所属方或单个对象。`var_get(scope, var)` 和 `var_set(scope, var, value)` 的 `scope` 为 0 表示全局，否则是一个所属方或对象引用。作用域与变量的声明不符属于非法参数。
- **可见度**决定客户端能否读到它：私有（全局变量没有任何客户端能读；所属方变量只有该所属方的玩家能读；对象变量只有对象所属方的玩家能读）、盟友（再加上盟友）、视野内（单个对象作用域专用：再加上当前能看到该对象的玩家）、公开（所有人）。
- **声明。** 模块在 Wasm 自定义段 `vera.vars` 中声明它的变量：名字、作用域、可见度和默认值。SDK 构建时按项目配置中的列表写入这个段。同一份声明生成模拟读写和客户端只读访问器：全局变量写作 `Wave.get()`，所属方和对象变量须传相应引用。访问器在初始化时解析并缓存本局 ID，筛选和原子动作也接受生成的变量名；客户端读取仍按可见度检查。动态跨来源引用继续通过名字解析。`lookup` 按名字给出变量 ID；变量名写在模块字节里，所以不算秘密。
- **红警 2 的局部变量和全局变量**是固定的特例：全局作用域、私有、默认值 0，取值只有 0 和 1（写入非零值即为 1），使用固定的 ID（附录[变量 ID](0001-wasm-extension-modules-api.zh-CN.md#id)）。
- 设置变量会像地图动作那样重置等待这个变量的触发器的计时器（事件 27、28、36、37，以及 `VariablePoll`）。
- 对象作用域的变量随对象一起消失。所有变量由引擎持有，按引用索引放在旁路表中，存档并计入哈希（第 15 节）。
- 变量可以在筛选子句中判断（`Var(Subject,Panicked) = 0`），可以用原子动作 `SetVar` 在触发器中写入，也可以用 `find` 的子句搜索。

**战役。** 每一关都是一次新的装载：模块内存、全局变量和表、随机流、声明的变量（所有作用域）、触发器、修饰器和排队的记录都从初始状态开始。跨关只延续引擎的战役继承记录：模块通过变量 ID 100..149（红警 2 的 50 个全局变量，值为 0 或 1）使用它，作者编写的战役系列须在 `[CarryOver]` 中写 `Globals=Yes`。继承值在 `on_scenario_start` 之前写回，`on_rules` 看不到它们。重开本关和失败重试从进入本关时的继承记录开始；读档恢复存档时的全部模块状态。

### 6f. 可决定事件

可决定事件取代了旧版本中的覆盖点。事件表有一列“可决定”，并写明结果槽的含义：例如 `TakeDamage` 的结果是护甲和免疫都结算之后的最终伤害，`TargetChanged` 的结果是选中的目标，`FatalDamage` 的结果是死亡方案，`Fire` 的结果是一份射击方案。只可决定的事件（例如 `ProductionAllowed`、`CommandAllowed`）没有投递形式。

- 带决定处理函数的触发器（SDK 中的 `.decideSync(fn)`）让事件在决策点以决定请求的形式引发，而不是在安全点投递。决定请求按附录事件表的绑定范围引发，并经过筛选子句；全局事件（如 `Defeat`）无需对象绑定。
- 引擎在决策点同步调用 `on_decide(ptr, count)`。每个请求是一条固定大小的决定记录：事件记录，加上原生值、上一环的结果、结果槽和“已处理”标志（附录的[固定布局](0001-wasm-extension-modules-api.zh-CN.md#固定布局)）。需要更多空间的结果（射击方案、路径、抛射体的逐帧结果、任务步的结果）写入请求附带的结果区。
- 决策点只在引擎提交结果的那一点：对象自己的回合里设定目标、提交一次伤害、射出一次射击的地方。调用是同步的，按引擎提交结果的确定顺序进行。引擎从不为推测性或并行的预计算（索敌预答、寻路批次、追猎评分）发出决定请求，因为这些计算的答案可能被丢弃。
- 版本 1 中 `count` 总是 1：每个请求、链上每一环各是一次 `on_decide` 调用，下一环的 `previous`、额度检查和 `random` 子流都以上一次调用结束时的状态为准。引擎在一点提交一批结果时（例如 `ProductionAllowed`），请求按主体的创建序号排列，主体相同时按所属方在数组中的下标、再按 `id` 排列，全部决定完成后一起提交。同一模块的多个决定触发器按创建顺序成为先后各环。投递区须容纳一条记录和它的结果区，结果区大小按事件种类固定（第 15.4 节）。成批决定若以后需要，以新的导出增加，不改变 `on_decide` 的含义。
- 处理函数只可使用[导入表](0001-wasm-extension-modules-api.zh-CN.md#11-导入)标为 `decide` 的函数；调用写入函数会停用模块。
- 处理函数可以在模块内存中保存自己的状态：调用只发生在提交点，按引擎的确定顺序，所以这份状态在每台机器上相同。处理函数中的 `random` 从派生子流取数（第 4 节），决定调用的次数不改变模块主随机流。
- mod 和地图的链式规则见第 2 节，不重入和额度见第 5 节。
- 侧边栏和 AI 这类本地或频繁的读者读取缓存的结果：例如 `ProductionAllowed` 每帧对每个所属方和每个绑定类型决定一次，侧边栏显示这个结果。
- 0.1.0 中带决定处理函数的触发器没有即时动作（`trigger_create` 返回 `Unsupported`）：在决定点执行原版或原子动作，会在正被决定的计算之中改变世界。可改用同一事件上的投递触发器，或在模块内存里记下请求、在 `on_frame` 中处理。
- 0.1.0 在模块阶段开头询问 `ProductionAllowed`：每个未战败的所属方（含 Neutral 和 Special）乘以每个绑定了决定者的类型。回答 1 不能解除引擎自己的拒绝（前提条件、科技等级、建造上限）。没有 `Command` 编号或没有执行者的指令，以及原生 AI 下达的任务，都不询问 `CommandAllowed`。

版本 1 冻结三个可决定事件：`TakeDamage`（结算后的最终伤害）、`ProductionQueued`（是否入队）、`Defeat`（否决引擎的判负）。拒绝电脑所属方的 `ProductionQueued` 时，引擎清除它对该类生产的选择，让它重选。

- **预览，不随版本 1 冻结：** `ProductionAllowed`（可用 `AllowType` 表达）、`CommandAllowed`（须先覆盖电脑 AI 的任务）。
- **单位控制点（预览，0.0.22）：** `FireAllowed`、`Retaliate`、`DestinationSet`、`CrushAllowed`、`HarvestCell`、`DeployAllowed`，每个只在引擎对该单位的提交点询问一次，不在并行或推测性的计算里询问（附录 4.5）。每个都在它所决定的原生计算（含其中的随机数抽取）跑完之后询问，答案不会跳过这段计算的抽取；被拒绝的动作不再做它之后本会做的抽取。
- **护盾：** 预览期新增 `DamageIncoming`（受伤入口的伤害，引擎按触发器声明的护甲算好盾伤）和可修饰属性 `TargetArmor`（索敌和开火许可用的护甲；0.1.0 未实现，所以下面的护盾验收用例暂时无法通过）。`TakeDamage` 只在结算后的伤害大于 0 时询问，所以不能用它实现另有护甲的护盾。这两项只有通过下述用例后才随版本 1 冻结；Phobos 兼容护盾仍由引擎实现，不要求模块逐点复刻。
- **预览：** `Fire` 的决定形式（射击方案，第 9 节）、`FatalDamage` 的决定形式（死亡方案，附录 4.3）、`Launch`、`ProjectileFrame`（第 9 节），单位级的 `IdleMission`、`MissionStep`、`HarvestCell`（附录 4.5）。
- **以后：** `TargetChanged` 的决定形式。模块用 `has_kind` 探测。

**护盾验收。** 用公开 SDK 写一个最小护盾和一个过载护盾（距离 0、倍率 1）：

| 用例 | 期望 |
| --- | --- |
| 车体 0%、盾甲 100%、盾 200，入射 50、100 | 盾各扣 50、100，生命不变（不施加最小伤害 1） |
| 盾 30、车体 50%、盾甲 100%，入射 100 | 盾 0，生命扣 35 |
| 盾 20、车体 100%、盾甲 50%，入射 100 | 盾 0，生命扣 60 |
| 负入射、盾未满 | 盾回复，生命不变 |
| 无视防御、铁幕、免疫 | 不询问，按原生结算 |
| 有衰减、上限或护甲倍率 | `value2` 等于引擎伤害核算出的值 |
| 车体 0%、盾甲 100% 的直射武器 | 有盾时自动索敌并开火，破盾后停止（允许晚一帧） |
| 同帧多次命中、模块自伤、决定额度用尽 | 按第 5 节，各机一致 |
| 过载中、破盾前一次命中后存档 | 续跑与连续运行的完整哈希相同（第 15.1 节） |
| 没有模块 | 状态哈希与原版逐帧相同 |

### 6g. 所属方指令

模拟模块用 `order(house, ptr, len)` 指挥一个电脑所属方，方式和玩家指挥自己的所属方一样。它使用客户端模块传给 `client_send_order`（第 10 节）的 `Order` 布局和[指令表](0001-wasm-extension-modules-api.zh-CN.md#83-枚举)，涵盖单位指令、生产、放置建筑、集结点、维修、出售和超级武器。

动作直接完成一项操作；指令则是让所属方去做它的玩家能做的事，花玩家要花的钱，过玩家要过的检查。`CreateObject` 直接造出一个单位，不花钱；`QueueProduction` 指令要付钱，还要等工厂造出来。

- **所属方。** `house` 必须是没有玩家控制（`IsHuman` 为 0，也不受战役玩家控制）且尚未战败的所属方，否则 `order` 返回 `Refused`。玩家的所属方只接受这名玩家的指令，包括该玩家的客户端模块。这只限制 `order`：写 `Mission` 或执行 `SetMission` 动作，可以给任何对象（包括玩家的）下任务，以它所属方的名义执行，如同该玩家点了鼠标。引用为 0 或不是所属方属于非法参数（第 3 节）。
- **时机。** 引擎把指令排队。第 F 帧发出的指令在第 F + 1 帧执行，位于执行所收到玩家命令的那一步，与模块阶段在帧中的位置无关（命令步在对象回合之后，所以单位从第 F + 2 帧的对象回合起照做）。这一步先执行该帧的玩家命令，再执行 mod 模块的指令，然后是地图模块的指令，各自按发出顺序。指令没有网络命令延迟：每台机器锁步发出同样的指令，与之并行的原生 AI 也没有延迟。
- **准入。** 原生的命令执行步骤只接受有玩家控制的所属方的命令；它也接受模块发给电脑所属方的指令。原版玩法从不为电脑所属方发命令，因此不受影响。
- **校验。** 执行时，指令按当时的状态经过与该所属方的玩家发出同一条指令时相同的检查，例如单位归属、前提条件和建筑放置。忽略玩家指令的单位（`IgnoreOrders`）同样忽略模块的指令。已消失或不再归该所属方的单位从指令中去掉。没有通过检查的指令什么也不做，和玩家一样。生产像玩家一样花钱、花建造时间。发出时，`order` 只检查所属方、指令表（`target` 和 `value` 的种类、单位列表的每一项都是对象句柄、只有表中列出单位列表的指令才带单位）和每帧上限；不符合时返回 `Refused`，不排队。未知的指令返回 `Unsupported`，0.1.0 中 `EjectBunker` 也是如此。0.1.0 还没有任何拒绝会报告 `IgnoresOrders` 或 `CannotAfford`。
- **结果。** 执行的指令引发与同一条玩家指令相同的事件和决定，包括 `Commanded`、`CommandAllowed`、`ProductionQueued` 和 `ProductionCancelled`。`order` 在调用期间不执行任何操作，也不引发事件；模块在之后的帧中通过属性、搜索和事件看到结果。
- **开销和上限。** 每次调用按指令条数和单位项数计费。每个模块每帧的指令条数和单位项数有上限（第 15.4 节）。
- **存档、回放和重连。** 指令从不进入网络命令流。等待下一帧执行的指令存档并计入哈希。回放和重连的玩家重新模拟模块，模块再次发出同样的指令，所以回放不必记录它们。
- **原生 AI。** 该所属方的原生 AI 在模块没有认领的领域照常运行（第 6d 节），可能改派同一批单位或排入别的生产。模块用 `ControlDomains` 按领域认领，让原生 AI 让出相应决策（第 6i 节）；不认领时可以用 `AiTriggersActive`、`AutoBaseBuilding` 和拒绝 `ProductionQueued` 收窄它。
- **被停用的模块。** 丢弃它排队中的指令（第 3 节）。

SDK 用 `Client.order` 所用的构造器组装指令（附录[第 3 节](0001-wasm-extension-modules-api.zh-CN.md#3-sdk-对应)）。

### 6h. INI 注册

模块可以把自己的机制提供给不写代码的 modder：modder 只写 INI，模块实现机制。模块在初始化函数中用 `ini_register` 注册 INI 名字；引擎记录每个名字归哪个模块、由哪个处理函数负责，开局时把最终规则中出现的已注册名字交给处理函数。值的格式、默认值和取值范围由模块定义和检查，引擎不解析，大厅也不校验。

```ini
; modder 写的 INI（mod 的 rulesmd.ini）
[HTNK]
Kratos.Shield=HeavyShield           ; 类型上的键
Wasm.Tags=ShieldMedicTag

[Kratos.ShieldTypes]                ; 注册表
1=HeavyShield

[HeavyShield]                       ; 条目节，内容由模块用 rules_get 读取
Strength=300

[ShieldMedicTag]
Trigger=ShieldMedic

[ShieldMedic]
Event=Wasm:Kratos.ShieldBroken      ; 模块事件
Action1=Wasm:restoreShield(Subject,50)   ; 带参数的模块动作，名字来自 vera.actions
```

```rust
static SHIELD_BROKEN: ini::EventSlot = ini::EventSlot::new();

fn init() {                         // 初始化函数：唯一可以注册的地方
    let _ = ini::registry("Kratos.ShieldTypes", ENTRY_KEY);
    let _ = ini::key("Kratos.Shield", IniSection::TechnoType, KEY_KEY);
    if let Ok(event) = ini::event("Kratos.ShieldBroken", EventScope::Object) {
        SHIELD_BROKEN.set(event);
    }
}
vera20k_sdk::init!(init);           // 导出 vera_init
```

**三种注册。**

| 种类（`IniKind`） | INI 写法 | 引擎做什么 |
| --- | --- | --- |
| `Key`：类型上的键 | 注册时指定的那类节（`IniSection`）中的 `名字=值` | 开局时，每个带非空值的节投递一条 `IniKey` 记录给处理函数 |
| `Registry`：注册表 | 列表节 `[名字]`，值为条目节名 | 开局时，列表中的每个条目投递一条 `IniEntry` 记录给处理函数 |
| `Event`：模块事件 | 触发器节的 `Event=Wasm:名字` | 分配事件 ID；`RaiseEvent` 引发它 |

- 只有初始化函数能调用 `ini_register`；在其他地方调用属于非法参数。
- 名字为 1 到 63 字节，只含 ASCII 字母、数字、`.` 和 `_`，按 ASCII 规则不区分大小写。同一种类中名字在本局唯一，mod 和地图共用：已被注册（任何来源，包括自己）时返回 `Refused`，以 `Vera.` 开头的名字也返回 `Refused`。不同种类可以同名。每个模块至多 4,096 个注册。约定（不由引擎检查）：名字以作者或包名开头，如 `Kratos.`。
- 模块动作名仍由 `vera.actions` 声明（第 12 节），不经 `ini_register`，前缀规则不变（第 2 节）。
- 注册表（名字、种类、来源、分派键）和字符串表由引擎持有，存档并计入状态哈希。读档时不运行初始化函数，注册从存档恢复。

**时序。** 初始化函数在模块所在的规则层运行（第 3 节），所以每个名字在被用到之前都已注册：

| 顺序 | 步骤 | 注册与使用 |
| --- | --- | --- |
| 1 | `RULESMD.INI`、`LANGRULE.INI`、模式层 | |
| 2 | mod 模块的初始化函数 | 注册 |
| 3 | mod 模块的 `on_rules` | 可以写任何键，包括已注册的；不应缓存它们的值，后面的层还会改 |
| 4 | 地图层 | 地图 INI 可以写 mod 注册的键 |
| 5 | 地图模块的初始化函数 | 注册；重名得到 `Refused` |
| 6 | 地图模块的 `on_rules` | 同 3 |
| 7 | 引擎解析 INI 触发器 | `Event=Wasm:名字` 须是已注册的事件，`RaiseEvent` 的事件名同样，否则拒绝开局 |
| 8 | 第一次模块阶段，各模块 `on_scenario_start` 之前 | 投递该模块的 `IniEntry`、`IniKey` |
| 9 | `on_scenario_start`，之后每帧 | 触发器调用模块动作，`RaiseEvent` 引发模块事件 |

**开局投递。** 每个模块先收到全部 `IniEntry`，再收到全部 `IniKey`，都按注册顺序；同一个注册中，`IniEntry` 按条目在合并后列表中的顺序（同名条目只投递第一次），`IniKey` 按该类节的 ID 顺序。值取自规则层全部处理完之后的合并文本。投递使用 `on_events`，记录的 `key` 是注册时给出的分派键；不受每帧条数上限约束，不进积压队列，全部计入 `on_scenario_start` 的一次性额度，用完时模块停用。处理函数发现值不合法时，模块应停止并指出节和键；读档时不重新投递。

**模块事件。** `RaiseEvent`（原子动作）引发一个已注册的事件，事件种类为 `ModuleEvent`，`EventDef.id` 为事件 ID。注册为对象事件时，目标须是存在的对象，事件只对绑定了相应触发器的对象引发；全局事件不需要绑定。0.1.0 中 INI 触发器只能经由类型上的 `Wasm.Tags` 接入，所以只有代码创建的触发器能听到全局模块事件。`other`、`value`、`value2`、`house` 取自动作参数，含义由注册它的模块说明。任何来源都可以引发任何已注册的事件。引发点是安全点（第 5 节）：监听它的触发器中原版动作和原子动作立即执行，模块动作排队，连锁照常计数。决定处理函数不能执行 `RaiseEvent`（待定问题 20）。

**参数文本。** INI `Action=Wasm:名字(目标,文本)`（第 6a 节）或代码中 `Module` 动作的 `ActionDef.target` 和 `ActionParams.text`，在触发器触发时成为记录的 `target` 和 `args`：参数文本合并为一个字符串 ID，模块用 `name_of(String, args)` 读出。字符串表只增不减，存档并计入状态哈希。地图触发器的动作 1036 不带参数（待定问题 19）。

**条件不注册。** 筛选子句在事件点由引擎原生求值，不调用模块；模块把结论写进变量，INI 用 `Where=Var(...)` 判断。

### 6i. 驱动所属方

模块可以像玩家一样操作一个所属方：模拟模块接管电脑所属方，客户端模块替本玩家操作。同一份决策代码可以编成 `rules.wasm`，也可以编成 `ui.wasm`。

| | 模拟模块驱动电脑所属方 | 客户端模块驱动本玩家 |
| --- | --- | --- |
| 运行在 | 每台机器，锁步 | 仅本机 |
| 指令出口 | `order`（第 6g 节） | `client_send_order`（第 10 节） |
| 读取 | 完整模拟状态；`Visible` 子句可自限为该所属方的视野 | 本玩家能看到的状态（第 10 节） |
| 事件 | 触发器（第 6a 节） | 客户端事件 `SimEvent`（第 10 节） |
| 原生 AI | 按认领的领域让位 | 不涉及 |
| 结果 | `Commanded`、`OrderRefused` | 同左，经 `SimEvent` 到达 |

**认领。** 所属方属性 `ControlDomains` 是按枚举 `Domain` 编位的掩码，只在模拟中可读写：

| 位 | `Domain` | 认领后原生 AI 让出的决策 |
| --- | --- | --- |
| 0 | `Production` | 选产品、建造队列、自动造基地（`AutoBaseBuilding`）、建筑选址，以及电脑矿车从守卫转回采矿 |
| 1 | `Forces` | AI 触发器、建小队、小队脚本、所属方更新中对已有部队的进攻、防守和集结调度，以及任务里替所属方安排单位的电脑分支：步兵空闲时的站位选择、战役中进攻部队向玩家进军、区域守卫把岗位移出己方建筑、受伤车辆自动找维修厂、被心控单位的去向 |
| 2 | `Abilities` | 所属方 AI 给单个单位下达的能力任务：部署和收起（基地车以外）、进驻和撤出建筑、工程师占领、间谍渗透、守卫中的爆破兵自动去安放 C4 |
| 3 | `SuperWeapons` | 超级武器的选择和发射 |

- 写入只接受没有玩家控制、尚未战败的所属方（同 `order` 的条件），对人类所属方为 `Refused`。值为 0 时原版行为不变（目标 5）。
- 单位自身的反应不属于任何领域，照常运行：索敌、还击、采矿循环、按单位规则的自动部署和空闲行为。基地车的部署属于 `Production`。认领让出的电脑分支里若有随机数抽取，抽取照常发生，只丢弃结果（例如被心控单位去向的掷骰），所以随机流不偏移。单位级的决定（`IdleMission`、`MissionStep`、`HarvestCell`，附录 4.5）不属于领域，按绑定询问。
- 认领归写入它的模块：一个所属方的一个领域同一时间只能由一个模块认领，另一模块写入已被认领的位为 `Refused`。模块停用时它认领的位全部清零，原生 AI 从下一帧起恢复（第 3 节）。
- 认领状态存档，计入状态哈希和联机校验。

**大厅席位。** mod 在 `[VeraWasm]` 写 `Controller=yes` 时，大厅为每个电脑席位多出“mod AI”选项。选它的所属方在场景开始时 `ControlDomains` 为全部四位，归 mod 模块，原生 AI 一开始就不运行。地图模块不能作控制器。0.1.0 中引擎按开局设置安排“mod AI”所属方，但大厅还不提供这个选项。

**额度和内存。** 模块每认领一个所属方的任一领域，该所属方算一个席位：额度 B = `Budget` + 席位数 × `SeatBudget`，席位数在每帧开始时按认领状态计算（第 15.4 节）。没有逐所属方的导出：模块在 `on_frame` 里自行错开各席位的工作。mod 模块的内存上限按房间里的“mod AI”席位数放宽（第 15.4 节），在实例化时按此分配；对局中认领普通电脑所属方不改变内存上限。

**指令结果。** 执行的指令照常引发 `Commanded`。在执行步骤中被拒绝的指令引发 `OrderRefused`：对其中每个单位一次，所属方级指令（生产、放置、超武、出售墙）一次，带原因（`RefuseReason`）。指令和结果按（单位，指令，目标）对应，`Order` 不带标签。

**读取。**

- 对象视点属性 `Visible`：视点所属方此刻能看到该对象，考虑迷雾、隐形和侦测，与该玩家的客户端一致。在 `find` 中把 `viewpoint` 填为所属方并加子句 `Visible=1`，模块就只看到该席位应看到的对象。引擎不强制，由模块决定是否只用可见信息。
- 对象属性 `Engage`（派生·高，`EngageResult`）：射手能否打击候选对象，以及不能的原因。在 `find` 中把 `viewpoint` 填为射手对象（`Query.viewpoint` 可以是对象引用）。复用引擎现有的开火许可和伤害判定。
- 生产、目的地、武器冷却、部署、连通区域等读取面属性见附录第 7 节。引擎不提供“原生 AI 会怎么选”的查询；建筑选址用带 `Placeable=1` 子句的 `find`。

**客户端驱动本玩家。** 沿用 `client_send_order`：指令像玩家输入一样校验、进入命令流、被回放记录。房间开关“允许自动操作”写入全局属性 `AutomationAllowed`，为 0 时客户端模块的指令返回 `Refused`。0.1.0 中引擎从房间设置读取这个开关（默认关闭），但大厅还不提供它。频率上限见第 15.4 节。客户端模块没有逐帧导出：SDK 在渲染函数里比较 `client_frame()`，模拟帧变化时才运行决策。

**引擎侧微操例程**（风筝、撤退、集火，动作 `AttachRoutine`、`DetachRoutine`）留到以后；做时复用上游 PR #5049 的例程，并先改为可存档、计入哈希的模拟状态。

### 7. 运行时的触发器和标签

模块按地图的同一模型创建触发器：

```ts
// TypeScript 设计示例，convoy 是要监视的运输车句柄：
const americans = Rules.country("Americans");
if (americans != NO_HANDLE) {
  const house = Find.houses().country(americans).first();
  if (house != NO_HANDLE) {
    const t = Trigger.on(Event.Killed).house(house).bind(convoy).enqueue(onConvoyLost).done();
    if (t != NO_HANDLE) Trigger.setEnabled(t, false);   // 暂停，写 true 恢复
  }
}

Trigger.on(Event.CrossesHorizontalLine) // 格子事件（附录 4.1 注明“绑定格子”）
  .bind(Cell.at(40, 52))                // 格子绑定
  .enqueue(onLineCrossed).done();

Trigger.on(Event.TakeDamage).bind(Rules.technoType("E1")).enqueue(giPanic).done();   // 同 Wasm.Tags=：每个 E1 运行自己的实例
```

- 新建的触发器放进现有触发器运行时的列表，和地图里的放在一起，不另存一份。它们使用确定性的编号，不会和地图里的编号冲突，并随触发器运行时一起存档和计入哈希。
- 绑定（INI 中的 `Wasm.Tags`、代码中的 `trigger_bind`）不占用对象的标签槽位，而是作为独立的订阅另外记录。所以地图上预先放置、自带标签的对象保留它的标签，同时也接收绑定的触发器。代码中的类型绑定立即作用于该类型的每个对象，mod 和地图的模块都可以使用。
- 一个对象只有一个标签，一个标签可以连接多个触发器。标签只为兼容红警 2 而保留：地图触发器通过标签挂到对象上，对象的 `Tag` 属性可以读，也可以设为另一个已有的标签（和原版一样替换原有的标签）。模块不创建标签：它用对象绑定代替。让一个对象挂多个标签属于 VERA 扩展，需要单独的 RFC。
- 被绑定的对象，以及得到一个含有模块触发器或 VERA 新增事件上的触发器的标签的对象，都会得到它自己的一个标志位，所以即使它的类型没有绑定任何东西，事件触发点也会为它引发这些事件（第 15 节）。
- 每个绑定对象以各自的实例运行绑定的触发器，重复状态按对象分开：一次性触发器对每个对象各触发一次。类型绑定只保存一份触发器定义；按对象的实例状态只在它不同于默认值时（例如一次性触发器已经触发）才创建（第 15 节）。禁用或删除触发器会作用于所有实例。触发器定义的所属方为 0 时，触发器的所属方是它触发那一刻主体的所属方；标签持有者是引发事件的对象。
- 对象绑定随对象消失，触发器本身留下，需要时用 `trigger_remove` 删除；`trigger_unbind` 提前解除绑定。删除对象、标签或触发器时，通过触发器运行时现有的清理逻辑解除关联。
- 编号：事件表和动作表各自独立，都保留原版和 Ares 的编号（事件 0..88，动作 0..149）。1000 以下只承载原版和其他扩展已有的语义；VERA 的新种类在各表中从 1000 起编号，已分配的编号不改变、不复用。0.0.25 及以前的草案从 100000 起写；引擎从 1000 起编号，草案的 100000 + n 就是 1000 + n。版本 1 中地图的原版触发器在 1000 以上只接受动作 1036（`Module`）：`[Events]` 中出现 1000 以上的事件，或 `[Actions]` 中出现 1000 以上的其他动作时，拒绝开局并指出触发器，因为原版把未知事件当作成立。0.1.0 未实现：地图触发器既不执行动作 1036，也不拒绝其他 VERA 编号。带模块动作的地图须填写 `VeraMinVersion`（0.1.0 会拒绝 `VeraMinVersion` 高于本游戏的地图，但不拒绝缺少这个键的模块地图）。

### 8. 修改规则

| 时机 | 能改什么 | 方式 |
| --- | --- | --- |
| `on_rules` | 任意规则键；新增类型（AI 定义除外，第 6d 节） | `rules_set(section, key, value)`：值是 INI 文本，走原生 INI 读取器、钳制和读后处理；计入大厅哈希 |
| 对局中，按类型 | 版本 1 中没有 | `rules_set` 和类型引用、全局规则引用上的 `set` 返回 `Refused`；按对象的变化用属性、动作和修饰器 |
| 对局中，按对象 | 生命值、所属方、任务、等级、弹药、变量；倍率等可修饰属性 | 通过现有的单对象 owner：`set`、`modify`、动作（第 6c 节） |

- `rules_get(section, key, out, cap)` 读出原始字符串，除初始化函数外都可用。常用的键还是类型引用和全局规则引用上的带类型属性（附录 [7.7](0001-wasm-extension-modules-api.zh-CN.md#77-类型与规则)），读到的就是引擎实际使用的解析后的值；引擎从不读取的键，只能通过 `rules_get` 从合并后的文本中读出。在 `on_rules` 中，`get` 读到的是本层之前处理过的值，本次调用写入的值要等这一层处理完才读得到；对类型引用 `set` 等于用值的 INI 文本调用 `rules_set`（0.1.0 未实现：这样的 `set` 返回 `Unsupported`）。
- 以后的次版本可以逐键开放对局中的修改。每个键必须先列出全部读者，写明已有对象、在飞抛射体、进行中的生产和计时器如何变化，以及要失效的缓存；值进入由模拟持有、存档、计入哈希和回放的覆盖层，所有读者只在帧边界看到新值。
- 对局中不能新增类型。
- 启用 Ares 或 Phobos 时，模块能在规则中看到它们的键，可在 `on_rules` 中修改，对局中同样只读。

### 9. 示例：抛射体弹道

四个层级都在 `rules.wasm` 中运行，因为它们决定打中什么。`ui.wasm` 可以加纯视觉效果，比如拖尾和光效。

| 层级 | 机制 | 开销 |
| --- | --- | --- |
| 1 | `on_rules` 设置现有键（`Arcing`、`ROT`、`Vertical`；Phobos 的 `Trajectory=` 尚未移植，移植后同属这一层） | 对局中无开销 |
| 2 | 武器开火、抛射体引爆的触发器：额外的抛射体、在引爆点分裂、连锁 | 每次事件，仅限绑定的类型 |
| 3 | 可决定事件 `Launch`：结果区中是一条路径（附录的 `PathSpec`：贝塞尔、抛物线、螺旋、路径点）；引擎用定点数沿路径推进抛射体 | 每个抛射体一次决定 |
| 4 | 每帧的可决定事件 `ProjectileFrame`：引擎在自己推进抛射体的过程中、按自己的顺序，在每个绑定的抛射体移动之前决定它：处理函数读速度（`VX`、`VY`、`VZ`）和位置，在结果区（附录的 `ProjectileStep`）中给出新速度、新位置、新的模块数据，或请求引爆 | 每帧每个绑定的抛射体一次调用 |

- 第 3、4 层为预览。它们只增加事件种类，不增加新的导出。
- 模块路径（`ProjectileFrame` 的一步，或 `Launch` 的路径）代替原生推进中“算出候选位置”的一步：制导分支、Vertical 分支或普通弹道。在此之前，等待动画和目标失效照常处理，本帧因此终止的抛射体不询问模块；引擎的帧数引信目前没有写入者。制导和 Vertical 分支自身的引爆判定（到达吸附、安全高度、接近率、桥面、`DetonationAltitude`）属于被替换的这一步，随之不再执行：需要时由模块请求引爆。在此之后依次照常执行：普通弹道的地面、桥、墙、建筑和出图检查，射程，火焰风暴墙，共享碰撞探测，近炸引信（参考点仍是发射时冻结的目标坐标），引爆；原本有制导的抛射体走模块路径时同样执行普通弹道的这些检查。碰撞、伤害和弹头仍由各自的 owner 处理。
- 速度是定点数（16 位小数），与引擎的 binary64 速度互换时精确；一步不设速度时保留原速度的每一位。引擎钳制模块的输出：速度、路径速度和单帧位移每轴至多 2,048 lepton（第 15.4 节）。设了位置时它就是候选位置，否则为当前位置加速度的整数部分。请求引爆等于在候选位置命中，出图优先；离开地图时删除、不引爆，与原生相同。碰撞只检查候选点，不检查中间线段。同一帧 `ProjectileFrame` 回答了时，路径这一帧不前进。
- 路径：引擎每帧把进度加上速度，按进度占路径长度 L 的比例放置抛射体，全部用整数：`Bezier` 以发射位置和各点为控制点，L 为控制多边形的长度；`Parabola` 沿到唯一一点的直线，抬高 `4h·u(1−u)`；`Spiral` 沿同一直线，在横向和竖直方向偏移半径 `4r·u(1−u)`、角度每 `param[1]` 帧一圈；`Waypoints` 依次直线经过各点。路径终点即命中。每帧把速度设为这一步的位移，抛射体的朝向随路径变化。
- 每个抛射体有 16 字节的模块数据（`Data0` 为第 0..7 字节，`Data1` 为第 8..15 字节，各为小端序 `i64`），存档并计入哈希，放在按抛射体索引的旁路表里（第 15.1 节第 9 条），可用 `set` 写入。决定处理函数不能调用 `set`，所以 `ProjectileFrame` 通过 `ProjectileStep` 写回模块数据，处理函数仍然只读。`ProjectileFrame` 的已飞行帧数从发射时算起（发射时该类型已绑定决定触发器，或带有路径、方案给的模块数据），否则从第一次询问算起。
- 在引爆点分裂：`Detonated` 记录带引爆点的坐标（附录 [4.3](0001-wasm-extension-modules-api.zh-CN.md#43-新的投递型事件)），模块动作用 `CreateProjectile` 以 `ProjectileSpec` 的绝对起点坐标在那里生成新的抛射体。记录中的抛射体此时已经不存在。

**齐射。** 要一次发出多枚不同弹道的抛射体，就在武器的 `Fire` 事件上挂一个模块动作，用 `CreateProjectile` 动作生成它们，每枚有自己的类型、模块数据和起点偏移。要让它们沿不同的路径飞，用 `Launch`；否则它们都沿原生弹道飞向各自的目标。这个动作从它的事件记录中读出射手、目标和原生抛射体（SDK 字段 `shooter`、`target`、`projectile`）。原生抛射体在单位更新时射出，模块生成的抛射体在模块阶段射出，所以它们比原生抛射体恰好晚一次推进，起点也按那时射手的位置计算。

**可决定的 `Fire`** 避免这段延迟。它的结果是一份射击方案：结果区中要生成的抛射体的列表，每枚带自己的类型、武器、目标、模块数据和起点偏移（附录的 `ProjectileSpec`），结果槽是条目数。

- 询问在原生发射已有解、弹体负载（伤害及各种倍率、Prism 支援加成、Ares 射程）已建好之后，原生射击本应射出的那一刻；这次射击的随机数此时都已抽过，方案不改变随机流。引擎立即生成方案中的抛射体，不生成原生抛射体。已处理的空方案什么也不发射，但仍算射出；未处理则沿用上一环的结果。首环的输入是原生射击的一条：原生抛射体类型、武器 −1（这次射击的武器和负载）、目标 0、模块数据 0、偏移 0。
- 不询问：发射无解的射击（按原生失败，射速和弹药都不动）、不产生弹体的分支（`Suicide=`、Sonic、Spawner、Drain、DiskLaser）和 `LimboLaunch=` 武器（弹体载着射手，即 Parasite）。
- 与原生一条相同（同类型、目标 0、偏移 0）的条目按原生抛射体的速度飞行；其他条目用开火的标量发射计算（不含扇形齐射、提前量、发射散布、Lobber 高弧和建筑仰角）从起点射向目标，无解的条目跳过。第一条用原生弹体的 id，其余各取新 id。
- 这次射击的其他所有原生效果照常发生：射速计时器、弹药消耗和装填、连发计数、开火音效、枪口动画、后坐、粒子系统，以及开火时解除隐形或暴露。磁轨线伤和激光、电弧、辐射束、波等效果仍画向并作用于原生目标。射击之后读弹体的地方（单位的 Scalable、飞机投弹的速度）读方案的第一枚。
- 方案中的每枚抛射体对它的目标对象引发 `AttackedBy`；`ProjectileIncoming` 尚未实现。投递型的 `Fire` 事件仍然引发，其 `projectile` 为 0。
- mod 和地图的模块都决定了这次射击时，地图的一环收到 mod 的方案，可以保留、修改或替换它。

### 10. 客户端模块

引擎建立界面树并读取 INI 布局后调用客户端启动函数。每个渲染帧先投递事件，再调用渲染函数，见[客户端导出表](0001-wasm-extension-modules-api.zh-CN.md#22-导出)。

**界面树。** 引擎持有节点并负责布局与绘制。模块按部件名查找当前生效布局中的节点（节名去掉布局前缀，即 `Parts=` 中的名字），创建或删除节点、修改属性。引擎按渲染帧批量提交修改。

**节点所有权。** 每个节点记下创建它的来源：引擎和 mod 的 INI 布局、mod 的模块、地图的 INI 布局、地图的模块。

- mod 的客户端模块可以读、写和删除任何节点，所以它能替换或重排对局界面。
- `MapUI=overlay` 时，地图的客户端模块可以找到和读取任何节点，但只能写和删除地图自己的节点；对其他节点的写入和删除返回 `Refused`。它新建的顶层节点放在覆盖层，画在对局界面之上。
- `MapUI=full` 时，地图模块的权限和 mod 模块相同；`MapUI=no` 时不加载地图的 `ui.wasm`，大厅中给出提示。

作者分两部分编写界面：

- **静态布局写在 INI 里**，不需要预编译，没有动态部分的界面不需要模块。mod 使用 [`veraui.ini`](../interface-layout.md)，沿用它现有的位置、阵营选择、玩家覆盖层和比对规则；模块不得依赖某个部件存在。地图在自身文件中写 `[VeraUI]`（`Parts=` 列出顶层部件）和 `[VeraUI.<部件名>]`（键与 `veraui.ini` 的新增部件相同）：对所有阵营相同，只新增属于地图的部件，顶层部件放在覆盖层。`MapUI=no` 时忽略这些节；`MapUI=full` 只扩大地图模块代码的权限，不让地图 INI 替换 mod 的布局。玩家布局不改动地图的部件。
  - 两者都新增 `Image`、`Bar`、`List` 三种 `Type`。`Button` 可以只有 `Label` 或 `Art` 而没有 `Command`（只产生 `Click`）；`Text` 可以用 `Label` 代替 `Value`。版本 1 中行和列不能嵌套。
  - 按名查找时，先在模块自己来源的节点中找，再按引擎、mod、地图的顺序找；同一组内同名时取先创建的。
- **动态部分写在模块代码里**：按名字找到节点后修改，或新建节点。

INI 的节点种类、布局键和可写属性见[客户端节点表](0001-wasm-extension-modules-api.zh-CN.md#710-客户端节点)。TypeScript 可在模块内部使用 React 或 JSX 风格的库。

**其他客户端功能：**

- 版本 1 不提供挂在对象上的显示（`Decoration`）和地图标记（`MapMarker`），它们留给以后的次版本。隐形等玩法属性属于模拟模块。
- 本地动作（`client_action`）：播放声音和 EVA 语音、移动镜头、本地选择、闪烁对象、显示消息、注册热键。镜头、光标和本地设置也是客户端拥有的引用：`Camera.cell()` 读镜头所在格子，`Camera.jumpTo(cell)` 跳转。按 lepton 写镜头位置留到以后。版本 1 的本地设置只有只读的 `Viewer` 和 `IsSpectator`，模块不能读写其他玩家设置。
- 点在可点击节点上的鼠标不再传给地图。点在地图上的鼠标作为 `MapClick` 客户端事件到达模块，同时照常传给游戏；模块把光标的 `CaptureMapClick` 写为 1 时，地图点击只交给模块，不传给游戏。模块热键与游戏热键冲突时，游戏热键优先。客户端可以读光标的屏幕位置和光标下的格子（附录 7.10）。
- 选中单位和点击按钮属于客户端事件。要改变游戏，模块发送一条消息，由模拟模块在 `on_message` 中处理，这样联机和回放都保持一致。
- 客户端模块可以发出标准玩家指令（移动、攻击、部署、建造……，`client_send_order`），引擎像校验任何玩家输入一样校验它们。模拟模块用同一张指令表指挥电脑所属方（第 6g 节），并可给任何所属方的单位下任务（`SetMission`）。消息用于自定义逻辑。
- 图像、动画和模型都按名字引用，从不按文件格式引用，所以以后新增素材格式（单独的 RFC）不需要修改 API。
- `client_log` 输出到游戏内控制台。
- 玩家自装的界面模块放到后续阶段。mod 或房间可以禁止它们。
- 模块新建的节点没有名字；模块可以用 `client_set_bytes` 给自己新建的节点写一次 `Name`，名字在同一来源中不得重复（地图模块与地图 `[VeraUI]` 的部件同属一组），否则为 `Refused`。INI 和引擎节点的名字只读。
- `client_init` 和 `client_on_start` 各有一份一次性额度，不占渲染帧的额度。
- 客户端模块只在本机运行：本机加载失败或运行出错时只停用该模块并删除它的节点，对局照常进行。读档后客户端模块从 `client_init` 重新开始（它们从不存档），本机存储保留。
- 只有 `ui.wasm` 而没有模拟模块的对局也转发 `SimEvent`。

**地图文字。** 版本 1 不为地图增加翻译格式，沿用地图附带文件中的 CSF：一张地图一种语言，并受 CSF 现有规则约束（`ra2md.csf` 替换整张表，追加表须开启 Ares）。独立的地图文件带不了字符串表，只能用已有的 CSF 条目或直接写文字。模拟只传递标签，从不查询 CSF 或译文，所以各玩家的语言文件不影响模拟结果。

**存储。** 每个 mod 和每张地图在玩家本机各有一个自己的小型键值存储，带容量配额，用于设置、成就和只供本机显示的进度（它不是战役继承：不随胜负、重开或读档回滚，跨关状态见第 6e 节）（`client_storage_read`、`client_storage_write`）。

- mod 的存储以它的 `[Mod] Name` 为键；地图的存储以它的存储 ID（`[VeraWasm] StorageId=`，默认为地图的文件名）为键，所以修改过的地图只要 ID 不变就保留它的存储。
- 地图的客户端模块使用地图的存储，在 mod 下也是如此，所以下载来的地图无法读取或修改 mod 的数据。
- 只有客户端模块能使用存储。需要影响对局的数据用消息送进模拟，因而成为命令流的一部分。
- 上限：键为 1 到 64 字节的 ASCII；单个值最多 16 KiB；每个 mod 或每张地图的存储最多 256 个键、合计 256 KiB（键和值都计入）。超出时写入返回 `Refused`，存储不变。写入长度为 0 的值即删除该键。上限按 API 主版本固定（第 12 节）。

**通知**从模拟模块发往客户端。

- 名字只解析一次，换成 ID：`lookup` 对通知名返回一个通知 ID，即名字按 ASCII 折叠为小写（只折叠 `A` 到 `Z`）后的 UTF-8 字节的 32 位 FNV-1a 哈希，在每台机器上、在两侧都相同。哈希为 −1 的名字在加载时被拒绝（第 3 节第 7 步）。
- 模拟模块要声明它发送的通知名：SDK 构建时按模块项目配置中的列表（属于 SDK 文档，不属于引擎 API），把这些名字写进 Wasm 自定义段 `vera.notify`。客户端模块不声明任何名字；已声明但没有任何客户端模块接收的名字不算错误。
- 对模拟模块没有声明的名字，以及在客户端模块中对本局没有任何模拟模块声明过的名字，`lookup` 返回 `(−1, NotFound)`：引擎保存着已声明名字的表，所以客户端从不会靠哈希匹配到未声明的名字。加载时的冲突检查（第 3 节第 7 步）保证每个已声明的名字都有 ID。
- `send_notify(to, id, ptr, len)` 发给所属方 `to` 的玩家的客户端；`to` 为 0 时发给每个观战者的客户端。那里的每个客户端模块都收到一个 `Notify` 客户端事件，带着 ID、数据和发送它的模块的来源。回放观看者收到他所观看视角的玩家的通知，或观战者的通知。单条通知的大小和每帧条数有上限（第 15.4 节），超出时 `send_notify` 返回 `Refused`。
- 观战者客户端的消息会被拒绝。

**模拟事件。** 客户端事件 `SimEvent` 把本方的部分模拟事件转给客户端模块：`ClientEventRecord` 的 `data`、`data_len` 指向投递区中的一条 `EventRecord`（与 `Notify` 的数据相同的方式）。转发的种类固定为 `Commanded`、`OrderRefused`、`TakeDamage`、`Killed`、`Birth`、`AttackedBy`，以后按表项追加；只转发主体是本方对象的事件和发给本方的所属方事件，`other` 是本玩家此刻看不到的对象时填 0。追帧期间不投递。

**客户端读取**（`client_get`、`client_get_many`、`client_find`、`client_var_get`）只暴露本玩家自己的界面能显示的内容；其他任何东西都通过通知送达客户端。属性表的“客户端”一列逐个写明。

- 本玩家的所属方和对象（含超级武器）可读取属性表中标为 all、own、seen 的项；标为 sim 的属性及小队、修饰器对象仅供模拟使用。
- 其他所属方，包括盟友：只有公开信息（名字、国家、阵营、同盟关系、是否已战败、是否为人类玩家），没有金钱、电力、建筑、生产、科技等级、超级武器或统计数据。
- 本玩家当前能看到的其他所属方的对象：只有类型、位置、所属方和生命，以及画面上看得到的染色和激光拖尾；没有乘客、目标、任务、等级、弹药、修饰器或真实的伪装身份。伪装的敌人读出来是它伪装成的样子（类型和所属方）。
- 黑幕下的对象不出现，迷雾下本玩家当前看不到的其他所属方对象也不出现：引擎不保存“最后一次看到”的副本。隐形的敌人除非被侦测到，否则不出现。格子的地形类型和高度对客户端全部公开，因为地图文件本身就是公开的；路径点编号也公开；其他格子属性遵守附录 7.6 的视野、视点或仅模拟限制。
- 变量按它的可见度（第 6e 节）。触发器和标签只属于模拟。视点属性只以本玩家自己的所属方为视点。
- 观战者的模块看到观战者能看到的范围，房间允许时为整张地图。观战者没有自己的所属方，所以只有在房间向观战者显示某个所属方的信息时，针对自己所属方的读取才有回答。
- 客户端只能写客户端拥有的引用：节点、镜头、光标和本地设置。没有对模拟状态的写入，模拟也从不读取客户端的状态，客户端之间也没有直接的通道。

**通信。** 模拟到客户端不经过网络：客户端读取它能看到的状态和变量，模拟用 `send_notify` 发出通知。客户端到模拟只有命令流：

- `client_send_message(ptr, len)`：消息进入命令流，在命令延迟之后的同一帧，在每台机器上到达同一来源的模拟模块的 `on_message`。
- `client_send_order(ptr, len)`：标准玩家指令。客户端模块可以用它替本玩家操作（第 6i 节），条件是全局属性 `AutomationAllowed`（房间开关“允许自动操作”）为 1，否则返回 `Refused`；频率上限见第 15.4 节。
- 两者都不可信：模拟必须校验内容，发送者由引擎填写，模块无法伪造。大小和频率有上限（第 15.4 节），回放记录它们。

一个完整的来回：玩家点击按钮，界面发出消息，模拟校验后写入一个所属方变量，界面读这个变量来更新按钮：

```ts
// ui.wasm — TypeScript 设计示例
import { ReinforcementsBought } from "./generated/vars";
const BUY_MESSAGE = new Uint8Array(1);           // 消息类型 1：购买
BUY_MESSAGE[0] = 1;
let buy: Node = 0;

onStart((): void => {
  buy = Ui.find("BuyReinforcements");            // veraui.ini 中的一个按钮
  Node.setClickable(buy, true);
});
onClientEvent(ClientEvent.Click, (e: ClickEvent): void => {
  if (e.node == buy) Client.sendMessage(BUY_MESSAGE);   // client_send_message
});
onRender((dt: f32, alpha: f32): void => {
  const me = Client.viewer();                                   // 观战者为 NO_HANDLE
  if (me == NO_HANDLE) { Node.setVisible(buy, false); return; } // 观战者没有所属方：以 0（全局）读所属方变量是非法参数
  Node.setVisible(buy, ReinforcementsBought.get(me) == 0);               // client_var_get：读本玩家自己所属方的私有变量是允许的
});
```

```ts
// rules.wasm — TypeScript 设计示例
import { ReinforcementsBought } from "./generated/vars";
const HTNK = Rules.technoType("HTNK");

onMessage((sender: House, data: Uint8Array): void => {
  if (data.length != 1 || data[0] != 1) return;                         // 消息不可信：全部要校验
  if (HTNK == NO_HANDLE) return;
  if (ReinforcementsBought.get(sender) != 0 || House.money(sender) < 2000) return;
  const tank = Action.createObject(Waypoint.cell(3), HTNK, sender);     // 格子被占时为 NO_HANDLE（Refused）
  if (tank == NO_HANDLE) return;                                        // 没造出来就不扣钱
  Action.addMoney(sender, -2000);
  ReinforcementsBought.set(sender, 1);                                           // 客户端下一次读取时就能看到
});
```

### 11. 联机

- 嵌入的模块随地图传输。mod 的模块计入现有的 mod 文件校验。
- 大厅比对模块哈希和所需的 API 版本；它在加载模块之前读取每个 `[VeraWasm] Api=`。需要房间的游戏所没有的 API 版本的地图或 mod 无法被选择；离线时，这样的存档或回放会被拒绝。每种拒绝都给出所需的版本。0.1.0 的大厅还不比对 `Api=`：地图的 `Api=` 本游戏不支持时，在对局加载时失败并指明版本；mod 的 `Api=` 不检查。
- mod 的 `[VeraWasm]` 键在它的 `rulesmd.ini` 中，mod 摘要包含这个文件，所以每个玩家都会比对它们；摘要不包括的 `mod.ini` 不放任何模块键。
- 每条消息的发送者由引擎填写，模块无法伪造；单条消息大小和每帧消息数有上限。
- 通知只送达目标玩家或观战者。通知的内容是模块自己的字节，由模块作者负责：引擎无法过滤它。
- 联机只交换指令，从不交换状态。重连的玩家从头重新模拟整局，包括模块；模块消息本身就是指令，所以不需要额外发送任何东西。因此模块每帧的开销也会拖慢追帧速度。追帧期间不投递通知，客户端模块也不运行；追帧结束后它们收到一次 `client_on_start`。
- 存档和回放记录游戏版本、模块哈希和 API 版本。模块与当前安装的 mod 或地图不一致的存档或回放会被拒绝，并提示是哪些模块；旧版本会拒绝新版本生成的存档和回放，并给出提示。
- 房间要求所有玩家运行同一版本，所以混合版本的房间不会开局。
- 离线时，支持模块之前的版本会不带模块地运行模块地图：它忽略 `[VeraWasm*]` 节，其触发器中的模块动作什么也不做。已发布的版本无法再修改，所以这是一个明确记录的遗留问题。为了涵盖之后的版本，支持模块之前的那个版本增加一个地图键 `[Basic] VeraMinVersion=`（名字未定），对需要更新版本的地图拒绝运行并给出指明版本的提示。模块地图设置这个键。
- 这项改动要更新 [Networking](../Networking.md)，说明已发布的游戏、混合版本的房间以及回退版本分别如何处理模块。

### 12. 版本与 ABI

- 一份用 WIT 语法编写的接口定义是 API 的唯一来源，附带机器可读的表（事件种类、动作种类、属性、名字种类、节点种类和其他枚举）。项目自己的生成器由它们生成 Rust 和 TypeScript SDK 的包装函数、参考文档和兼容性检查；其他语言的绑定也从同样的表生成。WIT 只是接口描述语言：模块不使用 Component Model 的 canonical ABI。0.1.0 未实现：还没有 WIT 文件和基于 WIT 的生成器；这些表在引擎的沙箱 crate 中（导入列表，属性、事件和动作的名字表），由附录记录，手写的 Rust SDK 由测试与它们核对。
- 二进制接口是 core module ABI：core Wasm 模块的导入和导出、`i64` 引用和值、`i32` ID、字符串、字节和缓冲区用的指针加长度，以及由宿主写入模块缓冲区的批量结果。宿主导入最多返回一个值：有返回值的调用返回状态，值由宿主经输出指针写入模块内存，因为稳定版 Rust 和 AssemblyScript 都无法导入多返回值的函数；模块内部仍可使用多返回值（第 3 节）。返回值、状态和续页位置见附录签名。
- 冻结两个接口的导入和导出签名（[附录第 1 节](0001-wasm-extension-modules-api.zh-CN.md#1-模拟-abi)和[第 2 节](0001-wasm-extension-modules-api.zh-CN.md#2-客户端-abi)）。事件种类、动作种类、属性、名字种类、搜索范围、节点种类、客户端事件和动作种类，以及其他枚举，都是只追加的表，在次版本中追加；`has_kind` 让模块在不认识某个表项的旧引擎上降级运行。
- 以后的某个主版本可以在 core ABI 之上增加一个 Component Model 适配层。已有模块继续使用 core ABI，不受影响。
- 接口是带版本的包：`vera:sim@1`、`vera:client@1`。版本号是“主版本.次版本”。新的主版本不兼容，每个主版本都通过适配层永久保留；新的次版本只做增加。模块通过它的导入说明需要的主版本和最低次版本（导入的模块名为 `vera:sim@<主>.<次>` 或 `vera:client@<主>.<次>`；0.1.0 只实现 `1.0`，只接受 `vera:sim@1.0` 和 `vera:client@1.0`），地图或 mod 在 `[VeraWasm] Api=` 中写明同样的版本。`vera:sim` 和 `vera:client` 共用一个版本号，总是一起发布，所以一个 `Api=` 同时说明两者。大厅用每个玩家的游戏检查 `Api=`；加载时检查模块的导入与 `Api=` 一致（第 3 节）。
- 不稳定的接口放在 `vera:unstable/*` 下，需要显式开启，可以不经通知就改变。它们和 `0.x` 预览版都不是已发布的版本：不保留适配层，使用它们的模块只能在为之构建的那个版本上运行。
- 每个已发布的版本都一直可用。旧版本是现行实现之上的薄适配层，从不是第二份实现。适配层从不把旧版本没有定义的值交给旧模块：该版本的表中没有的事件种类的记录不投递给它，该版本没有的属性对它不存在，更新的状态值或枚举值以该版本定义过的值交给它，具体对应关系按表写在接口定义中。
- CI 从仓库内的 Rust SDK 源码构建并运行各已发布版本的兼容性用例；不提交 Wasm 二进制。每次发布追加用例。0.1.0 中，引擎测试在拿到构建好的 `.wasm` 文件时运行 Rust 示例模块；目前还没有发布过任何版本。
- 计量单位、每个宿主函数的费用、默认额度和各项上限属于主版本的一部分，随主版本固定（第 4 节）。
- 函数和表项可以弃用并向模块作者发出警告，但已发布的版本永不删除。
- 已发布的函数、属性和表项永不改变单位或含义。要改变，就追加新的表项或发布新版本。
- 自定义段 `vera.actions`、`vera.notify`、`vera.vars` 和 `vera.delivery`（投递区声明）各有[附录中的固定布局](0001-wasm-extension-modules-api.zh-CN.md#自定义段)，以一个格式版本开头。其中的名字是 UTF-8，必须是 ASCII，并且只按 ASCII 规则统一大小写。
- 模块动作和决定处理函数用模块自选的 32 位分派键标识，写在触发器定义中；事件记录携带这个键，SDK 生成的 `on_events` 和 `on_decide` 据此分派，因此处理函数不必是 Wasm 导出函数。`vera.actions` 把名字对应到分派键，只有被 INI 或地图引用的处理函数才需要名字。分派键只在本模块内有意义，跨来源的名字只在 INI 中解析（第 2 节）。
- INI 注册（第 6h 节）不用自定义段：键、注册表和模块事件名由初始化函数调用 `ini_register` 注册，开发工具在沙箱中只运行初始化函数即可读出它们。

### 14. 项目契约

- 扩展模块功能（不要与浏览器版的 `wasm`、`wasm-net` 和 `wasm-threads` 构建 feature 混淆）存在于每个构建中，当 mod 或地图提供模块，或使用它的任何键（`Wasm.Tags`、筛选子句、INI 原子动作、`[VeraWasm]`）时，在运行时开启。从不放在构建 feature 后面。只要它开启，修饰器的 owner 就可用（第 6c 节）。
- Wasm 运行时按平台选择，放在平台构建 feature 后面，项目契约允许平台 feature 这样做：桌面上用原生引擎（Wasmtime，关闭其 fuel 和 NaN 规范化），浏览器版用浏览器自己的 WebAssembly 引擎（待定问题 1），独立的 WASI 工具用 wasmi 解释器；三者运行同样改写后的字节（第 3、4 节）。模拟通过同一个接口访问运行时，所以 `vera20k-core` 和 `sim/` 仍能为浏览器编译。浏览器中的模块实例属于主线程，所以带模块的浏览器对局把模拟帧留在主线程。
- 每次模块调用都通过状态现有的 owner 访问状态。属性写入、修饰器和变量都只有一个 owner；API 不引入竞争状态。
- 功能在 `docs/` 下为 modder 编写文档。`docs/modding.md` 目前写着 mod 只是数据、VERA20k 不会运行 mod 里的程序；这段要改成：模块只在沙箱中运行，无法访问文件和网络，模拟模块也无法访问时钟。Mods 菜单和地图列表要标出带模块的 mod 和地图。
- 模块出错在游戏中报告，从不只写进日志。

### 15. 性能

以 2 万单位、30 个所属方为性能基线（[模拟线程预算](../sim-thread.md)）。热路径用初始化时缓存的 ID 或引用；名字只用于初始化及低频规则修改。批量读取、分页和事件投递使用模块的缓冲区。搜索不分配内存，排序成本随结果数增长；抛射体逐帧数据直接写入模块结果区。SDK 原地读取事件，逐对象和逐事件均不分配包装对象。

#### 15.1 实现要求

以下各条都是必须的：它们是实现的验收标准，逐条审查。

1. **没有模块就没有开销。** 每个事件触发点和决策点先检查标志位；标志位不成立时不构造任何载荷，其余代码都不运行。每个被绑定的对象，以及得到带模块触发器的标签的对象，设置自己的一个标志位（第 7 节）；这些按对象的标志位放在实体存储的侧列中，检查时不加载对象本身。类型、武器、弹头和抛射体类型的绑定标志位放在模拟持有的可变表中：对局中规则数据是只读的，而模块可以在对局中绑定类型。
2. **有效值在变化时算出并缓存。** 修饰器加入、移除或到期时，引擎重新算出受影响属性的有效值，缓存在实体上；热循环（移动、开火判定、索敌评分）只读这个缓存，从不在读取时查旁路表或合成修饰器。没有修饰器的属性读到的就是基础值。修饰器保存绝对到期帧，按到期帧分桶处理，每帧的开销只随本帧到期的修饰器数增长；`Remaining` 由到期帧算出。这与引擎现有的各个倍率层的做法相同。
3. **对应 Phobos 键的修饰器沿用 Phobos 的读取阶段、运算顺序和取整**（第 6c 节），精度限于 Q16.16。它们与 Phobos 共用的代码存在于每个构建中，由运行时开关开启（Phobos 的键由 Phobos 的开关开启，模块修饰器由模块功能开启），从不放在构建 feature 后面（项目契约，第 14 节）。
4. **决定只在提交点。** 可决定事件只在引擎提交结果的那一点同步调用，按引擎的确定顺序；从不为推测性或并行的预计算（索敌预答、寻路批次、追猎评分）调用，因为这些计算的答案可能被丢弃。`count` 总是 1（第 6f 节）。投递型事件同样在结果提交的地方引发，从不在推测性的计算中引发（第 5 节）。
5. **决定处理函数中的随机数**从按请求派生的子流取数（键见第 4 节），所以决定调用的次数不改变模块主随机流。处理函数照常可以写自己的模块内存：调用只发生在提交点，按确定的顺序。
6. **`ProjectileFrame`**（预览）在引擎自己推进抛射体的过程中、按它的顺序、在该抛射体移动之前调用（第 9 节），不在推进之前另设一个阶段。
7. **模块内存的哈希。** 只哈希实际增长到的内存（`memory.size`）。页按轮转哈希：每帧哈希 1/15 的页，再与其余页缓存的摘要合成模块的摘要；页数也计入摘要，新增的页先取摘要 0，不在增长当帧集中计算，所以没有尖峰。摘要算法按字计算，在内存上限下每帧不超过第 15.4 节的目标。0.1.0 用 XXH32 计算每个 64 KiB 页的摘要，在 p ≡ 帧号（mod 15）的帧刷新第 p 页。
   - **轮转哈希**供联机同步校验和对局中周期记录的状态哈希共用。它只保证：一处页差异若持续到该页下一次轮到，会在写入后 15 帧之内可见（摘要碰撞除外）；在两次检查之间出现又消失的差异，包括与轮转同周期的差异，可能永远看不到。
   - **完整哈希**按需计算：重新读取此刻全部模块内存，不使用也不修改缓存的摘要，其余内容与状态哈希相同。存读档等价性、跨平台一致性和回放终点的校验必须用完整哈希；定位第一次不同步的帧时，在各机器上重放并逐帧计算完整哈希。
   - **存档**保存模块字节、页数、按页号递增排列的非零页（拼接后以 DEFLATE level 1 压缩）、全局变量和轮转摘要。读档时先检查页数和解压长度不超过上限。轮转摘要只为让读档后的在线校验与连续运行相同，不能作为内存恢复正确的证据。合并后的规则文本不随模块重复存档（0.1.0 未实现：模块存档仍带着它）。
8. **展示快照不含模块。** 每帧为绘制复制的展示快照不包含模块的运行时状态（实例、线性内存和全局变量）。
9. **稀疏的实例和旁路表。** 变量、修饰器、绑定和每个抛射体的模块数据放在按引用索引的旁路表里，类型绑定放在按类型索引的表里，只有用到它们的对象和类型才占空间；按对象的触发器实例状态只在它不同于默认值时才创建（第 7 节）。它们存档并计入哈希；它们对每帧同步校验的贡献在写入时增量维护，不在每帧遍历全部条目。

10. **引擎代模块做的工作也有上限。** 轮询先判断是否到期再取持有者，类型绑定的持有者不靠每帧扫描全部对象得到；搜索使用所属方、类型和区域索引；队列、绑定和修饰器的增删不随总项数平方增长。这些工作要么计入所属模块的额度，要么有与对象总数无关的每帧上限，并显示在开销叠加层中。

#### 15.2 引擎对模块的硬上限

下面是提议的默认值，取值见第 15.4 节，实测确认后（待定问题 7）按 API 主版本固定（第 12 节）。

- **每帧运算额度。** 每个模块每帧一份，与记录数无关。锁步联机中最慢的机器决定整体速度，计量会让模块代码变慢，浏览器版可能更慢，所以额度按最慢的受支持平台确定：提议为该平台上约 2 ms 的运算量。超出额度的工作推迟到下一帧，记录留在队列中（第 5 节）；在积压上限内追不上的模块被停用并给出提示。
- **内存上限。** 地图模块 16 MiB，mod 模块 32 MiB，房间里每个“mod AI”席位再加 8 MiB（第 6i 节）；改写把内存限制在这个上限（第 3 节）。
- **按绑定范围引发。** 高频事件和绑定范围为对象或类型的可决定事件只对相应绑定引发；全局决定按事件表引发（第 5 节、第 6a 节）。`bindAllTypes` 在开销叠加层中给出警告（第 13 节）。
- **派生属性计费。** 筛选子句中求值的派生属性（如 `NearbyEnemyCount`、`TargetInRange`）按费用计入所属模块的额度（第 6a 节）；附录的属性表标出费用高的派生属性。0.1.0 中每次宿主调用计 50 次运算加上它的工作量：`get_many` 每读一个值、`find` 每返回一个引用计 10，`find` 每检查一个候选计 2、每条子句再加 6，“派生、高”属性上的子句每个候选再加 60。

结果：在每个宿主调用都按工作量预先计费、引擎代做的工作都有上限（第 15.1 节第 10 条）的前提下，写得不好的模块只会让它自己变慢，或者在单次调用超额、积压超限时被停用；它无法拖住对局，也无法造成不同步。

#### 15.3 SDK 默认做法

SDK 与模板按对象或所属方错开周期任务。读多个对象或属性用一次 `get_many`；可在入队前判断的条件使用筛选子句。范围效果使用长时修饰器，仅在进入和离开范围时添加或移除。

这些是预览期的默认值，不是冻结值。标“待测”的取值须按待定问题 7、17 实测后才能随版本 1 冻结。表中是 0.1.0 实际执行的取值；草案取值不同或尚未执行之处，在该行注明。

## 流程

1. **草案。** 本文档公开讨论。每次修改都提升 RFC 版本号，并记入[修订记录](#修订记录)。
2. **回答待定问题。** 用一次性实验回答下面的待定问题，结论汇总到本文。
3. **接受。** 维护者把某个版本标为已接受，此后才开始开发。第 1、2 阶段是在本文仍为草案时以预览形式实现的；0.1.0 版让本文与实现一致，接受仍待定。
4. **预览。** API 以 `0.x` 发布，允许破坏性变更并记入变更日志；预览版不是已发布的版本（第 12 节）。至少用它重做一个真实任务或模式，并请外部 modder 试用。
5. **稳定。** 冻结 `vera:sim@1` 和 `vera:client@1` 的函数。表只含附录中标为 `v1` 的条目：它们必须已实现、在每个构建和每个受支持平台上语义一致、由 `has_kind` 如实报告，并各有一个兼容性用例；做不到的改标 `later`，以后在次版本中追加。`DamageIncoming` 和 `TargetArmor` 只有通过第 6f 节的护盾用例后才冻结。兼容性测试用例加入 CI。
6. **增长。** 每批新的表项（事件种类、动作种类、属性）或新函数是一个小的后续 RFC 和一个新的次版本。

接受之后的计划顺序：

| 阶段 | 内容 |
| --- | --- |
| 1 | `rules.wasm`：原版和新的事件与动作；筛选子句；属性和修饰器；变量；搜索；AI 动作和属性；类型标签绑定、对象绑定和触发器动作；首批三个可决定事件和预览中的护盾事件（第 6f 节）；INI 注册（第 6h 节）；所属方领域认领、`OrderRefused` 和驱动所属方的读取面（第 6i 节）；地图嵌入、`asset` 命令；TypeScript 和 Rust SDK 及模板 |
| 2 | `ui.wasm`：带 INI 布局的界面树、节点种类和属性、客户端事件、视野过滤、消息和通知 |
| 3 | 用模块重做一个真实任务，外部 modder 试用，冻结版本 1 |
| 以后 | 逐个增加更多可决定事件、模块弹道（`Launch`、`ProjectileFrame`）、对等调用、玩家界面模块 |

0.1.0 时的状态：第 1 阶段已进入引擎，包括控制点、第 6f 节和第 9 节的预览决定以及 Rust 和 TypeScript SDK；大厅还不提供“mod AI”席位和“允许自动操作”开关。第 2 阶段已进入引擎，只缺 `MapUI=no` 时的大厅提示。第 3 阶段尚未开始。本文标为“0.1.0 未实现”的各项仍留在所属阶段。

## 设计范围

使用 core Wasm 模块和版本化函数表。模拟可读完整状态，客户端按本机视野读取；跨客户端通信经过模拟。普通事件批量投递，同步决定可写模块内存并使用决定子随机流。沿用数据驱动的触发器、Phobos 弹道与 AttachEffect。

## 未来可能的方向

不在版本 1 中。每一项都会是一个后续 RFC 或一个新的次版本。

- 更多投递型事件：`Built`（`other` 为建造者）、`Idle`（任务结束且没有排队的任务）、`MoveFailed` 和 `Arrived`（`cell` 为目的地）、`Stunned` 和 `Unstunned`（`other` 为来源）、`Spotted` 和 `Lost`（`house` 为现在看到或失去该对象的所属方）、`AmmoChanged`（`value` 为旧值，`value2` 为新值）、`HouseDefeated`、`PlayerLeft` 和 `StorageFull`（`house`）、`MotionEnded`（`value` 为原因）。
- 由模块定义并每帧执行的自定义任务。
- 让 AI 学会使用 mod 新增的机制。
- 一个对象挂多个标签。
- 在盟友中搜索目标的修饰器。
- 引擎侧的微操例程（`AttachRoutine`、`DetachRoutine`，第 6i 节）。
- 对局中按类型修改规则（第 8 节）、模块写入 AI 定义（第 6d 节）、地图的多语言文字。
- 界面树中的数据绑定（节点属性绑定到一个公开的变量），以及供客户端模块改写指令的钩子。
- 模块弹道（`Launch`、`ProjectileFrame`）、运动动作、对等调用和玩家自装的界面模块（见上文的计划）。

## 待定问题

问题编号保持不变，便于对照以前的讨论。**已定**：答案已写入正文。**待实测**：有暂定答案，须完成所列实验才能随版本 1 冻结。

1. **浏览器版（0.1.0 已定）。** 浏览器版用浏览器自己的 WebAssembly 引擎运行模块，字节与原生版一样是改写后的（第 3、4 节）；wasmi 只用于独立的 WASI 工具。2026-11-24 在无界面 Chrome 中用改写后 200,000 次运算的调用实测：每次调用纯计算 0.025 ms、函数调用 0.045 ms、宿主调用（`get`）0.22 ms，wasmi 2 分别为 0.9、2.4、0.4 ms，在函数调用上达不到 2 ms 的标准。实例是主线程的对象，所以带模块的浏览器对局不把帧移到模拟 Worker。一个桌面客户端和一个浏览器页面用两个试玩 mod 在中继对局中各跑了 5,091 帧，没有不同步。仍待实测：Firefox、Safari 和最慢的受支持设备。
2. **TypeScript 编译器（待实测）。** 当前 SDK 锁定 AssemblyScript 0.28.20（第 5a 节）。实验：编译与 `tutorial-bounty`、`decide-damage` 等价的两个模块（后者每帧分配一次），通过加载检查，跑 9,000 帧并在中途存读档：完整哈希相同、内存有界、不超额即定案。已有示例通过了模块构建、加载与宿主调用检查。存读档实验中，每 500 帧比对的模块摘要一致，但最终的整局存档仍有差异。用 Rust 编译的对照模块也出现了这一差异，整局验收条件仍未满足。只有垃圾回收超额时换 `minimal` 运行时；仍不行时测 WARPO，再不行时版本 1 只发 Rust SDK。
3. **计量（待实测）。** 规则已定（第 3、4、15 节）：共用插桩、逐运算 NaN 规范化、按字计算的页摘要。实验：分别量出基本块计量、栈计量和 NaN 规范化在原生与浏览器版上的开销，以及候选摘要（如 XXH32）在 wasm32 上处理 53 页和一次完整哈希的耗时。结果只调整额度和上限。0.1.0 的摘要用每个 64 KiB 页的 XXH32（第 15.1 节）。
4. **INI 格式（已定）。** mod 用具名节和 `Wasm.Tags`（引擎对草案中 `Vera.Tags` 这个键的命名），地图用原版触发器编码和动作 1036（第 6a 节；0.1.0 未实现）。
5. **事件和动作编号（已定，0.1.0 修改）。** 两表的 VERA 新种类都从 1000 起编号（第 7 节和附录），与引擎一致；草案的 100000 + n 即 1000 + n。属性 ID 是它在属性表中的位置（附录 7）。
6. **FinalAlert2（待实测）。** FA2 v2.0、FA2sp、FA2sp-HDM 和 World-Altering Editor 的源码都保留未知的非空节。实验：用 FA2 1.02 原版程序对嵌入了小、512 KiB、3 MiB 模块的地图各保存两次，比较取出的模块和保存用时。内容相同即定案；被截断时缩短行或降低地图上限；节被删除时规定编辑后再嵌入。
7. **上限（待实测）。** 预览期取值见第 15.4 节。0.0.15 的试验实现在 Apple M4 原生版、2 万单位下实测：全对象搜索直到 200,000 运算耗尽，1 条子句用时 2.34 ms，8 条子句 10.05 ms；把较短的实测折算到 200,000 运算，纯计算约 12 µs（实测 168,071 运算），读属性约 160 µs（实测 139,815 运算）。在按工作量校准宿主费用之前，200,000 运算不代表 2 ms；32 MiB 内存的逐字节页摘要每帧约 2.25 ms，16 个按类型绑定的对象轮询每帧约 4.7 ms 且不计费（第 15.1 节第 7、10 条）。实验：写明最慢的受支持机型，逐类宿主调用校准到单价相差不超过 2 倍且用满 B 时 p95 ≤ 2 ms，再以 2 万单位、30 个所属方验证最坏帧、突发投递、最坏编译时间和全部示例模块。
8. **帧阶段（已定）。** 模块阶段在 Triggers 步末尾（第 5 节）；模块弹道代替“算出候选位置”一步（第 9 节）。
9. **存档体积（已定）。** 非零页拼接后用 DEFLATE level 1 压缩，不重复保存规则文本（第 15.1 节；0.1.0 仍保存规则文本）。典型模块远小于 1 MiB，最坏情况只受内存上限约束，不承诺小于 1 MiB。
10. **首批可决定事件（已定）。** `TakeDamage`、`ProductionQueued`、`Defeat`（第 6f 节）。
11. **白名单（已定）。** 版本 1 为空：对局中不能按类型修改规则（第 8 节）。
12. **版本 1 清单（已定）。** 见附录第 9 节和各表的层级列，冻结门槛见“流程”第 5 步。
13. **修饰器叠加（已定）。** 见第 6c 节。Phobos AttachEffect 保留自己的实例和计时，不映射成修饰器。
14. **界面布局和节点种类（已定）。** mod 用 `veraui.ini`，地图用 `[VeraUI]` 节（第 10 节、附录 7.10）。
15. **地图文字（已定）。** 沿用地图附带文件中的 CSF，一图一语言，不增加格式（第 10 节）。
16. **战役（已定）。** 每关重新开始，只延续原版继承记录中的全局变量（第 6e 节）。
17. **连锁上限（待实测）。** 超限推迟，按来源计数，取值见第 15.4 节。0.1.0 用深度 8、两个来源共用的每帧 256 次连锁触发、每个来源 4,096 次等待。实验：在各平台（先测 Windows debug）量出深度 8 时的原生栈高水位，须不超过可用栈的一半；1,024 次连锁 ≤ 2 ms，5,120 次触发的一帧 ≤ 15 ms，否则降低上限。
18. **所属方接管（已定，0.0.21 改）。** 版本 1 按领域认领（第 6i 节）；0.0.20 的“版本 1 不做”作废。
19. **地图触发器的参数文本（已定）。** 版本 1 中地图的动作 1036 不带参数：FA2 的 `[Actions]` 以逗号分隔，放不下参数文本（第 6h 节）。
20. **决定中引发模块事件（已定）。** 版本 1 不支持：决定处理函数不能执行动作，例如护盾在 `TakeDamage` 决定中被打破时，事件要到下一次模块阶段才能引发（第 6h 节）。
21. **玩家设置的额度（已定）。** `VERA.INI` `[VERA] WasmBudget=`，联机时由房主的值成为房间设置（第 15.4 节）。
22. **地图默认额度（已定）。** 100,000，mod 可调到 500,000（第 15.4 节）。
23. **控制器模块的内存（已定）。** 每个“mod AI”席位加 8 MiB（第 15.2、15.4 节）。
