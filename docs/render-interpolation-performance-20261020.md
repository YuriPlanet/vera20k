# 插值开关 CPU 成本对比 — 2026-10-20

## 结论与边界

完成了当前原型的两轮配对 ON/OFF 测量。**这是生产插值接口的受控 CPU 机制测试，
不是完整游戏 FPS、GPU 时间、1% low 或真实 20k 单位战斗的性能验收。**

- 世界 1,000 个对象、视野采样 250 个，按 200 次呈现/秒、31.25 次提交/秒的
  调度比例回放：开启平均额外约 **0.036 ms/呈现**。
- 世界 20,000 个对象、视野采样 500 个，同一比例：平均额外约 **0.64 ms/呈现**；
  新逻辑帧的全局缓存捕获单次额外约 **3.62 ms**，不能简单认为可忽略。
- 两轮主要结果一致；所有配对最终权威状态哈希相等，首尾观察/采样不改权威状态。
- 本次只增加测试、日志归约脚本和文档，没有优化算法、修改玩法、推送或替换游戏 exe。

  上游 `a02f7f068e6d187b13dfaff871d0b7af124f4552`。插值代码仍为本地未提交工作，

- 零售 `rulesmd.ini` / `artmd.ini` 构造真正的 MTNK，克隆到指定对象数量，保持

## 测量方法

每轮 10 个用例，每个用例 8 对。顺序交替 OFF→ON / ON→OFF，每次运行预热
128 次呈现，再测量 768 次。每轮 122,880 次、两轮合计 **245,760 次计时呈现迭代**；
它们是虚拟时间回放，不是已实际显示到屏幕的帧。

计时范围：

1. 真实 `RenderInterpolation::observe`：新逻辑帧捕获/更新/清理全世界的缓存；
   同逻辑帧上的后续呈现只更新相位。
2. 每个可见对象固定调用一次 `sample_entity`、一次 `entity_offset` 和一次
   `entity_coord`。每四个对象额外调用一次真实的惰性几何 `sample_draw_point`。
   这是明确声明的接口调用组合，不表示所有实机对象每帧都恰好调用这些次数。
3. 烟雾用例额外调用 `sample_point`。输入姿态构造不计时。

使用 `black_box` 保留结果。权威输入提交、场景构造、哈希、结果统计、JSON 输出不计时。
开启时检查缓存对象数量及半相位的实际不同位置，防止误测了 bypass；两模式接收相同
输入。两轮均完整通过所有断言。关闭模式仍调用原型里的接口并返回权威姿态，
**不是“原型不存在的上游代码”与“加入原型”之间的对比**。

初次校验用 4 lepton 的位移，可能在整数像素投影后落在同一位置，半相位位置断言拦下
该轮，数据未采用。正式数据改成每提交 16 lepton，并增加相位/连续位置检查。

## 结果

下表取第二轮（无编译、无原始数据终端回显）作为主结果。
OFF/ON 为各自 8 次运行的“每次平均耗时”的中位数；增量为 8 对均值差的中位数。
中位数不满足直接相减，因此末位不一定严格相等。单位均为 ms/呈现迭代。

除特别标出外，调度比例均为 **200 次呈现/秒、31.25 次权威提交/秒**。

| 世界对象 / 可见采样对象 | OFF | ON | 配对额外 CPU | 相对 5 ms 目标预算 |
| --- | ---: | ---: | ---: | ---: |
| 100 / 100 | 0.0093 | 0.0198 | 0.0105 | 0.21% |
| 1,000 / 250 | 0.0233 | 0.0590 | 0.0357 | 0.71% |
| 5,000 / 500 | 0.0480 | 0.1806 | 0.1329 | 2.66% |
| 20,000 / 500 | 0.0508 | 0.6917 | 0.6403 | 12.81% |
| 1,000 / 1,000 | 0.1029 | 0.2271 | 0.1243 | 2.49% |
| 1,000 / 250，外加 320 个烟雾系统/粒子点 | 0.0461 | 0.0925 | 0.0464 | 0.93% |

**预算占比不是 FPS 损失百分比。** 表中 OFF/ON 也不是整帧耗时，不能取倒数当游戏 FPS。
若其他逻辑/绘制已经用尽预算，即使小增量也可能使一帧错过呈现时限；本测试不能判断
真实对局是否已经处在该边界。

### 全局捕获尖峰

| 世界 / 可见 | 新逻辑帧捕获额外 CPU/次 | OFF 计时组合 P95 | ON 计时组合 P95 |
| --- | ---: | ---: | ---: |
| 1,000 / 250 | 0.0614 | 0.0248 | 0.1155 |
| 5,000 / 500 | 0.4869 | 0.0557 | 0.6533 |
| 20,000 / 500 | 3.6173 | 0.0678 | 3.8773 |

这里的 P95 是各次运行的 P95 再取中位数，不是实机帧时间 P95。
20k 用例只看平均 0.64 ms 会掩盖提交帧上的成本集中。当前 `observe` 遍历所有符合
条件的世界对象，不只当前镜头里的对象，这是本轮最值得后续研究的规模问题。
在该受控用例中，仅单次缓存增量就约占 5 ms 预算的 72%，尚未加真实逻辑或绘制。

### 调度比例变化

固定世界 1,000、可见 250：

| 呈现/秒 : 提交/秒 | 配对额外 CPU/呈现 | 说明 |
| --- | ---: | --- |
| 200 : 15.625 | 0.0303 ms | 提交较少，捕获成本摊到更多次呈现 |
| 200 : 31.25 | 0.0357 ms | 基准比例 |
| 200 : 62.5 | 0.0462 ms | 提交增加，需要更频繁更新全局历史 |
| 62.5 : 62.5 | 0.0931 ms | 每次呈现都是新提交，仍有缓存/采样成本 |
| 200，`interval=None` 的 BYPASS | 约 0 | 8 对差值范围 -0.000663～+0.000309 ms，按噪声处理，不声称更快 |

呈现约等于提交时，不能据此说开启免费；当前原型没有按 FPS/TPS 比例自动禁用。
反过来，高刷新也不免费：缓存成本跟提交次数、世界规模相关，采样成本跟呈现次数、
可见对象/几何数量相关。粗略分解为：

`每秒增量 CPU ≈ 每秒提交次数 × 单次捕获增量 + 每秒呈现次数 × 单次采样增量`。

## 没有测到什么

- 完整实例构建、体素姿态缓存命中/重建、GPU 上传/绘制、驱动/VSync、输入交互。
- 插值可能带来的真实画面改善、响应延迟，以及整局 FPS/1% low。
- 当前 opt1 `debug` 游戏 exe、其他 CPU、真实混合兵种/战斗、任意 20k 单位对局。
- 大量子弹、四元数碎片旋转、动画生成/销毁、缓存冷启动/开关瞬间分配、内存峰值。

因此本轮能确认“中小规模输入下缓存/采样成本低，大规模全局捕获有明显额外成本”，
**不能确认“整局只损失 0.71% FPS”或“高刷新下一律没有影响”**。
完整帧差异还需要同一存档、同一镜头、同一游戏速度、同一渲染配置的端到端配对测量。
