## Systemic notes (not counted)

- The most common harness is a locomotor-less fixture: 27 movement_tests use a `GameEntity::test_default("HTNK")` with no locomotor, driven through `issue_move_command` + the `#[cfg(test)]` `tick_movement(_with_grid)` wrappers (mod.rs:579-640). That lane is the command-time search/adapter lane. In production, units always get a locomotor when Speed>0 (world_spawn/construction.rs:318), and a Drive HTNK never reaches that lane. Hover and queued Walk do reach it. The tests are live but mislabelled, e.g. `test_tick_movement_partial_progress` has a stale ms-based comment saying ~192 while asserting ~162 with a float tolerance.
- Pathfinding has many `#[cfg(test)]` entry wrappers: `find_path_with_costs`, `find_layered_path`, `find_path_zoned(_marker)`, `find_layered_path_zoned_marker`, and the ungated but production-dead `core::find_path`. Several pass `movement_zone: None`, and core.rs:2804 notes production no longer does that. Tests through them exercise `astar_search` in a configuration production does not use.
- `homing_movement::bam_cos_table`/`bam_sin_table` are built at runtime from f64 `cos`/`sin`, then rounded (homing_movement.rs:139-170). The table feeds hover.rs and wave.rs simulation math. That is a cross-platform determinism risk under CLAUDE.md and needs a separate issue.
