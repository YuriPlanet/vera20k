# 插值历史缓存第一轮优化 — 2026-10-20

## 范围

这是给 vera20k 新增的插值原型自身的优化，不是上游模拟引擎重构。
仅修改 `interpolation.rs`，新增 `interpolation/history.rs` 与测试；原有实体存储、
模拟更新、命令、RNG、存档、INI 开关与插值数学保持原样。`scene.rs` 和原来的
`perf_tests.rs` 未改动。

没有采用视野裁剪、跳过静止对象、降低捕获频率或预测来换性能；所有符合条件的世界
Techno 仍每个逻辑提交捕获完整姿态，保留原有的一逻辑帧显示延迟、同帧改动检查、
瞬移/桥面/类型变化回退。动态 Display 对象继续使用原有 scene 历史。

## 实现

- Techno 的历史姿态改为连续 `Vec<Endpoints>`，旁边保留按 stable ID 排序的 ID
  数组。使用 `EntityStore::values()` 已有的稳定 ID 顺序，不借用会因整理/读档而变的
  模拟实体槽号，也不直接把稀疏 stable ID 当数组下标。
- 对象集合不变时顺序原地更新历史，没有逐对象的历史哈希读取、写入及全表 `retain`。
- 独立 `HashMap<ID, index>` 仅供采样查找，成员及行位置不变时不更新它；哈希表遍历
  顺序从不进入结果。出生/删除/资格变化时，用可复用的辅助数组合并发生变化的后缀，
  更新必要索引，立即退休消失对象。
- `entity_offset` 复用同一次调用中已读取的当前姿态；关闭、暂停或历史为空时直接
  返回零偏移。`entity_coord` 在未采样时直接返回调用方坐标。
- 初版试过仅用二分查找定位历史，捕获有收益但采样抵消了一部分，因此最终采用
  连续姿态数组加 ID 索引。该候选的独立测试 exe 和全部数据仍保留，未删掉差结果。

这不是“只要换成 Vec 就快”：实体的完整姿态仍必须读取，频繁成员变化也仍有合并
成本。辅助数组保留容量以复用，未测内存峰值，不声称内存也必然下降。

## 最终性能对比

环境和输入边界同[原始开关报告](render-interpolation-performance-20261020.md)：
i5-12600KF / Windows 11 / Rust 1.97.0，Release，受控零售 MTNK 姿态输入。
**下表是插值接口组合 CPU 时间，不是整帧或实际显示 FPS。**

旧、新独立测试 exe 按 `旧→新→新→旧` 运行两组，即每个版本 4 个完整运行。
每次包含 10 用例 × 8 对 ON/OFF，预热 128、测量 768 次呈现迭代。
最终统计保留全部 1,280 条运行记录、983,040 次计时迭代；每个版本、每用例、每模式
32 个运行均值取中位数。没有根据收益挑选或删除原始异常帧。

下列均按 200 次呈现/秒、31.25 次提交/秒回放：

| 世界 / 可见采样对象 | 优化前 ON | 优化后 ON | 被测 ON 时间下降 |
| --- | ---: | ---: | ---: |
| 100 / 100 | 0.01942 ms | 0.01835 ms | 5.5% |
| 1,000 / 250 | 0.05835 ms | 0.05287 ms | 9.4% |
| 5,000 / 500 | 0.17707 ms | 0.15526 ms | 12.3% |
| 20,000 / 500 | 0.69183 ms | 0.52075 ms | 24.7% |
| 1,000 / 1,000 | 0.22438 ms | 0.20942 ms | 6.7% |
| 1,000 / 250，320 个烟雾系统/粒子点 | 0.09153 ms | 0.08625 ms | 5.8% |

烟雾与 5k 用例波动较大，汇总 JSON 保留运行均值的完整范围，不将单轮最慢值作为
优化收益。上述百分比不表示整局 FPS 也提升同样幅度。

### 20k 捕获尖峰

- 新逻辑帧的缓存捕获配对额外成本：**3.6313 → 2.5506 ms/提交**，下降约 **29.8%**。
- ON 计时组合的单次运行 P95 再取中位数：**3.9067 → 2.8034 ms**。
- 同版本 ON−OFF 的配对均值差中位数：**0.6433 → 0.4973 ms/呈现**。

没有消除全局捕获，2.55 ms 仍需预算。尤其不能仅凭平均时间推断真实对局一定不会
错过 200 Hz 呈现时限；真实逻辑和 GPU 绘制未计时。

### 关闭及 BYPASS

世界 1,000 / 可见 250 的关闭路径：**0.02171 → 0.00909 ms**；BYPASS 请求开启时：
**0.02180 → 0.00918 ms**。省掉了不需要的完整姿态读取。

因此小规模下，新版 ON−OFF 差值可能反而大于旧版，例如 1,000 / 250 为
0.0364 → 0.0437 ms。**这是 OFF 也被明显优化了，不能把移动后的参照当成 ON 退步**；
同一 ON 的优化前后 0.05835 → 0.05287 ms，才是本次算法优化的直接比较。

## 正确性及边界验证

- 保留旧版 HashMap 更新表达式作为测试 oracle，不复用新 `Endpoints::next`。
  比较完整前后姿态、所有整数/枚举字段和全部浮点字段的位值；覆盖连续更新、
  中间/头尾出生删除、空集合、超大稀疏 ID、帧回绕/跳帧、清空/重置、瞬移、
  类型/桥面变化，以及五种采样相位和同帧权威状态改动的整姿态回退。
- 偏移/坐标辅助函数对照原表达式，验证开关、暂停及 BYPASS 的等价性。
- 最终 8 个完整性能运行内，全部 ON/OFF 配对状态哈希一致；进一步核对旧、新二进制
  的 640 个对应 case/round/pair/mode，最终权威状态哈希全部一致。
- 完成全部测试代码后，插值聚焦测试 **27 passed / 3 ignored**；展示层测试
  **238 passed / 84 ignored**。两个手动性能测试已分别显式运行，GPU 抽查也单独运行；
  不将这些重叠计数相加当作全套测试。
- 5 项离屏 GPU 测试通过：采样 Kirov 弹体姿态上传、变帧姿态重放、体素调色板、
  降落伞 owner remap、焊接附着效果；这是部分 GPU 连接验证，不是整局像素等价或
  玩家对运动观感的实机验收。
- 正常 `cargo build -p vera20k --bin vera20k` 成功，既有三个警告未做无关修改。
  新叶文件 `rustfmt --check` 与 `git diff --check` 通过。

### 成员频繁变化的压力检查

另一个独立手动测试在同一进程内交替计时保留的旧 HashMap 算法与真实新历史实现，
每组 8 对、预热 32、测量 128 次提交；每次都比较所有 20k 个完整历史条目和索引数量。
新高 ID 替换低 ID，故意触发前部删除及后缀合并，而不只测廉价的尾部追加。

**这里仅测缓存更新：姿态已预构造，不包含真实对象姿态读取或整个 `observe`，
不能与前面的 3.63 / 2.55 ms 直接相加或相减。**

| 每次提交退休并新生的对象数 | 旧缓存更新 | 新缓存更新 |
| --- | ---: | ---: |
| 0 | 1.0778 ms | 0.2653 ms |
| 1 | 1.1773 ms | 0.6760 ms |
| 200 | 1.1715 ms | 0.5956 ms |
| 2,000 | 1.4587 ms | 0.6802 ms |

全部内容相等断言通过，运行 16.68 s。它支持“这些成员变化模式下仍有缓存收益”，
不证明任意真实战斗的最终帧率。原始数据为同目录 [churn.log](../logs/interpolation-opt-20261020/churn.log)。
