# Optional capabilities

The engine ships optional feature flags that no default or release build
compiles: `ares`, `phobos`, `npatch` and the diagnostic builds
(`debug-tools`, `telemetry-dashboard`). They are orthogonal and mixable
(`--features ares,phobos,npatch`); an implemented capability must keep working
with the others present without assuming they are absent. A flag that nothing
compiles is a break waiting to be found by whoever tries it first — that gap
is tracked as #2798, and #2789 (`telemetry-dashboard` unbuildable from `main`
for a day) is what it costs.

## The one list

The capability list lives in `tools/capability_tests.py` and nowhere else:
`CAPABILITIES` names each flag with its cargo features and how to run it, and
`COMBINATIONS` names the mixes that are compile-covered. Adding a feature to
`Cargo.toml` without registering it fails `tools/tests/test_capability_tests.py`,
which the capability workflow runs before it compiles anything (the Python
suite, `python-tools.yml`, runs the same guards but is manual), so another flag
cannot silently skip coverage. The CI workflow
`.github/workflows/capability-tests.yml` runs the tool's `check`, not a
hand-written command list, so the registry is the coverage. The guard also
checks `src/Cargo.toml`: core features must be enabled through a registered
client capability or its test dependency.

## Running one capability

```
python -m tools.capability_tests list                        # the registry
python -m tools.capability_tests test phobos                 # full suite, phobos on
python -m tools.capability_tests test phobos -- --test-threads=8
python -m tools.capability_tests focus phobos                # dedicated modules only
python -m tools.capability_tests build npatch                # compile coverage only
python -m tools.capability_tests check                       # the CI sequence
```

`test` is the complete run: the capability's own tests are gated inside
broadly-named modules, so no module selector list can be exhaustive. `focus`
is the quick pass over the modules dedicated to the capability; its selectors
are advisory. Local builds use `tools/cargo_run.py` for build coordination.
GitHub Actions jobs use plain `cargo` because they have no cooperating
worktrees; set `CARGO_TARGET_DIR` to share a local cache.

The suites currently carry failures that predate this coverage, so `check`
runs in CI with `--soft-tests`: library and test compilation/linking still
block, and Cargo continues to the other crate when one crate's tests fail.
Suite failures are reported by capability name without turning the job red
on arrival. Drop the flag once that list is empty
(`tools/tests/test_capability_tests.py` pins both behaviours, so the flag
cannot quietly swallow a compile error).

## Test maps

For repeatable map runs, `tests/maps/` holds a small committed set of
purpose-built shapes, one per
scenario the engine needs to prove, each regenerated byte-identically by the
`tools.scale_map` command its entry records (pinned by
`tools/tests/test_test_map.py`). One entry point runs them:

```
python -m tools.run_test_map list
python -m tools.run_test_map flat                     # headless march run
python -m tools.run_test_map match --ticks 300        # headless match run
python -m tools.run_test_map flat --interactive       # launch the client on the map
```

The rules and archives still come from the retail install through `RA2_DIR`;
these runs do not need its loose maps. Existing tests that name retail maps
still need those files. Map names also work after an explicit `play`
subcommand. Builds use `tools/cargo_run.py`, then launch its recorded binary
after releasing the build lock; interactive runs use the `fast` profile.
Interactive previews start with a small stock YR force including an MCV, so
the empty map stays playable. Set `RA2_DEBUG_SPAWN_UNITS` to choose another
force or types for a different ruleset.
