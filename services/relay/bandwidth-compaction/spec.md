# 联机协议带宽压缩方案

## 0. 摘要

**目标：** 在自适应冗余与重传方案（`services/relay/adaptive-transport/spec.md`，下文称"传输方案"）实现完成的基础上，进一步压缩每个数据报的字节数。

**不变的部分：**
- **发送策略：** 链路状态机、发送条件、重传、捎带深度 K、补推、FEC 一律不改，也不加。
- **规范记录：** 布局和顺序不变。日志、replay、断线重放、联邦链路传递的都是同样的规范记录字节。

**四项改动：**

| # | 改动 | 主要收益 |
|---|---|---|
| 1 | 删除端到端加密，批次以明文传送 | 每个批次少 40 B |
| 2 | 批次去掉多余头部（版本号、事件包头） | 每个批次少 15 B |
| 3 | PACK 编码改为 v2：记录字段相对编码，包内自包含 | 每条批次记录少约 11 B，每条帧结束记录少 6 B |
| 4 | 信封改为 v3：会话 ID 代替票据和房间号；序号 4 B；MAC 4 B；去掉 magic、长度等冗余字段 | 中继发出的每个包少 67 B，客户端发出的每个包少 132~133 B（DATA 包的 target 移进 payload，少 132 B） |

此外，`UPLINK`、ACK、STATUS 里的整数字段改为 varint 编码。

**预期效果**（30 人、30 Hz、300 APM、良好链路）：

| 指标 | 现在 | 压缩后 | 变化 |
|---|---|---|---|
| 每读者下行 | 20.4 KB/s | 约 6.7 KB/s | −67% |
| 每人上行 | 2.9 KB/s | 约 0.8 KB/s | −72% |
| 中继出口 | 约 5.0 Mbit/s | 约 1.6 Mbit/s | −67% |

现有 `main` 协议的中继出口约 9 Mbit/s，压缩后约为它的 1/5.5。

**兼容性：** 不兼容旧版本。中继和客户端同版发布，大厅最低版本同步提高。

**约定：**
- 整数默认小端序。
- `varint` 指无符号 LEB128（§8）。
- "包"指一个 UDP 数据报。
- 字节估算都含 28 B 的 IPv4/UDP 头。

---

## 1. 范围

### 1.1 做

1. 删除批次的端到端加密（§3）。
2. 批次明文去掉版本号和事件包头（§4）。
3. PACK v2：线上编码压缩，客户端还原出同样的规范记录（§5）。
4. 信封 v3（§6）。
5. `UPLINK`、ACK、STATUS 的整数字段改为 varint（§7）。

### 1.2 不做，以及原因

| 项 | 原因 |
|---|---|
| 状态心跳、ACK 并进回合包；放宽确认间隔；调整回合长度 | 会改变包数和传输方案的时序，可能影响已验证的成果 |
| 用 FEC 代替补推；改变 K 或补推规则 | 属于冗余策略，同上 |
| 修改规范记录布局 | 风险大，收益可以通过 §5 的线上编码拿到 |
| 指令记录本身的紧凑编码（单位 ID、目标格子用 varint 或增量） | 要逐个核对 gamemd 的指令类型，原生编解码器（Compress64B660 一族）的语义也要保持；收益约 5~8 B/批次。列为后续可选项（§14） |
| 读者自己的批次只发占位 | 收益约 3%，复杂度不划算 |

**包数会自然下降，但不是改了策略。** 内容变小以后，30 人局一个回合原来要 2 个新包，现在 1 个就能装下。这只是"捎带不增加包数"（传输方案 §7.4）这条规则在更小的内容上算出的结果，规则本身不变。

## 2. 现在的开销（自适应传输实现后，30 人、300 APM、良好链路，每个读者）

**中继发出的每个数据报：** 108 B 固定开销 = IP/UDP 28 + 信封头 48（magic 4、kind 1、room 16、nonce 16、seq 8、source 1、len 2）+ HMAC-SHA256 32。

**客户端发出的每个数据报：** 174 B 固定开销 = IP/UDP 28 + 信封头 114（magic 4、kind 1、票据 98、sent 8、target 1、len 2）+ HMAC 32。

**一个批次在 PACK 里约 90 B：**

| 部分 | 字节 | 说明 |
|---|---|---|
| PACK 内的长度字段 | 2 | |
| 记录头 | 14 | kind 1、frame 4、source 1、batch_id 8 |
| opaque | 74 | |
| └ nonce | 24 | |
| └ 密文 | 34 | |
| 　　└ 版本号 | 1 | |
| 　　└ 事件包头 | 14 | FRAME_INFO：House、帧号、checksum 等，在线模式下全部可以推出或恒为 0 |
| 　　└ 指令本体 | 约 19 | 一条移动指令 |
| └ 认证标签 | 16 | |

**每秒下行 20.4 KB 的构成：** 批次内容 13.5 KB，包固定开销 3.9 KB，状态心跳和 ACK 1.3 KB，捎带 1.3 KB，帧结束记录和 PACK 头 0.4 KB。

## 3. 改动一：删除端到端加密

### 3.1 新的批次表示

- **UPLINK：** 批次段直接携带明文 `P`，没有 nonce 和 tag（§7.1）。
- **规范记录 BATCH（kind 3）：** 布局不变，`opaque` 字段改为直接存放明文 `P`：

```
[3][seq u64][frame u32][source u8][batch_id u64][P]
```

  - `P` 的长度：1 ≤ |P| ≤ 512（`ORDERING_BATCH_CAPACITY` 不变）。
  - 规范记录的字段顺序和定长部分都不变，只是 `opaque` 的内容从"nonce ‖ 密文 ‖ tag"换成了明文。日志、replay、联邦都按原样传递。

### 3.2 删除的内容

- **DATA 消息**（中继转发的玩家间消息）**同样改为明文**，去掉它的端到端加密（`payload_cipher`、`DecryptedPayload` 的解密路径）。大厅仍会下发负载密钥，客户端接收后不再使用，这样大厅服务不用改；从大厅协议里删掉这个字段列为后续项。

- **加密相关：** 对局负载密钥的派生（`ORDER_KEY_DOMAIN`、`payload_key`、`payload_prefix`）、`order_cipher` / `order_aad`、`OPAQUE_OVERHEAD`。
- **读不懂的批次：** 客户端"批次解密失败就把发送者判为离开"的路径改为"批次**解码**失败"：明文不是合法的事件包时，仍按现有规则判该来源离开。
- **`ModifiedRetry`：** 原来比较的是密文，改为比较明文字节。语义不变，客户端缓存的已封批次照样不可修改。

### 3.3 安全影响（已接受）

- 中继和日志都能读到全部指令。**更正：** 中继日志本身从来没有加密，以前只是日志里的批次是密文。删除端到端加密后，日志里存的是明文指令，只靠文件权限（0600 / 0700）保护。已决定：日志不另行加密。
- 能伪造指令的只剩"攻破中继"这一条路，或者通过逐跳 MAC 伪造（§6.4）。联邦房间里的每台中继都要被信任。
- **好处：** 中继可以校验指令，可以统计指令类型和大小，日志也可以直接当 replay 读。

## 4. 改动二：批次去掉多余头部

**现在：** `P = [BATCH_VERSION = 2][事件包头 14 B][指令记录 …]`

**改为：** `P = [指令记录 …]`

- **版本号：** 去掉，协议版本由信封 v3（§6.1）统一表示。
- **事件包头（FRAME_INFO）：** 去掉。在线模式下：
  - `house_id` 由批次的来源推出（证书和开局协议里的来源 → House 映射）；
  - `event_frame` 由中继分配的帧号决定，就是 BATCH 记录的 `frame` 字段；
  - `checksum`、`timing_word`、`delay` 在线时恒为 0。
- **接收方：** 解析批次时，用"来源对应的 House + 记录的帧号 + 0"重建出完整的 FRAME_INFO，再交给现有的事件包解码器（`EventPacketCodec::decode_packet`）。解码器和 `NetworkCommandQueues` 都不用改。
- **约束：**
  - 批次里不得出现 FRAME_INFO 或 FRAME_SYNC 操作码（现有规则）；
  - 记录里的 House 字段必须等于来源对应的 House，否则按"读不懂的批次"处理（现有校验）。

每个批次少 15 B。

## 5. 改动三：PACK v2

### 5.1 原则

- PACK v2 只是规范记录在线上的另一种写法。客户端解码后，必须**逐字节还原**出和 v1 完全相同的规范记录（kind、seq、frame 以及其余字段）。
- **每个 PACK 自包含：** 解码只依赖这个 PACK 本身，不依赖之前收到的任何包。原因是 PACK 可能乱序到达、可能被捎带重复、可能是重传或 PULL 回复。

### 5.2 格式

```
[12][base_seq varint][base_frame varint][count u8] {entry} × count
```

- `base_seq`：第一条记录的序号。第 i 条的序号是 `base_seq + i`（同 v1）。
- `base_frame`：第一条记录的帧号。
- `count`：1..255。

每条 entry 以一个标签字节开头：

```
tag u8:  bit0..3  kind（3 BATCH、4 FRAME_END、5 DEPARTURE、9 PAUSE、10 RATE、11 DESYNC，其他值 Malformed）
         bit4..5  帧号编码：0 = 与上一条相同（第一条与 base_frame 相同）；1 = 上一条 + 1；2 = 后跟 varint 增量（上一条 + d，d ≥ 2）；3 保留（Malformed）
         bit6     仅 BATCH：1 = 批次 ID 是"本包内同一来源上一条 BATCH 的 ID + 1"；0 = 后跟 varint 绝对值
         bit7     保留，必须为 0
```

在 tag 之后，按 kind 跟以下字段：

| kind | 字段（在帧号增量之后） |
|---|---|
| BATCH（3） | `[source u8]`，`[batch_id varint]`（bit6 = 0 时才有），`[len varint][P len]` |
| FRAME_END（4） | 无 |
| DEPARTURE（5） | `[source u8][lost u8]`，`lost` 为 0 或 1；为 1 时还原成 v1 末尾带 `1` 的形式 |
| PAUSE（9） | `[epoch varint][paused u8][source u8]` |
| RATE（10） | `[fps u16][source u8]` |
| DESYNC（11） | `[sample_frame u32][outlier u8][checksum u32][other u8][checksum u32]` |

### 5.3 解码规则（任何一条不满足，整个 PACK 按 Malformed 丢弃）

1. **帧号：** 第一条以 `base_frame` 为"上一条"。帧号只增不减（规范历史本来就是这样）。
2. **bit6 = 1** 只能用在本包内**之前已经出现过同一来源 BATCH** 的条目上。
3. **varint：** 必须是最短编码，长度不超过 10 字节，值不超过 u64（§8）。
4. **长度：** 所有长度字段和 `count` 要和 payload 正好吻合，不能有多余字节。
5. **大小：** `P` 的长度必须在 1..512 之间；单个 PACK 的 payload 不超过 681 B（打包上限，§5.4）。
6. **非最短编码一律拒收**，所以编码唯一对编码器和解码器都成立：
   - 第一条的帧号编码不是 0；
   - 帧号编码 2 的增量 d < 2；
   - bit6 用在非 BATCH 条目上；
   - 能用 bit6（本包内之前已有同一来源的 BATCH，且 ID 正好加 1）却没用。
7. **超出规范宽度：** 帧号累加超过 u32，或序号（`base_seq + i`）超过 u64。

### 5.4 编码（中继）

- 打包算法不变（`pack_entries`：贪心装满，上限 681 B）。只是每条记录按 v2 计算长度，所以同样的上限能装下更多记录。
- **帧号编码选择：** 编码器必须选最短的写法：相同帧用 0，下一帧用 1，否则用 2。
- **批次 ID 编码选择：** 同理，能用 bit6 时必须用。
- 这样同一组记录只有一种编码结果，测试可以直接比对字节。

### 5.5 节省

| 记录 | v1 | v2 |
|---|---|---|
| BATCH（同帧、本包内首个同来源批次、批次 ID < 16384） | 16 B（len 2 + kind 1 + frame 4 + source 1 + batch_id 8） | 5 B（tag 1 + source 1 + batch_id varint 2 + len 1） |
| FRAME_END | 7 B | 1 B |
| PACK 头 | 10 B | 约 6 B |

## 6. 改动四：信封 v3

### 6.1 格式

**客户端 → 中继：**

```
[hdr u8][session u32][seq u32][payload][tag 4]          固定开销 13 B
```

**中继 → 客户端：**

```
[hdr u8][session u32][seq u32][payload][tag 4]          固定开销 13 B
```

- `hdr`：bit5..7 是协议版本，本方案为 3；bit0..4 是 kind，取值见下表。
- `session`：中继在 CONFIRM 时分配给这一跳的 32 位随机 ID（§6.2）。HELLO 和 CONFIRM 本身没有会话，这个字段填 0。
- `seq`：逐跳序号，u32，从 1 开始。每跳的票据最长 300 s，按每秒 100 个包算约 3 万个，远不到上限；到达上限时这一跳必须续期，同现有的 `CounterExhausted`。
  - **中继侧：** 中继不能自己续期。在票据寿命和推送预算的约束下，中继的序号实际不可能用尽；万一用尽，中继停止向这一跳发送，客户端按断线流程续期。
- **信封负载上限：** 720 B，涵盖联邦房间的 CONFIRM（票据 98 + cookie 40 + 名单最长 561 = 699 B）。整个数据报最长 733 B，加上 IP/UDP 头仍低于 IPv6 的最小 MTU 1280。PACK 的打包上限仍是 681 B（§5.4），不变，因为改它会改变包数。
- **去掉的字段：**
  - `magic`：版本已在 hdr 里；
  - `len`：UDP 自带长度；
  - 客户端的 `ticket`：只在 HELLO 和 CONFIRM 的 payload 里带；
  - `target`：改为放进 DATA 的 payload；
  - 中继的 `room`、`nonce`：由 session 代替；
  - `source`：改为放进 DATA 的 payload。

**各 kind 的 payload：**

| kind | 方向 | payload |
|---|---|---|
| HELLO（0） | 上行 | `[ticket 98]` |
| CHALLENGE（0） | 下行 | `[cookie 40]`；`seq` 回显 HELLO 的 seq（同现状）；信封 `session` 填 0 |
| CONFIRM（1） | 上行 | `[ticket 98][cookie 40][联邦名单，可选]` |
| READY（1） | 下行 | payload 为空。对 CONFIRM 的回复：信封 `session` 填新分配的会话 ID，`seq` 是中继在这一跳的第 1 个序号；对 PING 的回复：正常的 session 和 seq |
| DATA（2） | 双向 | 上行 `[target u8][数据]`；下行 `[source u8][数据]`。数据是**明文**，DATA 同样去掉端到端加密（§3.2） |
| PING（3） | 上行 | 空 |
| CONTROL（4） | 双向 | 排序请求和回复，同传输方案，字段按 §7 改为 varint |
| LEAVE_ACK（5） | 下行 | 空；`seq` 回显 LEAVE 的 seq（同现状） |

### 6.2 会话 ID

- **分配：** 中继收到合法的 CONFIRM 后，生成一个在本中继上唯一、非零的 32 位随机数作为 session，写在回复 READY 的信封 `session` 字段里交给客户端。
- **客户端认领 READY：** 客户端在 READY 到达之前还不知道新会话的 ID。它用正在握手的跳的密钥校验 tag；续期过渡期内有新旧两跳，最多试两次密钥，校验通过的那一跳认领这个 session。之后这一跳的所有数据报都带这个 session，双向一致。
- **查找：** 中继用 `session → Peer` 的哈希表找到这一跳，取出跳密钥、重放窗口、读者链路状态。以前要从票据重新派生，现在只在 HELLO 和 CONFIRM 时派生一次。
- **续期：** 新票据走一遍 HELLO/CONFIRM，拿到新 session。中继对每个来源只保留一个 `Peer`（同现状），续期 CONFIRM 被接受时，新 session 接管这一跳，旧 session 转为**离开状态**（同下面的"释放"），保留 `LEAVE_GRACE`，期间只接受 LEAVE 并回 LEAVE_ACK，其他数据报一律丢弃。
  - 原因：如果客户端在收到新 READY 之前退出，它的 LEAVE 仍从旧 session 发出。旧 session 立即删除的话，这些 LEAVE 都会按未知会话丢弃，玩家只能等静默超时，被记成失联离开。客户端在 READY 到达之前，可能同时持有新旧两跳，按 session（和认领 READY 时的密钥）区分。
- **同一票据重复 CONFIRM：** 沿用原来的 session。
- **换地址（NAT 重绑定）：** 中继收到一个已知 session、MAC 校验通过、**序号被重放窗口接受**、但来源地址不同的数据报，就把这一跳的端点更新为新地址，推送订阅保持不变。重放的旧包不能改端点。
  - **和现状的区别：** 现状遇到新地址时先回 CHALLENGE，走一遍 cookie 握手，并且要重新订阅推送。v3 不做路径验证，直接切换，这样 NAT 重绑定时不中断推送。
  - **取舍（已接受）：** 处在路径上、能抢先转发一份合法包副本的攻击者，可以把这名读者的推送流暂时转到自己的地址，直到客户端的下一个包把端点改回来。这种攻击者本来就能丢弃或延迟这名玩家的包。本方案不考虑伪造源地址（§6.4）。
- **中继重启：** 会话表丢失。客户端收不到回复，判为断开，按现有的重连流程重新 HELLO（同现状：重启本来就会丢失 `Peer`）。
- **释放：** 收到 LEAVE 之后，或者票据过期之后，这个 session 进入**离开状态**，保留 `LEAVE_GRACE`：期间只接受 LEAVE，每次都回 LEAVE_ACK（客户端重发的 LEAVE 是原样的，LEAVE_ACK 回显它的 seq）。宽限期结束后删除。删除后，用它的数据报一律丢弃；同一个 session 值至少 10 分钟内不重复分配。

### 6.3 MAC

- `tag = HMAC-SHA256(跳密钥, 域标签 ‖ hdr ‖ session ‖ seq ‖ payload)` 的前 4 字节。跳密钥和域标签沿用现有的派生方式（`derive_packet_key`、`CLIENT_DOMAIN` / `SERVER_DOMAIN`）。**只有** `CLIENT_DOMAIN` 和 `SERVER_DOMAIN` 的版本号改为 v3，确切字节分别是 `"VERA20k relay client v3\0"` 和 `"VERA20k relay server v3\0"`；`KEY_DOMAIN`、`TICKET_DOMAIN`、`COOKIE_DOMAIN` 不变，大厅不受影响。
- 校验用常数时间比较。
- **重放窗口：** 128 位，规则同现有 `ReplayWindow`，只是序号宽度改为 u32。

### 6.4 4 B MAC 的条件

截到 4 B 以后，单个伪造包的成功率是 2⁻³²。WebRTC/SRTP 的标准套件 `AES_CM_128_HMAC_SHA1_32` 用的也是 4 B 认证标签。

**不做任何会丢弃合法包的限速。** 早先的方案写过"按来源 IP、按会话限制失败次数，超出后直接丢弃"，这会让合法包被别人发来的假包连累，已删除。本方案不考虑伪造源地址的攻击。现在的规则：

1. **未知会话：** session 不在会话表里，或者 session 为 0 却不是 HELLO / CONFIRM 的数据报，没有可用的密钥，直接丢弃，不做 HMAC 运算。只做全局计数，用于统计和告警，不影响任何合法会话。不按来源 IP 计数。
2. **已知会话：** 每个数据报都做 HMAC 校验。校验失败的只丢弃这一个包，计入这个会话的失败次数；同一会话在固定的 60 s 窗口内失败超过 4096 次时，记录一条告警。合法包永远照常校验、照常接受。
3. **每跳独立密钥、票据最长 300 s：** 同现状。
4. **重放窗口：** 同现状。
5. **验证之前不改任何状态：** 只有 MAC 校验通过、并且序号被重放窗口接受（不是重放）之后，才更新重放窗口、接收窗口（传输方案 §4.1）和端点。
6. **客户端** 只接受来自中继地址的数据报，校验失败的直接丢弃并计数，不限速。

**残余风险（已接受）：**
- 路径外的攻击者看不到会话 ID，要同时猜中 32 位会话 ID 和 32 位 tag，成功率 2⁻⁶⁴，实际不可行。
- 路径上的攻击者能看到会话 ID，只需猜 tag。按中继的入口总预算（每秒 16384 个包）全部用来猜同一个会话，期望约 3 天猜中一次，期间会持续触发告警。真正处在路径上的攻击者本来就能丢弃或延迟这名玩家的包，这一项不额外增加它能造成的破坏。

MAC 长度是一个常量 `HOP_TAG_LEN`。想要更大的安全余量时改成 8 即可，格式其他部分不变。

## 7. 改动五：排序消息字段改为 varint

### 7.1 UPLINK（request 8）

```
[8][flags u8]
[recv_next varint]
[down_high varint][down_bits u64]
[srtt_ms varint][base_ms varint][rttvar_ms varint]
[link u8]
[checksum_count u8]{[frame varint][checksum u32]}
[pace：flags.bit1 时 [pace u8][fps varint][tick_micros varint]]
[batch_count u8][first_batch_id varint（batch_count > 0 时）]{[len varint][P len]}
```

- 字段的含义、取值范围、解码规则都同传输方案 §3.2，只是编码方式改了。例外：批次长度改为 `1 ≤ len ≤ 512`（明文，§3.1），不再是密文的 `40 < len ≤ 552`。
- **varint 字段的取值范围：** 每个字段的取值范围和它原来的定长宽度一致，例如 `frame`、`head_frame` 不超过 u32，`srtt_ms`、`echo_delay` 不超过 u16，`seq` 一类不超过 u64，超出就按 Malformed 处理。编码方需要截断的字段（`echo_delay`、`srtt_ms` 等）先按原来的规则截断到上限，再编码。
- 原来"长度和计数正好吻合"的检查照旧，另外加上 §8 的 varint 规则。
- 典型的不带批次的 UPLINK：35 B → 约 18 B。

### 7.2 ACK（event 2）

```
[2][accepted_through varint][frame varint][up_high varint][up_bits u64][echo_delay varint]
```

31 B → 约 13 B。

### 7.3 STATUS（event 1）

```
[1][head_frame varint][oldest_seq varint][next_seq varint][active_sources u32][tick_hz u16][start_delay_ms varint][started u8][up_high varint][up_bits u64][echo_delay varint]
```

50 B → 约 22 B。

### 7.4 其他

- ERROR（event 6）：`[6][code u8][expected varint]`。
- ordering READY（event 0）、PAUSE_STATUS（event 8）里的 u64 字段同样改为 varint。
- READY_REQUEST、PULL、PAUSE、LEAVE 等请求里的 u64 字段同样改为 varint。
- 证书（66 / 67 B）和开局协议摘要（32 B）保持定长。

## 8. varint 规则

- **编码：** 无符号 LEB128，每字节低 7 位是数据，最高位为 1 表示后面还有字节。
- **最短编码：** 编码器必须输出最短编码。解码器遇到非最短编码（例如末字节为 `0x00` 且总长度大于 1）按 Malformed 处理。
- **上限：** 最多 10 字节，值不超过 `u64::MAX`；第 10 个字节只允许取 0 或 1。
- **越界：** 解码到 payload 末尾仍未结束，按 Malformed 处理。
- **共用一份实现：** varint 只有一份编解码实现，放在 `vera20k-relay-protocol` 里，所有消息共用。

## 9. 安全分析汇总

| 威胁 | 现在 | 压缩后 |
|---|---|---|
| 中继读取指令 | 读不到 | 能读到（已接受） |
| 中继伪造或篡改指令 | 做不到：端到端认证 | 能做到：中继必须被信任 |
| 路径外的第三方伪造上行或下行包 | 32 B HMAC | 要同时猜中会话 ID 和 4 B tag，成功率 2⁻⁶⁴ |
| 路径上（能看到会话 ID）的第三方伪造 | 32 B HMAC | 4 B tag；按中继入口总预算全部用来猜，期望约 3 天猜中一次，期间持续告警（§6.4） |
| 利用限速踢人 | 不适用 | 不存在：没有任何会丢弃合法包的限速（§6.4） |
| 路径上的攻击者抢先转发，把推送流转走 | 新地址先走 CHALLENGE 验证 | 能暂时转走，直到客户端下一个包把端点改回来（§6.2，已接受） |
| 重放 | 重放窗口 | 不变 |
| 伪造源地址做放大攻击 | 握手 cookie | 不变：HELLO 和 CONFIRM 仍带票据和 cookie |
| 猜测会话 ID | 不适用 | 猜错的直接丢弃，不做 HMAC；猜中会话 ID 后还要猜中 tag（见上两行） |
| 日志泄露 | 批次是密文，其余是明文 | 全部是明文指令；日志文件只靠文件权限保护 |

## 11. 边界情况

| # | 情况 | 处理 |
|---|---|---|
| 1 | PACK 乱序到达、重复、捎带、重传、PULL 回复 | v2 自包含，每个包独立解码，结果和 v1 一样 |
| 2 | 同一个 PACK 里同一来源有多个批次 | 第一个写绝对批次 ID，后面的用 bit6 |
| 3 | PACK 跨帧 | 帧号按增量编码，只增不减 |
| 4 | 批次 ID 很大（> 2⁵⁶） | 用 varint，最长 9 字节，仍合法 |
| 5 | 续期过渡期，两个 session 同时有效 | 按 session 区分，各自有密钥、窗口和统计 |
| 6 | 同一 session 的数据报从新地址来 | MAC 通过、并且不是重放，就更新端点（不做路径验证，见 §6.2）；MAC 失败的只丢弃这个包，计入这个会话的失败次数 |
| 7 | 序号接近 u32 上限 | 发送方在 2³² − 2¹⁶ 时发起续期；到达上限后拒绝再发（`CounterExhausted`） |
| 8 | 4 B tag 恰好碰撞 | 包被接受后，按排序层规则处理；概率见 §6.4 |
| 9 | 明文批次不是合法的事件包 | 按"读不懂的批次"判该来源离开（现有规则） |
| 10 | 记录里的 House 和来源不符 | 同上 |
| 11 | 中继重启 | 会话丢失，客户端重连（同现状） |
| 12 | 联邦 | 联邦链路 `VF1L` 传递的是规范记录，批次字段改为明文；链路信封不在本方案范围 |
| 13 | 按序号触发续期（§6.1） | 生产代码没有接入：票据最长 300 s，序号实际用不到 2³² − 2¹⁶。列为已知残留 |
| 14 | 离开状态的会话表 | 每个到期或被替换的会话保留 `LEAVE_GRACE`。表的大小受大厅发放的票据数量限制，正常对局量下只有几 MB；没有另设上限，列为已知残留 |

## 12. 测试

### 12.1 单元测试

1. **varint：** 最短编码；超长、截断、第 10 字节越界都按 Malformed 处理；u64 边界值。
2. **PACK v2 往返：** 随机生成合法的记录序列，编码再解码后，和 v1 的规范记录逐字节相同；编码结果唯一。
3. **PACK v2 拒收：** §5.3 的每一条规则各一个用例。
4. **信封 v3：**
   - 编解码往返；
   - 4 B tag 校验，常数时间比较；
   - 失败计数：未知会话不做 HMAC 直接丢弃；已知会话校验失败只丢这一个包，计数，超过阈值告警；
   - 会话 ID 的分配、查找、释放和不复用期；
   - 换地址；
   - 续期过渡期两个 session 并存。
5. **批次去头：** 接收方重建 FRAME_INFO 后，解码结果和现有路径一致；House 不符时按读不懂处理。
6. **UPLINK、ACK、STATUS** 的新编码往返，以及 Malformed 规则。

### 12.2 端到端（netsim）

- **原有判定全部通过：**
  - 涉及字节数的断言（附录 A 的长度、§13.3 的包数上限等）按新格式更新；
  - 发送时机、状态、重传、捎带、补推的判定，**一条都不应改**。如果哪条必须改，说明这次改动影响了传输方案的成果，要先停下来分析原因。
- **测试专用接口：** `RelayServer::ordering_history(room)`，只在 test-support 下编译，返回这个房间的全部规范记录（日志中的加上内存中的），用于和客户端读到的流逐字节比对。
- **新增判定：**
  - 每个客户端读到的规范记录流，和中继日志里的规范记录逐字节相同；
  - 每个 PACK 都能独立解码。
- **新旧对比：** 在同一批场景和种子上，对比字节数、包数、延迟。延迟和卡顿应和压缩前持平，按传输方案 §13.2 的统计口径加 5 ms 容差。
- **模糊测试：** 对 PACK v2、UPLINK、信封 v3 的解码器做随机字节输入，确认不 panic、不无界分配内存。

### 12.3 附录 A

按新格式重算每个包的长度和字段，写成新的附录，作为字节级固定样例。

## 13. 预期效果（30 Hz，RTT 40 ms，良好链路，每秒）

**估算前提：**
- 一条移动指令的批次明文约 19 B；
- 中继发出的包固定开销 41 B（28 + 13）；客户端发出的同样是 41 B；
- 捎带按"前一回合有一半时间还没被确认"估算；
- 发送策略不变。

| 30 人 300 APM | 每人上行 | 11.7 包 / 2.9 KB | 约 11 包 / 0.8 KB | 字节 −72% |

## 14. 实施顺序

每步一个 PR，每步都要求传输方案的全部端到端判定仍然通过。

1. **信封 v3（§6）+ varint（§8）+ 排序消息改为 varint（§7）。** 只改线上格式，排序语义完全不变；上行收益最大。
2. **删除端到端加密（§3）+ 批次去头（§4）。** 规范记录字段不变，只是 `opaque` 改为存明文。
3. **PACK v2（§5）。** 只改中继的编码和客户端的解码，规范记录不变。
4. **后续可选：** 指令记录紧凑编码。要逐个核对 gamemd 的指令类型，并保留原生编解码器的语义；预计每个批次再省 5~8 B，30 人局下行再降约 15%。
