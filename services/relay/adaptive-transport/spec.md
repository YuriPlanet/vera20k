# 联机协议改造方案：自适应冗余与重传

## 0. 摘要

**目标：** 在线对局里，客户端和中继之间每个方向的发送策略，都按这个客户端当时的网络状态自动调整。

- **网络好：** 不发重复包，只在包里顺带上一份旧数据，几乎不增加包数。
- **丢包：** 发隔开的重复包，捎带更多旧数据。
- **拥堵：** 不发重复包，降低确认频率，合并发送。
- **断开：** 只发探测包；恢复后立即补齐。

**要改的东西：**

1. **上行：** 新增合并请求 `UPLINK`，一次带上未确认批次、接收水位、下行接收统计、checksum 和 pace，取代现在的 4 种独立请求。
2. **下行：** 打包格式不变。中继给每个读者维护发送记录和链路状态，按状态决定三件事：捎带深度 K、要不要 8 ms 补推、丢包后怎么重传（按确认重传和尾部探测）。
3. **测量：** 两端用已有的逐跳序号，精确统计对方方向的丢包，再通过反馈字段告诉对方。RTT 由中继回显来计算。
4. **回合长度按延迟自适应：** 第三阶段，可选，见 §9。

**兼容性：** 不兼容旧客户端，中继和客户端同版发布。新协议的版本上线时，大厅最低版本同步提高到这个版本。

**本文约定：**

- 所有整数都是小端序。
- `u8/u16/u32/u64` 是无符号定长整数。
- 时间单位是毫秒（ms），另有说明的除外。
- "包"指一个 UDP 数据报。

## 1. 范围与不变项

### 1.1 不变的部分

- **骨架：** 中继定序，客户端确定性锁步，不做预测和回滚，指令端到端加密。
- **逐跳信封：** 客户端信封 `VR2C`，中继信封 `VR2S`，HMAC 认证、票据、续期，以及重放窗口（128 位）。
- **规范记录：** 布局不变（§3.5）。规范历史（全局序号 `seq`）、日志、replay、断线重放、联邦链路 `VF1L` 都不变。
- **打包回复 PACK（event 12）：** 格式不变。
- **批次：** 加密方式、明文格式、批次 ID 的规则不变。
- **保留的请求：** READY（0）、PULL（2）、LEAVE（3）、PAUSE（5），格式和语义都不变。
- **封帧与节奏：** 中继的封帧、回合（`turn_frames`，到第三阶段之前）、降速、checksum 比较逻辑都不变。

### 1.2 删除的部分

| 删除项 | 由谁取代 |
|---|---|
| SUBMIT（request 1） | `UPLINK` 的批次段 |
| PUSH（request 4）和 PushState 回复（event 7） | `UPLINK` 的推送标志位和水位；推送订阅由 `UPLINK` 隐式维持 |
| PACE（request 6） | `UPLINK` 的 pace 段 |
| CHECKSUM（request 7） | `UPLINK` 的 checksum 段 |
| 客户端"首发背靠背连发 2 份"和"固定 100 ms 重发" | §6 的上行调度 |
| 中继"对所有读者都做 8 ms 补推" | §7.4，只对丢包状态的读者开启 |
| 客户端"缺口等一帧后发 Pull" | §7.7：先立即发 `UPLINK` 让中继重传，Pull 作兜底 |
| 客户端推送状态 `Probing`：开局后发 request 4 申请推送，等待 PushState 回复期间每 16 ms Pull 一次，每 500 ms（3 次后每 5 s）重新申请 | 删除。不存在不支持推送的中继，申请也不再需要握手：每个 `UPLINK` 的 PUSH 标志位就是申请和续订，中继收到即开始推送 |
| 客户端推送状态 `PullOnly`：中继明确回 `PushState{enabled: false}` 后，永久改为每 16 ms Pull 一次。这是给不支持推送的旧中继留的后路；当前中继只在客户端主动关闭推送时才会这样回复，正式客户端从不关闭，所以这条路径实际已走不到 | 删除。推送是唯一的常规下行方式，Pull 只作兜底（§7.7） |

## 2. 术语

| 术语 | 含义 |
|---|---|
| 跳（hop） | 一个票据对应的一条认证会话：客户端的 `ClientSession`，加上中继端对应的 `Peer` |
| 逐跳序号 | 每个认证数据报信封里的 u64 计数器。客户端发出的是 `sent`，中继发给某个 peer 的是 `peer.sent`。每跳从 1 开始，严格递增 |
| 记录（entry） | 规范历史里的一条：BATCH、FRAME_END、DEPARTURE、PAUSE、RATE、DESYNC，带全局序号 `seq` |
| 回合（turn） | 中继一次封帧追加的记录组，包含 `turn_frames(rate)` 帧 |
| 新包 | 中继推送新记录的 PACK。新记录指 `seq ≥ sent_next` 的记录 |
| 捎带 | 新包在新记录之前，附带上已经发过、但读者还没确认的记录 |
| 水位 `recv_next` | 客户端连续收到的下一条 `seq`。比它小的记录都已经收齐 |
| `acked_next` | 中继记录的这个读者已确认的水位，取收到过的 `recv_next` 的最大值 |
| `sent_next` | 中继给这个读者推送新记录推到了哪里 |
| 方向状态 | 每个方向各一个：良好 / 丢包 / 拥堵 / 断开（§5） |
| 回合时长 `turn_ms` | `turn_frames(rate) × 1000 / rate`，**按整数毫秒向上取整**：30 Hz 时为 67 ms，45 Hz 为 67，20 Hz 为 100。客户端的所有间隔判断都用这个整数值；中继封帧的时刻仍按精确的帧周期计算（附录 A 里的 396.7、463.3 等） |

## 3. 线上格式

### 3.1 信封（不变，列出备查）

**客户端 → 中继（`VR2C`），包头 114 B + MAC 32 B：**

```
[magic "VR2C" 4][kind u8][ticket 98][sent u64][target u8][len u16][payload len][hmac 32]
```

**中继 → 客户端（`VR2S`），包头 48 B + MAC 32 B：**

```
[magic "VR2S" 4][kind u8][room 16][nonce 16][seq u64][source u8][len u16][payload len][hmac 32]
```

- ordering 消息都放在 `kind = CONTROL(4)` 的 payload 里，客户端发送时 `target = 255`。
- payload 最长 `MAX_WIRE_PAYLOAD = 681` B。

**逐跳序号的覆盖范围：** 发往同一个 peer 的**所有**数据报（CONTROL、DATA、READY、CHALLENGE 回复等）共用同一个计数器。所以接收方统计的丢包率是这一跳的整体丢包率。

### 3.2 新请求 `UPLINK`（CONTROL payload，request 8）

```
偏移  长度  字段
0     1     type = 8
1     1     flags
2     8     recv_next            u64，≥ 1
10    8     down_high            u64，本跳收到的中继最高逐跳序号；没收到过为 0
18    8     down_bits            u64，bit i = 1 表示序号 down_high − i 已收到（bit0 必为 1，除非 down_high = 0）
26    2     srtt_ms              u16，0 表示还没有样本
28    2     base_ms              u16，0 表示还没有样本
30    2     rttvar_ms            u16，RFC 6298 的 RTT 波动值；srtt_ms 为 0 时也为 0
32    1     link                 u8，见下
33    1     checksum_count       0..2
34    8×n   {frame u32, checksum u32} × checksum_count
..    7     pace                 仅当 flags.bit1：[pace u8][frames_per_second u16][tick_micros u32]，tick_micros = 0 表示没有
..    1     batch_count          0..4
..    8     first_batch_id       仅当 batch_count > 0
..          {len u16, opaque len} × batch_count，批次 ID 依次为 first_batch_id + i
```

**flags：**

| 位 | 含义 |
|---|---|
| bit0 PUSH | 订阅或续订推送。对局开始后始终置 1 |
| bit1 PACE | 带 pace 段 |
| bit2 PROBE | 这是断开状态下的探测包，中继应立即回 STATUS |
| bit3 RESTORING | 正在断线重放：中继不要推送新记录，只回应 PULL |
| bit4..7 | 保留，必须为 0，否则按 Malformed 丢弃 |

**link 字节**（客户端对自己链路的判断）：

| 位 | 含义 |
|---|---|
| bit0..1 | 上行方向状态：0 良好，1 丢包，2 拥堵，3 断开（断开时实际不会发普通包，探测包可以带 3） |
| bit2 DELAYED | 客户端判定这条路径有排队延迟（§5.3）。中继用它来判下行拥堵 |
| bit3 JITTERY | 客户端判定下行回合包的到达抖动过大（§4.8）。中继据此对这个读者开启补推（§7.2） |
| bit4..7 | 保留为 0 |

**opaque（同现状）：** `[nonce 24][ciphertext n][tag 16]`，其中 `1 ≤ n ≤ 512`。

**长度上限：** 固定部分 35 B（偏移 0~34，含 `checksum_count` 和 `batch_count`）。不含批次时最多 35 + 16（2 个 checksum）+ 7（pace）= 58 B。加上 `first_batch_id`（8 B）和一个最大批次（2 + 552 B）共 620 B，小于 681 B。所以**第一个未确认批次一定装得下**。

**中继解码规则（任何一条不满足，整包按 Malformed 丢弃，不回复）：**

1. 长度和各段计数正好吻合，没有多余字节。
2. `checksum_count ≤ 2`，`batch_count ≤ 4`，保留位都是 0。
3. `batch_count > 0` 时 `first_batch_id ≥ 1`。
4. 每个批次满足 `40 < len ≤ 552`。
5. `recv_next ≥ 1`。
6. `down_high > 0` 时 `down_bits & 1 == 1`。

### 3.3 回复 ACK（event 2，新布局）

```
[2][accepted_through u64][frame u32][up_high u64][up_bits u64][echo_delay u16]   共 31 B
```

| 字段 | 含义 |
|---|---|
| `accepted_through` | 这个来源被中继接收的最大批次 ID（累计确认） |
| `frame` | `accepted_through` 那个批次被放进的帧 |
| `up_high` / `up_bits` | 中继在这一跳上收到的客户端最高逐跳序号，以及最近 64 个的接收位图。含义同 `down_high` / `down_bits` |
| `echo_delay` | 从中继收到 `up_high` 那个数据报，到这个回复被**编码**的时间差（ms，超过 u16 上限取上限） |

### 3.4 回复 STATUS（event 1，末尾追加）

```
[1][head_frame u32][oldest_seq u64][next_seq u64][active_sources u32][tick_hz u16][start_delay_ms u32][started u8]
   [up_high u64][up_bits u64][echo_delay u16]      共 50 B
```

前 32 B 和现在相同，后 18 B 含义同 ACK。

ERROR（event 6）不变：`[6][code u8][expected u64]`。PUSH 订阅不再回复 PushState。

### 3.5 记录与 PACK（不变，列出备查）

**记录通用头：** `[kind u8][seq u64][frame u32]`，共 13 B。

| 记录 | 布局 |
|---|---|
| BATCH（3） | 通用头 + `[source u8][batch_id u64][opaque]` |
| FRAME_END（4） | 通用头，共 13 B |
| DEPARTURE（5） | 通用头 + `[source u8]`，失联离开时再加 `[1]` |
| PAUSE（9） | 通用头 + `[epoch u64][paused u8][source u8]`，共 23 B |
| RATE（10） | 通用头 + `[fps u16][source u8，255 表示无]`，共 16 B |
| DESYNC（11） | 通用头 + `[sample_frame u32][outlier u8][checksum u32][other u8][checksum u32]`，共 27 B |

**PACK（12）：**

```
[12][base_seq u64][count u8]{[len u16][不含 seq 的记录：kind + 其余字节]} × count
```

第 i 条的序号是 `base_seq + i`。单条记录最长 578 B，单独装进一个 PACK 一定放得下。

**客户端处理 PACK 时：**

- `seq < recv_next` 的记录直接丢弃。
- `recv_next ≤ seq < recv_next + 256` 的记录放进重排缓存，同一 `seq` 只收第一次。
- 更远的记录丢弃。

这条规则保证：捎带和各种重传，无论重复多少、乱序到达，结果都一样。

## 4. 链路测量

### 4.1 接收窗口（两端都有，每跳一个）

```
RecvWindow { high: u64, bits: u64 }
```

收到一个**通过认证**的数据报（序号为 s）时：

- `s > high`：
  - `d = s − high`
  - `bits = (d ≥ 64) ? 1 : (bits << d) | 1`
  - `high = s`
- `high − 63 ≤ s ≤ high`：`bits |= 1 << (high − s)`。
- 更旧的序号：不更新窗口。数据报本身照常交给重放窗口处理。

**不计入窗口的数据报：**
- 中继的 CHALLENGE（server kind 0）和 LEAVE_ACK（server kind 5）：信封序号回显的是客户端请求的序号，不是 `peer.sent`。
- 客户端的 HELLO：发生在中继为这一跳建立 `Peer` 之前。

中继的 `up` 窗口从这一跳的 CONFIRM 开始统计。客户端的 `down` 窗口从第一个 READY 开始统计。

**归属：**
- 客户端在 `ClientSession` 认证数据报时更新 `down` 窗口。
- 中继在 `Peer` 认证数据报时更新 `up` 窗口。

**填字段的时机：** `UPLINK` 的 `down_high` 和 `down_bits`、ACK 和 STATUS 的 `up_high` 和 `up_bits`，都在**编码那一刻**从窗口读取。

### 4.2 发送记录（两端都有，每跳一个）

发送方为每个发出的数据报记一条，用环形缓冲，按 `逐跳序号 mod N` 寻址：

- **客户端，N = 128：** 每条是 `{seq_low u32, sent_at Instant}`，用来算 RTT 和统计上行丢包。
- **中继，按读者 N = 64：** 每条是 `{seq u64, first u64, count u8, sent_at_ms u32, kind u8, lost u8}`。
  - `kind`：0 非 PACK，1 新包，2 补推，3 重传，4 尾部探测。
  - `first` 和 `count` 是 PACK 携带的记录区间，非 PACK 时为 0。
  - 大约 30 B 一条，每个读者约 1.9 KB。

### 4.3 丢包判定（发送方执行）

每次收到对方反馈 `(high, bits)`，假设 `high ≥ 1`：

1. 反馈的 `high` 小于已处理的最大 `high`（旧反馈乱序晚到）：跳过本步，不统计。
2. 对每个序号 s，`eval_next ≤ s ≤ high − 3` 且 s 是本跳发出过的：
   - `s < high − 63`：超出位图范围，**不计入统计**，直接跳过。
   - 否则 `received = (bits >> (high − s)) & 1`，计 `n += 1`；没收到时再计 `l += 1`，并把这条发送记录标为丢失。
3. `eval_next = high − 2`。`high − 2` 到 `high` 这三个序号留到下次反馈再判，作为乱序容忍，阈值 3 沿用 QUIC。
   - **时间条件：** 位图里没收到的序号 s，还要满足 `t_fb − sent_at(s) ≥ srtt + 4 × rttvar`，才判为丢失。`t_fb` 是**收到这份反馈的时刻**，不是现在。位图只是对方编码反馈那一刻的快照，只有在快照拍下时 s 本该早已到达，才能凭这份快照判它丢失。客户端用自己的 `srtt` / `rttvar`；中继用 §4.6 的 `srtt_c` / `rttvar_c`。不满足时，在 s 处停下，`eval_next = s`，s 和它后面的序号留到下次反馈再判。
   - 已收到的序号不受时间条件限制，直接计入。
   - 等待期间如果 s 落到位图范围之外（`s < high − 63`），按第 2 步不计入统计。
   - **判定只在收到反馈时进行。** 同一份反馈的结论不会随时间改变，所以不需要、也不能在之后拿旧反馈重判：快照之后才到达的包会被误判为丢失。早先的方案写过"每轮用最近一份反馈重判"，端到端测试发现它让 ±50 ms 抖动、零丢包的读者又被判成了丢包状态，已经删除。要让中继更快判出丢包，靠客户端在缺口持续时补发反馈（§6.7 第 1 条）。
   - 原因：只靠"被后面 3 个包越过"判丢，抖动大的链路上，乱序的包会被误判为丢失。端到端测试中，±50 ms 抖动、零丢包的链路被判为丢包状态。时间条件参照 RFC 9002 的 time threshold。
4. **折算：** `n ≥ 32` 时：
   - `sample = l × 1000 / n`
   - `loss‰ = (3 × loss‰ + sample) / 4`
   - `n = l = 0`

被判为丢失的包后来又出现在位图里（乱序太严重），不回退统计，也不撤销已经发起的重传。重传的数据是幂等的，最多多发一次。

### 4.4 RTT（只由客户端计算）

收到 ACK 或 STATUS 时，读取 `up_high` 和 `echo_delay`：

1. 跳过 `up_high ≤ 上次用过的 up_high` 的回复。
2. 跳过 `up_high` 已经不在发送环里的回复（判据：`seq_low` 对不上）。
3. `R = received_at − sent_at[up_high] − echo_delay`。`received_at` 是套接字收到这个回复的时刻，不是游戏线程处理它的时刻。R 小于 0 时取 0。
4. 按 RFC 6298 平滑：
   - 第一个样本：`srtt = R`，`rttvar = R / 2`。
   - 之后：`rttvar = (3 × rttvar + |srtt − R|) / 4`，`srtt = (7 × srtt + R) / 8`。
5. **基准 RTT：** `base = min(win_prev, win_cur)`。`win_cur` 是当前 10 s 窗口里的最小 R。窗口到期时，`win_prev = win_cur ?? win_prev`，`win_cur = 空`。
6. `srtt`、`rttvar` 和 `base` 填进 `UPLINK`，单位 ms，向下取整，按 u16 饱和。

中继不自己算 RTT，下行要用的 RTT 一律取客户端上报的值。

### 4.5 RTO（客户端上行用）

- `RTO = clamp(srtt + max(16, 4 × rttvar), 48, 1000)`。没有样本时 `RTO = 100`。
- 连续超时：第 k 次 `RTO_k = min(RTO << k, 1000)`。
- 任意批次的确认前进时，k 归零。

### 4.6 PTO（中继下行尾部探测用）

`PTO = clamp(srtt_c + max(16, 4 × rttvar_c) + ack_delay_max, 50, 1000)`

- `srtt_c` 和 `rttvar_c` 是客户端在 `UPLINK` 里上报的 `srtt_ms` / `rttvar_ms`。没有上报（`srtt_ms = 0`）时，`srtt_c = 100`、`rttvar_c = 50`。
  - 早先 `UPLINK` 不带 `rttvar`，中继只能取 `srtt_c / 2`。端到端测试发现这个值太保守：好链路上中继要等约 3 倍 RTT 才判一个包丢失，总是被客户端的兜底 PULL 抢先，按确认重传几乎派不上用场。
- `ack_delay_max` 取 §6.3 里这个读者当前状态下的确认间隔：良好 100，丢包 `turn_ms`，拥堵 200。
- 连续探测：第 k 次 `PTO_k = min(PTO << k, 1000)`。`acked_next` 前进时 k 归零。

### 4.7 跳续期

- **客户端：** 续期产生新的 `ClientSession`，`sent` 从 1 开始。新跳的 `down` 窗口、发送环、丢包判定游标都从零开始。`loss‰`、`srtt`、`base` 保留（路径基本不变），方向状态也保留。
- **中继：** 新跳是新的 `Peer`，推送订阅要等新跳上的第一个 `UPLINK` 才建立（同现状）。新 `Peer` 沿用旧 `Peer` 已测的 `loss‰` 和链路状态（同一来源、路径基本不变，和客户端一致，见 §5.4）；发送记录、接收窗口和丢包判定游标从零开始。
- **切换时要立即发包：** 客户端改用新跳的那次服务里，立即在新跳上发一个 `UPLINK`，PUSH 置 1，带全部未确认批次，不等任何发送条件。新订阅从 `recv_next` 开始推送。旧跳上已经发出、但客户端还没收到的记录，在新跳上自然会重新推送，因为中继以新订阅的 `recv_next` 为起点。仍有缺口时，按 §7.7 修复。
- **旧跳收尾：** 在旧跳还在续期过渡期内，旧跳上收到的反馈只用于旧跳自己的统计。


### 4.8 下行抖动（客户端计算）

**为什么需要：** 端到端测试发现，只有抖动、没有丢包的链路（RTT 200 ± 50 ms）被判为良好、关掉补推后，卡顿反而比现状多：2 人空闲时每分钟 14.5 → 39 次。现状的补推把同一回合发两份，各自独立抖动，客户端取先到的那份，相当于削掉了一截抖动。

**测量对象：** 只看"带来新回合"的 PACK，也就是包含了至少一条 `seq ≥` 之前 `recv_next` 的 FRAME_END 的 PACK。重复包、捎带包、重传包、PULL 回复里的 PACK 都不参与测量。

客户端无法逐包区分推送包和 PULL 回复：PACK 格式里没有这个信息。约定的识别办法是：PULL 发出后到达的那个 STATUS（PULL 回复总是以 STATUS 开头），与它同一毫秒到达的 PACK 视为 PULL 回复。补推包或重传包如果首次带来了新记录，同样计入测量，这是允许的误差。

**算法：**

1. 记下上一个新回合包的到达时刻 `t_prev`，以及它带来的最大帧号 `f_prev`。
2. 新回合包到达（时刻 t，最大帧号 f）时，计算偏差：`D = (t − t_prev) − (f − f_prev) × 1000 / rate`。`rate` 用当前的封帧速率（RATE 记录生效后用新值）；帧号差乘以帧周期，就是中继封出这两批帧相隔的时间。
3. 按 RFC 3550 的到达抖动公式平滑：`J = J + (|D| − J) / 16`。
4. 更新 `t_prev = t`、`f_prev = f`。

**JITTERY 判定：**

- 至少有 16 个样本之后才判定。
- 记 `j0 = max(10, turn_ms / 4)`，按精确值计算，不取整（30 Hz 时为 16.75 ms）：
  - 当前为假时：`J ≥ j0` 置真；
  - 当前为真时：`J ≤ j0 / 2` 置假。
- 暂停期间不测量（暂停时没有新回合）；恢复后第一个新回合包只记 `t_prev` / `f_prev`，不计样本。
- 跳续期时 J 和 JITTERY 保留（路径基本不变）；断开时不测量，恢复后同样重新起算 `t_prev`。

## 5. 链路状态机

### 5.1 谁判什么

| 判定 | 判定方 | 依据 |
|---|---|---|
| 上行丢包率 `up_loss‰` | 客户端 | ACK 和 STATUS 里的 `up_high` / `up_bits`，对照客户端发送环 |
| 下行丢包率 `down_loss‰` | 中继（每个读者） | `UPLINK` 里的 `down_high` / `down_bits`，对照中继发送记录 |
| 排队延迟 DELAYED | 客户端 | `srtt`、`base`（§5.3），通过 `link.bit2` 告诉中继 |
| 下行抖动 JITTERY | 客户端 | 新回合包的到达抖动（§4.8），通过 `link.bit3` 告诉中继 |
| 客户端断开 | 客户端 | 1000 ms 没收到本跳的任何数据报 |
| 读者断开 | 中继 | 1500 ms 没收到这个读者本跳的任何数据报 |

读者断开的阈值比客户端的大，原因是客户端游戏线程偶尔会卡顿。另外 §6.6 要求 `UPLINK` 心跳由 IO 线程补发。

### 5.2 状态与优先级

每个方向的状态，按以下顺序取第一个满足的：

1. **断开：** 满足 §5.1 的断开条件。
2. **拥堵：** DELAYED 为真，或者（只对上行）2000 ms 内收到过 Backpressure 错误。**进入拥堵后，要上述条件连续 10 s 都不成立才退出**（拥堵保持期）。保持期内，即使测到丢包或抖动也不补推，K ≤ 2。
   - 原因：真正的排队拥堵下，扣掉抖动后的排队判定（§5.3）只断续成立，队列溢出又会造成丢包。没有保持期时，读者在判定的间隙里按丢包或抖动补推，把本已饱和的下行压得更满。端到端测试中，30 人局下行 256 kbit/s 时 p99 达到 5140 ms；只对抖动补推加保持期后降到 854 ms，仍不够。
   - 纯抖动链路扣掉抖动后不会被判为拥堵，不受保持期影响。
   - **已知残留：** 30 人局、每人 300 APM、下行 256 kbit/s、队列 1 s 的极端场景下，指令延迟 p99 约 870 ms（现有协议 40.3 s）。这时网络没有丢包，平均带宽也没超，延迟主要来自瞬时突发在 1 s 长队列里的排队。这类排队靠这套状态机解决不了，要解决只能降低突发，比如做中继侧的发送整形。作为后续项，不在本次范围内。
3. **丢包：** `loss‰` 处于丢包回差区间（§5.4）。
4. **良好：** 其他情况。

**"严重丢包"是丢包状态的子档：** `loss‰ ≥ 150` 时进入，`≤ 100` 时退出。

### 5.3 DELAYED 判定（客户端）

- 至少有 8 个 RTT 样本之后才判定，在此之前恒为假。
- 记 `q = max(base, 100)`：
  - 当前为假时：`srtt − 2 × rttvar ≥ base + q` 置真。
  - 当前为真时：`srtt − 2 × rttvar ≤ base + q/2` 置假。
  - 扣掉 `2 × rttvar`，是为了不把抖动当成排队：两个方向各有 ±50 ms 抖动时，`base`（最小样本）约 100 ms，`srtt` 约 200 ms，不扣就会误判为拥堵、关掉补推。端到端测试里这让纯抖动链路的卡顿比基线多。真正的排队拥堵 RTT 抬高而波动小，扣掉之后仍然判得出来。

### 5.4 丢包回差

- 进入丢包：`loss‰ ≥ 5`。
- 退出丢包：`loss‰ ≤ 2`，**并且最近 20 s 内没有判出任何丢失的包**（冗余保持期）。
  - 早先的规则是"连续 8 次折算没有丢失"。端到端测试发现，1% 丢包时一次折算有 27% 的概率丢包，连续 8 次都不丢的概率约 7.6%，所以读者有约 7.5% 的时间意外回到良好。退出后丢的第一个包没有补推，必然卡顿：30 人局 5 个种子合计卡顿 212 次，基线 24 次。按时间算以后，1% 丢包时 20 s 不丢包的概率几乎为零，会一直补推；0.1% 丢包时约一半时间退回良好。
  - 原因：只看平滑值时，1% 丢包的链路会反复进出丢包状态（一次折算丢 1 个包，平滑值约 8‰，十次左右没丢包的折算后就降到 2‰ 以下）。退出期间不补推，30 人局包是满的，捎带也补不上，只能靠 PULL，卡顿比基线多。
  - 代价：偶发丢包的链路，每丢一次包要多补推 20 s（下行每秒约多 15 个包）。
  - **这条只适用于测到丢包后进入的丢包状态。** 开局时的初始丢包状态（见下一条）只是保守的默认值，不代表测到了丢包：第一次折算时直接按进入门槛判定，`loss‰ < 5` 就转为良好，不受 20 s 保持期限制。
- 门槛最初定为 30‰ / 10‰。端到端测试发现：30 人局 1% 丢包时链路仍判为良好、不开补推，每分钟卡顿从 0.2 次升到 13.6 次，p99 从 127 ms 升到 250 ms，所以调低。代价是偶发丢包的链路会短暂进入丢包状态：一次折算里丢 1 个包，平滑值约 8‰，大约 5 次折算后才退出。
- **第一次折算之前，按丢包状态处理。** 每个方向从开局（中继侧是读者订阅推送）起都先处于丢包状态：上行发副本，下行 K = 2 并开补推。第一次折算（§4.3）之后，按上面的门槛和回差正常判定。
  - 原因：端到端测试中，4 人局双向 5% 丢包时，最慢的指令全部集中在开局头 3 秒。那时还没攒够一次折算的 32 个包，链路被当作良好，没有任何冗余。
  - 代价：每局开头的几秒（上行约 3 s，下行约 1 s）多一些冗余流量。
  - 跳续期（§4.7）保留已测的丢包率，不回到初始状态；从断开恢复时同样保留。

### 5.5 状态切换的副作用

| 切换 | 动作 |
|---|---|
| 任意状态 → 断开 | 发送方清空 `n`、`l`，不统计断开期间的丢包 |
| 断开 → 其他（客户端） | 立即发一个 `UPLINK`，带全部未确认批次；RTO 退避 k = 0；上行丢包判定游标 `eval_next` 跳到下一个将要发出的逐跳序号，恢复前发出的包一律不判 |
| 断开 → 其他（中继） | `sent_next = acked_next`，从水位处重新推送；清空补推状态和重传队列；PTO 退避 k = 0；下行丢包判定游标 `eval_next` 跳到下一个将要发给这个读者的逐跳序号，恢复前发出的包一律不判 |
| 每次切换 | 写一行 info 日志，计入 §10 的统计 |

## 6. 上行：客户端调度

### 6.0 开局前

- **配置请求：** 跳就绪后，客户端发 READY_REQUEST（request 0，`[0][证书 66 或 67 B][协议 32 B]`）。中继回两个数据报：
  - ordering READY（event 0，`[0][ready_mask u32][sources_mask u32]`）；
  - STATUS（§3.4）。
- **未开局时重发：** `started = 0` 时，客户端每 125 ms 重发一次 READY_REQUEST。客户端从每次回复的 STATUS 里得知：开局倒计时 `start_delay_ms`、是否已开局 `started`、当前头帧。这条路径同时提供开局前的 RTT 样本和上行丢包反馈。
- **和现状的区别：** 现在的客户端每次重发 READY_REQUEST 时还附带一个 PULL。新协议**不再发**这个 PULL：开局前没有记录可拉，配置回复本身已经带了 STATUS。这样也消除了一个现有问题：READY_REQUEST 丢失或被乱序超过时，后到的 PULL 会先被中继拒收（基线测试里见到的 `Authentication PULL`）。
- **开局前的限制：** 客户端不发 `UPLINK`，不生成批次。中继也不推送。
- **开局：** 收到 `started = 1` 的 STATUS 后，客户端在同一次服务里立即发第一个 `UPLINK`（PUSH 置 1），之后按 §6.3 调度。
- **订阅确认：** 收到第一个 PACK 之前，客户端每隔 `RTO`（§4.5）重发一次 `UPLINK`，防止第一个 `UPLINK` 丢失后要干等 250 ms 心跳。这条规则**每跳各自生效**：跳续期后，新跳收到它的第一个 PACK 之前同样按 RTO 重发。
- **由谁判定开局和第一个 PACK：** 客户端状态机在接收数据报时自行判定（看到 `started = 1` 的 STATUS、看到 PACK），不需要排序层另行通知。

### 6.1 批次窗口（同现状）

- 批次 ID 从 1 开始连续编号，未确认的批次最多 4 个（`ORDERING_SUBMISSION_WINDOW`）。
- 批次一旦封好，密文就固定不变，直到被确认。
- `accepted_through` 来自 ACK、`BatchGap` 的 `expected − 1`，以及流里自己来源的 BATCH 记录，取最大值。

### 6.2 `UPLINK` 里放哪些批次

- 从 `accepted_through + 1` 开始，按 ID 顺序装批次，能装几个装几个，最多 4 个。遇到装不下的就停，后面的不装。
- **装不装批次，和这个包为什么要发无关。** 只要发 `UPLINK`（探测包除外），就装上全部能装下的未确认批次。所以确认、心跳、缺口这些原因发出的包，也都同时承担了批次的冗余。

### 6.3 发送条件

每次服务（游戏线程大约每 16 ms 一次）按顺序检查，满足任意一条就编码一个 `UPLINK`。**每一跳在一次服务里最多发一个 `UPLINK`，没有例外**（续期过渡期内新旧两跳各自计算，这样新跳的"立即发"不会被旧跳的发送挡掉）：丢包副本（第 6 条）也是各自在后续的服务里单独发出。如果服务被耽误，导致两个副本同时到期，这次服务只发一个，下一个副本的到期时间顺延到这次发送之后 16 ms，保证副本之间至少隔开 16 ms。

**IO 线程心跳（§6.6）也算一个 `UPLINK`**，后面所有条件里"距上一个 `UPLINK`"的计时都从它算起。

| # | 条件 | 良好 | 丢包 | 拥堵 | 断开 |
|---|---|---|---|---|---|
| 1 | 有**从未发过**的批次 | 立即 | 立即 | 距上一个 `UPLINK` 满 33 ms 才发；不满就等，期间新出的批次合并进同一个包 | 不发 |
| 2 | 出现缺口，并且距上一个 `UPLINK` ≥ 16 ms。缺口指：重排缓存里有 `seq > recv_next` 的记录（真正的乱序）；或者 STATUS 的 `next_seq > recv_next`，并且持续了 `turn_ms` 仍未补上（状态心跳会先于同一轮的打包到达，所以要给这段宽限） | 立即 | 立即 | 立即 | — |
| 3 | 水位前进了，并且距上一个 `UPLINK` ≥ 确认间隔 | 间隔 100 | 间隔 `turn_ms` | 间隔 200 | — |
| 4 | 有未确认批次，并且距上一次携带它们的 `UPLINK` ≥ `RTO_k` | 发，k += 1 | 发，k += 1 | 发，k += 1 | 不发 |
| 5 | 心跳：距上一个 `UPLINK` ≥ 250 ms | 发 | 发 | 发 | 发探测包（PROBE 置 1，不带批次） |
| 6 | 丢包状态副本：上一个 `UPLINK` 带了**首发**的批次，而且这个批次仍未确认 | — | 16 ms 后再发一个（重新编码，用新的逐跳序号）；严重丢包时在 16 ms 和 32 ms 各发一个 | — | — |
| 7 | 链路恢复（§5.5） | 立即 | 立即 | 立即 | — |

**checksum 段：** 有尚未发出的 checksum 样本时，放进下一个要发的 `UPLINK`，放最新的样本和它的前一个样本。样本出现后 100 ms 内还没有任何 `UPLINK` 发出，就按条件 3 的方式单独发一个。

**pace 段：** 每秒一次。新的 pace 测量结果只放进下一个 `UPLINK`，**只放一次**，后面的包不再重复带。中继会把每次 pace 报告都当作最新的，重复带会让过期的报告一直显得新鲜。

**丢包副本（第 6 条）的内容：** 副本是在发送时刻重新编码的完整 `UPLINK`：水位和反馈字段取当下的值，带全部未确认批次；checksum 段带上原包里的那组样本（中继只记第一次，重复无害）；**不带 pace 段**。

### 6.4 回复的处理

- **ACK：** 更新 `accepted_through`，释放窗口，做 RTT 采样（§4.4），做上行丢包判定（§4.3），RTO 退避 k = 0。
- **ERROR `BatchGap(expected)`：** `accepted_through = max(accepted_through, expected − 1)`。下一个 `UPLINK` 从 `expected` 开始装。这个错误本身不额外触发发送，也不重置任何批次的发送状态。
  - **删除现有行为：** 现在的客户端收到 BatchGap 后，会把从 `expected` 起的批次全部重置为首发，再按 2 份重发。拥堵时它和固定 100 ms 重发形成正反馈：重复提交 → BatchGap → 重置 → 再连发。基线测试中，30 人局、上行 96 kbps 时，部分客户端的指令延迟超过 20 s。新协议靠 RTO 退避来重发，不再有这条路径。
- **ERROR `Backpressure`：** 记下当前时刻（上行拥堵维持 2000 ms），批次保留，按条件 4 的 RTO 重发。
- **ERROR `NotStarted`：** 批次保留，等对局开始。客户端在 `started` 之前本来就不应该生成批次。
- **ERROR `ModifiedRetry`：** 终止对局，报 InvalidTimeline（同现状）。
- **ERROR `Inactive` / `StorageUnavailable` / `HistoryGap`：** 同现状。
- **STATUS：** 同现状，另外做 RTT 采样和上行丢包判定。

### 6.5 时钟

- 发送间隔用服务时钟（ms）判断。
- RTT 一律用套接字层的 `Instant`：发送时刻在编码时记录，接收时刻在套接字收到时记录。

### 6.6 IO 线程心跳

游戏线程 250 ms 内没有产生 `UPLINK` 时（比如加载卡顿、拖动窗口），由传输层的 IO 线程补发一次。上行处于**断开**状态时，补发的是探测包（PROBE 置 1，不带批次和 checksum，同 §6.3 第 5 条）；其他状态下，把**最近一次 `UPLINK` 的内容**重新编码再发一次：

- 用新的逐跳序号，`down_high` / `down_bits` 取当下的值。
- 批次段按 §6.2 的规则在补发时刻重新装：从当下的 `accepted_through + 1` 开始装全部未确认批次，已确认的批次不再带。
- checksum 段原样保留（中继只记第一次，重复无害）。
- pace 段**去掉**。

这样可以避免游戏线程卡顿时，中继误判这个读者断开。

### 6.7 补充约定（实现中确定）

1. **条件 2（缺口）每个缺口最多触发两次。**
   - 第一次：缺口从"无"变为"有"时。
   - 第二次：**第一次发出后**过了 `max(16, 4 × rttvar)` ms 仍未补上时，补发一次。从第一次发出算起，而不是从缺口出现算起：STATUS 落后形成的缺口，第一次本身要等 `turn_ms`（§6.3 第 2 条），从缺口出现算起的话，第二次可能早于第一次。这时中继拿到的快照满足 §4.3 的时间条件，能判丢并按 §7.3 重传，赶在 §7.7 的兜底 PULL（宽限期 `srtt + 4·rttvar + turn_ms`）之前。
   - 之后缺口仍持续，就不再发 `UPLINK`，交给兜底 PULL。
2. **条件 4（RTO）只对已经被某个 `UPLINK` 带出去过的批次计时**，批次的首发不算超时。
3. **订阅确认重发（§6.0）用不退避的 RTO。** 中继不可达时，1000 ms 后链路判为断开，转为探测包。
4. **副本到期时恰好有普通 `UPLINK` 要发**，由这个普通包顶替副本：它同样带着全部未确认批次，满足"首发后 16~32 ms 内再出现一次"的目的。这种情况不计入 `copies` 统计。
5. **IO 线程心跳**保留上一个 `UPLINK` 的 flags 和 `recv_next`；`srtt`、`base`、`link`、`down_high` / `down_bits` 取当下的值。
6. **收到 CHALLENGE**（同一票据换了地址，中继要求重新确认）时，本跳重置为"未发过 `UPLINK`、未收到 PACK"。确认后立即发 `UPLINK` 重新订阅。
7. **RESTORING 期间的 PULL**（每 100 ms）只在仍有缺口时发。
8. **兜底 PULL 的宽限期**从"发现水位前进"的那次调用开始重新计算。
9. **客户端时钟：** 生产环境用 IO 线程的单调时钟，精确到毫秒；手动时钟的测试模式用 16 ms 粒度。客户端和中继在测试里共用同一个虚拟时钟。

### 6.8 由谁负责

| 职责 | 归属 |
|---|---|
| 批次、checksum、pace 的**内容**（封批次、取样、测 pace），以及读取记录流 | `src/net/live_commands/sequenced.rs`（`SequencedSession`） |
| 上行**调度**（§6.3 的全部发送条件）、链路测量（§4）、上行状态机（§5）、RTO、`UPLINK` 编码 | `vera20k-relay-protocol` crate 的客户端会话（`ClientSession` 及其排序状态），做成**不做 IO 的状态机**：时间一律由调用方以 `now_ms: u64`（单调毫秒）传入，内部不读系统时钟 |
| 兜底 PULL 的时机（§7.7），因为宽限期要用状态机里的 `srtt` / `rttvar` | `vera20k-relay-protocol` 的客户端状态机 |

## 7. 下行：中继按读者调度

### 7.1 读者链路状态

在现有 `PushSubscription` 里扩展字段：

```
ReaderLink {
  acked_next, sent_next,                    // 已有
  sendlog: [SendRecord; 64],                // §4.2
  eval_next, n, l, down_loss‰,              // §4.3
  lossy, severe,                            // §5.4，严重丢包回差
  delayed,                                  // 来自 UPLINK.link.bit2
  srtt_c, rttvar_c,                         // 来自 UPLINK.srtt_ms / rttvar_ms
  last_heard_ms,                            // 本跳最后一次收到任何数据报
  retransmit: VecDeque<(u64,u64)>,          // 待重传的 seq 区间 [from, to)，按 from 排序且不重叠
  repeat_next, unrepeated_since,            // 已有的 8 ms 补推状态
  pto_backoff, last_ack_progress_ms,
}
```

**`UPLINK` 处理顺序**（在 §8 的批次处理之前）：

1. 更新 `last_heard_ms`。
2. 把收到的 `recv_next` 合并进 `acked_next`（取最大值），并刷新推送租约（3000 ms，同现状）。
3. 记下 `link`、`srtt_ms`、`rttvar_ms`。
4. 用 `down_high` / `down_bits` 做下行丢包判定（§4.3），判为丢失的包进入 §7.3 的重传流程。

**RESTORING 标志：** 只维持订阅，不推送新记录，等同现在客户端断线重放时的行为。

### 7.2 每次推送时的处理顺序

`drain_ordering_push` 对每个读者，按以下顺序使用这一轮的额度（每个读者最多 8 个包，同现状）：

| 顺序 | 内容 | 断开 | 良好 | 丢包 | 拥堵 |
|---|---|---|---|---|---|
| 1 | 状态心跳（250 ms 到期，或状态有变化。"状态"指 `(是否已开局, active_sources)` 这一对值，同现状） | 不发 | 发 | 发 | 发 |
| 2 | 重传队列（§7.3） | 不发 | 发 | 发 | 发 |
| 3 | 新包，带捎带（§7.4） | 不发 | K = 1；JITTERY 时 K = 2 | K = 2，严重丢包时 K = 3 | K = min(当前 K, 2) |
| 4 | 8 ms 补推（§7.5） | 不发 | 不发；**JITTERY 时发** | 发 | 不发 |

JITTERY 来自这个读者最近一个 `UPLINK` 的 `link.bit3`。它不改变读者的链路状态（统计里仍算良好），只改变良好状态下的捎带深度和补推开关。拥堵状态下（包括 §5.2 的 10 s 拥堵保持期内）JITTERY 不起作用，依然不补推。

**抖动链路可能被判为丢包状态。** 单程抖动很大时（例如 ±50 ms），往返最坏情况可能超过 `srtt + 4·rttvar`，快照之后才到达的包仍会被判为丢失（§4.3）。这时读者进入丢包状态，补推和 K = 2 的效果与 JITTERY 相同，只是 `down_loss‰` 统计偏高，偶尔会多一次重传。这是可以接受的误差，不再为此加大判丢等待时间，否则真丢包时重传会更慢。
| 5 | 尾部探测（§7.6） | 不发 | 发 | 发 | 发 |

- 第 1~3 项用新数据预算（每个房间 32 个包、每轮共 128 个包和 96 KiB，同现状）。
- 第 4~5 项另用补推预算（全中继每秒 8192 个包，同现状）。
- 每发一个数据报，都要记入发送记录（§4.2）。

### 7.3 按确认重传

一个包 s 被判为丢失，且它是 PACK、`count > 0` 时：

1. 取区间 `[first, first + count)`，减去 `seq < acked_next` 的部分。
2. 再减去**比 s 晚发出**、而且**没有被判为丢失**的 PACK 所覆盖的区间。这些包要么已经收到，要么还在路上。
3. 剩下的区间并入 `retransmit` 队列，相邻或重叠的区间合并。
4. **同一个区间在一个 `srtt_c` 内只重传一次：** 发送时记录时刻；排队时如果发现这段区间最近一次发送距今不足 `srtt_c`，就丢弃。

**发送：** 从队首取区间，用 `pack_entries` 打包（区间可能拆成多个包），`kind = 3`。队列里 `to ≤ acked_next` 的区间直接删除。

### 7.4 新包与捎带

当 `sent_next < 房间 next_seq`，并且推送额度还有剩余时：

1. **算捎带起点：** 在发送记录里，从新到旧找出**本次之前已经发出的**最近 K 个 `kind = 1` 新包，取其中最早那个的 `first` 作为候选。找不到 K 个时，用实际找到的。
   - `start = max(acked_next, 候选)`。
   - 如果 `start ≥ sent_next`，就没有可捎带的内容，`start = sent_next`。
2. **打包：** 把 `[start, 房间 next_seq)` 里的记录按 `pack_entries` 顺序装包。规则如下：
   - 第一个包从 `start` 开始，所以旧记录在前、新记录在后。
   - **捎带不能增加包数：** 先算只装新记录 `[sent_next, 房间 next_seq)` 需要 P 个包（受本轮额度限制时，按额度内实际要发的新记录算）。然后从候选 `start` 开始，用 `pack_entries` 试装 `[start, 同一终点)`。包数超过 P 时，`start` 往后挪一条记录，舍弃最旧的旧记录，再试，直到包数等于 P。最坏情况是 `start = sent_next`，也就是不捎带。
   - 结果是：旧记录只占用这 P 个包本来就空着的空间。空闲时一个回合的新记录只有几十字节，旧记录能全部捎带上；活跃对局里包快装满了，只能捎带一部分，甚至完全不捎带。
   - **接力是预期行为：** 候选起点取的是"最近 K 个新包的 `first`"，而那些包本身也带了捎带，所以记录小的时候，未确认的记录会一直出现在之后的每个新包里，直到被确认。K 实际限制的是"往前看几个包"，不是"最多重复几次"。
3. **推进与计费：** `sent_next` 推进到已经装进包里的最后一条新记录之后。推送额度只按新记录计（`PUSH_WINDOW = 64`，同现状），捎带的旧记录不占额度。
4. **记录：** 每个包按 `kind = 1` 记入发送记录，`first` 和 `count` 是这个包的完整区间，包括捎带的部分。

> K 的含义是"再带上最近 K 个新包的内容"，而不是"K 个回合"。这样不需要在房间层面记录回合边界，联邦房间里各中继的回合对齐也不受影响。正常情况下一个回合就是一个新包，两种说法等价。

### 7.5 8 ms 补推（丢包状态，或良好状态且 JITTERY 时开启）

规则同现状：首次发送 8 ms 后，未确认、也还没补推过的记录再打包推一次，`kind = 2`。

- 补推的区间先去掉已经在重传队列里的部分，避免重复。
- 补推关闭时（离开丢包状态，或 JITTERY 清除且处于良好状态），`unrepeated_since = None`。

### 7.6 尾部探测

同时满足以下条件时，发一次探测：

- `acked_next < sent_next`；
- `now − last_ack_progress_ms ≥ PTO_k`；
- `now −` 最近一个 `kind ∈ {1, 3}` 的发送时刻 `≥ PTO_k`。

**探测内容：** 重发最近一个 `kind = 1` 新包的完整区间，减去 `seq < acked_next` 的部分，`kind = 4`。之后 `pto_backoff += 1`。

**说明：** 正常对局每个回合都有新包，所以探测只在暂停、对局最后一帧、或者推送额度被占满时才会触发。

### 7.7 客户端缺口修复（兜底 Pull）

- 发现缺口时，按 §6.3 条件 2 立即发 `UPLINK`，由中继按确认重传。
- 缺口持续超过 `G` 并且水位没有前进时，才发 PULL（request 2，`next_seq = recv_next`）：
  - `G = clamp(srtt + 4 × rttvar + turn_ms, 100, 1000)`
  - 继续没有进展就按 `G` 的倍数退避，最长 1000 ms。
- PULL 的回复同现状：一个 STATUS，再加最多 32 条打包记录。
- 以下情况**直接用 PULL**，不等宽限期：
  - 开局前、断线重放（RESTORING）期间：由排序层自己调用 PULL。RESTORING 期间每 100 ms 一次（同现状）。
  - 最近一个 STATUS 的 `next_seq` 比 `recv_next` 大 64 条以上（恢复后缺口太大、刚恢复时的追赶）：由客户端状态机判定，立即发 PULL，之后每隔 `G` 一次，直到差距回到 64 条以内。

### 7.8 补充约定（实现中确定）

1. **尾部探测（§7.6）还要求距上一次探测满 `PTO_k`。** PTO 封顶 1000 ms 之后，"最近一个 kind 1/3 发送"的时刻不再变化，没有这个条件会每一轮都发探测。
2. **PULL 回复里的 PACK** 在发送记录里记为 kind 0，但同样记下 `first` / `count`。它丢失后也按 §7.3 重传。
3. **"一个 `srtt_c` 内只重传一次"** 只对照 kind 3（重传）的发送时刻判断。
4. **读者链路状态挂在 `Peer` 上，不挂在推送订阅上。** 订阅因租约过期被删除后，测量状态和发送记录保留。
5. **`UPLINK` 的 `recv_next` 越界**（超过 `next_seq`，或早于最早保留的记录）时：不建立、也不续订推送订阅，批次照常处理；没有批次要回复时，回游标错误（同 PULL 的游标错误）。
6. **PUSH 位为 0 的 `UPLINK`** 不新建、也不续订推送订阅；已有的订阅保留到租约到期。
7. **pace 段的 `pace` 字节**只允许 0、1、2（KeepingUp / Behind / CatchingUp），其他值按 Malformed 丢弃整个包。这是 §3.2 解码规则的第 7 条。
8. **只含已接收批次的 `UPLINK`**（全部 `id ≤ last_batch.id`，比如晚到的旧副本）回 ACK，不回 BatchGap（§8 的回复规则）。
9. **断开期间漏推的包数**（§10.2），估算为"断开期间每出现一个新的流头，计 1 个包"。

## 8. 中继处理 `UPLINK` 的批次段

在 §7.1 之后执行，按批次 ID 顺序逐个处理。这个来源还没有接收过任何批次时，`last_batch.id` 视为 0：

| 情况 | 处理 |
|---|---|
| 对局还没开始（`starts_at` 为空） | 停止处理，回 ERROR NotStarted |
| 来源不是活跃来源 | 停止处理，回 ERROR Inactive |
| `id ≤ last_batch.id − 1` | 早已接收过，跳过 |
| `id == last_batch.id` | opaque 和上次一致就跳过；不一致就停止处理，回 ERROR ModifiedRetry |
| `id == last_batch.id + 1` | 按现有提交逻辑接收：检查帧上限、`MAX_SOURCE_PENDING`、`MAX_FRAME_BATCHES` 和日志预留，失败就停止处理，回 ERROR Backpressure；成功就放进当前开放帧，更新 `last_batch` |
| `id > last_batch.id + 1` | 停止处理，回 ERROR BatchGap(`last_batch.id + 1`) |

批次处理完以后，处理 checksum 和 pace：

- **checksum：** 同现状，每个来源每个采样帧只记第一次。
- **pace：** 同现状，覆盖为最新的报告。

**回复规则：**

- `batch_count > 0`，并且没有回 ERROR：回一个 ACK（§3.3），`accepted_through = last_batch.id`。即使这个包里全是重复批次，也要回 ACK，这样上一个 ACK 丢了也能补上。
- 回了 ERROR：只回这一个 ERROR。
- `batch_count == 0` 且 PROBE 置 1：立即回一个 STATUS。
- 其他情况不回复。上行反馈由下一个状态心跳带回。

**联邦房间：** 批次在本地中继接收，同现状。`UPLINK` 不经过联邦链路，各种反馈也只在本跳内使用。

## 9. 第三阶段（可选）：回合长度按延迟自适应

先完成 §6~§8，用 §10 的统计确认"回合延迟"确实是玩家能感受到的问题，再做这一阶段。

### 9.1 决定方

单中继房间由本中继决定，联邦房间由协调者中继决定。

**每 30 s 评估一次：**

1. 取活跃读者最近上报的 `srtt_c`，联邦房间里由跟随者中继转发，算 p90。
2. 目标回合时长 `T = clamp(p90 / 2, 33, 100)` ms。
3. `frames = clamp(round(T × rate / 1000), 1, ⌈rate/10⌉)`。
4. **回差：** 新值和当前值不同，并且距上次变化 ≥ 30 s，才变更。
5. 速率变化时，用同样的 T 重新计算 `frames`。

**初始值：** `turn_frames(rate)`，即现在的 `⌈rate/15⌉`。

### 9.2 新记录 TURN（kind 14）

```
[14][seq u64][frame u32][turn_frames u8]     共 14 B
```

- `frame` 是第一个使用新回合长度的帧，必须是旧回合的边界。
- **联邦房间：** 协调者把它作为来源 255 的控制贡献下发（`batch_id = u64::MAX − 2`，内容 `[turn_frames u8]`），各中继在该帧之后发出同样的 TURN 记录。规则和 RATE 一样。
- **客户端：** `frame_pacer` 改用最近一条已生效 TURN 记录的回合长度，不再用本地算的 `turn_frames(fps)`。

### 9.3 封帧

- 回合从最近一次速率变化或回合长度变化的帧开始，按整回合计数。
- 回合长度变化和速率变化同时到期时，先应用速率，再应用回合长度。

## 11. 边界情况

| # | 情况 | 处理 |
|---|---|---|
| 1 | 反馈乱序：旧的 `UPLINK` 或 STATUS 晚到 | 丢包判定按 `high` 单调性跳过（§4.3）；水位和 `accepted_through` 一律取最大值；批次处理照常进行，因为本来就是幂等的 |
| 2 | 两次反馈之间发了超过 64 个包 | 超出位图的序号不计入统计（§4.3），也不重传。缺口由 §7.7 兜底 |
| 3 | 判为丢失后，包又晚到了 | 不回退。重传最多多发一次，客户端会去重 |
| 4 | 中继进程重启 | 所有链路状态丢失，客户端按断开处理并重连（同现状） |
| 5 | 跳续期 | 见 §4.7 |
| 6 | 对局开始前 | 按 §6.0 处理：只发 READY_REQUEST（每 125 ms 一次），不发 `UPLINK`，不生成批次；中继不推送 |
| 7 | 暂停期间 | 没有新回合。确认按心跳节奏发，中继靠尾部探测补齐暂停前最后一段 |
| 8 | 对局最后一帧，或者离开 | LEAVE 流程不变。离开后不再发 `UPLINK` |
| 9 | 断线重放（RESTORING） | 用 PULL 读历史，`UPLINK` 带 RESTORING 标志，中继不推送新记录。重放追上之后清除这个标志，中继从 `acked_next` 开始推送 |
| 10 | Backpressure | 批次保留，上行进入拥堵 2 s，按 RTO 重发，不立即重发 |
| 11 | `UPLINK` 里的批次装不下 | 一定能装下第一个（§3.2），后面装不下的留到下一个包 |
| 12 | 一个回合的新记录超过一个包 | 拆成多个新包；只有第一个包带捎带（§7.4） |
| 13 | 读者推送额度耗尽（64 条） | 停推新记录，等水位前进。重传、补推、探测不受这个额度限制，只受补推预算限制 |
| 14 | 补推预算耗尽（全中继每秒 8192 个） | 第 4、5 项本轮不发；按确认重传不受影响，它用的是新数据预算 |
| 15 | 客户端游戏线程卡住超过 250 ms | IO 线程补发心跳（§6.6）；超过 1500 ms 中继仍收不到，才判读者断开 |
| 16 | NAT 映射变化，同一个票据换了地址 | 中继现有的地址重绑逻辑不变；读者链路状态跟着 `Peer` 走 |
| 17 | `echo_delay` 饱和（≥ 65535 ms） | 这个样本丢弃 |
| 18 | 逐跳序号耗尽 | u64 用不完；计数器溢出时返回 `CounterExhausted`（同现状） |
| 19 | 客户端 `srtt` 未知时上报 0 | 中继计算 PTO 时用默认值 `srtt_c = 100`（§4.6） |
| 20 | 联邦房间 | 读者链路是逐跳的、只在本地中继内；联邦链路和规范顺序都不受影响 |
| 21 | 收到一个 PACK，其中部分记录是重复的 | 客户端按 §3.5 的规则处理，结果不受重复影响 |
| 22 | 推送租约过期（3000 ms 没收到 `UPLINK`） | 只会发生在读者已经断开的情况下（1500 ms 时已经停推）。客户端恢复后的第一个 `UPLINK` 重新订阅，按 §5.5 从水位处重新推送 |
| 23 | 开局 STATUS 丢了 | 125 ms 后的 READY_REQUEST 重发会再带回一个 STATUS |
| 24 | 第一个 `UPLINK` 丢了 | 中继不推送。客户端在收到第一个 PACK 之前按 RTO 重发 `UPLINK`（§6.0），通常 100 ms 内重新订阅成功 |

## 13. 测试

### 13.1 单元测试

1. **接收窗口：** 递增、乱序、超过 64 的跳跃、旧序号。
2. **丢包判定：** 正好卡在阈值 3 上；超出位图不计入；旧反馈跳过；折算公式正确。
3. **RTT：** 回显延迟要减掉；重复的 `up_high` 跳过；发送环被覆盖后不采样；基准 RTT 的窗口滚动。
4. **状态机：** 每条进入和退出边界；优先级；断开前后的统计清空；恢复时的副作用。
5. **编解码：** `UPLINK` 的每个字段；§3.2 的每条 Malformed 规则；最大长度。
6. **中继批次处理：** §8 表格里的每一行；全是重复批次时也回 ACK。
7. **捎带：** 起点计算；新记录优先时舍弃旧记录；不同 K 值；推送额度只按新记录计。
8. **按确认重传：** 区间相减（已确认、后来的包已覆盖）；队列合并；一个 RTT 内只重传一次。
9. **尾部探测：** 触发条件；退避；水位前进后清零。

### 13.2 集成测试

用 `live_commands_tests.rs` 里的中继 + 双客户端框架，加 `fault_proxy` 注入以下场景：

| 场景 | 断言 |
|---|---|
| 良好链路，下一条指令 | 指令的首发只有 1 个包，没有副本（ACK 到达之前发出的其他 `UPLINK` 按 §6.2 顺带携带它，属于正常冗余）；下行没有 kind 2 的补推包 |
| 良好链路，丢一个上行包 | 下一个 `UPLINK` 补齐，延迟不超过 max(100 ms, RTO) |
| 良好链路，丢一个下行新包 | 下一回合的捎带补齐，不发 PULL |
| 5% 随机丢包 30 s | 两个方向都进入丢包状态；出现上行副本和下行补推；指令执行延迟的 p99 不超过良好链路 p99 的 1.5 倍 |
| 连续丢 3 个下行包 | 客户端立即发 `UPLINK`，中继按确认重传补齐；最后丢失的那几个包要等后续反馈越过它 3 个序号才能判丢（§4.3），可能先由 §7.7 的兜底 PULL 补齐，**最多一次** |
| RTT 从 40 ms 涨到 300 ms | 进入拥堵状态，没有副本和补推；带首发批次的 `UPLINK` 距上一个 ≥ 33 ms，其他 `UPLINK` 之间 ≥ 16 ms（§6.3 第 1、2 条） |
| 只有抖动：RTT 200 ± 50 ms，不丢包 | 客户端判出 JITTERY，中继对它开补推、K = 2；每分钟卡顿次数不高于基线（第 1 阶段实测的现有协议） |
| 1% 随机丢包，30 人 300 APM | 两个方向都进入丢包状态；卡顿次数和指令延迟 p99 不高于基线 |

**"不高于基线"的判法：** 卡顿等计数类指标，按统计误差界比较（多个种子，泊松计数的置信界）。延迟类指标除了统计误差界，再给 **5 ms 的绝对容差**：5 ms 小于一次 16 ms 的服务周期，玩家看不出来。比如 30 人局 1% 丢包时 p99 比基线高 0.25 ms，按这条规则算作持平。
| 断线 5 s 后恢复 | 断开期间只有探测包；**从恢复后第一个到达中继的 `UPLINK` 算起**，1 个 RTT 内推送到达客户端（断线超过 3 s 时推送租约已过期，只有 `UPLINK` 能重新订阅；PING 结束读者的断开状态；推送租约还有效时（断线不到 3 s），中继随即从水位处恢复推送，租约已过期时则要等 `UPLINK` 重新订阅）；积压按推送额度（每个确认往返最多 64 条）追平；断开期间的包不计入丢包统计 |
| 暂停 + 尾部丢包 | 尾部探测补齐 |
| 跳续期 | 新跳的统计从零开始；推送在新跳上重新建立 |
| 断线重放 | RESTORING 期间中继不推送新记录；重放完成后正常推送 |

### 13.3 负载与对局验证

- **负载：** `relay_load` 模拟 30 人、30 Hz 的房间，对比改造前后每个读者每秒的下行包数。目标：空闲时良好链路 ≤ 20 个/秒（基线实测 48.5 个）；300 APM 的 30 人局 ≤ 新包数 + 10 个/秒（新包数由每回合新记录的字节数决定，30 人 300 APM 时约 27 个/秒；另加状态心跳 4 个、ACK 约 5 个）。
- **真实对局：** 至少 2 局真实网络对局，导出 §10 的统计作为阈值校准的基线。

| 空闲（2 人或 30 人一样） | 下行 | 48.5 包 / 6.3 KB | 19 包 / 2.7 KB | 34 包 / 4.6 KB |
| | 上行 | 12.5 包 / 2.3 KB | 10 包 / 2.0 KB | 15 包 / 3.1 KB |
| 2 人局，300 APM | 下行 | 58.5 包 / 9.4 KB | 24 包 / 4.6 KB | 44 包 / 8.4 KB |
| | 上行 | 22.6 包 / 4.9 KB | 10 包 / 2.5 KB | 20 包 / 4.9 KB |
| 30 人局，300 APM | 下行 | 82.7 包 / 36.4 KB | 39 包 / 21.3 KB | 74 包 / 40.4 KB |
| | 上行 | 22.1 包 / 4.8 KB | 10 包 / 2.5 KB | 20 包 / 4.9 KB |

现在的下行里，有约 18 包/秒是每次推送水位换回的 PushState + STATUS 两个回复，每个批次还有 2 个 ACK；新方案删掉了这两项。30 人 300 APM 时每回合的新记录要 2 个包才装得下，所以新方案在这个场景下的下行包数下限约为 27 个新包 + 4 个状态心跳 + 约 5 个 ACK。

| 恢复时间 | 现在 | 新方案，良好 | 新方案，丢包 |
|---|---|---|---|
| 丢一个下行新包后补齐 | 8 ms（补推） | ≤ 1 回合（≈ 67 ms，靠捎带） | 8 ms |
| 连续丢多个下行包后补齐 | 一帧宽限 + 1 RTT（PULL） | ≈ 1 RTT（按确认重传） | ≈ 1 RTT |
| 丢一个上行批次后补齐 | 0（连发两份） | ≤ max(100 ms, RTO) | ≈ 16 ms（副本） |
| 断线期间上行 | 每 100 ms 重发一次批次（实测间隔 112 ms） | 每 250 ms 一个探测包 | — |

**良好链路的代价：** 偶尔丢包时恢复变慢，下行从 8 ms 变成约 1 个回合，上行从 0 变成约 100 ms。这是用来换中继包量的。

开发分两条线并行：协议实现，以及只依据本文判定实现的端到端测试（`services/relay-protocol/src/netsim/`）。实现中发现本文有歧义或错误时，先改本文，再改代码。

- **内容：** PACK `base_seq = 1`，`count = 7`（seq 1~7）。
- **发送记录：** `{seq 10, first 1, count 7, kind 1}`。

#### 包 23：R → B，回合 4 新包，捎带补上丢失的回合 3（t = 596.7，B 在 t = 616.7 收到）

- IO 线程补发心跳时，checksum 段会原样重复；R 只记第一次，不受影响。

#### 包 31：A → R，LEAVE（A 在 t = 1480 发出，R 在 t = 1500 收到）

**R 的处理：**
- 来源 0 离开，`active = 0b10`。
- 此时已封到帧 34（回合 17 在 1463.3），所以在开放帧 35 追加一条离开记录。

#### 包 33：R → B，回合 18 新包（t = 1530）

| seq 38 | `[len 5][kind 4][frame 35]` | FRAME_END f35 |
| seq 39 | `[len 5][kind 4][frame 36]` | FRAME_END f36 |

B 在执行到帧 35 时移除 House 0。

此后 STATUS 里的 `active_sources` 变成 0b10。A 已经离开，R 不再给 A 推送。

#### 包 34、35：B → R LEAVE，R → B LEAVE_ACK（约 t = 2000）

B 结束对局后发 LEAVE，R 回 LEAVE_ACK。

R：`active = 0`，房间结束，不再封帧，也不再推送。房间按现有规则保留到清理时间，供断线重放读取历史。

### A.6 换成丢包状态，这一局会有什么不同

假设 B 的 `down_loss‰ ≥ 30`（下行丢包状态），同时 `up_loss‰ ≥ 30`（上行丢包状态）：

| 时刻 | 良好（上文） | 丢包状态 |
|---|---|---|
| 回合 3 新包发出（530） | 只有一个新包 | 新包 K = 2；538 时再按 8 ms 补推一次（kind 2）。新包丢了也能在 538 补上，不用等回合 4 |
| B 的确认（500） | 每 100 ms 一次 | 每个回合一次（约每 66.7 ms） |
| B 的指令（950） | 一个 `UPLINK` | 950 和 966 各一个 `UPLINK`（副本隔开 16 ms 发送，重新编码，用新的逐跳序号）。R 对第二个按重复批次跳过，仍然回 ACK |
| 包 26 的丢包判定 | 不重传 | 如果捎带和补推都丢了，中继按确认重传，排在下一轮推送最前面 |
