# 联机协议改造结果

本文记录两阶段在线中继协议改造的实测结果：

- **第一阶段 · 自适应冗余与重传**：方案见 `spec.md`。
- **第二阶段 · 带宽压缩**：方案见 `../bandwidth-compaction/spec.md`。

对比的三个版本：

| 版本 | 内容 |
|---|---|
| main | 改造前的原协议（`720f12400`） |
| 自适应 | 第一阶段完成后 |
| 压缩 | 第二阶段完成后，也就是本分支的最终状态 |

## 1. 结论

- **流量**：30 人对局的中继出口带宽降到原协议的约 **1/5**（良好链路：9.79 → 1.95 Mbit/s）。每名玩家的上下行合计降到约 **1/5**（49.9 → 10.0 KB/s）。所有网络条件下，中继出口带宽比原协议低 62%~83%，每人上下行合计低 66%~91%。
- **延迟和卡顿**：没有任何场景比原协议明显变差。网络拥堵时改善最大：30 人局上行 96 kbit/s 时，指令延迟 p99 从 22.5 s 降到 0.14 s；严重拥堵时从 40.3 s 降到 0.16 s，卡顿从每分钟 47 次降到 0。
- **两个阶段的分工**：
  - 第一阶段让冗余和重传跟着每个玩家的链路状态走：网络好就不浪费，丢包或抖动时才补推。
  - 第二阶段在发送策略完全不变的前提下，压缩了每个包的字节数：去掉端到端加密，批次去掉多余头部，记录相对编码，信封瘦身，整数改用 varint。
- **兼容性**：新协议不兼容 0.2.6 及更早的客户端。中继和客户端必须同版发布，大厅最低版本同步提高（`docs/lobby-protocol.md` 写的是 0.2.7，发布时按实际版本号确认）。PR 需要打 `relay-compat-break` 标签。

## 2. 测量口径

- **工具**：端到端模拟框架 `services/relay-protocol/src/netsim/`。单线程虚拟时钟，客户端和中继都是生产代码，场景文件在 `services/relay-protocol/netsim/`。
- **运行方式**：
  ```sh
  python -m tools.cargo_run -- build --release -p vera20k-relay-protocol --features test-support --example relay_netsim
  ```
  然后用生成的程序运行场景文件。同一场景、同一种子，结果逐包一致。
- **采样**：每个场景测 60 s（预热 5 s 之后）。帧率 30 Hz，基础 RTT 40 ms；"300 APM"表示每名玩家每分钟 300 次操作，"空闲"表示没有操作。
- **字节**：含 28 B 的 IPv4/UDP 头。KB = 1000 B；Mbit/s 按 1 KB = 1024 B、1 Mbit = 1024 Kbit 换算。
- **中继流量**：在网络层直接统计，不是把客户端的数据相加。
- **卡顿**：两次帧推进的间隔超过 2 个回合，单位是每客户端每分钟次数。框架没有模拟游戏的播放缓冲，所以绝对次数偏高；但三个版本用的是同一口径，可以直接比较。
- **判定"持平"的标准**（`spec.md` §13.2）：计数类指标用多个种子，按泊松计数的统计误差界比较；延迟类指标在统计误差界之外，再加 5 ms 的绝对容差。

### 3.1 30 人、300 APM、良好链路的分解

| 指标 | main | 自适应 | 压缩 |
|---|---|---|---|
| 每读者下行 | 82.7 包 / 36.44 KB/s | 36.5 包 / 20.40 KB/s | 24.3 包 / 7.47 KB/s |
| 每人上行 | 22.1 包 / 4.77 KB/s | 11.7 包 / 2.93 KB/s | 11.6 包 / 0.85 KB/s |
| 中继出口 | 8.34 Mbit/s | 4.67 Mbit/s | 1.71 Mbit/s |
| 中继发出包数 | 2480 包/s | 1096 包/s | 728 包/s |

- **第一阶段的主要收益**：
  - 网络好时，不再对每个回合包都补推一次；
  - 推送水位的两个回复（PushState + STATUS）、批次的两份连发都删掉了。
- **第二阶段的主要收益**：
  - 每个批次从约 90 B 降到约 24 B（去掉端到端加密、版本号、事件包头，记录相对编码）；
  - 每个包的固定开销，中继发出的从 108 B 降到 41 B，客户端发出的从 174 B 降到 41 B（含 IP/UDP 头）。
  - 30 人局一个回合从 2 个包变成 1 个包，这是内容变小以后"捎带不增加包数"这条规则自然得出的结果，发送策略本身没有改。

## 4. 验证

- **端到端判定**：44 个，全部通过。判定只依据两份方案推导，由独立的开发者编写，不参考实现代码，覆盖：
  - 发送条件、链路状态机、捎带、按确认重传、补推、尾部探测、断线恢复、续期、断线重放；
  - 信封 v3 布局；每个 PACK 独立解码、编码唯一；客户端读到的流和中继历史逐字节一致；
  - 伪造包被拒且不影响合法包；会话的分配与释放；换地址与重放；
  - 解码器模糊测试；
  - 方案附录 A 的逐包、逐字节复现。
- **单元测试**：`vera20k-relay-protocol` 176 个测试（包括端到端判定和较慢的测试）、`vera20k-core` 的 `net::` 174 个测试全部通过；中继、示例程序和客户端都能编译。
- **独立审查**：两个阶段各做了一次只读审查，发现的问题都已修复。
  - 第一阶段最严重的一条：恶意读者可以让中继每轮推送都重读整段历史。已为重传读取量和重传队列加上限。
  - 第二阶段最严重的一条：续期期间退出时，LEAVE 收不到确认。已改为被替换的旧会话保留到宽限期结束，仍能接收 LEAVE，并补了回归测试。

## 5. 已知残留与后续项

1. **抖动链路的卡顿略多**：RTT 200 ± 50 ms 的 2 人局，卡顿约每分钟 18 次，原协议约 14 次，多种子比较在统计误差内。原因是抖动链路上只给下行补推，上行批次不加冗余。
2. **断线恢复**：断线超过 3 s 后，积压超过推送额度（64 条），要分几轮追平，p99 和原协议基本相同（约 4.8 s）。
3. **安全取舍**（已决定）：
   - 没有端到端加密，中继能读取和伪造指令；中继日志里是明文，只靠文件权限保护。
   - 逐跳 MAC 为 4 B：路径外的攻击者要同时猜中会话 ID 和 tag，路径上的攻击者按中继入口预算全部用来猜，期望约 3 天猜中一次。
   - 不考虑伪造源地址的攻击。
   - 换地址不做路径验证：处在路径上、能抢先转发合法包副本的攻击者，可以暂时转走一名玩家的推送流，直到客户端的下一个包把端点改回来。
   - 按序号触发续期没有接进生产代码（票据最长 300 s，序号实际用不完）；离开状态的会话表没有另设上限，规模受大厅发放的票据数量限制。
4. **后续可选**：
   - 指令记录本身的紧凑编码（`../bandwidth-compaction/spec.md` §1.2），预计 30 人局下行再降约 15%；
   - 回合长度按延迟自适应（`spec.md` §9）；
   - 从大厅协议里删掉已不再使用的负载密钥字段。
