## 第 1 阶段：模拟框架 + 现有协议的基线（现在开始）

### 1.1 虚拟时钟与网络

- **时钟：** 单线程、确定性，事件按虚拟时间推进。中继用 `RelayServer::process_at(…, now_ms)`、`advance_clock`、`drain_ordering_push(now_ms, …)`，全部在同一个进程里调用。
- **每个客户端的上下行链路，可以分别设置：**

| 参数 | 含义 |
|---|---|
| `delay_ms`、`jitter_ms` | 固定延迟加抖动。抖动用均匀分布，抖动可能造成乱序 |
| `loss` | 随机丢包率 |
| `burst` | Gilbert-Elliott 连续丢包模型：`p_good_to_bad`、`p_bad_to_good`、坏状态下的丢包率 |
| `duplicate` | 重复包比例 |
| `bandwidth_bps`、`queue_ms` | 带宽上限和排队上限，超过就丢；用来制造排队延迟 |
| `outages` | 断线时间窗，例如 `[[20000, 25000]]` 表示第 20~25 秒完全不通 |
| `drop_rules` | 按条件精确丢包，例如"第 n 个上行 UPLINK"、"中继发给某客户端的第 m 个 PACK"，附录 A 复现要用 |

- **随机数：** 用固定种子的自写 PRNG。同一个场景、同一个种子，结果逐包一致。

### 1.2 无界面客户端

- 每个客户端：一个 `ClientSession`，加上内容源和记录流读取器。
- **内容源：**
  - 按 APM 用泊松过程下指令，批次明文大小可设，默认 34 B；
  - 每 15 帧交一次 checksum，各客户端的值相同；也可以设置成某个客户端在某帧出错，用来测试不同步；
  - 每秒交一次 pace。
- **第 1 阶段（现有协议）：** 客户端的发送策略按**当前生产代码**的行为来模拟，因为现有调度在 `src/net/live_commands/sequenced.rs` 里，和游戏绑在一起。可以读这部分代码，常量照搬：
  - 首发连发 2 份，固定 100 ms 重发；
  - 推送水位每 100 ms 一次，落后 32 条时立即发；
  - 缺口等一帧后 Pull；
  - checksum 用 request 7，pace 用 request 6；
  - 开局前每 125 ms 重发 READY_REQUEST。

  这是第 1 阶段唯一允许的"模型客户端"，第 2 阶段就换掉。

### 1.3 观测

- 网络层能看到每一个数据报。写一个**按方案 §3 的格式**解析信封和明文 payload 的检查器，第 1 阶段解析当前格式。检查器只看字节，不调用生产代码的解码器。它本身就是一份对线上格式的独立核对。
- **每个客户端、每个方向，统计：**
  - 包数、字节数（含 28 B 的 IPv4/UDP 头），按消息类型分开计；
  - 指令从下达到在本端执行的延迟：p50 / p95 / p99 / 最大值；
  - 帧结束到达的间隔、卡顿次数（间隔超过 2 个回合）；
  - 缺口次数、Pull 次数、重发次数；
  - 网络层实际丢掉的包数，用来和协议自己报告的丢包率对照。

### 1.4 场景矩阵与基线

至少包含以下场景：

- 2 人和 30 人；空闲和 300 APM；
- 网络：良好（RTT 40 ms）、1% 和 5% 随机丢包、连续丢包、RTT 200 ms 加 50 ms 抖动、拥堵（带宽上限）、断线 5 s 后恢复；
- 混合局：30 人里 3 种网络条件混在一起。

每个场景跑 60 s 虚拟时间。

- 把基线数据和方案 §14 的估算对照，列出差异。

## 第 2 阶段：对新协议的判定（A1 接口骨架到了以后开始）

协调者会通知你合并 A 分支上的 A1 提交。

### 2.1 切换客户端

- 无界面客户端改为调用 A1 的接口：内容通过接口交给 `ClientSession`，发送时机完全由 `poll_uplink` 和 `next_uplink_deadline` 决定。

### 2.2 判定规则

每条规则写成独立的测试，注释里写方案出处。至少包括：

| # | 判定 | 方案出处 |
|---|---|---|
| 1 | 每个 `UPLINK` 和 ACK、STATUS、PACK 的字节布局都符合规定（用检查器解析，所有长度和计数自洽） | §3 |
| 2 | 良好链路下，每个批次只出现在 1 个首发的 `UPLINK` 里；没有副本 | §6.3 |
| 3 | 丢包状态下，首发批次 16 ms 后有一个副本；严重丢包时 16 ms 和 32 ms 各有一个 | §6.3 第 6 条 |
| 4 | 良好状态的读者收不到 kind 2 补推包；丢包状态的读者能收到 | §7.2、§7.5 |
| 5 | 捎带后的包数，等于只装新记录时需要的包数 | §7.4 |
| 6 | 中继重传的区间，都是"未确认，而且没被后来未丢的包覆盖"的区间 | §7.3 |
| 7 | `down_bits` / `up_bits` 和网络层实际丢掉的包一一对应；CHALLENGE、LEAVE_ACK、HELLO 不计入 | §4.1 |
| 8 | 协议报告的丢包率，和网络层实际丢包率的偏差在合理范围内（写明怎么算出这个范围） | §4.3 |
| 9 | 断开期间客户端只发探测包，中继不推送；恢复后 1 个 RTT 内补齐；断开期间的包不计入丢包率 | §5.5、§6.3 |
| 10 | RTT 升高时进入拥堵：没有副本，没有补推，`UPLINK` 间隔 ≥ 33 ms | §5.3、§6.3、§7.2 |
| 11 | 第一个 `UPLINK` 丢失后，按 RTO 重发，订阅成功 | §6.0 |
| 12 | 跳续期后立即在新跳上发 `UPLINK`，统计从零开始 | §4.7 |
| 13 | 断线重放期间中继不推送新记录 | §11 第 9 条 |
| 14 | 任何场景下，每个客户端执行的帧和指令都与中继的规范历史一致；没有卡死；没有误报不同步 | §1.1 |

### 2.3 附录 A 复现

- **场景：** 2 个客户端，30 Hz，单程固定 20 ms，无抖动。只丢附录 A 里那两个包：B 的第 2 个 `UPLINK`，以及中继发给 B 的回合 3 新包。
- **断言：** 逐包核对附录 A 列出的每一个包：类型、长度、逐跳序号、关键字段（位图、`base_seq` / `count`、ACK 的 `accepted_through` / `frame`、STATUS 的 `start_delay_ms` / `started` / `echo_delay` 等）、发出和到达的时刻。
- **不一致时：** 先判断是附录算错了、实现错了，还是你的场景和附录设定不一样，然后报告。

### 2.4 新旧对比

在 1.4 的同一批场景上，跑新协议和基线，输出对比表：每秒包数和字节数、指令延迟、卡顿、Pull 次数。和方案 §14 的预期对照。

### 2.5 CI 冒烟测试

从场景里挑 4~6 个，每个 10~15 s 虚拟时间，写成 lib 测试，断言判定规则和流量、延迟上限。每个测试的运行时间要控制在几秒以内。

### 2.6 `relay_load` 迁移

把 `relay_load` 改为在真实套接字上使用和模拟框架相同的无界面客户端，删除它自己的那份客户端逻辑。保留它现有的命令行参数和 JSON 输出字段，新增字节数统计。
